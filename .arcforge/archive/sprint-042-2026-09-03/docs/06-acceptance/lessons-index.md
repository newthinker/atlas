## 触发：**当我刚发现自己一个缺陷、正准备说它「可能也造成了别的问题」时**

### 🔴 把责任揽到自己身上的因果，同样需要证据 —— 而它不会被任何人质疑

实撞（TASK-010，M1c-4）：我发现自己的监视器有个真缺陷（`git branch --list 'task/TASK-010*' | head -1` 在 4 个同前缀分支下**恒取上个 sprint 的 `-m1c3a`**）。这个缺陷是真的、已确认、已修。

**然后我多说了一句**：

> 「如果你之前发过 merge 通知而我没回，很可能就是这个原因，不是你的问题。」

dev 查证后回我：**不是。** 它 TASK-009 / TASK-010 的 merge 请求我都收到了也都 merge 了。

🔴 **我混了两条不同的链路**：

| 链路 | 方向 | 本 sprint 状况 |
|---|---|---|
| **派验通知** | leader → `test-*` | 🔴 丢过两次（TASK-007 48min、TASK-009 138min） |
| **merge 通知** | `dev-*` → leader | ✅ 从没丢过 |

我的监视器缺陷影响的是**后者**（我看不到待 merge 分支），而丢失的两次是**前者**。**两件事都真，因果是我编的。**

### 🔴 第二次（同一 sprint，我）：**用一个正确的一般性事实，解释一个它不适用的现象**

我数 TASK-010 的处数得 **11**，dev 与验证者得 **14 / 18**。我给的解释：

> 「`grep -n` 每行只报一次，而同一行可能出现多次 ⇒ 我数的是**包含它的行数**，你们数的是**出现次数**。」

dev 去复现：**本批数据里没有任何一行出现两次**，`出现次数 == 行数 == 14`。⇒ **那个差别在这里恰好为 0，解释不出 11 ≠ 14。**

**真成因**（我随后查实，可复现）：

```
git show bdc8252:calibrate.go | grep -c 'M1c-1 的 TASK-010'   →  2   ← TASK-012 merge 前
grep -c 'M1c-1 的 TASK-010' calibrate.go   （当前 master）     →  5
```

差的 3 处正是 **TASK-012 自己新加的 milestone 注释**。⇒ **我测的是更早的树。** `11 + 3 = 14` ✅

🔴 **这是本 sprint 第四次「数字采于比声明锚更早的树」** —— 前三次是 TASK-005 的 39/38、TASK-009 的等价树自证、TASK-001 的 `4c9ca20` vs `8d02371`。**我记了三次，然后自己犯了第四次。**

### 🔴 为什么我会编：**那个机制是真的**

「`grep -n` 数行、`grep -o` 数次数」**是一个正确的一般性事实**。所以它读起来完全可信 —— 包括对我自己。

> **错的不是那个机制，是它不适用于这批数据。**

而我**没有验证「这批数据里有没有一行出现两次」**就用了它。⇒ 验证成本是一条命令，我没跑。

⚠️ **这比编一个假机制更难发现**：假机制经不起推敲，而**真机制用错地方，推敲它本身永远推敲不出问题** —— 你得去看数据。

🔴 **判别式**：我这个解释，**在这批数据上求过值吗？** 一般性事实要成为具体解释，中间必须有一次求值。

### 两次编因果的形态对照（同一 sprint，都是我）

| | 第一次 | 第二次 |
|---|---|---|
| 形态 | 两件真事之间**编了因果**（监视器缺陷 → 通知丢失） | 用一个**真机制**解释一个它**不适用**的现象 |
| 为什么可信 | 我刚承认了一个真缺陷 | **那个机制本身是对的** |
| 怎么被拆穿 | dev 查 `transitions.jsonl`（两条不同链路） | dev 实测「有没有一行出现两次」 |
| 共同点 | 🔴 **我给出了一个解释，而那个解释从未被求值** —— 两次都是 dev 去求的值 | |

⇒ **通则：解释是断言，和数字一样需要证据。** 而它比数字更容易蒙混，因为**读起来像推理而不像主张**。

### 为什么这一类特别不容易被自己发现

- **它看起来像负责任** —— 我在把别人的问题揽到自己身上，没有任何人会因此警觉
- **方向无害** ⇒ 不会有人来查
- **它出现在我刚确认一个真缺陷之后** ⇒ 那个真缺陷给了它可信度（「他刚承认了一个错，这个大概也是真的」）

⚠️ 与「我看见了矛盾，然后给它编了一个不用追究的解释」是**同一族的反面**：那一条是编解释**免除**核对义务，这一条是编因果**主动认领**责任。**两者都让「去查一下」这个动作消失。**

🔴 **判别式**：我这句「很可能是因为我的 X」，**有没有一个观察支持它？** 答「没有，但方向上说得通」的，就写成「我不确定这两件事有没有关系」，或者干脆去查 —— 本例查证成本是**一条 `transitions.jsonl` 的 grep**。

## 触发：**当我准备解释掉一条扫描/告警信号时**

🔴 **一律主动去合或去问，不等对方的请求。**
上一个 sprint：leader 因「它没发过 merge 请求」没行动 → dev 等 11 分钟、hook 空烧 8 次。
本 sprint：我因「在处理反审报告」没扫队列 → 两个 dev 等 **280/286 分钟**、hook 唤醒 **33 次**。
**那条扫描存在的全部理由就是对抗通知丢失。用「没收到通知」解释它的输出，等于亲手抵消它的价值。**

**同族：命令报了失败而我继续往下走。**

实撞（TASK-003 重派）：订正 DoD 的 `update` 报了 `✗`，我**没查就继续做了 `transition`**。若不是下一条命令的 grep 结果与 `✗` 矛盾让我回头，那个任务会带着**未订正的 DoD** 被重派 —— 而验证者刚刚明确警告过「例句不换，下一轮可能原样再来一次」。

⇒ 🔴 **判落盘成功不要用退出码，用 diff**：

```bash
diff <(jq -S '.done_criteria' <我打算写的>) <(jq -S '.done_criteria' <磁盘上的>) && echo 一致
```

退出码只说「命令自己觉得怎么样」，diff 说「磁盘上到底是什么」。

## 触发：**当同一个环节连续失败第三次时**

### 🔴 别再优化那个环节 —— 问它能不能**被绕开**

实撞（M1c-4 的 QA token）：QA 的写通道 token 与矩阵登记不符，写不了报告。我连试三次：

| 次 | 我做了什么 | 结果 |
|---|---|---|
| 1 | 登记 `qa-m1c4`，把明文发它 | ❌ 不符 |
| 2 | 换名 `qa-m1c4-r2`，**当场核过 hash**，再发明文 | ❌ 仍不符 |
| 3 | 换名 `qa-m1c4-r3`，再发明文 | ❌ 仍不符 |

**三次我都在优化同一个环节**：怎么把明文**发得更清楚**（「原样复制这一整块」「不要用 context 里的旧值」「极简消息只发 token」）。

**QA 提出的解法是把问题倒过来**：

> 用**我已经持有的**那个明文去登记一个新名字，哈希自己就对上了 —— **你不需要再发给我任何东西。**

⇒ 一条命令，成功。**传递环节整个消失了，而前三次全部卡在传递上。**

### 判据

> **同一个环节连续失败三次 ⇒ 停止改进它，开始问「这一步能不能不做」。**

⚠️ **为什么我三次都没想到**：每次失败都有一个**看起来合理的局部成因**（「它没读到消息」「它用了 context 里的旧值」「消息交错了」），而每个成因都指向「**发得更清楚**」这个方向。**三个不同的局部解释，指向同一个错误方向。**

🔴 **这与「结论对但理由错」是镜像**：那个是结论对、理由错所以没人复查；**这个是每次的理由都对（它确实没读到、确实用了旧值），但方向错了。**

⚠️ 判别式：**我这三次的动作，是同一个动作的三个版本，还是三个不同的动作？** 答「同一个的三个版本」就该停下来换维度。

## 触发：**当我挂了个自动的东西去替我盯着某件事时**

### 🔴 只在成功时出声的监视器，在它自己死掉时同样不出声

实撞（TASK-009，M1c-4）：我挂了个后台等待

```bash
until [ "$(jq -r .status TASK-009.json)" != "verifying" ]; do sleep 20; done
```

**timeout 给了 10 分钟**。它静默超时被杀，我一直把它的沉默读成「还在跑」。

⇒ **代价 138 分钟**（阈值 30），最后是**用户问「有进展吗」**才发现的。

🔴 **真正糟的地方不是漏了一次扫描，是我以为有东西在替我盯着** —— 因此**主动跳过了**本该每轮做的 validator 扫描。而 `stale-dispatch` 这条规则**正是为这个场景设计的、30 分钟就会报**。

> **我用一个坏监视器，替代了那条专门防这件事的规则。**

| 失效形态 | 处方 |
|---|---|
| 「忘了跑 validator」 | 靠提醒 / 清单 |
| **「我以为有东西在替我盯着」** | 🔴 **完全不同**——必须让监视器**在自己死掉时也出声**（超时、非零退出码都要变成事件），或者干脆别拿它替代周期扫描 |

⚠️ **判据**：我挂的这个东西，**在它自己失败时会告诉我吗？** 答「不会」的，就不能拿它当防线——它只是个锦上添花的加速器，周期扫描照跑。

⚠️ 与本文件「当我准备解释掉一条扫描/告警信号时」那节是**同一族的反面**：那节讲的是**告警响了我把它解释掉**，这节讲的是**告警根本没机会响，因为我把发起它的动作省了**。后者更隐蔽——**没有任何东西出现在日志里**。

## 触发：**当我要在文档里登记一个「统计本仓库/本文档」的数时**

### 🔴 自指计数：**报告它，就会改变它**

实撞（TASK-013，dev-m1c4-a）。它把「扫描清单」做成了**重采器**而不是抄一张表，**试跑当场查出它自己刚提交的表已经错了**：

| 口径 | 提交时写的 | 重采 | 差从哪来（`comm -23` 逐文件定位，非推断） |
|---|---|---|---|
| **C**（全仓库）M1c-1 | `38` | **`41`** | **+3 全在 `wisdom/learnings-dev-m1c4-a.md`** —— **那个文件正是它为了记录这条教训才写的** |
| **B**（含 `.md`）M1c-1 | `18` | **`20`** | +2 来自它 §G 新增的正文自己 |
| **B** M1c-3b | `2` | **`3`** | +1，同上 |

> **我提交那张表时它是对的，现在它是错的，而没有任何东西会因此变红。**

🔴 **和「数字采于更早的树」不是同一回事**：那个是**你没跟上树的变化**；这个是**你写下它的动作本身改变了它**。前者重采就能修，后者**重采完写进文档又错了**。

### 修法不是把 38 改成 41

那样下一个人写一句就又错了。**正确修法是按「是否自指」分层**：

| | 处置 |
|---|---|
| **A**（`internal/hestia/*.go` —— **不自指**，写文档不改 `.go`） | ✅ **登记绝对值**（`14/0/17/1/15`，三个锚上完全一致） |
| **B / C**（含 `.md` / 全仓库 —— **自指**） | 🔴 **标注自指，不登记绝对值** |
| 判据 | 换成**锚不变的关系式** `B − A == 本文件自身提及数` —— 三个锚上五个 milestone 全部成立，**而绝对值在同样三个锚上已经分叉** |

🔴 **这给「关系式让两个量互相定义」补了一个更强的性质**：

> **关系式不会被「引用它」这个动作改变。**

### 活体演示（预测在测量之前）

dev 在文里写「`M1c-2 的 TASK-010` **在口径 A 下**恰好是 0 处」，并**当场注明写下这句话本身会把口径 B 从 0 变成 1**。重采实测：**A 仍 0，B 变 1，关系式仍 ✓**。

⇒ **不带口径的话，那句话会自我证伪。** 这就是「自指」的全部含义。

### 判据

> 🔴 **写下一个数之前问：「我写下这个数的动作，会不会改变这个数？」**
> 答「会」⇒ **不登记绝对值，登记关系式，并注明重采方式。**

⚠️ 常见的自指数：文档里「本仓库有 N 处 X」「共 N 条教训」「N 个 TODO」「N 个已知问题」—— **只要 X 会出现在这份文档里，它就是自指的。**

### 顺带两个脚本坑（同属「0 不能是沉默」）

- `grep -c` 无命中 **exit 1**
- `set -o pipefail` 下 `git grep` 无命中 **同样 exit 1**

⇒ **而 `M1c-2` 恰好是 0 处，首次试跑就死在那一行。**

🔴 **`0` 必须能作为数据被打印，不能变成脚本悄悄终止。** 写成 `... | wc -l` 或 `|| true`，别让「没有」和「崩了」在输出上同形。

## 触发：**当别人报的数与我算的对不上时**

### ✅ 一次「先对齐口径」真的起了作用的实例（罕见，值得记）

TASK-013 验证者报：「`done_criteria` 变更共 **7 次全部 `by=leader`**，dev 一次都没改过。」

我一查：**82 次，其中 dev 改过 8 次**。

⚠️ **我的第一反应是「它错了」** —— 而且我手上有硬数据（8 次，逐条列得出任务号和时刻）。

**先对齐口径，然后**：

| 口径 | 结果 |
|---|---|
| 只看 **TASK-013**（验证者的口径 —— **它在验 TASK-013**） | **7 次，全是 leader** ✅ |
| 全部 **13 个任务**（我的口径） | 82 次，dev 8 次 |

🔴 **两个都对。** 它报的是它负责的那个任务，口径完全正确；我算的是全 sprint。

### 为什么这次值得单列

本文件记了很多次「口径不同就不可比」，但**几乎都是事后追认**（数字已经写进报告了才发现）。**这次是它真的挡住了一次误判** —— 而误判的代价会是：我回一条「你错了，dev 改过 8 次」，附上八条逐项证据。**看起来无懈可击，而且是错的。**

⚠️ **危险信号恰恰是「我手上有硬数据」**：数据越具体，越不会想到去问「我们量的是同一个东西吗」。

🔴 **判据（比「先对齐口径」更可操作）**：对方在做什么范围的事？**它报的数几乎总是它那个范围内的。** 我要拿全局数字去反驳一个局部结论之前，先把我的查询限制到它的范围里跑一遍。

⚠️ 而它的**结论**（那三处订正的载体是 CONTRACTS 不是 `done_criteria`）**是对的** —— 这也是本节要说的第二层：**口径对齐之后，它的结论仍然成立**。对齐口径不是为了驳倒对方，是为了知道分歧在哪一层。

## 触发：**当我把「核实」和「据核实结果写东西」放进同一个脚本时**

### 🔴 两个错叠在一起，而结论碰巧是对的

实撞（M1c-4 收尾，Leader 自己）。我写了一条命令，前半 `grep` 核实「TASK-013 补进去了没有」，后半 python 更新 checkpoint：

```bash
# 前半：核实
for s in '两者同值是巧合\|同值是巧合' ...; do grep -cE "$s" CONTRACTS.md; done
  → 0        # 🔴 错一：ERE 里 `\|` 是**字面竖线**，不是「或」（那是 BRE 的语法）

# 后半：python 写 checkpoint
add = "✅ **6、7 已由 TASK-013 完成**..."
  #      🔴 错二：**硬编码，完全不读前半的输出**
```

**实际情况**：TASK-013 **确实完成了**（`CONTRACTS.md:2370` 就写着「同值是巧合」）。

⇒ **结论对、两个环节都错**：

| | 错在哪 | 单独的后果 |
|---|---|---|
| grep 语法 | ERE 用了 BRE 的 `\|` | 报 0（假阴） |
| python 硬编码 | 不读核实结果 | **无论核实结果是什么，都写「✅ 已完成」** |

🔴 **两个错互相掩盖**：grep 报 0 本该让我发现「没补进去」，但 python 根本不看它；python 硬编码本该被 grep 的 0 打脸，但我没让它们对话。

⇒ **结论对而过程全错，是最不会被追查的一类** —— 我这次是**顺手多跑了一次宽模式**才发现的，不是被任何东西提醒的。

### 两条处方

1. 🔴 **核实与「据核实结果行动」不要放进同一个脚本**，除非后者**真的读前者的输出**。放一起而不接线，等于**制造一个永远说同一句话的证人**。
2. **正则方言**：`grep -E` 用 `|`，`grep`（BRE）用 `\|`。⚠️ 写错时**不报错、只是匹配不到** ⇒ 与「东西不存在」在输出上完全同形。
   **判据仍是那条**：报 0 时先用**已知存在的短锚**验一次搜索空间 —— 这次我该搜 `同值`（短、无元字符），而不是带 `\|` 的整句。

## 触发：**当我要报「某某为 0 / 全部通过」的数时**

1. **问：这把尺什么条件下会给出像样的错数？误差方向哪边？** 朝安全方向偏的可用（**须声明**），朝危险方向偏的必须换尺。**一把朝安全方向偏的尺，反过来用就是朝危险方向偏。**
2. **扫 `done_criteria` 的脚本必须同时处理字符串与对象两种形态** —— 无代码任务用对象形态，`select(type=="string")` **系统性假阴且不报错**（实撞：验证者差点报「漏补 3 个」，实为 11/11）。
3. 🔴 **写 grep 前先决定「数的是哪个单位」**（dev-m1c4-b 提炼，我俩各犯一次后收紧的处方）：

   | 要数什么 | 模式 |
   |---|---|
   | **定义** | `grep -c '^func momFields'` |
   | **调用** | `grep -c 'momFields('`（带括号） |
   | **引用**（含注释、字符串） | 裸 `grep -c momFields` |

   🔴 **裸 grep 恒等于三者之和 —— 它永远是最大的那个。** 所以「有没有删干净」这类怀疑**用裸 grep 查必然假阳**。
   实撞两次：dev 数「零消费者」时 `pr` 得 97（全是 `printf`/`sprint` 子串）；Leader 数 `momFields` 是否退场得 3（全在注释里，`func` 定义实为 0）。
   ⇒ **先定单位再挑模式，比事后换仪器便宜。**

   🔴 **变体：搜「这个机制在不在」时，单位对了也可能全错 —— 因为你搜的名字不是调用点用的那个。**

   实撞（TASK-010 的 DoD）：我搜**类型名** `grep 'CaliberExemption\|Exemptions' validate.go` → **命中 0**，据此写下「那个机制定义了但 validate 不读它」。
   实际调用点是**方法名** `exemptionFor`（小写 e），就在闸门主循环 `validate.go:114`，4 条测试全 PASS。

   ⇒ **一个机制有多个名字形态**：类型名 / 构造函数 / 方法名 / 字段名 / 配置键。**搜其中一个为 0，只证明那一个不在。**

   ⚠️ **这次的危害不是数字错，是它变成了一句禁令**：「加它超出射程（要动 validate 的接线）」—— 而接线早就在。
   **禁令带着假理由，读的人还是会去补那段正常工作的代码。**
   ⇒ 订正时**保留结论、换掉理由**，并留防回流标记，别写成「结论错了」。

4. **数 Go 声明的元素个数不要 grep 源码** —— 塞临时 `_test.go` 打印 `len(...)`。`grep -oE 'Field[A-Za-z0-9]+'` 在 `fieldOrder` 上得 78（真值 76），多的 2 个是块注释里的标识符。
4. **报仪器输出要么给全量，要么声明「N 条中的 M 条」** —— `head -n` 与「我认为相关的」**都是筛选**（我犯过：报 9 条，实际 36 条）。

## 触发：**当我要判「某个改动在不在这棵树上」时**

### 🔴 别挑「脑子里正装着的那个符号」—— 它恰是区分力最差的那个

实撞（TASK-012，dev-m1c4-a）：查 merge 是否发生，它挑的内容判据字串是 `M1c-1 的 TASK-010 之前`。

**那个字串在 master 上本来就有** —— 是 `calibrate.go:410` 的**注释**，而它改的是**输出字符串**。⇒ **假阳，报了 1。**

它自己的归因（准确，原样收录）：

> 我挑的是**脑子里正装着的那个符号**，而它恰是**跨版本最稳定、区分力最差**的那类字串。

🔴 **危害方向是单向的**：

| | 会发生什么 |
|---|---|
| 假阴（判「不在」而实际在） | 你会**继续追查** ⇒ 迟早发现 |
| **假阳**（判「在」而实际不在） | 🔴 **下一步是停止追查并推进流程** |

⇒ **这类判据只产假阳不产假阴**，而假阳恰好是不会被自己纠正的那一半。

### 处方：不要靠「挑一个有区分力的字串」这个判断

**因为「哪个字串有区分力」正是你会做错的那一步。** 两个不需要判断的办法：

1. **先跑 `git diff <旧> <新>`，从 diff 里挑字串** —— diff 的定义就是只有一边有
2. **直接比目标文件的 sha256** —— 完全不需要挑

⚠️ **它是靠「两把尺不一致」发现的，不是靠想起纪律** —— 它自己说「这条我以前记过」。

⇒ 又一次印证：**记住纪律不产生遵守纪律的能力。** 能指望的是**制造一个会响的东西** —— 这里是第二把独立的尺（「CONTRACTS 有无 `## Sprint M1c-4`」同时报 0），两把不一致时它才去查。

## 触发：**当我发现「引用的行号对不上」时**

### 🔴 两种成因在输出上完全同形，而处置正好相反

实撞（TASK-014，dev-m1c4-b）。QA 报告写 `configs/hestia.yaml:213`，实际在 `:218`。

**它没有直接下结论，先分辨成因**：

| 成因 | 怎么查 | 处置 |
|---|---|---|
| **树变了**（漂移） | `git diff --numstat <锚A> <锚B> -- <文件>` | 更新引用，**并检查还有多少别的引用也过期了** |
| **对方写错**（笔误） | 同上，结果为**空** ⇒ 排除漂移 | 按实际值写，**并标注来源偏差** |

它查了：该文件在 `c6f33b7`↔`4735b81` 之间**零改动** ⇒ 排除漂移 ⇒ 是笔误。

⚠️ 而且它确认了 `:213` **确实是另一句**（关于「区间宽度 / 实测宽度比值」）—— **照 `:213` 去找会找到一句不相干的话，还以为是自己理解错了。**

### 它自己的总结（原样收录）

> **「行号对不上」的两种成因在输出上完全同形**，而它们的处置正好相反……**跳过那一步会得到一个看起来同样合理、方向却相反的结论。**

⚠️ 「漂移」那条的处置里有一句关键的：**「检查还有多少别的引用也过期了」** —— 漂移**从来不是单点的**，一次文件改动会让所有指向它的行号一起失效。**判成笔误就不会去查那个「还有多少」。**

⇒ **判据**：看到引用对不上，**先问「是文件变了还是引用写错了」，用 `git diff --numstat` 在两个锚上求值** —— 这一步的成本是一条命令，而跳过它会导致一个方向相反的结论。

## 触发：**当 DoD 里有一条「禁止 X」的纪律时**

### 🔴 把禁令变成**可核对的数**，纪律才真的生效

DoD 原文（TASK-010）：「**禁止为消掉 failed 而调宽容差**」。这是一句纪律 —— 谁来判「调宽到多少算『为了消 failed』」？没有判据，它只能靠人自觉。

**dev 把它变成了一个可算的量**：

> 对每个候选容差，算「该档在**中位分母**下允许的绝对差额」，与**历史最大绝对差额**比。

| 族 | 候选 | failed | 中位分母下可放行 | 历史最大差额 | 结论 |
|---|---|---|---|---|---|
| deposit ytd | 0.17 | 1/52 | 25041 | 28000 | ✅ 闸门仍抓得住 |
| deposit ytd | **0.26** | **0/52** | **38298** | 28000 | 🔴 **实质失效** |
| deposit mom | 0.50 | 4/21 | 6350 | 8681 | ✅ |
| deposit mom | **0.85** | **1/21** | **10795** | 8681 | 🔴 **实质失效** |

⇒ **「failed 归零」与「闸门有效」在这两族上是互斥的** —— 这不再是一句劝告，是一个**可以逐档验算的事实**。

🔴 **通用形式**：一条禁令若只说「不要为了 A 而做 B」，它约束不了任何人 —— **A 和 B 都是意图，不可观测**。要让它生效，必须找到一个**在 B 发生时会变的可观测量**（这里是「该档允许的绝对差额 vs 历史最大差额」），然后禁令就变成了那个量的阈值比较。

⚠️ 找这个量的方法：问「**如果有人真的为了消 failed 而调宽了，什么东西会变得荒谬？**」这里的答案是「闸门允许的误差超过了历史上出现过的最大误差 ⇒ 它再也拦不住任何已观测幅度的东西」。

## 触发：**当一条测试被标为「最不能省」时**

🔴 **交付前自己先变异一次**：把这条测试声称在守卫的那个东西去掉，看它会不会红。

实撞（TASK-003）：`TestMoneyRERefusesToCrossSentences` 的跨句子测试**守不住它声称的约束** —— 把 `clausePat` 字符类里的 `。` 去掉，**测试 SURVIVED，全包仍绿**。

成因：`moneyRE` 里 `unitPat` 之后是**字面量 `，`**，而测试串 `…万亿元。广义货币…` 在那一步就已不匹配，**根本走不到 `clausePat`** ⇒ 该子测试对 `clausePat` 的任何写法都恒绿。

⚠️ **两处注释都声称「三个子测试逐条对应三重约束」，均为假。这类断言写在注释里永远不会红**，下一个人会据它放心重构。

### 🔴 机制成因（dev-m1c4-b 提炼，可推广到任何多段拼接的匹配器）

> **多段拼接的正则里，反例的关键字符若落在更早片段的射程之前，控制流根本走不到被测片段 ⇒ 测试恒绿。**

本例：`moneyRE = … + numPat + unitPat + `，` + clausePat + `同比` + …`
反例把「。」放在**字面量 `，` 之前**（`万亿元。`）⇒ 在 `unitPat + `，`` 那一步就失配 ⇒ `clausePat` 从未被求值 ⇒ 它写成什么都不影响结果。

⇒ **构造反例时先问：被测的那个片段，会被执行到吗？**
把关键字符放到**控制流确实能到达的位置**（本例是第一个 `，` 之后），测试才有区分力。

### 纯测试轮次的自证：**必须成对用**（dev 提出行为判据，验证者补上结构判据与限定）

改动若是**纯测试 + 注释**（实现一个字节没动），用**两条判据**证明，缺一不可：

| 判据 | 怎么跑 | 证明什么 | 它兜住对方的哪个失效 |
|---|---|---|---|
| **结构** | `git show <sha>:<file> \| grep -vE '^\s*//' \| shasum -a 256`，两端同值 | 代码部分没改，**不依赖语料覆盖率** | 行为判据的**语料盲区** |
| **行为** | 隔离对两端交替各 2 轮，四份输出 sha256 全同 | 实际执行路径行为未变，**顺带证了确定性** | 结构判据的**过滤器可能出错** |

🔴 **单写行为判据是错的——它是必要非充分**：它**只覆盖语料实际走到的代码路径**。改一条本语料触发不到的分支（错误路径、未入语料的模板、配置分支），输出照样逐字节相同，而**实现确实变了**。它也不区分「没改代码」与「做了保行为的重构」，而纯测试轮要证的恰恰是前者。

🔴 **单写结构判据也是错的**：`grep -vE '^\s*//'` 的过滤器本身会错——**字符串字面量里含 `//` 的行会被误删** ⇒ 结构判据**假绿**。

⇒ **单写任一条，另一条的盲区就没人注意。**

⚠️ 配套的**结构闸**（确认「删了 N 行」不是删断言）：顶层 `func Test` / `t.Run` / `assert|require` 计数 / `go test -list` 四项在两端持平。

⚠️ 本条的来历值得记：dev 提出行为判据时，我（leader）打算直接写进索引；**是验证者指出它是必要非充分的**。⇒ **一条「比现有做法更硬」的新判据，第一次使用时要问：它在什么情况下为真而结论为假？**

### 配套：**「构造不出反例」≠「反例不存在」**

验证者的原话：「**我没有停在『构造不出反例就当它不存在』**」——它构造并实跑了能区分的输入：

```
狭义货币(M1)余额54.55万亿元，持平。广义货币，同比增长8.5%
   原实现 → nil ✓        变异体 → 命中，同比=8.5（这是 M2 的值）
```

关键在于让被守卫的那个字符出现在**控制流真的能到达的位置**（这里是第一个字面量 `，` 之后）。原例句把「。」放在 `，` 之前，于是在更早一步就失配了。

⇒ 写「这条测试守住了 X」之前，问：**我有没有实际造出一个「没有 X 就会出错」的输入？** 造不出来时，先怀疑自己的构造，再怀疑约束不存在。

### 处方

- **核多行文本里的句子，先 `tr -d '\n'` 或用 `grep -z` / `python` 读全文再匹配**
- 🔴 **markdown 尤其危险**：软换行、`> ` 前缀、表格竖线**都会把一句话切开**，而渲染出来看是连续的一行
- ⚠️ **判据仍是那条**：报 0 时先用**已知存在的短锚**验一次搜索空间 —— 这次我该搜的是 `变成了` 或 `假话`（短、不跨行），而不是整句

### 🔴 它的处置比「抹掉」强：**保留原文 + 标注它何时失真**

> （原标题写的是「由人类执行，agent 未跑过任何一条」，**在人类授权 Leader 代跑之后它变成了假话**）

它写进文件的理由：

> **留一句已变假的自证比没有自证更糟 —— 它看起来像有据可查。**

⇒ **改掉一句假话有两种做法**：

| | 结果 |
|---|---|
| 抹掉它 | 留下一个**看起来一直如此**的现状，读者不知道这里发生过变更 |
| **留下它并标注何时失真** | 读者知道「这里发生过一次授权变更」，**而那本身是信息** |

### 它把自己那次「结论对、理由错」也写进了文件

> ⇒ **文件层证据只能证明「有人执行了」，不能证明「谁执行的」。**

它给的理由是「**它会被下一个人复用**」—— `git` / mtime / 文件出现与否都是关于事件的真信号，但回答的是「**发生了什么**」，**不回答「谁做的」**。

⚠️ 放进产物而不是只在 inbox 里说，正是本文件反复强调的载体问题：**inbox 里的自陈随 sprint 消失，文件里的会被下一个人读到。**

- `verified` 之后 ⇒ 时机守卫**无条件 DENY**（对所有角色，含 leader 与 owner）

1. **强度**：写进哪个字段才够硬？
2. **接收方**：谁会读它？（最容易漏判定者，它那时还没被 spawn）
3. 🔴 **时序**：它会在对方**还写得动**的时候到达吗？——若答案依赖消息及时送达，就换成 `done_criteria`

**补救办法（本例用上了）**：内容若已在 discovery 的别处，让对方给出**精确的 jq 路径**，下游直接取。落点不同不影响可用性，只要路径稳定且被记下。


## 触发：**当我写 A/B / 背对背判据时**

🔴 **问：这条判据描述的是「输出的**性质**」，还是「输出的**文本长相**」？**

凡是句子里出现「只在 X 相关行」「diff 为空」「只有 N 行变化」——**那是长相**。
**长相由报表的渲染逻辑决定，不由我的改动决定。**

**本 sprint 我在同一形状上犯了两次，两次都由 dev 在 `dev_done` 前实测发现**：

| 我写的（长相） | 为什么错 | dev 换上的（性质） |
|---|---|---|
| TASK-004「背对背 diff **必须为空**」 | `calibrate_report.go` 全序遍历 `fieldOrder` 且不跳过 n=0 行 ⇒ 空 diff **结构上不可能** | 「恰好 **22 行纯新增、0 删除 0 修改**，既有 54 行逐字节不变」 |
| TASK-003「diff **只在 `2020-01` 相关行**」 | `2020-01` 进成功样本 ⇒ 它贡献的字段 `n` 全 +1 ⇒ 分布表里每个这样的行都变，**而那些行不含期次字符串**。全量 diff 56 行，字面提到 `2020-01` 的只有 2 行 ⇒ **按字面判会 reject 一次正确的交付** | 「字段 `Δn` 只能 `+1` 或 `0`，**不得有负值**」（实测 25 个 +1 / 51 个 0 / 零负值） |

### 🔴 性质判据有个好认的特征（dev-m1c4-b 提炼）

> **它能对着「没变的那部分」也说出话。**

「51 个字段 `Δn=0`」与「25 个 `+1`」是同一条判据的两半；
而「只在 `2020-01` 相关行」**对没变的部分什么都没说，所以它挡不住任何东西**。

⇒ 写完一条 A/B 判据后自问：**如果改动意外影响了别的东西，这条判据会不会变红？** 长相判据的答案通常是「不会——因为那些行本来就不在我数的范围里」。

### 🔴 判据的**方向性**（dev-m1c4-b 命名，与「对没变的部分说话」同族）

> **一个判据只覆盖它「正着用」的方向时，反方向的实现缺陷对它不可见。**

⇒ 凡是**成对 / 对称 / 互逆**的机制（twin map、双向转换、编解码、正反查表），**判据必须两个方向各测一次**。

实撞（TASK-006）：`missingCaliberAware` 的 `twin` map 是双向的（`ytd↔mom`）。原有两条断言只走 ytd→mom，⇒ **只建单向 twin 的实现能让它们全绿**。dev 补的交叉是「把 golden 的 `_ytd` 全翻成 `_mom`，同样不该缺」——只有它抓得到。

与「**性质判据能对着没变的那部分也说出话**」是同一族，但形式不同：

| | 判据要对着什么说话 |
|---|---|
| 性质 vs 长相 | **没变的那部分**（「51 个字段 `Δn=0`」） |
| 方向性 | **反方向**（把 ytd/mom 对调后仍成立） |

⇒ 两条合起来的通则：**判据不该只在「我期待的那个情形」上有话说。**

### 附：这类订正的时机是机制问题，不是纪律问题

会让验证者按字面判错的判据，**必须在 `dev_done` 之前订正**——之后到 `accepted` 为止没有任何角色写得了（`verifying` 期间改会漂 `discovery_sha256`，`verified` 之后时机守卫无条件 DENY）。
dev-m1c4-b 的原话：**「这是时机问题不是纪律问题。」**

| | 会被验证 | 不会被验证 |
|---|---|---|
| 长相 | 「25 个字段 `Δn=+1`」「覆盖率 96.1%」 | 「`boundary[0]` 里写着…」「`extract.go:582`」 |
| 心理归类 | **断言**（需要证据） | **元数据**（只是指个位置） |

⚠️ **而位置引用同样是可真可假的断言** —— 它的真值决定读者能不能找到东西。

**实例**：验证者报告里每个数字都有命令支撑，唯独条目号写错（实际在 `boundary[1]`）；Leader 的 DoD 里 5 处行号 4 处错，全部是「核实过代码之后」写下的。**两个人、同一形态、都发生在自己最严谨的产出里。**

**处方**：写下坐标时问一句「**这也是个断言吗？**」——答案永远是「是」。要么核一遍，要么只给内容特征（`grep -n 'func xxx'`），不给坐标。

**发现后**：像验证者那样**留防回流标记**（明写「初版误作 X，若你从别处读到该引用，那是本错误的回流」），而不是静默改掉 —— 错误的坐标可能已经被别人抄走了。

### 处方

- 定位一律用 `grep -n '<函数名或特征串>'`，**把命令本身写进 DoD**（读的人可以直接跑，且它永远指向当前状态）
- 若确实要给行号（比如引用一段长注释），**紧跟一句内容特征**，让读的人能在行号失效时自救
- ⚠️ **行号写完自己核一遍** —— 本例 4/5 不准，而全部是我「核实过代码之后」写下的

## 触发：**当我把一个比较式两边同乘一个量来「避免除法」时**

### 🔴 `r*tot > tol*tot` 与 `r > tol` 在浮点上**不等价**

实撞（TASK-010，dev-m1c4-a）：换仪器时它第一版把判据写在**绝对域**（两边同乘 `|tot|` 以避免除法），结果 **`TestDepositSumBoundaryIsInclusive` 变红**。

⚠️ **那条测试是专为抓这个而存在的** —— 它挑的残差与容差字面量**实测是同一个 float64**，所以任何在边界上「差一点」的实现都会被它逮住。

改回**比值域**写 `r > max(tol, abs/|tot|)` 之后，`absTol = 0` 的三族才**真正逐位不变**。

🔴 **为什么这类改写特别危险**：

- 数学上等价 ⇒ **审查时看不出问题**（「两边同乘一个正数」是恒等变形）
- 只在**边界上**不等价 ⇒ 绝大多数输入下行为相同
- 而边界正是判据的**全部意义所在** —— 容差判据的作用就是决定「恰好等于容差」算不算通过

⇒ **改动只影响边界的实现，必须有专门钉边界的测试**。本例里那条测试已经存在（是前面某个任务留下的），**它是唯一发现这个问题的东西**。

⚠️ 推论：看到「为了避免除法而两边同乘」这种优化时，先问 **`absTol = 0` 的退化情形还逐位不变吗？** —— 那是最容易被认为「显然没变」而跳过的一格。

### 处方

- 谁读同一批输入？（本例：`fieldOrder` / `requiredFields`）

- 谁的**输出会被拿来和我的输出比**？（两份判定分叉的表现是**互相矛盾的报告**，那是最难归因的一类）

⇒ 找到之后二选一：**复用同一个函数**（本例 dev 的选择），或**显式记下为什么必须是两份**。**不要让第二份静默存在** —— 它今天与你一致，只是因为你刚改完。

## 触发：**当我用变异测试当作「查全了」的证据时**

### 🔴 变异测试对「缺了一段从未写过的代码」**结构性失明**

QA 在 M1c-4 的观察（Leader 已核实代码，属实）：

> 三个 lens 子代理找到的 MAJOR 与我本体找到的**几乎不重叠**（只有一条双源命中）。**不是「多跑几个视角提高覆盖率」，而是它们看的东西根本不同**：我做变异 + 真语料 A/B（**动态**），它们做 AST 与调用图可达性（**静态**）。
>
> 🔴 **B-1 那种缺陷，变异测试结构上发现不了** —— 变异只问「改了会不会红」，而这里**没有东西可改：缺的是一段从未写过的代码。**

### 那条缺陷长什么样

```go
// extract.go:402-408   合计句：二选一
if hasCum {
    return m, true, err          // ← 有累计族就返回它，当月族整个不看
}
return m, false, err             // 调用方据这一个返回值写一列

// extract.go:1038      社融总量句：真双写
if len(cumulative) == 0 && len(current) == 0 { return nil, err }   // 两族都没有才报错
```

**同一个 sprint、同一个概念、两条路径形状相反。** 而 CONTRACTS 自述「两种口径同时原样存下，**一个都不丢**」—— 对第一条路径为假。

⇒ **变异能杀死「写错的代码」，杀不死「没写的代码」。** A/B 对照同理：两边都没有那段逻辑，输出当然逐字节相同（本任务实测四份 sha256 完全一致）。

### 判据

| 方法 | 能发现 | 结构性看不见 |
|---|---|---|
| **变异测试** | 断言没在守 | **缺失的分支** |
| **真语料 A/B** | 行为变了 | **两边都缺的行为** |
| **AST / 调用图可达性** | 没接线、写了不生效、孤儿 | 运行时才成立的性质 |
| **读契约自述 vs 读实现** | 🔴 **说了但没做** | — |

⇒ **「变异全 KILLED + A/B 逐字节一致」不构成「实现完整」的证据**，它只构成「已写的部分是对的」。

⚠️ **要发现「说了但没做」，唯一的办法是拿契约的每一句去对实现** —— 而那是静态的、读文档的活，不是跑测试的活。

⚠️ 本 sprint 的实例里，`absTol` 那条（写了字段但消费点只有一个）同样是**静态**发现的（`grep` 全部读写点），不是变异发现的。

## 触发：**当我跑变异测试 / 任何红绿判定时**

### 🔴 两组测量的**口径**不同就不可比 —— 连提出这条判据的人也会栽（同一天）

实撞（TASK-009 验证者自陈）：它的变异 harness 用 glob `calibrate*.go` 取主工作区指纹（**4** 个文件），而它**开工时手工列了 3 个**。收尾比对时多出的第 4 个哈希被读成「🔴 主工作区被污染」。

实为既有的 `calibrate_test.go`。核实后：`git status -- internal/hestia/` 为空、HEAD 未动、三个文件哈希与开工前逐一相同。

⚠️ **「两组测量口径不同就不可比」这条判据，正是它上一轮刚对 dev 用过的** —— 隔了不到一天栽在自己身上。

🔴 **为什么会这样**：口径不一致**不产生错误**，它产生一个**看起来像信号的差异**。而这个差异指向的方向恰好是你最警惕的那个（「被污染了」），所以你会**立刻相信它**、而不是先问「这两组数是同一把尺量的吗」。

⇒ **指纹类比对，两端必须由同一条命令生成**（同一个 glob、同一个排序、同一次调用），不能一端手工列一端自动展开。

**崩溃型失败与断言失败的退出码相同**（都是 1）⇒ 不加有效性闸会把「跑都没跑起来」记成「变异被杀死」。
实撞：验证者的 harness 因 `go test` 用绝对路径导致 `setup failed`，**差点把两个变异误记成 KILLED**。
闸的形态：`setup failed|build failed|outside main module` + 对照组。

### 🔴🔴 现有的有效性闸挡不住**崩溃型变异**——要加「`=== RUN` 计数比对」

实撞（TASK-008 验证，test-m1c4-a）：变异手法是**短路 `if err != nil`** ⇒ `rows` 为 nil 仍被 `Next()` ⇒ **panic**。

那次输出的样子：

| 观察项 | 值 | 会让人以为 |
|---|---|---|
| 退出码 | 非 0 | 「变异被杀死了」 |
| FAIL 行 | 有，且**只有一条** | 「精确杀死了目标测试」 |
| **`=== RUN` 计数** | **1196**（对照组 **1461**） | 🔴 **128 个顶层测试根本没跑** |

> **唯一拆穿它的是 `=== RUN` 计数。**

⚠️ 现有闸（`setup failed|build failed|outside main module`）挡的是**构建期**失败；这次是**运行期 panic**，构建正常、测试也真的开始跑了，**只是跑到一半炸了**。⇒ **两种形态，现有闸只挡一种。**

⇒ **加进 harness**：每个变异体的 `=== RUN`（或 `--- PASS/FAIL` 总数）必须与对照组一致；不一致 ⇒ 该变异体**作废重做**，不得记 KILLED。

⚠️ 与「变异全绿有两种成因」合起来看：**变异结果有三种坏法**——全绿（守卫无效 / 打不到）、**部分没跑**（崩溃型）、以及外溢（杀掉不相干的）。三种都要有闸。

### 🔴 有效性闸挡住的假结论**方向相反**，所以它不能省

test-m1c4-a 在 TASK-011 验证中两次被闸拦住，它自己的总结：

| 失误 | 若无闸会被记成 | 方向 |
|---|---|---|
| 探针字段名写错 → `build failed` | 「探针跑出 **0 违反**」 | **低估**问题（以为没事） |
| 变异删了 `%g` 却留实参 → `go vet` printf 拦下 | 「抬头改动导致测试红 ⇒ **有守卫**」 | **高估**保护（以为有人看着） |

> **两个都是假结论，而且方向相反。**

⇒ 这就是为什么「跑完看红绿」不够：**同一个技术故障（构建/静态检查失败），在不同语境下会被读成相反的两个结论**，而两个都会让人停止追查。

⚠️ 闸不只挡「变异没生效」，也挡「变异生效得太多」。**两侧都要挡。**

### 🔴🔴 「变异全绿」有**两种**成因，混淆会产生一个**看起来很有分量的假发现**

| 成因 | 结论 | 下一步 |
|---|---|---|
| **守卫无效** | 「这条测试守不住它声称的东西」 | 严重，要返工 |
| **变异打不到** | 「我这个变异没打中被测路径」 | 换变异重来 |

🔴 **两者在输出上完全相同（全绿）**，而第一个结论**看起来很有分量**——报出去会引发返工，而代码其实是对的。

实撞（TASK-006 验证，test-m1c4-a）：验「放松边界」守卫时**连续三个变异都杀不动**，逐个追查才发现全是「打不到」：

| 变异 | 为什么打不到 |
|---|---|
| M4 | 被**无关守卫**（字段名字面量检查）先拦住，变异体作废 |
| M4b | `fieldOrder[0]` 恰是 `tsf_stock`，而交叉格的 `want` 就是它 ⇒ **自己配自己等于没配** |
| M5 | 第一格的 `values` 是**空 map** ⇒ 任何 twin 都查不到 |
| M6 | ✅ 终于打中，守卫转红 |

⇒ **区分办法：读被测测试的实际输入，而不是从变异的意图去推断它生效了。**

⚠️ **顺带发现的东西往往比结论更值钱**：追查过程暴露出那条守卫**两格射程不同**——第一格对「乱配 twin」结构上免疫，真正守边界的是第二格交叉。**若后人删掉第二格留下第一格，守卫会静默失效。**

### ⚠️ 打印时不要把结论硬编码在数据旁边

同一轮里 test-m1c4-a 报：「我打印时把标签硬编码成『3 处』（抄了 Leader 的数）而数据是 8 行，**幸好把行都打了出来**。」

🔴 **硬编码的标签永远不会错，也永远不告诉你任何事**；而它紧挨着数据，版式上更像结论 ⇒ 矛盾时人眼取标签。

⇒ 计数类输出**只打数据**（`printf "命中 %s 条" "$n"`），或让判定进条件（`[ "$n" = 0 ] && echo A || echo B`）。判别式：**这一行输出错了的话，什么东西会告诉我？**

### 🔴 隔离变异树里**不能用 `git checkout --` 还原**

实撞（TASK-005）：变异前把改好的实现 `cp` 进隔离树，变异后用 `git checkout -- <file>` 还原 —— **它把 `cp` 进去的实现一起擦掉了**，还原成了 base 版本 ⇒ **后续变异全部打在旧实现上**。

dev 第一次就撞到，改用 `cp` 自备份还原，并把已跑的 V1 重跑了一遍。

⇒ **隔离树里的「还原」必须还原到「变异前的那份」，而 `git checkout --` 还原的是「版本库里的那份」——当你 `cp` 进去过东西，这两者不是一回事。**

🔴 **症状是：全绿、diff 非空、看不出任何异常** —— 变异静默打在旧版本上，而你以为在测新版本。

⚠️ **两个方向相反的检查都要做**（只做一个会漏掉另一半）：

| 检查 | 问的是 | 漏了会怎样 |
|---|---|---|
| 隔离树跑的**是我的版本**吗 | `cp` 进去的实现还在不在 | 变异打在旧实现上，结论无效 |
| 主工作区**未被污染**吗 | 变异有没有漏回主树 | 污染他人在途工作 |

前者是「我测的对不对」，后者是「我有没有害到别人」。**归档里反复出现的是后者，而这次踩的是前者。**

### 🔴 语义级变异做不出严格双向对角线，**该如实报而不是硬凑**

我在 TASK-005 的 DoD 里要求做**双向**对角线（每行一个 FAIL 且每列一个 FAIL），那是照搬 TASK-003 的形态。dev 如实报告做不到，并说明了原因，我接受：

| | TASK-003 | TASK-005 |
|---|---|---|
| 变异性质 | **字符级**（字符类去掉一个 `。`） | **语义级**（口径判定反向、选列反向） |
| 影响面 | 小，只波及一条断言 | 大，`NotContains` 类断言必然跟着红 |
| 能否行唯一 | ✅ | ❌ **不可能** |

⇒ **判据该收窄成「列唯一性成立 + 行不唯一且逐条有解释」**：
- **列唯一**（每条守卫只被自己那条变异杀）排除了「另一条才是真正抓到它的那个」—— 这是双向对角线的主要价值，它在语义级变异下**仍然成立**
- **行唯一**（每个变异只杀一条）在语义级变异下没有意义，要求它只会逼出硬凑的矩阵

⚠️ **「如实报告做不到并说明为什么」比一张漂亮的矩阵有用。** 我给判据时照搬了上一个任务的形态，没问「这个形态依赖什么前提」。
