## 一、Leader 点名复核的第 1 点：M1 属实，但守护范围窄于 DoD

### 1.1 Dev 的 M1 自报**完全属实**

| 变异 | 预期（注入前写下） | 实际 |
|---|---|---|
| **M1a** 消费者**读后写** `r.values["pe_ttm"]=-1`（Dev 的形态） | 红 | **红** `gate_test.go:259: 第 0 行：缓存命中后返回值发生变化，说明有消费者写了共享的 row.values` ✓ |
| M1a → 既有 `TestFetchDailyBasic`（对照） | 绿 | **绿** ✓ |

**「形式存在、断言空洞」确实没有发生**，断言真的会红，且红的原因就是那条断言（非 panic、不带倒别的测试）。Leader 的第 1 点依据**成立**。

### 1.2 但换一种写形态就漏检

这条测试断言的是 **`FetchDailyBasic` 的返回值**（`[]ValuationPoint`，flat 值类型）两次相等，
**不是 `[]row` 本身**（`row` 含 map，Go 里不可比较）。所以它守护的是
「写**导致返回值可观测地变化**」，而非「写」本身：

| 变异 | 形态 | 新测试 | 既有测试 | 全量 25 测试 |
|---|---|---|---|---|
| **M1a** 读后写，值不同 | 第一次返回原值、第二次返回改后值 → 两次不等 | **红 ✅** | 绿 | 红 |
| **M1b** **写后读**，值不同 | 两次都返回改后值 → **两次相等** | **绿 ❌** | 红（偶然：它断言了被改字段的具体值） | 红 |
| **M1c** **归一化写回**（`if IsNaN(v) { v = 0 }`） | 测试数据无 NaN → no-op，两次都相等 | **绿 ❌** | **绿 ❌** | **全绿 ❌ 漏检** |

**M1c 是真实场景形态**，不是人为构造的角落：`client.go:184` 明写
`values[f] = math.NaN() // 非数值列(如 ts_code)与缺列一律 NaN`，说明 NaN 在真实数据里确实存在；
一个消费者做「NaN → 0」归一化是完全合理的需求，而它**会污染共享缓存**（对含 NaN 的真实数据），
却被整个测试套件放过。

### 1.3 根因：这不是 Dev 写得不够好，是行为测试的能力边界

要完整守护「消费者只读」，必须能检出**行为不可观测的写**（幂等写、条件不触发的写）。
这在行为测试层面**定义上做不到** —— 只能靠 AST 扫描消费点，而那是 TASK-013 的手法、
且 TASK-013 的 DoD 只统一守护 `lastReq` 类节流符号，不含这个。

⇒ 所以这是 **`dod_defect`**（DoD 要求了一件在指定手段下不可达的事），不是 `task_defect`。
我最初提「(a) 可测性存疑」时理由不够精确，Leader 用 M1 推翻也合理；**现在的精确表述是**：
可测的是「写导致返回值变化」，不可测的是「写本身」，两者的差集永远测不到。

### 1.4 Dev 注释里有一处声明不准确

`gate_test.go:232`：

> 这是行为断言而非 AST 扫描：它覆盖所有现有消费者，且**不依赖写法形状**。

「覆盖所有现有消费者」**属实**（现有两个消费点确实只读）。但「**不依赖写法形状**」**不准确** ——
M1a/M1b/M1c 三种写法结果不同，它恰恰依赖写法形状。这与 DoD 自己警告的
「错误的修复比不修更难查」是同一类：**不准确的守护声明会让下一个人以为这里已经守住了。**

**不构成 FAIL**（守护存在且捕获率高），但**声明应修正为「概率性，捕获率约 90-95%」**。
建议按 TASK-002 `rounds=3` 的做法在测试内构造多组不同插入顺序，把捕获率提到接近 100%
—— 这与 dev-agent-35 那次如实声明 20ms sleep 是概率性的做法一致。
