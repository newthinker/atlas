### T2 `internal/collector/policy/gate.go`（方案 Task 2，行 438-1014）

```go
var ErrTimeout = errors.New("policy: fn timeout")
const maxCacheEntries = 512

type Gate struct { ... }   // nil *Gate 透明直通
type Option func(*Gate)
func WithWarn(f func(msg string, err error)) Option
func New(t *Table, opts ...Option) *Gate                    // ← T3 变更为 New(t, q QuotaStore, opts...)
func Fetch[T any](g *Gate, topic, key string, fn func() (T, error)) (T, error)
func (g *Gate) Do(topic, key string, fn func() error) error // 强制 TTL=0
func (g *Gate) Wait(topic string)                           // 只节流，供 fn 内重试循环复用
```

**返回值所有权**：`Fetch` 命中缓存时**不复制**返回值，多个调用方拿到同一个值。返回切片/映射的 collector 必须自行深拷贝后再交给上层（取代旧 `CachedCollector.cloneOHLCV`）。

> ⚠️ **`slices.Clone` 只在元素是 flat value type 时才等于深拷贝。** 这个限定旧实现本来写了（**`internal/core/types.go` 的 `OHLCV` 定义处**（原在 `internal/collector/cache.go` 的 `cloneOHLCV` 上，该函数已随装饰器于 TASK-011 删除，约束已转移到会被违反的那一侧）：「OHLCV is a flat value type, so a shallow element copy is a deep copy」），是本契约表在迁移时**丢掉**的——属于回归而非新隐患。元素含 map / slice / 指针字段时（如 tushare 的 `row.values map[string]float64`），`slices.Clone` 复制的是结构体、底层数据仍共享，必须逐元素深拷贝。**给错误的隔离手段比不给更糟**：照做的人以为自己安全了，而这种 bug 表现为偶发的数据串改，比缓存没生效难查一个数量级。

**`Wait` 使用约定**：`Fetch` 在调用 `fn` 前已节流一次；`fn` 内的重试循环只在 `attempt > 0` 时调 `Wait`，否则首次请求等两倍间隔。

## 补充契约（开发中沉淀，TASK-006~010 接入前必读）

### 陷阱 1：`Do` 在 `Coalesce=true` 的主题上会被合并

`Do` 虽强制 `noCache=true`，但仍走同一个 `fetch`，因此**照样受 singleflight 合并**。内置表里**所有登记主题的 `Coalesce` 都是 true**，所以：

> 20 个并发 `Do(topic, key, fn)` 只会真正发生 **1 次**副作用。

各 collector 接入时若拿 `Do` 去做「必须每次都发生」的调用（计数、审计、写操作），会静默合并且极难排查。需要每次都发生时，请用不同的 `key`，或为该主题关闭 `Coalesce`。

（来源：dev-agent-35 在 TASK-002 预读阶段提出。行为照方案不改，仅在 `Do` 的文档注释与本表中标注。）

### 陷阱 2：类型断言失败是**静默**的，测试必须断言调用次数而非返回值

`fetch` 有两处 `T` 断言失败后不 panic 的降级，二者都会让「断言返回值」的测试形同虚设：

| 位置 | 失败时的行为 | 后果 |
|---|---|---|
| 缓存命中处（方案行 862） | 当作未命中，重新调 `fn` | 返回值**仍然正确**，bug 自愈成「多调一次 fn」 |
| singleflight 返回处（方案行 898） | `tv, _ := v.(T)` | **静默返回零值 + nil error** |

推论，对所有涉及缓存 key / 合并 key 的测试成立：

- **验证「key 必须含 topic」只能断言 `fn` 调用次数**。正确写法：`Fetch(a.x,"AAPL")` → `Fetch(a.y,"AAPL")` → 再 `Fetch(a.x,"AAPL")`，断言第一个 fn 的调用次数**仍为 1**（key 不含 topic 时会变成 2）。断言返回值的写法**永远绿**。
- **singleflight 相关测试必须断言每个 waiter 拿到非零值**，只断言 `err == nil` 会漏掉零值静默返回——这与设计 §5.2 要求的「coalesce 失败时全部等待者共享同一错误」是同一类静默失败。

（来源：同上。这条是本 Sprint 迄今最有价值的测试方法论输入，TASK-007~010 写 collector 侧缓存测试时同样适用。）

### 教训 3：变异验证会抓出「跑通但无效」的断言

TASK-001 的首轮验证跑了 16 个变异，**3 个存活**，其中一条是阻塞项：把 `shanghai()` 的 `return time.UTC` 改成 `panic(err)` 后**整个测试套件仍然 `ok`** —— 那条「LoadLocation 失败时退回 UTC 而非 panic」的 DoD 实际上零守护（测试验的是「加载成功」，而 DoD 要的是**失败分支**的行为）。

对所有任务的启示：**为「不可达的错误分支」写的测试，极易退化成验证正常路径**。写这类测试时先自问「如果我把这个分支的行为改成相反的，我的测试会红吗」。

### 陷阱 4：构造函数**快照**全局单例，测试里的替换必须发生在构造之前

各 collector 的构造函数取的是 `policy.Default()` 的**当时值**（`gate: policy.Default()`），不是每次调用现取。因此：

> `policy.SetDefault(g)` 必须在 `xxx.New(...)` / `NewWithBaseURL(...)` **之前**调用，否则拿到的是旧的默认闸门。

方案给的两个 prism 集成测试恰好顺序正确（行 4109→4112、4148→4150），**但方案没说这是必须的**。把这两行对调后：编译通过、`errors.Is` 断言**大概率仍然绿**（拿到的是生产策略而非零策略，表现只是变慢或偶发失败，不是确定性红）。典型的「顺序即语义」依赖。

处置：在各 collector 构造函数的注释里写明「gate 在构造时快照 `policy.Default()`」。零成本，且比改成每次现取更不容易引入新问题。

（来源：dev-agent-36 预读 TASK-014 时发现。）

### 教训 5：注释描述的是「当前巧合」还是「被守护的契约」

本 Sprint 撞到三次同一个模式：

| 处 | 注释说的 | 实际状态 |
|---|---|---|
| tushare `row` 的消费者只读 | 「所有消费者都只读 row，故不额外复制」 | 今天属实（唯二消费点确实只读），但**无任何测试守护**，加一个写消费者就静默污染缓存 |
| 路由表「`.HK` 优先于加密前缀」 | 注释断言优先 | **只在具体度相等时成立**，`ATOM*`(4) > `*.HK`(3) 仍判 crypto |
| `KnownIndexMarket` 的「已登记」口径 | —— | 依赖「表内非通配 pattern 只能是指数」这条**从未写下**的不变量；验证者实测：往表里加 `{"AAPL","yahoo",MarketUS}` 后 `KnownIndexMarket("AAPL")` 即误报 `(US,true)` |

⇒ 写注释前先问：**这句话是我保证的，还是我观察到的？** 前者要有测试，后者要写明「当前如此，非契约」。

### 陷阱 6：两类「断言看起来在、实际不设防」的写法（TASK-001 两轮验证共抓出 5 例）

本 Sprint 前两轮变异验证抓出的 5 个空转断言，归纳为两类。**写测试时先对照这两条自查，比返工便宜得多。**

#### ① 弱断言：只钉住「不是 X」，没钉住「是 Y」

```go
// ✗ 反例（TASK-001 M21 存活）
if p.Quota.Loc == nil || p.Quota.Loc.String() == "UTC" {
    t.Errorf("Loc = %v, want Asia/Shanghai", p.Quota.Loc)
}
// 把 Loc 改成 Asia/Tokyo → 断言仍然通过。首轮变异恰好只试了 UTC，
// 所以这条弱断言「看起来」有效，换任何其它非 UTC 时区即静默放行。

// ✓ 正解
if p.Quota.Loc == nil || p.Quota.Loc.String() != "Asia/Shanghai" { ... }
```

DoD 写的是明文值（`Asia/Shanghai`）就断言那个值。排除法只有在候选集是二元时才等价。

**真实影响**：`Quota` 语义是 `Window >= 24h` 时按 `Loc` 自然日对齐；tushare 的 5 次/天是北京时间重置，`Loc` 错成 Tokyo 会让 Gate 在错误时刻重置配额，进而撞 40203。

#### ② 空真（vacuous truth）：遍历一个可能为空的集合

```go
// ✗ 反例（TASK-001 M26 存活）
for _, topic := range tbl.Topics() {
    if p, _ := tbl.Lookup(topic); p.TTL != 0 { t.Errorf(...) }
}
// 把 Topics() 改成恒返回空切片 → 循环零次执行 → 断言 vacuously true → 全绿。
// DoD 说的是「**全部**主题 TTL 归零」，而「全部」这个量词没有下界。

// ✓ 正解：先给量词一个下界
topics := tbl.Topics()
if len(topics) != 9 {
    t.Fatalf("内置主题数 = %d, want 9", len(topics))
}
for _, topic := range topics { ... }
```

凡是 DoD 里出现「全部 / 所有 / 每个」，测试里就必须先断言集合大小或非空，否则量词无下界。

#### 自查口诀

> 写完一条断言，问自己：**能不能构造一个错误的实现让它仍然通过？** 弱断言问「换个错值行不行」，遍历断言问「集合空了会怎样」。

#### 陷阱 6 的补充：这两类缺陷**肉眼可查，不必靠造变异撞**

看断言原文的**谓词形式**即可判别（test-agent-17 提出）：

| 谓词形式 | 强度 | 例 |
|---|---|---|
| `if got != 期望值` | **强** —— 等值断言，任何错值都转红 | `Loc.String() != "Asia/Shanghai"` |
| `if got == 某个错误值` | **弱** —— 排除断言，只挡住枚举到的那几个值 | `Loc.String() == "UTC"`（换成 Tokyo 即静默通过） |
| `for range 集合 { 断言 }` 无长度守卫 | **弱** —— 全称量词无下界，集合空则空真 | 遍历 `Topics()` 却不约束长度 |

⇒ **code review 时扫一遍谓词形式，比事后造变异便宜一个数量级。** 变异验证应当用于确认「强断言确实覆盖了预期行为」，而不是用于发现「断言写成了弱形式」——后者读代码就能看出来。

> ⚠️ **本条规则的早期版本（「同时约束基数与成员有效性」）已被实测证伪，勿沿用。** 正确的规则是：
>
> **集合类断言应当对集合本身做等值断言**，而不是用「基数 + 逐元素谓词」组合去逼近。**逐元素谓词尤其危险——当该谓词比目标集合更宽时，基数与成员校验可以同时满足而集合完全错误。**

证伪过程（test-agent-17 实测，三条独立逃逸路径）：`len(topics) != 9` 加上「每项都能被 `Lookup` 命中」，仍被以下变异绕过——

| 变异 | 内容 | 结果 |
|---|---|---|
| M26b | `Topics()` 返 9 个不存在的主题名 | 被命中断言捕获 ✅ |
| **M26c** | 返 9 个 `lixinger.*` 域下的**假名** | **存活 ❌** —— `Lookup` 是三段查表，任何 `lixinger.<随便什么>` 都经**通配段**命中；「能被 Lookup 命中」这个谓词比「已登记主题」宽得多 |
| **M26d** | 返同一真实主题**重复 9 次** | **存活 ❌** —— 基数对、每项都真实，但集合错 |

危害不止于「`Topics()` 坏了没人发现」：M26c 会让宿主断言**整体空转**（循环检查的全是假名，9 个真实主题一个都没被检查）。实测 **M26c + M27 组合**（`Topics()` 返假名 **且** `DisableTTL` 只清 `lixinger.*`）→ **全绿逃逸**，boundary[0] 的「令全部主题 TTL 归零」被完全架空。公允地说：逃逸需两处协同改坏且恰好互补，**单点故障仍全部被守护**。

**正解**：构造 `want` map、把 `Topics()` 收进 `got` map，`len(topics) != len(want) || !reflect.DeepEqual(got, want)` 即 `Fatalf`（`len` 比较兼管去重）。代码量与「基数 + 逐元素」两段基本持平，一步覆盖基数 / 重复 / 成员有效性 / 完整性四件事——分开列反而容易再漏第五件。

**为什么要写成「集合等值」而不是「再补两条」**——这条推理路径值得完整走一遍，因为后来者会自然地重走它：

> 发现 M26（空集合）→ 补基数守卫 → 发现 M26b（假名）→ 补成员有效性 → 发现 M26c（宽谓词下的假名）、M26d（重复）→ 还要补去重、补覆盖完整性 → **补不完**。

「基数 + 成员有效性」两条加起来**仍然不够**，这是实测结论不是推测。逐条打补丁的思路本身是错的：每补一条只堵住已经想到的那个逃逸，而逃逸空间由「你的谓词比目标集合宽多少」决定，不由补丁数量决定。**直接对集合本身做等值断言，一次性把整个逃逸空间关掉。**

**这是谓词判据的集合版，同样肉眼可查**：看到「先 `len(x) != N` 再 `for range x` 逐项校验」的形状，就问一句——**这个逐项谓词是不是比目标集合更宽？**

### 变异验证的操作纪律（三条，均有实际踩坑记录）

1. **注入后先确认代码确已改动，再解释测试的红绿。** 重构会挪动注入点（`shanghai()` 拆出 `loadLoc` 后，首轮那些 perl 表达式全部静默匹配失败），不改代码却跑出绿 = **假绿**。用 `grep -n` + `git diff --stat` 双查。

2. **不要用 `grep -c pattern file && run` 串联。** 0 匹配时 `grep` exit 1、`&&` 短路，`run`（含还原步骤）整段不执行 —— 变异未还原就叠加了下一个，**两个结果都不可信**（test-agent-17 二轮的 M26/M27 即因此污染，两条单独重跑才拿到可信结论）。用 `grep -n`，或每个变异一条独立命令。

3. **还原用 `md5` 校验，不靠「我记得还原过」**；收尾 `git status --porcelain` 必须为空。

### 变异分析的两条对称结论（本 Sprint 三轮验证共同得出）

- **变异存活 ≠ 测试无效** —— 可能是等价变异体。需构造语料对比行为后才能下结论（TASK-012 的 MU6/MU10，58 符号逐行 diff 无输出）。
- **变异捕获 ≠ 断言够强** —— 可能只是恰好落在弱断言唯一覆盖的那个值上（TASK-001 首轮 M7 转红，掩盖了 `Loc` 断言是排除式写法这一事实，二轮 M21 才暴露）。

两条合起来才是完整的变异分析纪律：**先证明变异有效，再解释红绿，最后回看断言形式**。

### 陷阱 7：并发测试会在慢机器上静默退化成顺序执行

时序类断言（「跨域不阻塞」「缓存命中不等节流」）的失败模式是**串行化**，而串行化的测试极易写成「跑通了但没证明并发」。

**反例思路**：起一个 goroutine 让它卡在 throttle，主协程「确认它已进入 sleep」后再计时另一个域。
**为什么不行**：throttle 的 sleep 发生在**持锁临界区内，从包外没有任何可观测信号** —— 「确认已进入 sleep」无法确认，只能靠 `time.Sleep` 猜。慢机器上猜错即退化为顺序调用，而断言照样绿。

**正解：双域对称 + barrier，让两种实现产生不同的总耗时**

- 两域 `MinInterval` 都设 300ms，各预热一次（两域 `lastReq` 均置为 T）
- barrier（`ready.Wait()` 后 `close(start)`）同时放行两个 goroutine，分别发 `a.x` 与 `b.x`
- 测**总耗时**：按域隔离 → 并行等待 ~300ms；全局锁 → 串行 ~600ms；断言 < 450ms

三点优势：① 无论 goroutine 调度顺序如何，两种实现的耗时都是确定的 —— **消掉了「谁先进入 throttle」这个无法确认的前提**；② 把测试写成顺序调用必然 600ms 而转红 —— **测试自身杜绝了退化成串行仍绿**；③ barrier 消除 goroutine 启动开销，不靠 sleep 猜时序。

**并发测试专用自查**（在陷阱 6 口诀之外另加一条）：

> 在单核 / 慢机器上，这条断言会不会退化成「顺序执行也能通过」？

（来源：dev-agent-35 在 TASK-002 设计阶段复查后废弃原方案。）

### 教训 6：注释永远贴在「受害者一侧」，防线必须在「违反者一侧」

`Fetch` 的文档注释写「返回值不复制，调用方须自行深拷贝」—— 读 `Fetch` 定义的人**本来就在关心缓存语义**；真正会违反它的是写 collector 的人，他调 `Fetch` 拿到切片直接往上层传，根本不会翻到 `Fetch` 的注释。

同构的三例：

| 约束 | 注释写在 | 会违反它的人在改 |
|---|---|---|
| 「新增字段必须是值类型」 | `cache.go` 的 `cloneOHLCV` | `core/types.go` 的 `OHLCV` |
| 「调用方须深拷贝」 | `policy.Fetch` | 各 collector 的 `FetchHistory` |
| 「调用方须先大写」 | `lookupRoute` | 包内新增调用点 |

### 教训 7：「我论证过它正确」不等于「它被验证过」

TASK-002 的 Dev 曾向 Leader 完整论证过一个并发测试设计，理由三条、逻辑自洽、Leader 认可并写进了契约（陷阱 7）。**那个论证是错的**，而且是 Dev 自己注入变异时才发现的。

**错在哪**：throttle 等的是**绝对时刻** `lastReq + MinInterval`，不是「轮到我时再等 MinInterval」。原论证假定「全局锁 → 两个域串行等待 → 总耗时 600ms」，但两域几乎同时预热时，A 持全局锁等到 `T+300ms` 释放，**B 拿到锁时它要等的那个绝对时刻也已经过了** → 立即返回 → 总耗时与按域隔离无异 → **假绿**。

**修正**：「跨域不阻塞」有**两种独立失效形态，需要两个测试**——

| 失效形态 | 捕获者 |
|---|---|
| 所有域共享同一个 `lastReq` | 双域对称 + barrier（原设计，对这一形态有效）|
| 每域独立 `lastReq` **但 throttle 额外持一把全局锁** | a 域长等待 + b 域**不设** `MinInterval`，测 b 是否被阻塞 |
| （方案原版的串行写法）| **两种都测不出** |

实证：注入「每域独立 lastReq + 额外全局锁」变异后，**只有第二个测试转红**，串行版与双域对称版都绿。

**通用启示**：设计评审能发现「明显不对」的方案，但发现不了「论证自洽但前提错了」的方案。**论证的产物是假设，变异的产物才是证据。** 凡是「我想清楚了所以它是对的」，都要用一次注入把它变成「我试过了所以它是对的」。

（附带一条诚实的边界声明：新增的那个测试靠 20ms sleep 让 a 域先进 throttle，是**概率性**的——包外无法观测持锁状态。但猜错的后果是**假绿而非假红**，且用 rounds=3 降低漏检。Dev 把这个局限写进了测试注释，而不是假装它是确定性的。）

#### 集合等值规则的适用边界（防过度应用）

新规则针对的是**「集合由被测代码返回」**的情形。不要见到 `len` + `for` 就改写 —— 判据是**谓词是否可能比目标集合宽**：

| 形态 | 是否适用新规则 | 理由 |
|---|---|---|
| `for _, x := range 被测代码返回的集合 { 谓词(x) }` | ✅ **适用** | 基数与成员都由被测代码决定，谓词若比目标集合宽即可逃逸 |
| `for i := 0; i < n; i++ { assert(results[i] == 确定值) }` | ❌ **不适用** | **索引由测试自己控制**、每个位置断言的是确定值。谓词是**等值**，宽不了 |
| `len(calls) != 2` 后跟 `calls[1].Sub(calls[0])` | ❌ **不适用** | 精确索引访问，不是逐元素谓词 |

**核心区分：集合的基数是测试定的，还是被测代码给的？** 前者（如并发测试里 `n=20` 的定长切片）不存在逃逸空间 —— 测试自己知道该有几个、每个该是什么；后者（如 `Topics()`）才需要集合等值断言。

（来源：dev-agent-35 在 TASK-002 交付后按新规则自查，正确判定 `gate_test.go` 的三处并发断言 `results[i] != "value"` / `xs[i] != 42` / `errors.Is(errs[i], wantErr)` 无需改写。）

**更好记的判据**（dev-agent-35）：

> 问一句 —— **「如果被测代码返回一个我没预料到的集合，这个断言会不会仍然通过？」**
>
> - 定长切片 + 逐索引等值：被测代码**根本没机会决定基数**，这个问题不成立 → 不适用新规则
> - `range 被测代码返回的集合`：基数与成员全由它决定 → 适用

这与「能不能构造一个错误的实现让它仍然通过」是同一个问法，只是聚焦到集合上。

### 教训 8：规格歧义的真正修复是改规格，不是加注释

TASK-002 的 DoD functional[3] 写「`Do` 强制 TTL=0 **每次都执行 fn**」，而实现在并发下受 singleflight 合并成 1 次 —— 字面互斥。验证者开验前发现并要求 Leader 裁定口径，**挡下了一次假 FAIL**。

但 Dev 指出了一件 Leader 该承认的事：

> 这次挡下靠的不是 DoD 措辞本身，而是我在 `Do` 注释里写了合并语义。**如果没有那段注释，验证者读到「每次都执行 fn」、看到 20 并发只调 1 次，判 FAIL 是完全合理的** —— DoD 字面就是那么写的。所以这条能被挡下有一半是运气：注释恰好在那儿，且它恰好读了。

⇒ **注释是补丁，改规格才是修复。** 一份会被字面执行的规格（DoD 就是验证的唯一依据），有歧义就必须改规格本身；指望下游读到某处注释来消歧，是把确定性换成了运气。

**推论**：凡是「实现的语义比 DoD 字面更微妙」的地方，要么改 DoD 措辞，要么写进本契约文档（**必读入口**），而不是只留在源码注释里 —— 这也是 `Do` × Coalesce 当初被写进契约总表而非仅靠注释的理由。

#### 重要修正：集合等值**不能**替掉逐元素断言 —— 它们守的不是同一个对象

上文说集合等值「一步覆盖基数 / 重复 / 成员有效性 / 完整性」，**那四件事全部是关于「集合本身」的**。它不覆盖「用集合去查的那个函数」。

具体到 `TestDisableTTLKeepsThrottle`，三个断言各守一个**不同的对象**，缺一漏检：

| 层 | 断言 | 守护对象 | 若删掉则漏检 |
|---|---|---|---|
| ① | `DeepEqual(sorted(topics), want)` | **`Topics()`** | M26 空 / M26b 假名 / M26c 域内假名 / M26d 重复 |
| ② | `p, ok := Lookup(topic); if !ok { Fatal }` | **`Lookup()`** | **`Lookup` 恒返 `ok=false`** —— ① 仍通过（`Topics()` 是对的），③ 也仍通过（`p` 是零值、`TTL` 恰好为 0）|
| ③ | `if p.TTL != 0` | **`DisableTTL()`** | M27 只清部分主题 |

②那条尤其反直觉：**集合都精确相等了，成员当然能被 `Lookup` 命中** —— 这个推理是错的，因为它假定了 `Lookup` 本身是好的。而 `Lookup` 恰恰是这个测试链条里第二个被依赖的被测对象。

⇒ **通用原则：一个测试里的多个断言可能各守不同的被测对象。不要因为「引入了更强的断言」就删掉「较弱的断言」，除非确认二者守的是同一个对象。** 强弱只在同一守护对象内可比。

（来源：dev-agent-35 在设计 `Topics()` 修复形态时自我纠正 —— 它原本也以为集合等值让命中断言冗余了。）

**另一处同源纪律**：`want` 里那 9 个主题名应当从实现直读（`grep 't\.Set("' policy.go`），**不要凭记忆写字面量** —— 凭记忆写等于把「我以为表里有什么」当成「表里有什么」，与本文档反复出现的那个偏差同源。

### 陷阱 8：否定断言（「X 不该被调用」）不能用结果状态推断

「TTL 命中时 `QuotaStore.Take` **不被调用**」这类**否定断言**，若靠观察计数值是否变化来验，是错的：

> 计数值不变，可能是「**没调用**」，也可能是「**调用了但被拒且不计数**」—— 而 `boundary[0]` 恰恰规定「被拒的请求不计数」，所以后一条路径是合法存在的。**两种情况在计数值上无法区分。**

正解：注入一个**可观测的假实现**（记录 `Take` 被调用的次数与参数），直接断言调用次数为 0。同理「Coalesce 合并的 N 个请求只消耗 1 次配额」也要断言 `Take` **被调用 1 次**，而不是断言计数值增加了 1。

**通用形态**：当结果状态可由**多条不同路径**产生时，用结果状态去推断「某条路径未发生」是无效的。否定断言必须直接观测那条路径本身 —— 这通常意味着要注入可观测的测试替身，而不是复用生产实现去看它的外部状态。

与陷阱 6（弱断言）的区别：弱断言是**谓词太宽**（`== 错误值` 只挡住枚举到的值）；本条是**观测量选错**（计数值无法区分两条路径），谓词再强也救不了。

（来源：dev-agent-35 预读 TASK-003 boundary[2] 时提出。）

### 变异操作纪律第 4 条：不以「套件转红」为准，对 DoD 的专属守护者单独 `-run` 确认

全量跑套件时，**首个报错的未必是你以为在守护那条 DoD 的测试** —— 可能是别的测试先炸。若只看套件红绿，就会漏掉「那条 DoD 的专属断言其实是空洞的」这种情况。

⇒ 注入变异后，除了跑全量，**还要对 DoD 点名的那个测试单独 `-run` 一次**，确认它自己能转红。

（来源：test-agent-17 在 TASK-002 验证中，G3 与 G5 全量跑时首个报错的都不是 Dev 声称的那个测试。这是 TASK-001「M7 转红掩盖了断言是排除式写法」教训在时序场景的复现 —— **变异捕获 ≠ 你以为的那条断言捕获**。）

### 陷阱 9：early-return 会让「持锁」类断言绕过临界区

TASK-002 首轮的失效实例：测「throttle 期间是否持有全局锁」，把对照域配成 `MinInterval: 0`（完全不节流），于是该域走 `throttle` 的 early-return（`if p.MinInterval <= 0 { return }`），**根本不进入持锁临界区** —— 任何加在该 return **之后**的全局锁，对它都不可见。

| 全局锁位置 | 该测试 |
|---|---|
| early-return **之前** | 红 ✅ |
| early-return **之后**（只锁真正节流的路径）| **绿 ❌ 存活** |

而「先做快速路径检查、再拿锁」是很自然的写法，这个形态是现实的回归风险。

**修复**：对照域取**极小正值**而非 0（`MinInterval: time.Millisecond`）—— 既进入持锁路径，又在正确实现下几乎立即返回、不影响时间阈值。

**通用形态**：**验证「某段临界区的性质」时，对照组必须真的进入那段临界区。** 用「完全不触发该路径」的配置做对照，测的是「不进入时会怎样」，而非「进入时会怎样」。

#### 陷阱 9 的根因（Dev 的总结，比「对照组要进临界区」更通用）

> **为满足一个约束而选的参数值，可能同时使另一个约束失效。**

TASK-002 的实例：把对照域配成 `MinInterval: 0` 是为了满足「B 要等的时刻必须晚于 A 的完成时刻」——**这个推理本身没错**（上一版双域对称设计正是栽在没满足它）。但该值同时触发了 `throttle` 的快速路径，让对照域根本走不到要测的持锁路径。

⇒ 修一个问题时选的参数，要回头对照**所有**约束检查一遍，而不只是它要满足的那一个。「方向对、落点差一步」多半就是这么来的。

**配套动作 —— 闭环对比**：修复后不要只验「新版能捕获变异」，还要验「**旧版在同一变异下确实不捕获**」。前者只能声称修复有效，后者才是证明。（Dev 自发做的：在变异下把参数退回 `{}`，确认绿。）

### 陷阱 10：有效性判定与被测缺陷耦合时，判定顺序决定错误信息指向哪儿

概率性测试常加一层「本轮是否真正构成检验」的有效性判定（例：并发测试里判断「B 返回时 A 是否仍在等待」，不满足则 `continue` 跳过本轮）。**当这个有效性条件与被测缺陷的表现耦合时，判定顺序会决定读者看到什么。**

TASK-002 的实例（验证者第一版就写反了）：

- **有效性判定在 `elapsed` 断言之前** → 两种缺陷形态**都转红**，但错误信息是「本轮未构成检验」，不是「b 域被阻塞 480ms」。
  **根因**：全局锁下 B 恰恰是等到 A 完成才返回的 —— **有效性条件必然不满足**，于是每轮都 `continue` 跳过了真正的断言，最后靠兜底断言 fail。
  **后果**：读者会以为是测试构造失败，而非被测行为有问题 —— **缺陷伪装成「测试没测到」**。
- **先判被测行为、再判本轮是否有效** → 修正后两种形态都红，且错误信息准确指向「被阻塞 480ms」。

⇒ **规则：先判被测行为，再判本轮是否有效。** 反过来会让缺陷把自己伪装成测试构造失败。

**附带**：概率性无法消除时（包外没有可观测信号），至少把它**变成可观测的** —— 统计有效轮次，全部无效则 fail，而不是让假绿静默通过。

（来源：test-agent-17 在评估 `TestGateThrottleDoesNotHoldGlobalLock` 的 20ms sleep 局限时实测发现。顺带一提：`go vet` 在该过程中抓到它把 `t.Fatal` 写成带 `%d` 的格式串 —— 本仓库 vet 有效。）

#### 闭环对比的完整形态：2×2 同环境对照

上文说「还要验旧版在同一变异下确实不捕获」。**完整形态是四个格子，且必须跑在同一环境（同 worktree、同会话）**：

| | 无变异（正确实现） | 注入变异 |
|---|---|---|
| **旧版断言** | 绿 | **绿 ❌ 漏检** ← 这一格才是返工的理由 |
| **新版断言** | 绿 | **红 ✅ 捕获** |

只有左下角那一格能证明「以前抓不到」。单独跑「新版 + 变异 → 红」只说明**现在能抓到**，**不说明以前抓不到** —— 而后者才是返工的全部理由。缺了它，返工的必要性就只是一句断言。

**「我上一轮已经验过了」不能替代这一格。** 上一轮的 worktree、进程、调度状态都不同 —— **跨轮引用不等于同环境对照**。四个格子跑在同一环境下，绿/红差异才**只能**归因于那一行改动，因果隔离才成立。这对时序类测试尤其重要，它们本身就有抖动。

（来源：test-agent-17 在 TASK-002 二轮补做时提出。它首轮确实在旧版上注入过同一变异并发现存活——那正是判 rejected 的依据——但仍认为跨轮引用不足以替代同环境对照。）

### 变异证据链的三个可断裂点（统一框架）

「注入变异 → 测试转红 → 所以该断言有守护」这条推理，有**三处**可能断裂。三条纪律各管一处：

| # | 断裂点 | 表现 | 对策 |
|---|---|---|---|
| 1 | **变异没生效** | 表达式静默失配，代码根本没改 | 注入后校验 `git diff --numstat` 改动量非空 / `md5` 已变（纪律 1）|

> ⚠️ **第 1 条不是「改动量非空」一条，而是两条：改动量非空 **且** 编译/vet 通过。**
> `git diff --numstat` 非空只证明文件被改了，**不证明改对了**。删掉一个断言块常常连带让某个 import 变成未使用 → **编译失败** → 测试报 FAIL → 脚本把它当成「捕获」。这是**第 3 类断裂点伪装成第 1 类通过**。
>
> 本 Sprint 三个不同实例先后栽在这上面（test-agent-16 的 M15：`domainOf` 改 `return topic` 使 `strings` 未使用；dev-agent-35 的 R5b 闭环：删 `DeepEqual` 使 `reflect` 未使用；test-agent-17 复核同一处时**重犯**）。第三位读过前一份报告仍然重犯 —— **说明写在报告里不够，必须进操作纪律**：变异注入后先 `go vet`（或至少 `go build`），通过了再跑测试。
>
> 保留 import 的变通写法：`(false && !reflect.DeepEqual(...))` —— 让表达式失效但引用仍在。
| 2 | **红的是别的测试** | 套件里另一个测试先炸，你以为是目标守护者捕获的 | 对 DoD 点名的守护者单独 `-run` 确认（纪律 4）|
| 3 | **红的不是断言** | **编译失败 / vet 失败 / panic / 超时** —— 全都表现为「红」 | **看报错内容，确认红来自目标断言（最好核到 `file:line`）** |

第 3 条的实例（dev-agent-35 在 TASK-001 R5b 闭环实验中撞上）：退化集合等值断言时删掉了 `reflect.DeepEqual`，导致 `import "reflect"` 未使用 → **编译失败** → 两个变异都报红。只看退出码就会得出「旧形态也能捕获」，**与真实结论相反**，并据此认为该次修复没有必要。

> 它是因为「结论与验证者矛盾」才回头查的 —— `grep` 报错内容才发现红来自编译器。改用 `(false && !reflect.DeepEqual(...))` 保留引用后，才拿到真实结果（M26c/M26d 双双存活）。

**做法**：变异脚本打印首条 `<被测文件>:NNN` 的断言错误，而不是只看 exit code。

**与陷阱 10 同源**（Dev 自己指出的）：两者**都是让一个非目标原因抢先决定了输出** —— 一个是编译错误抢在断言前，一个是有效性判定抢在行为断言前。凡是「红/绿」这种单比特输出，都要问一句：**这一位是被谁置上的？**

#### 变异注入的控制变量原则

同样是「让集合等值断言失效」，两种写法：

| 写法 | 副作用 |
|---|---|
| 删掉断言块 | `reflect`/`sort` 变成未使用 import → **改动了 import 列表**（无关变量）→ 编译失败 |
| `(false && !reflect.DeepEqual(...))` | 表达式失效，**引用仍在，import 列表不变** |

后者更好，**不只是因为省事，而是因为做对照实验时少动一处就少一个混淆因子**。变异应当只改「被测行为」这一个变量，任何连带的结构改动都会污染因果归属。

**同一个坑落在不同位置，代价差一个量级**：验证者的假红只让结论**存疑**（与首轮矛盾，回头查了）；Dev 的假红会得出**与事实相反的结论**（「旧形态也能捕获 → 这次修复没必要」）。前者浪费时间，后者会撤销一次正确的返工决定。

**runner 固化做法**（test-agent-17 已实装）：判「红」的条件是**输出中存在 `<被测文件>:NNN` 断言行**，而非 `exit != 0`；出现「exit 非 0 但无断言行」报 `红但非断言 ⚠` 且**不计为捕获**；`go vet` 不过直接报「变异无效」跳过。

**操作教训**：`git worktree remove` 要在主仓库执行 —— 站在被拆的目录里会让 cwd 失效，后续写通道调用 exit 127 而**产物没落盘**。这是「落盘后必须直读核实」那条纪律救下的一次实例。

### 教训 9：前瞻推理链会在「相邻但不同的两件事」处断裂

TASK-002 验证者发现 G8（删掉 `fetch` 里未登记主题的直通短路）当时是等价变异体，并**前瞻推断**：接入真实 QuotaStore 后它将不再等价，未登记主题会被计入配额（违反 C6）。Leader 据此给 TASK-003 加了一条 DoD。

**TASK-003 实测：G8 仍然是等价变异体，那条新 DoD 的测试捕获不了它。**

断裂点在这里：

| 验证者实测的 | 前瞻推断的 | 实际隔在中间的 |
|---|---|---|
| 注入 G8 + 让 `takeQuota` **函数本身** panic → 未登记主题**进入了该函数** | → 所以接入真实 store 后会**触达 `QuotaStore.Take`** | `takeQuota` 开头还有 `if p.Quota == nil \|\| g.quota == nil { return nil }` —— 未登记主题拿到零值 `Policy`，`Quota` 就是 nil，**第二道短路** |

「**进入了 `takeQuota` 函数**」与「**触达了 `QuotaStore.Take`**」是两件相邻但不同的事，前瞻把它们当成了一件。

**提炼**（Dev 的原话）：

> **「删掉守卫 X 后行为不变」不等于「X 无用」，可能只是存在另一道守卫。**
> 判断某测试是否守护某变异**只能靠实测，不能靠推理链转述**。

**处置示范**：Dev 没有照抄前瞻结论写进 discovery —— 那会留下一个**假的覆盖声明**。它的做法是：保留那条测试（它守住了 DoD 明确要求的性质，且两道短路同时失效时确实转红，已用 G8+ 组合变异实证），但**明确声明「它不是 G8 的守护者，我不宣称已覆盖 G8」**。

⇒ 前瞻性 DoD 有价值（它让防护早于缺陷存在），但**前瞻的覆盖声明必须在实现落地后重新实测**。写 DoD 时的推理链，与代码落地后的实际路径，可能差一道守卫。

### 变异证据链纪律的两处补全（TASK-003 验证得出）

#### 补全 A：核到 `file:line` 后，还要区分**断言输出**与 **panic 堆栈**

第 3 条纪律说「看报错内容，核到 `file:line`」—— 不够。**panic 也会打印 `file:line`**，而且那是堆栈里的调用点，不是断言。

| 形态 | 输出样子 | 证明了什么 |
|---|---|---|
| 断言 | `quota_test.go:289: Take 调用 3 次, want 0` | **该断言抓到了目标行为** |
| panic 堆栈 | `policy.(*Gate).takeQuota(...) gate.go:308` | 只证明**崩了**，且**会中断整个测试二进制** |

TASK-003 里 Dev 两次把 panic 当成断言捕获。验证者把判定门改成**正则匹配断言格式** `^\s+\w+_test\.go:\d+:\s+\S` 才识别出来。

⇒ **判「红」的正则要求「`<file>_test.go:NN:` 后跟消息」这个完整形状**，裸的堆栈行不算。

#### 补全 B：变异无效的**第三类**形态 —— 改动量非空但语义未变

门①（改动量非空）与门②（编译通过）之外还有一类：**只改了注释**。验证者自己造 Q17 时就只删了注释，门①放行了它 —— 因为**注释也算 diff**。

> **门①的固有局限：`diff` 非空只证明字节变了，不证明语义变了。**

至此「变异无效」共三类形态，全部在本 Sprint 实际发生过：

| # | 形态 | 表现 | 门 |
|---|---|---|---|
| ① | 表达式静默失配 | 改动量为空 | `numstat`/`md5` |
| ② | 改坏代码致编译失败 | 红是**构建的红** | `go vet` / `go test -c` |
| ③ | **改动量非空但语义未变** | 绿，被误记为「等价变异体」 | **无自动门，靠人审 diff 内容** |

③ 最危险：它会让人得出「这里是等价变异体、无需守护」的错误结论，而真相是**变异根本没造出来**。

### 教训 10：一个测试倒下会带倒一片 —— panic 型失败的连带损害

`TestWindowStartNilLocUsesUTC` 缺 `recover`，注入变异后裸 panic：**50 个测试只跑了 38 个，12 个测试根本没跑到**，它们守护的 DoD 在那次运行中完全失去检验。

「测试转红了」于是看起来一切正常 —— 但**红的方式决定了其他测试还能不能跑**。

⇒ **凡是「不该 panic」型的 DoD，测试必须用 `defer recover()` 把 panic 转成断言失败**，而不是让它裸奔。这样既守住了性质，又不会中断测试二进制。（同文件里 `TestFailOpenWithoutWarnDoesNotPanic` 是写对的范例。）

### 教训 11：「判断偏差」与「应用失败」是两类错误，防御手段不同

本 Sprint 前面的教训几乎都指向**判断偏差** —— 论证自洽但前提错、把「我认为」误存成「我试过」、记法选了让自己舒服的那个。它们的解药是**改变认知**（把确信变成验证）。

但 TASK-003 的 R1 不是这一类。Dev 的自述：

> 我两条同型测试**一条对一条错** —— `TestFailOpenWithoutWarnDoesNotPanic` 写对了 `defer recover()`，`TestWindowStartNilLocUsesUTC` 没写。两条在**同一个文件里、间隔不到 200 行、我同一轮写的**。
>
> 这说明**知道规则不等于每次都应用**。规则我当时就知道，只是写第二条时没去对照第一条。

| 类型 | 症状 | 解药 |
|---|---|---|
| **判断偏差** | 你的推理是错的，但你相信它对 | 改变认知：变异、实测、独立视角 |
| **应用失败** | 你知道规则，只是这一次没用上 | **机械化**：清单、模板、自动检查 —— **不靠记得** |

误诊会让防御失效：把应用失败当成判断偏差，就会去「加深理解」，而理解从来就在；把判断偏差当成应用失败，就会去加检查清单，而清单挡不住一个错误的前提。

**判据**：问「**当时如果有人问我这条规则，我答得出来吗？**」答得出来 → 应用失败 → 上机械化手段；答不出来 → 判断偏差 → 上验证手段。

同源实例：test-agent-17 读过 test-agent-16 关于「编译失败的红」的报告，**仍然重犯** —— 它自己的诊断是「不是记性问题，是纪律缺位问题」，正是把它识别成了应用失败，于是把门固化进 runner 而非「下次注意」。

### 教训 12：复合句 DoD 的硬证据 —— 分句 2 的判据决定它是否真的独立

TASK-004 首次为「复合句必须分句取证」拿到实测证据。注入 F1（读到坏 JSON 只报错、**不重建**）：

| 测试 | 结果 |
|---|---|
| 分句 2「必须能自愈」 | **红** |
| 分句 1「不 panic 不阻断」 | **仍绿** |

只写分句 1 的话，「**配额永久静默失效**」这个故障完全不可见 —— fail-open 一直成立、告警一直发出、而配额再也不生效。

**但分句 2 能否独立，取决于判据怎么选**（Dev 的关键发现）：

- ✗ 断言「不再报错」→ 与分句 1 高度重叠，测不出「只是不报错但没恢复」
- ✓ 断言**功能确实恢复**：账本重建为合法 JSON + 计数从新窗口起算 + **到达 Limit 时能正确拒绝**

**最后那条才是「恢复」与「只是不报错」的分水岭。** 写复合句的第二个分句时，先问：**这个判据能否被「表面正常但实质未恢复」的实现骗过？**

### 陷阱 11：守卫失效的第三种形态 —— 静默 SKIP

已知两种：断言太弱（转绿）、panic 带倒一片（转红但连带损害）。**第三种是 `t.Skip`** —— 测试既不红也不绿，在汇总里几乎不可见。

TASK-004 实例：用 `os.ReadDir("/dev/fd")` 数 fd 检测泄漏，在 macOS **独立程序里可读**（Dev 写探针验证过），**但 go test 进程内读不到** → `t.Skip` → 这条守护**从未真正执行过**，而 CI 一片绿。

⇒ **任何带条件 `t.Skip` 的测试，都要确认它在目标环境下确实没被 skip。** 本 Sprint 另一实例：`TestNoImportOfCollectorRoot` 早期版本在 `go list` 出错时一律 Skip，会把「依赖解析失败」这种本该转红的情况一并吞掉（已修为仅 `exec.ErrNotFound` 时 Skip）。

**验证报告里应显式记录 `0 SKIP`** —— 本 Sprint 的验证者一直这么做，那不是形式主义。

#### 附：间接检测资源泄漏通常无效

「跑 N 次看是否 too many open files」测不出 fd 泄漏：`ulimit -n` 可能高达百万级，且 `os.File` 带 finalizer，**GC 会把泄漏的 fd 悄悄收掉**。Dev 实测删掉 `Close()` 后该写法仍全绿。

**有效做法**：直接观测**下一个可用 fd 号**（POSIX 保证 `open` 返回最小可用 fd）—— 变异下 fd 号从 5 涨到 55，立刻捕获。这与陷阱 8（否定断言要直接观测那条路径）同源：**别用一个可能由多种原因产生的间接现象去推断。**

### 变异无效的统一判据（取代原来的分类枚举）

本 Sprint 已实际发生**四种**「变异无效」形态。验证者建议按**共同点**归类而非并列枚举 —— 因为将来还会有第五种：

> **所有形态的共同点：红/绿的原因不是「被测行为」。**

| # | 形态 | 表现 | 门 |
|---|---|---|---|
| ① | 表达式静默失配 | 改动量为空 | `numstat` / `md5` |
| ② | 改坏代码致编译失败 | 红是**构建的红** | `go vet` / `go test -c` |
| ③ | 改动量非空但**语义未变**（如只改注释） | 绿，被误记为等价变异体 | 无自动门，人审 diff |
| ④ | **测试名打错 → 跑了 0 个测试** | `exit 0`、无断言行 → 被判「绿存活」 | **确认 `=== RUN` 数 > 0** |

④的实例：验证者把定向测试名打成 `...DoesNotWrite`（实际是 `...DoesNotIncrement`），`go test -run '^不存在的名$'` **exit 0 跑了 0 个测试**，门③（无断言行）判成「绿存活」—— **差点报出一个不存在的缺口**。

**判据用法**：拿到红/绿结论后，先问 —— **这个结果是被测行为造成的吗？** 逐一排除：变异真的改了语义吗？代码编译过了吗？测试真的跑了吗？红的是断言还是 panic/构建？全部通过才谈「捕获」或「存活」。

**这比记住四条更可靠**，因为它对第五种形态同样成立。

## 方法论的边界：变异验证能证伪什么，不能证伪什么

本 Sprint 建立了一套相当严的自证流程（四道门 + 单独 `-run` + 断言行核对 + 2×2 同环境闭环）。但 TASK-004 暴露了它的固有边界，Dev 的原话：

> **我的四道门全是在检验「变异是否有效」，没有一道能检验「我是否没想到别的办法」。**
> **变异验证只能证伪我写下的断言，不能证伪我没写的那些。**

具体到那次：Dev 在 discovery 里写「I/O 失败分支无法可靠构造」，这句话在它自己的流程里**结构上无法被证伪** —— 所有门都在检验已写下的变异是否有效，没有一道会问「还有别的构造方法吗」。验证者用两种方法实测推翻（父路径设为文件 → `MkdirAll` 失败；`chmod 0o500` → `CreateTemp` 失败），代价是那三处 I/O fail-open **一直无守护**。

| 错误类型 | 能被什么发现 |
|---|---|
| **写下的断言无效**（弱断言、空转、假红） | **变异验证**（自证即可）|
| **该写的断言没写**（覆盖缺口、「测不了」的错误结论） | **只能靠独立视角** —— 另一个人从零开始想「这里应该测什么」 |

⇒ **这是「Dev 自证 + 独立验证」双层结构必要性的根据，不是冗余。** 两层覆盖的是两类不同的错误；去掉任何一层，对应那类错误就没有任何防线。

**推论 —— 写「测不了 / 无法构造」时的纪律**：这是一个**关于自己能力边界的断言**，与「代码行为如何」不是一类判断。后者能用变异证伪，前者只能靠别人试出来。因此必须**连同「试过哪些方法、各自为什么不行」一起写** —— 否则下一个接手的人会重复得出同样的错误结论，而缺口一直在。

### 补：第三类错误 —— 归因错误

上表两行不完整。验证者（在自己修正首轮一处归因后）补了第三行：

| 错误类型 | 能被什么发现 |
|---|---|
| **写下的断言无效** | 变异验证（自证即可）|
| **该写的断言没写** | 只能靠独立视角 |
| **归因错了**（红/绿的原因不是被测行为） | **构造更精确的对照形态** |

第三类既不是「断言无效」也不是「没想到」，而是**证据解释错误** —— 拿到了红或绿，但把它归到了错误的原因上。

本 Sprint 两个实例，双方各一：

- **Dev**：把 nil 指针 panic 的堆栈行号当成断言捕获（TASK-003 R2）
- **验证者**：把「改坏返回值类型导致的存活」当成「fail-open 语义无守护」（TASK-004 首轮 F17）—— 更精确的形态 F17b（`Take` 在 `readErr != nil` 时返回 `(false,err)`）在旧测试集下**本来就是红**，因为 JSON 解析失败走同一条 `readErr` 路径

**关键**：第三类**不能靠「更仔细地想」发现** —— 验证者的原话是「这个错误也只能靠再做一次精确形态验证才发现」。解药是**构造更贴近目标语义的变异形态**，而不是重读一遍结论。

（验证者的自评值得记：「我提出的判据，我自己也踩了。」它提出「红/绿的原因要归因到位」这条判据用于批评 Dev，随后自己在另一处犯了同类错误 —— 说明判据本身正确，但**知道判据不等于每次都应用**，与教训 11 同源。）

### 第③类断裂点（语义变错）的解药：先写预期，再比对实际

此前记为「无自动门，靠人审 diff」。TASK-005 给出了可操作的手段。

**实例**：Dev 注入 O2（就地改共享 `Quota`）时用 `defer` 把值写回 `*p.Quota`，但 **`defer` 在 `p.Quota` 已被重新赋值之后执行** —— 改的是新实例而非共享实例。变异语义与意图不符，测试绿。**门①（改动量非空）、门②（编译通过）、门④（`=== RUN` > 0）全部放行了它。**

**解药**：

> **对每个变异先写下预期，再比对实际。**
> 「变异绿」有两种解释 —— **测试无守护** / **我的变异没打中** —— **不先写预期就无法区分。**

这也解释了为什么第③类**无法自动化**（Dev 的原话）：

> 判断「语义是否按我意图改变」需要**我的意图**，而那只存在于我脑子里。**写下来它才变成可比对的东西。**

⇒ 变异记录表应有「预期」列，且**在注入前填**。事后补写的预期会被实际结果污染 —— 这与「回头检查时人已站在『我认为它对』的位置上」同源。

**注意 O2 的特殊性**：这次第③类发生在**验证工具**上，而非被测代码上。变异脚本本身也是代码，也会有 bug，而它的 bug 表现为「被测代码看起来没问题」。

#### 预期列是**双向**的，而且它不是自动化

TASK-005 首次实践「注入前写预期」，14 次变异中 **3 次与预期不符，全部是变异本身有问题，没有一处是代码缺口**。若不写预期，前两处会报出**不存在的缺陷**。

**两个方向都要诊断**（验证者补充）：

| 不符方向 | 查什么 | 实例 |
|---|---|---|
| **预期红、实际绿** | **我的变异是否打中** | O2「又只删了注释」；O5「变异位于不可达路径 —— `Default()` 开头有快速路径，第二次调用根本走不到」|
| **预期绿、实际红** | **我对被测系统的理解是否有偏差** | O6 —— 正因查了这处才拿到比转述更精确的结论 |

**「变异没打中」有两种形态，只看 diff 都判不出来**：
- 改了错的东西（只删注释、`defer` 时序打偏）
- **改对了地方，但那个地方在该场景下不可达**（O5）

⇒ 判据：**不能只看 diff 是否改动，要看它在目标路径上是否可达。**

**边界（验证者对 Dev 那句「意图只存在于我脑子里」的补充）**：

> **写下的预期本身也可能是错的**（O6 就是）。所以这不是自动化，是**把一次判断变成两次判断** —— 两次都错的概率显著低于一次。

#### 附：`-race` 的价值在归因，不在检出

TASK-005 的 2×2（变异 × 是否带 `-race`）：

| 变异 | 不带 `-race` | 带 `-race` |
|---|---|---|
| 每次新建实例 | 红(断言) | 红(断言)，**无 DATA RACE** |
| 去掉锁 | 红(断言)，10/10 稳定 | **DATA RACE** |

单例断言对两者都稳定捕获，**检出层面是充分的**；`-race` 的独立价值在于**归因** —— 同样是「拿到不同实例」，它能区分根因是数据竞争还是逻辑错误（有锁、无竞争但违反单例）。

**两条都该保留**：这正是「能转红不够，红得指向哪里也重要」的应用。

### 教训 13：方案自带的测试可能与方案自带的缺陷「共谋」

TASK-006 发现方案代码有一个**静默丢配置**的实质缺陷：

> **viper 用 `.` 作 key 分隔符，而策略主题名本身含点（`yahoo.chart`）。** `v.Unmarshal` 到 `map[string]TopicConfig` 时把主题名当嵌套层级拆开，结果只剩 `{"yahoo": {全字段 nil}}` —— **装载不报错、覆盖不生效**。

**关键在于它为什么没被发现**：方案给的测试**都是直接构造 map、不经 yaml 装载**，所以 `TestInitPolicyGateAppliesTopicQuotaOverride` 一直是绿的。Dev 是写「经 yaml 装载」的测试时撞上的。

⇒ **当实现与测试出自同一份方案时，二者可能共享同一个盲区。** 方案作者若在某处没想到（这里是「主题名含点会与 viper 的分隔符冲突」），他写的实现和他写的测试会在**同一个地方**绕过去。

**对策**：照方案实现时，至少补一条**走真实入口**的测试（经 yaml/config 文件装载，而非直接构造内存结构）。真实入口会引入方案未模拟的中间层（序列化、解析、类型转换），那里正是共谋盲区的所在。

### 方法论边界的第二层：检验工具本身不被任何门检验

四道门检验的是「**变异对不对**」，**没有一道检验「检验工具对不对**」。本 Sprint 三个实例：

| 实例 | 工具缺陷 | 后果 |
|---|---|---|
| TASK-005 O2 | 变异脚本用 `defer` 写回，时序打偏 | 变异绿，差点报「无守护」 |
| TASK-006 顺序检查 | 按「文件内首个匹配」比较，误报 `prism.go` 顺序错 | 实为 helper 内的构造，不在执行流上 |
| TASK-004（验证者） | 定向测试名打错 → 跑了 0 个测试 | 判成「绿存活」，差点报不存在的缺口 |

Dev 的总结：**变异脚本、检查脚本都是我写的代码，它们的缺陷不会被任何门捕获。**

**目前唯一的对策是「先写预期，再比对实际」** —— 它把工具错误转化为「预期与实际不符」这个可观测信号。这也是为什么该纪律**不是自动化**：它需要一个独立于工具的判断源（人的预期）来交叉验证工具的输出。

### 教训 14：可判定 ≠ 可满足 —— 「既有测试一条不删一条不改」的适用条件

反审 B4 把不可判定的「行为不变」改写成可判定的「**master 基线上的既有测试用例一条不删、一条不改且全部通过**」。这个改写方向是对的，但**它与「删除私有状态」类 DoD 存在字面冲突的可能，而我写 DoD 时没做相容性检查**。

wave 7 的实测对比（test-agent-17 核实），同一条表述在三个任务里表现完全不同：

| 任务 | 既有测试对将被删符号的引用 | 分布 | 结果 |
|---|---|---|---|
| **tushare** | 4 处 | **全部在 `TestThrottleMinInterval` 一条测试内** | DoD 已点名豁免该测试 → **自洽** ✅ |
| **yahoo** | 8 处 | 散落在 `throttle_test.go` **7 个不同位置**、跨多条测试 | **字面不可兼得** ❌ |
| **twelvedata** | 4 处 | 其中一处在**共享 helper** `tdServer()` 内，被文件**全部 6 个测试**调用 | **整个测试文件编译失败** ❌ |

⇒ **适用条件**：这条表述**只在「被删符号的引用集中于可点名的少数测试」时才自洽**。引用一散开，它就必然与删除类 DoD 冲突。

**写 DoD 时的动作（一次 grep 就能定）**：

> 先 `grep` 既有测试对将被删符号的引用 —— **集中**则点名豁免那几条测试；**散落**则改用「不删函数、不改断言与场景，**允许适配签名/字段变更所必需的机械改动**」的口径。

**这比事后逐个裁定省事得多**，而且是写 DoD 时就能做完的。

**附带观察**：同一条表述，Leader 在一个任务里写对了（tushare 点名豁免）、在另外两个里写错了 —— 这是**应用失败**而非判断偏差（教训 11）：规则当时就知道，只是没对照着逐个检查。解药同样是机械化：**把这次 grep 写进 DoD 撰写清单**。

**验证者视角的补充**：「不删函数、不改断言与场景，仅适配性机械改动」这个口径**是可验证的** —— 用 `git diff` 逐条核对函数数量不变、断言文本不变、只有签名/字段访问方式变了。所以它不是含糊的免责条款。

### 教训 15：方案给的测试可能引用**已经漂移的上游语义**

教训 13 说的是「方案的实现与测试共享同一盲区」。这是它的**时间维度变种**：

> **方案写于上游定稿之前，上游语义后来变了，而方案没跟着改。**

实例（dev-agent-36 在 TASK-009 撞上，并预告 TASK-014 会再撞）：方案行 3026 与 4143 都写 `Quota{Limit: 0}` 期待「配额立即耗尽」，但 `policy/quota.go:57` 的判定是

```go
if q.Limit > 0 && e.Count >= q.Limit {
```

⇒ **`Limit <= 0` 的语义是「不设上限」**（TASK-003 定的），与方案的期待完全相反。

**后果不对称，取决于误用后的表现形态**：

| 任务 | 照抄后的表现 | 能否发现 |
|---|---|---|
| TASK-009 | `err == nil` 而非 `ErrRateLimited`，测试直接红 | ✅ 立刻 |
| TASK-014 | httptest handler 里是 `t.Error("配额已满时不应发出请求")` —— 照抄会**真的发出请求**并触发它 | ⚠️ 会，但**表现为「实现有问题」而非「测试写错」**，容易误诊 |

⇒ **纪律**：**凡是方案给的测试用到上游的语义常量（阈值、哨兵值、边界值、零值含义），接任务时必须回查上游实现的实际判定，不能照抄。**

**为什么这类特别难防**：方案代码看起来是「权威的、已验证的」，而它的过期是**静默**的 —— 上游改语义时不会有人回头改下游方案文档。任务链越长、方案定稿越早，漂移越可能发生。本 Sprint 方案共 4243 行、14 个任务，上游 TASK-003 的决策影响下游 TASK-009/014 两处。

### 陷阱 12：「构造函数忘了取 `Default()`」是一个**全绿的缺陷**

各 collector 接入 Gate 时，构造函数写 `gate: policy.Default()`。**删掉这一行，整套测试可能一片绿。**

TASK-010 实测：注入该变异后 7 条测试**只有 1 条转红**，其余 6 条照常绿 —— 因为它们各自 `l.gate = ...` 注入了测试闸门，而 **nil `*Gate` 是透明的**（设计如此，让未接线的调用点安全降级）。

⇒ **没有那条专门的构造函数测试，生产路径上缓存整体静默 no-op，而全套测试一片绿。**

**每个接入 Gate 的 collector 都必须有一条「构造函数确实取了 `Default()`」的独立测试**（如 `TestXxxConstructorSnapshotsDefaultGate`），且它是该缺陷的**唯一**守护者。这是陷阱 4（构造快照单例）的后果面：陷阱 4 讲的是测试里 `SetDefault` 要在 `New` 之前，本条讲的是**生产代码里那一行本身没人守**。

### 陷阱 13：接入缓存会让「多个既有用例共用同一 topic+key」变成互相串味

接入前，多个测试用同一个 endpoint + 同一份 payload 是无害的。**接入缓存后它们变成同一个缓存槽。**

TASK-010 实测：本包 10 个错误路径用例都用 endpoint `"x"` + 空 payload；带 5m TTL 的默认闸门下，先跑的成功用例写进的 body 会被后跑的「畸形响应应报错」用例**命中**，使后者静默失效。

**对策**：包级 `TestMain` 把默认闸门换成零策略（或每个用例用独立 key）。

⇒ **这是接入前完全不可见的耦合** —— 既有测试没变、新代码也没错，但两者组合产生了新的失效面。**每个接入缓存的 collector 都要自查一遍既有用例的 key 分布。**

### 陷阱 14：可缓存的 fn 边界 —— 校验必须在**被缓存的函数内部**

某些 API 的业务错误走 HTTP 200 + 响应体内的错误码（lixinger 即如此）。**把信封/错误码校验挪到 `policy.Fetch` 外面是很自然的分层写法，但它会把错误响应当成功 body 写进缓存** —— 一次瞬时故障被缓存成**整个 TTL 期间的持续故障**，且期间不再发请求。

⇒ **凡是「响应看起来成功但内容表示失败」的协议，校验必须留在被缓存的 `fn` 内部**，让 `Fetch` 看到的是 error 而非成功值（`Gate` 不缓存错误）。

### 「预期红、实际绿」的**三种**归因，第三种最危险

契约先前写的是两种（断言弱 / 变异没打中）。TASK-007 补出第三种：

| # | 归因 | 实例 |
|---|---|---|
| ① | **断言弱** | TASK-006 C2：内置 TTL 5 分钟，删掉 `ApplyTTL` 后照样命中缓存 |
| ② | **变异没打中** | TASK-005 O2（`defer` 时序打偏）、TASK-005 O5（改对地方但该路径不可达） |
| ③ | **瞄错了目标测试** | TASK-007 Y6：`TestFetchHistoryCachesViaGate` 里 `y.gate` 是显式赋值的，`New` 做没做装配对它毫无影响 |

**③ 最危险**（Dev 原话）：

> 它最容易被误记成 ①，然后我会去「**加强**」一条本来就不该守护它的测试 —— **而真正的缺口原地不动。**

⇒ 诊断顺序：先确认**这条测试在逻辑上是否可能受该变异影响**（③），再查变异是否打中（②），最后才考虑断言强度（①）。搞反顺序会把精力花在错误的地方，且**留下一条虚假的「已加强」记录**。

### 陷阱 15：主题常量拼错在**本包内天然无守护**

各 collector 用 `gateWith(topicXxx, ...)` 在测试里自己登记策略 —— **常量写成什么都自洽**，因为登记与查询用的是同一个值。

但生产上走内置表：常量拼错 ⇒ `Lookup` 落空 ⇒ **Gate 直通、不节流不缓存**。twelvedata 尤其危险（该域**没有** `twelvedata.*` 通配兜底，不同于 lixinger），直接撞免费层 8 req/min。

⇒ **每个 collector 都需要一条「主题常量 ↔ 内置表」的断言**（形如 `TestTopicMatchesBuiltinPolicy`：用 `policy.NewTable().Lookup(topicXxx)` 确认命中且策略值符合预期）。yahoo 独立补了同型的 `TestEachMethodUsesItsOwnTopic`（三主题各自独立，写成同一个也照样绿）。

### 陷阱 16：「同参数只发一次」测不出「缓存键少了参数」

方案给的缓存用例通常只用**一个** symbol。此时缓存键里**丢掉 symbol** 也照样全绿 —— 而生产上 AAPL 会拿到 NVDA 的收盘价。

**这是静默错数据，比缓存没生效危险得多**：后者只是慢，前者是错。

⇒ 缓存键测试必须**用至少两组不同参数**，断言它们不互相命中。与陷阱 2（key 含 topic 只能断言调用次数）配套使用。

### 陷阱 17：覆盖率 profile 也是**有锚的**，不只是 git ref

`go tool cover -func=profile.out` **同时读 profile 与当前工作区源码** —— profile 里存的是行号区间，源码一变行号即错配，**结果是一个看似合理的错数字，不报错**。

TASK-008 实例：验证者在主仓库（HEAD 已前移到 `b0bc78a`）对 `b197394` 时期的 profile 跑 `cover -func`，得到 **91.7%**；改在**同源 worktree** 内重测才拿到正确的 **92.7%**。1 个百分点的偏差，正好可能跨过判定线。

⇒ **覆盖率复算必须在与 profile 同源的代码状态下做**（同 worktree / 同 sha），不能拿旧 profile 配新源码。

**这与「验证命令的锚必须钉全 sha」是同一类失效**：

> **依据在被使用时，已经不是写下时的那一份。**

本 Sprint 的同类实例：跨轮引用变异结论（TASK-002）、门禁报过期覆盖率（TASK-012 的 98.2% vs 99.1%）、方案引用已漂移的上游语义（教训 15）。**凡是「我之前测过」的结论，都要问一句：那次测的对象和现在这份是同一份吗？**

### 独立视角该问的问题：「它没想到测什么」

TASK-008 的验证者在复现 Dev 全部 9 个变异之后，**另加了 2 个 Dev 没做的**，依据正是「变异只能证伪写下的断言，不能证伪没写的那些」：

- **V10**：本包那条「8s 数值」断言**锚在 policy 包的内置表**里（别的任务的产出）。它直接去改内置表的 8s→5s，确认**本包这条断言真会转红** —— 验的是「跨包锚点是否活着」，而不是本包自说自话。
- **V11**：Dev 用「绕过 Gate」间接证明节流，但那**同时废掉了缓存，红的原因不唯一**。它只让 `policy.throttle` 失效、其余不动，**只有一条转红**，把节流单独隔离归因。

⇒ **两种独立视角的典型动作**：① **跨包锚点验证** —— 本包断言依赖别包产出时，去改那个产出，确认依赖链真的活着；② **归因隔离** —— Dev 的变异若同时影响多个机制，重造一个只动目标机制的。

### 教训 16：行为测试的能力边界 —— 「写本身」测不到，只能测「写导致的可观测变化」

TASK-009 的 DoD 曾给出二选一：(a) 写测试钉死「消费者只读」这条不变量 / (b) 逐行深拷贝。**(a) 经实测证明在行为测试层面定义上不可达。**

验证者构造三种写形态：

| 形态 | 结果 |
|---|---|
| M1a 读后写、值不同 | **红** ✅ |
| M1b 写后读、值不同 | **绿漏检** —— 两次都返回改后值故相等，仅被既有测试**偶然**抓到（它恰好断言了被改字段的具体数值）|
| **M1c 归一化写回** `if math.IsNaN(v) { v = 0 }` | **全量套件全绿漏检** |

**M1c 不是人为角落**：`client.go:184` 明写 `values[f] = math.NaN() // 非数值列与缺列一律 NaN`，NaN 在真实数据里确实存在，**消费者做 NaN→0 归一化是完全合理的需求** —— 它会污染共享缓存，而整个套件放过。

**精确表述**：

> 行为测试**可测的是「写导致返回值可观测地变化」，不可测的是「写本身」，两者的差集永远测不到。**

差集包括：**幂等写**（写入与原值相同）、**条件不触发的写**、**写后读同一值**。要完整守护「只读」这类不变量，只能靠 AST 静态检查。

**推论**：凡是 DoD 写成「X 不得发生」而 X 是**调用方行为**（而非被测函数行为）时，先问一句 —— **这个「不发生」有没有可观测的后果？** 没有的话，行为测试守不住，应改为「消除依赖」（如深拷贝）或转为静态检查。

**附带**：Dev 在测试注释里写「不依赖写法形状」**不准确**（三种写法结果不同，恰恰依赖）。验证者归类为「错误的修复比不修更难查」同类 —— **不准确的守护声明会让下一个人以为已经守住。**

### 覆盖缺口只能用**结构性证明**，变异证明不了

TASK-010 的验收标准 6 是「lixinger 能进入缓存路径」。验证者指出：

> 对 `request()` 做多少变异都证明不了「**没有第三条路径绕过它**」—— 那是**覆盖缺口**，不是断言强度问题。

它改用**结构性证明**：`l.client.Do(req)` 全包**只出现 1 次**；`requestHTTP` 的调用点**只有 1 处**（就在 `policy.Fetch` 的 `fn` 内）；8 个上层方法**全部**经 `l.request(...)`。⇒ **包内不存在任何绕过 Gate 的 HTTP 路径**，两种身份（eastmoney fallback / Valuation source）结构上都被覆盖。

**判据**：

| 要证明的 | 手段 |
|---|---|
| 「这条路径的行为正确」 | 变异验证 |
| 「**不存在别的路径**」 | **结构性证明**（穷举调用点 / AST / 类型系统）|

变异只能证伪**已存在**的断言，**无法枚举不存在的路径** —— 这是「变异只能证伪我写下的断言」在**覆盖维度**的表现。

### 双层结构的一个干净实例：Dev 止步处正是验证者的起点

TASK-010 的 Dev 在 discovery 里如实声明一处未做：

> 该变异需改 policy 包，**超出我的 writes 范围**，且当时三个 Dev 在并行跑依赖 policy 的测试，瞬时改坏会给他们制造假红 —— 未注入，该分句目前只有「等值谓词」这一肉眼判据。

验证者的回应：**「这个约束对 Dev 成立，对我不成立」** —— 它在一次性 worktree 里改内置表补上了两个变异（L7 加 `MinInterval` → 红在策略表侧与请求路径侧**两处**；L9 加 `Quota` → 红）。

⇒ **Dev 自证到能力/权限边界处如实止步并声明，验证者从没有该约束的位置补上。** 这比「Dev 硬做」和「就此放过」都好：前者会污染并行工作，后者留下无实证的一格。

**前提是那份声明必须诚实且具体** —— 它写清了「为什么不做」「缺的是哪一格」「目前只有什么判据」，验证者才能精确接手。

### 一处值得记的接缝（非缺陷）

lixinger 的 52 个既有测试跑在包级 `TestMain` 注入的**零策略闸门**下（否则 18 个会因缓存串味转红，验证者量化过）。副作用是：**这 52 个测试对生产缓存配置的覆盖为零** —— 该包全部缓存行为只由新增的 7 个 gate 测试守护。

这是接入缓存后的**结构性副产品**：为了让既有测试不受新机制干扰而中和它，代价是既有测试也不再覆盖新机制。**注释已写清原因，删掉 `TestMain` 会看到 18 个测试莫名转红。**

### 「绿」的两种含义看起来一样 —— 必须用探针区分

TASK-009 改 (b) 后，M1c 变异（归一化写回）**全绿**。但：

> **「绿」在 (a) 下是漏检、在 (b) 下应是无害，两者从套件看完全一样。**

Dev 没有把「(b) 下消费者只能改到自己的副本」直接写成结论 —— **那是推理链**（教训 9 禁止的那种）。它做了 2×2，用一次性探针**直接读缓存里那份 row**：

| | 归一化消费者 M1c |
|---|---|
| **(b) 深拷贝** | 缓存中 `pe_ttm` 仍为 **NaN** ✓ 无害 |
| 退回不深拷贝 | 缓存被污染成 **0** ✗ 漏检（复现验证者的发现）|

⇒ **修复后「变异不再转红」有两种可能：真的无害了，或者守护本来就没生效。** 二者在测试输出上不可区分，只能靠**直接观测被保护的状态**（探针读缓存内部）来分辨。探针答完即删，不留在套件里增加维护面。

### 僵尸测试：名字承诺了它不再守护的东西

改 (b) 后 Dev **主动删掉**了首轮的 `TestCachedRowsNotMutatedByConsumers`，理由：

> 在 (b) 下它会**永远绿**（消费者写的是副本），成为一条不守护任何东西的测试；**而它的名字暗示「消费者只读被守护着」，留着比删掉更有害。**

⇒ 实现方案变更后，为旧方案写的测试可能变成**恒真**。恒真测试本身无害，**但它的名字仍在向读者承诺一个已经不存在的守护** —— 这与「不准确的守护声明」「错误的修复比不修更难查」同源。**换方案时要回头清理为旧方案写的守护。**

### `dod_defect` 不计入 `rework_count` 的理由

Dev 提出（我采纳并写入）：

> **「DoD 不可达」与「实现有缺陷」若都记进返工计数，会让熔断阈值在规格问题上误触发** —— 而规格问题恰恰是继续机器循环最没用的那一类。

`max_rework` 熔断的设计意图是「反复返工 N 次 ⇒ 大概率 DoD 本身不可实现或自相矛盾 ⇒ 停下来让人介入」。但 `dod_defect` **已经把结论直接给出来了**，不需要靠计数去逼近它。把两者混记，等于让额度被「已经诊断清楚的规格问题」消耗掉，真正需要熔断的「实现反复做不对」反而更早触顶。

⇒ **`reason_class` 应当参与调度决策，而不只是记录分类。**

#### 陷阱 14 的风险形态由**被缓存函数的返回类型**决定

TASK-008 验证者的结构性观察 —— 同一个陷阱，两个包的**现实风险形态不同**：

| 包 | `fn` 返回类型 | 校验能否挪出 `fn` | 现实风险形态 |
|---|---|---|---|
| **lixinger** | `[]byte`（raw） | **能** —— `parseEnvelope` 天然可以放到 `Fetch` 外面 | **「挪到外面」** |
| **twelvedata** | `[]core.OHLCV`（已解析） | **不能** —— 错误信号只存在于解析层内部，结构上挪不出去 | **「忘了写这个校验」** |

⇒ 变异要按形态设计：前者注入「把校验上提」，后者注入「短路掉 fn 内的校验」。**用错形态会得出「不适用」的错误结论。**

**判据**：看被缓存的 `fn` 返回的是 **raw 字节**还是**已解析结构** —— 返回 raw 的包，校验有条件被挪出去，风险更高。

**决定性断言是「HTTP 请求数」而非「返回 error」**：twelvedata 的 W1 变异下，`:238`（want error, got nil）与 `:242`（两次调用应各发一次 HTTP，got **1**）双双转红，**后者才证明「不被缓存」这一面有独立守护** —— 前者只证明「返回了 error」。

### 陷阱 18：门禁口径与 DoD 口径共用一个数字，却量不同的东西

TASK-011 派发前发现（test-agent-16）：

| 口径 | 实测 | 谁在用 | 余量 |
|---|---|---|---|
| 三包合并（`-coverpkg`） | 76.5% | **门禁** `coverage_floor=74` | 2.5pp |
| **`cmd/atlas` 单包** | **74.4%** | **DoD**「cmd/atlas 不低于 74%」 | **0.4pp** |

两者共用数字 `74`。而该任务要**删除** `maybeCache` 函数 + 4 个独占约 5% 语句的测试 —— **删除已被覆盖的代码会把总覆盖率往下拉**（`(0.744−0.05)/(1−0.05) ≈ 73.1%`，粗估但方向确定）。

**危险在于门禁不会报警**：

- 门禁算合并值 → 删完仍过 74 → **exit 0，Dev 以为没事**
- 验证者按 DoD 算单包 → 已跌破 → **判 FAIL**

⇒ **Dev 什么都没做错、门禁一路绿灯，却在验证这一步被判不过。**

1. **同一个阈值数字在两处使用时，必须确认两处量的是同一个量。** 「74」在门禁是合并值、在 DoD 是单包值 —— 数字相同掩盖了口径不同。
2. **对「主动删除已覆盖代码」的任务，「不低于既有水位」这个口径本身就不适用** —— 删除会拉低分子分母比，这是**数学必然而非质量下降**。此类任务应改用合并口径、或按删除后实测重定阈值，并在 DoD 里写明理由。

**处置**：本任务改为合并口径判定，单包数值仍要求记入 discovery **作为观测项而非判定线** —— 口径统一了，但信息不丢。

### 「权限允许不等于该做」的判据是**语义归属**，不是谨慎程度

test-agent-16 的补充（比原表述精确）：

> 判据是「**这个字段的语义归属是谁**」，不是「我能不能」。`questions` 是 Dev↔Leader 的对话，`discovery` 指针是任务的客观产物 —— 所以后者我直接补了，前者我停下来问。**同一条原则，两个不同结论，靠的是归属判断而不是谨慎程度。**

⇒ 谨慎程度是个滑动标尺，会随疲劳/压力漂移；**归属判断是个可回答的问题**，答案稳定。遇到「我技术上能写但要不要写」时，问的是**这条记录是谁的**，不是**我够不够小心**。

### 防回归抽查：目标测试被重构过时，沿用旧 `-run` 会得出错误结论

TASK-009 二轮，验证者沿用首轮的 `-run TestCallKeyDistinguishesParams` 做防回归抽查，得到**捕获率 0%**，一度判为「守护完全失效」。查 diff 才发现：**测试名还在，但排序守护已被迁移到新拆出的测试**。

### 跨目录变异的还原必须用仓库根作用域

同轮另一处失误：变异改的是 `policy/gate.go`，而 runner 在 `tushare/` 子目录执行 `git checkout -- .` —— **作用域不含 policy 目录**，变异残留在 worktree 里。

⇒ **`git checkout -- :/`（仓库根作用域）或直接在根目录执行**。子目录的 `-- .` 只还原当前目录树。

（该次判定未受污染 —— 那是最后一批变异，之后只写报告没再跑测试；验证者核对时序后如实报告了这次失误。）

**至此「验证工具自身缺陷」已累计四类**：测试名打错（跑 0 个测试）、import 未使用（编译失败伪装成捕获）、`-run` 目标过期（跑的不是那条守护）、还原作用域不足（变异残留）。**四者都不被任何门捕获，唯一信号仍是「预期与实际不符」** —— 第三类正是靠它发现的（预期红、实际 0%，反常到必须查）。

#### 探针的 2×2：右下格证明的是**探针本身有区分能力**

TASK-009 的补做（test-agent-17 复现 Dev 的 2×2）给出了一条容易被跳过的理由：

> **缺了右下格，左上格的 ✓ 与「探针写错了、什么都没测」在输出上同样无法区分。**

⇒ 这与陷阱 10 同族，但方向不同：陷阱 10 是**缺陷伪装成测试构造失败**；这里是**「无害」与「测不出」伪装成同一个绿**。

**配套观察** —— 套件与探针守的不是同一件事：

| | 守什么 |
|---|---|
| 套件里的常驻测试 | **深拷贝在不在**（删掉就红） |
| 一次性探针 | **深拷贝确实起了作用**（直接读被保护的状态） |

**两者缺一不可**：前者防回归、后者防「写了但没生效」。探针答完即删，不进套件增加维护面。

### 归因错误的新变体：错误信息把人引向**相反**的结论

TASK-014 预读时识别出的形态（test-agent-17）：

方案原文用 `Quota{Limit: 0}` 期待配额耗尽，而 policy 语义里 `Limit <= 0` = **不设上限**。照抄后 `TestQuotaErrorSatisfiesRateLimitedAssertion` 的 handler 会**真的收到请求**并触发 `t.Error("配额已满时不应发出请求")`。

> 失败信号看起来像「**配额拦截没生效**」（实现问题），实际是「**测试构造错了**」（`Limit:0` 不设上限）。

⇒ 前面记的归因错误是「**红/绿的原因不是被测行为**」（编译失败、panic、跑了 0 个测试）—— 那些至少**看起来可疑**。这一种更隐蔽：**错误信息措辞精确、指向明确，只是指反了方向。**

**对策**：看到一条指向实现缺陷的失败时，**先确认测试构造的前提值是否符合被测系统的语义**（尤其是阈值、哨兵值、边界值 —— 与教训 15 的上游语义漂移是同一处风险的两个表现）。

### 共享主工作区的提交风险：`git commit` 必须带显式 pathspec

wave 7 起有 4 个 agent 共用主工作区。TASK-014 交付时 `git status` 显示：

```
D  internal/collector/cache.go        ← 别人(TASK-011)的在途删除，已 staged
D  internal/collector/cache_test.go   ← 同上
 M internal/core/types.go             ← 同上
```

> **此时任何 agent 执行不带 pathspec 的 `git commit -m ...`，都会把别人未完成的工作一并提交。**

⇒ **纪律**：`git commit` **必须带显式 pathspec**，且**提交后核对 `git show --stat`** 确认只含自己的文件。

**这是结构性风险不是谁的疏忽** —— 删除类任务尤其危险，因为 `git rm` 天然进暂存区，而别人看到的是一个"已 staged 但不属于自己"的状态。

### 纯回归测试任务没有 RED→GREEN 可用

### 「关系」性质不能靠分别断言两端来证明

TASK-014 的 DoD functional[2]「本地配额与服务端限频**行为路径一致**」是一条**关系**性质。Dev 的判断：

⇒ 它新增 `TestLocalQuotaAndServerRateLimitDegradeIdentically`，**并排比对两条路径产出的 Report 形状**，判据不依赖对文案的预设。

| 1 | **checkpoint 里的行号指针** | 指向的代码已移位 | 直读核对 |
| 2 | **`-run` 的测试名** | 测试跑了，但守护已迁移到新拆出的测试 → 捕获率 0% | 「预期红实际 0%」反常到必须查 |
| 3 | **变异正则的源码文本** | `return rows, err` 已被上游任务改成 `return cloneRows(rows), err` → 静默失配、文件一字未改 | 「有显式反向断言却全绿」不合常理 |

**共同点**：**验证工具的锚，在被使用时已经不是写下时的那一份。**

⇒ **跨任务/跨轮次复用验证脚本时，锚点必须重新对齐当前代码。** 这与「跨轮引用变异结论」「拿旧 profile 配新源码算覆盖率」是同一个家族 —— **依据的有效期问题**。

**三次都不是靠门捕获的**（门只能拦下已经发生的失配，拦不住「锚写对了但代码变了」），**全部靠「预期与实际不符」触发追查**。这再次印证：预期表是应对工具自身缺陷的唯一通用信号。

### 测试的**前提条件**本身也需要守护

TASK-014 的验证者自加 N4：让 `FileStore.read` 恒返空账本，验证「**预填账本**」这个前提有守护 —— 预填若失效，请求会真的发出去，测试转红。

> **前提不是摆设。**

⇒ 凡是测试依赖某个**构造好的初始状态**（预填账本、预热缓存、注入的桩数据），要问：**如果这个前提没生效，测试会不会仍然绿？** 会的话，那条测试实际在测一个不存在的场景。

这与陷阱 8（否定断言需正向对照）同源：正向对照守的是「链路接上了」，前提守护守的是「初始状态到位了」—— **两者都是在防「测试跑在一个空场景上还显示成功」**。

### 多个测试夹具不能共用一个 root —— 遍历顺序会造成隐式耦合

TASK-013 原型阶段撞出（dev-agent-38，开工前）：

`WalkDir` 按**字典序**遍历，夹具目录 `broken` < `decoys` < `throttleback`。若阳性对照的 root 指向 `testdata/` 而非 `testdata/throttleback/`：

> 遍历会在 `broken/`（语法错误夹具）处**因解析错误提前返回**，**根本走不到 throttleback** —— 于是「应检出 ≥1」的断言失败，而失败信息是「**解析失败**」。

⇒ **测的是阳性对照，红的是解析夹具，错误信息指向的方向完全不对。**

这是「归因错误的新变体」（错误信息措辞精确、指向明确，只是指反了方向）的又一形态，成因是**夹具之间的遍历顺序耦合**。

**更麻烦的是它的顺序依赖性**：夹具一改名（`broken` → `zbroken`），就翻转成「阳性对照通过、解析失败夹具反而没被走到」的**静默假绿** —— 同一份代码，改个目录名就从假红变成假绿。

⇒ **纪律：每个夹具一个专属 root，一次遍历只验一件事。** 不靠一次扫描同时验多个性质。

#### 附：AST 相对 grep 的价值可以被量化

同一份 `decoys` 夹具里放三种诱饵 —— **注释里的** `lastReq`、**局部变量** `lastReq`、**`_test.go` 里的**结构体字段 `lastReq`：

| 手段 | 误报 |
|---|---|
| AST 扫描 | **0/3** |
| grep | **3/3** |

（这也解释了为什么此前有 Dev 做过一次**不必要的预防性改名** —— 它按 grep 的强度模型估计了 AST 扫描的覆盖面。**别人对你的守护强度的心智模型可能是偏高的**，边界要写进注释。）

### 「今天无人守护的规则」：承重与未来承重

TASK-013 的 `testdata` skip 规则，2×2 显示它**承重**（关掉则扫描因解析夹具失败）。但 Dev 指出一个时间维度的事实：

> **今天它是「未来承重」** —— `edgar/testdata` 现在 0 个 `.go` 文件，所以在我加进夹具之前，**这条 skip 规则删掉也不会有任何测试转红**。

⇒ 一条规则可以**正确、必要，且当前无人守护** —— 它的守护者是它自己将来要防的那个场景。**这类规则最容易被当成死代码删掉**，必须在注释里写明「为什么现在看起来没用」。

（与教训 5「注释描述的是当前巧合还是被守护的契约」互补：那条讲**观察被误当契约**，这条讲**契约被误当死代码**。）

### 「形式与内容不符的测试比没有更糟」

TASK-011 的 Dev 主动废弃了自己最初写的一版测试：运行期 type assert，**在「代码能编译」的前提下恒真**（lixinger 直接实现接口，经 `collector.Collector` 传递后动态类型不变）—— **注入变异时才发现**。

它的措辞值得原样保留：

> **形式与内容不符的测试比没有更糟** —— 它看起来在守护运行期行为，实际什么都不防，**还会让人以为这块已经有覆盖**。

这与「僵尸测试：名字承诺了它不再守护的东西」同族，区别在于：僵尸测试是**曾经有效、方案变更后失效**；这一种是**从写下起就恒真**，只是没人注意到。**两者的危害相同：占据了「这里有守护」的位置。**

⇒ **新写的测试也要过一次变异** —— RED→GREEN 只证明它对「实现缺失」敏感，不证明它对「实现错误」敏感。

### 估算的方向与数值要分开评价

TASK-011 派发前，验证者粗估删除后 `cmd/atlas` 覆盖率会跌到 **73.1%**（跌破 74）。实测 **74.3%**。

⇒ **估算用于「要不要处置」是够的，用于「处置到什么程度」不够。** 那次估算促成了口径切换（正确的处置），但若拿 73.1% 去定新阈值就会定错。**分清一个数字是用来触发决策的，还是用来当判定线的。**

（顺带：即便实测只到 74.3%，按旧口径也只剩 **0.3pp** 余量 —— **口径切换的必要性不因估算偏悲观而减弱。**）

### scope 漂移判据拦的是「当前 transition 的人」，不是「造成漂移的人」

TASK-007 返工完成后 `transition dev_done` 被 DENY，漂移路径却全是 **dev-agent-38 的 TASK-013 未提交产物**（`internal/collector/testdata/{decoys,parsefail,throttleback}`）。

**根因**：TASK-013 声明的是 `./internal/collector`，而 **Go 语义下它不包含子目录** —— `testdata/decoys` 是独立包路径，门禁按目录路径算，认为无人声明，于是记到**当前 transition 者**头上。

⇒ **并行任务多时，未登记路径会串扰**：A 的声明疏漏，表现为 B 的门禁失败。B 看到的错误信息完全指不到 A。

**正确处置（dev-agent-35 做对了）**：

> 我**没有**自行把这三个路径加进自己的 `packages` —— 它们不是我的产出，加了就是错误声明，而 `writes` 同时驱动 scope 互斥与漂移判据。

**为解除自己的阻塞而伪造声明，能立刻过门禁，但会在文件里留下一条假的归属记录，后续所有基于 `writes` 的判定都被它污染。** 正确做法是通知产出方补声明（单写者原则：只有 owner 能写自己任务的 `packages`）。

**两条时机要点**：`packages` 只能经 `update` 写、不能随 `transition` 带；**一进 `dev_done` 就没有任何角色能合法补该字段** —— 必须在 `in_progress` 期间补。

| 工具 | 视角 |
|---|---|
| `go build` / `go vet` / `go test` | **忽略** testdata |
| 门禁的漂移判据、`gofmt -l` | **普通目录**，照常计入 |

⇒ 用 testdata 放夹具时，**两处都要处理**：`packages` 里显式声明各子目录、`gofmt` 检查限定到具体文件列表。同源问题，一起想。

### 「变异锚定错误」的三种形态 —— 四道门全部放行，只有预期列能发现

本 Sprint 三次实例，**错法不同但同源：锚定到了错误的位置**。

| # | 形态 | 实例 | 表现 |
|---|---|---|---|
| ① | **位置错** —— 同一文本在文件中出现多次，替换了错误的那一处 | `if result.Chart.Error != nil` 在 `yahoo.go` 有两处（`fetchQuote:254` / `fetchHistory:332`），`replace(..., 1)` 只换了第一处 —— **删的是 quote 路径的校验，测的是 history 路径** | 预期红、实际绿 |
| ② | **名字过期** —— `-run` 的测试名还在，但守护已迁移到新拆出的测试 | TASK-009 二轮防回归 | 捕获率 0%，一度判为「守护完全失效」 |
| ③ | **文本过期** —— 正则锚的源码文本已被上游任务改掉 | `return rows, err` → `return cloneRows(rows), err` | 静默失配、文件一字未改，伪装成「变异存活」 |

**①的关键教训**（验证者原话）：

> **落盘校验通过了（0+/3-）、编译通过了、测试也跑了 —— 前四道门全部放行。只有预期列能发现它。**

⇒ 四道门检验的是「变异有没有生效」，**检验不了「变异有没有作用在目标位置上」**。后者只能靠「预期与实际不符」触发追查。

**实操**：多处匹配的文本用 `rindex` / 全量替换 + 断言替换次数，或直接按行号锚定；替换后 **diff 一眼确认改的是哪一处**。

### 自造夹具与被测实现可能共谋 —— 用「不是自己写的」真实语料做阳性对照

TASK-013 的 Dev 为「跳过规则对 root 自身不生效」这一行补测试时，**没有再造一个夹具**，而是拿**真实的 `policy` 包**当阳性语料（本仓库唯一合法的 `lastReq` 在 `gate.go` 里）。理由：

> **夹具是我按扫描器行为造的，与扫描器可能共享同一个盲区**；而 `policy/gate.go` 不是我写的。

⇒ 这是教训 13（方案的实现与测试共享盲区）在**同一个人写实现与夹具**时的形态。**阳性对照的价值取决于它的来源独立于被测实现** —— 自造夹具只能证明「扫描器对我想到的形态有效」，真实语料还能证明「对我没想到的真实写法也有效」。

**同一任务的另一处应用**：该 Dev 采纳 code-simplifier 抽出的共用 AST 遍历后，**没有盲接**：把全部 10 个变异在简化版上重跑（红集逐条相同），并**另补一个变异直接打那个新抽出的共用函数**，确认归因消息仍指向扫描器而非「夹具本身失效」。

> **共用遍历让预言机（算期望行号）与被测实现（扫描）共代码 —— 正是共谋形态。**

⇒ **重构把「独立的两份」合并成「共用的一份」时，要重新证明预言机没有被合并进被测对象。**

### 并行期 `git status` 里可能出现「注入到一半的变异」

TASK-013 交付前 `git status` 一度显示 `M internal/collector/yahoo/gate_test.go`（**非该 Dev 改动**），**数秒后自行消失** —— 那是另一个 agent 变异注入与还原之间的窗口。

> **若此刻跑不带 pathspec 的 `git commit`，提交进去的会是「注入到一半的变异」。**

这比「提交了别人的未完成产物」更糟：未完成产物至少是有意写的代码，**而变异是有意写坏的代码**，且原作者会在几秒后还原、从此无人知道它被提交了。

⇒ **「commit 必须带显式 pathspec」在有并行变异验证时不是洁癖，是必需。**

### `testdata` 的三处可见性 —— 「Go 工具链忽略它」只对通配模式成立

本 Sprint 三次撞到同一个错误心智模型，**最后一次是 Dev 自己持有的**：

| 工具 | 是否看见 testdata |
|---|---|
| `go build ./...` / `go vet ./...` / `go test ./...` | **忽略**（通配模式）|
| **`gofmt -l <dir>`** | 看见 |
| **门禁的漂移判据**（按目录路径算） | 看见 |
| **门禁的 `go test $PKGS`** | **看见** —— `packages` 是**显式路径**，绕过了 `./...` 对 testdata 的忽略 |

⇒ **「go 工具链忽略 testdata」这个心智模型只对通配模式成立，对显式路径不成立。**

#### 由此产生的一个不可兼得约束（TASK-013 实例）

`packages` 字段**同时驱动两件事**（`task-completed.sh`）：

- `:58` `DRIFT=$(comm -23 MINE_ACTUAL PKGS)` —— **漂移判据**
- `:112-119` 按同一个 `PKGS` 跑 `go test`，**失败即 BLOCKED**

而该任务的 `testdata/parsefail/bad.go` 是**故意语法错误**的夹具（用于验证「解析失败时清晰报错」）。于是：

| 要满足 | 后果 |
|---|---|
| 漂移判据 ⇒ 必须**逐条字面列出**三个子目录（`comm -23` 是**精确集合差、不是前缀匹配**，声明父目录无效）| — |
| 而 `parsefail` 一旦进 `packages` | `go test` 构建失败 ⇒ **此后任何 `dev_done` 迁移永久 BLOCKED**，错误信息显示「测试失败」、**看不出根因是声明本身** |

**两个约束在「畸形夹具存在于仓库」的形态下不可兼得。**

**正解不是二选一，是消除根因**：把语法错误夹具从仓库移走，改为测试运行时用 **`t.TempDir()` 现写**一个畸形 `.go` 文件。一次解决四处：`go test` 不再构建失败、少一个要声明的目录、`gofmt -l` 不再报错、**而解析失败分支的守护不变**。

（可读语料型夹具 —— 如 `decoys`/`throttleback` —— 应留在仓库：它们对 `go test` 无害，且作为语料需要被人读。**只有「故意不可编译」的夹具必须运行时生成。**）

### 留痕的前提是过时了要更正 —— 否则留痕反而制造噪音

TASK-013 的 Dev 在裁定未到达时按最合理解读推进，并在 discovery 里写明「已请示但未获答复，按超集推进……建议收尾时把措辞改齐」。**那句在写下时准确。** 裁定到达后它主动更正，理由：

> 它会让验证者去追一个**不存在的 DoD 与实现偏差**。

它自己的归纳最准：

> 契约记的是「**不准确的守护声明**会让下一个人以为已经守住」；**这里是「过时的偏差声明会让下一个人去追一个不存在的问题」—— 同一个病，方向相反。**

⇒ **声明留痕的前提是：过时了要更正。** 否则留痕从「降低不确定性」变成「制造噪音」。

**保留原始经过 + 标注当前结论**是正确形态（它保留了「裁定未到达时如何处置」这个可复用记录，同时明确标注「本条不存在偏差，验证者无需追查」）—— 而不是删掉重写，那会丢掉过程知识。

### 权限模型按**文件类型**分，不是统一的

同一状态下，不同产物的写权不同（Dev 实测，非读文档推断）：

| 在 `verifying` 状态下 | task JSON | discovery 文件 |
|---|---|---|
| 原 owner（`dev-*`） | **硬 DENY**（`合法写者: ["test-*"]`）| **仍可写**（exit=0，直读确认）|

⇒ **「我在 `verifying` 下什么都写不了」是个错误的概括。** 状态机管的是**任务状态文件**的单写者，产物文件（discovery / wisdom / checkpoint）另有规则。

**实践含义**：交付后发现自己的 discovery 有错，**不必等派回** —— 直接更正即可。而 task 文件的字段（`packages`/`questions`/`done_criteria`）必须找当前状态的合法写者。

## 契约条目的两种形态：「写的时候照做」与「跑完了核对」

test-agent-17 在 Sprint 收尾时提出的区分，**它决定了一条契约条目的实际收益**：

| 形态 | 特点 | 本 Sprint 实例 |
|---|---|---|
| **写的时候照做** | 是一条**可以直接采用的写法** —— 采用了就避开了，**不依赖任何人记得** | 行号**现读不写死**；`if false { _ = ... }` 保留引用；`t.TempDir()` 隔离；`defer recover()` 把 panic 转断言；构造函数封装保证顺序不可能写错 |
| **跑完了核对** | 是一个**检查动作** —— 只能在犯错后触发，**依赖执行者记得去做** | 变异证据链的五道门；2×2 闭环；单独 `-run` 到守护者；核断言行而非 panic 堆栈 |

**证据**：「行号现读不写死」这一条，让 TASK-013 的 Dev **在写测试时就排除了「锚点过期」这个失效模式** —— 而同一个失效模式，另外两人**踩了三次**（`-run` 目标过期、正则文本过期、多处替换错位）才靠「预期与实际不符」诊断出来。

⇒ **沉淀教训时优先找「照做型」的表述。** 同一个教训往往两种形态都能写：

- 核对型：「注入变异后要确认锚点仍然有效」
- **照做型**：「**行号/位置一律现读，不写死**」

**后者更强，因为它不需要在正确的时机被想起来。** 核对型条目是兜底，不是首选。

（这也解释了为什么「机制化」反复出现在本 Sprint 的教训里 —— 把核对型固化进 runner，本质上是把它转成了「照做型」：执行者不必记得，工具替他做了。）

### 返工回归：红还在，但**守护的东西可能已经不同了**

TASK-013 返工后重跑 11 个变异，红集**逐条相同**。但 Dev 核到断言行时发现 **N2 的红机制变了**：

| | 返工前 | 返工后 |
|---|---|---|
| N2（`skipDirs` 去掉 `testdata`） | 生产扫描撞上畸形夹具 → 报**「解析失败」**而中断 | `throttleback` 夹具**被真正检出为 offender** → 「发现私有节流状态字段」 |

**同一个变异、同一条测试转红，但红的原因换了 —— 而且换得更好**（从附带崩溃变成语义检出）。

> **若只看红/绿会以为什么都没变。**

⇒ **「判红要核到断言行」不只用于分辨真红假红，还用于发现「红还在但守护的东西已经不同了」。** 返工回归时尤其要看：红集相同 ≠ 守护未变。

**这也是那条 `testdata` 跳过规则的承重方式转移**：先前由「畸形夹具导致解析失败」承重（附带效果），现在由「真实夹具被语义检出」承重（正面效果）—— **验证者预判它会失去承重，实际是换了个更好的承重方式。**

### 修一个会说谎的错误信息，比修一个会报警的缺陷更值得

Dev 解释它为何在自己的任务已 `verified`、隐患尚未影响任何人时仍要推动修复：

> 真正让我不肯放过的是那个错误信息：`BLOCKED: Tests failed in task scope` 会把根因是「**声明写错了**」的问题伪装成「**代码有问题**」，而踩到的人**手里拿着一份看起来完全正常的代码**。

⇒ 缺陷的严重性不只看后果大小，还要看**它把排查引向哪里**。会报警的缺陷消耗一次修复；**会说谎的错误信息消耗的是排查者的信任与时间，而且他找错方向的每一步都符合逻辑。**

（本 Sprint 的同类：`Limit:0` 让「测试构造错」伪装成「实现有问题」、有效性判定顺序让「缺陷」伪装成「测试没测到」、编译失败伪装成「变异被捕获」。**四例都是错误信息指反了方向。**）

### 第三类条目：**无守护的事实性声明**

前面把契约条目分成「写的时候照做」与「跑完了核对」两类。dev-agent-38 指出还有第三类，**而且它是最危险的**：

> **注释与 discovery 里的事实性声明两类都不属于** —— 它们既没有「写的时候照做」的机制，也不在五道门的核对范围内。**唯一的守护是有人恰好想起来去看。**

**本 Sprint 的实证**：同一个 Dev 在同一个任务里**连续三次**写下「当时准确、事后失效」的声明 ——

| # | 位置 | 失效原因 |
|---|---|---|
| ① | discovery 的「未获答复的 DoD 偏差」 | 裁定到达后仍留着 |
| ② | 头部映射注释的「四个子包」 | DoD 已改为全树 |
| ③ | `skipDirs` 注释的「被解析失败夹具打断」 | 畸形夹具已改为运行时生成 |

**三次都不会被任何测试发现** —— 测试验的是**行为**，注释的**准确性**无人守护。而三次都是它自己发现的，**它自己的评价是「纯属运气」**。

**危害形态**（以③为例）：下一个人读了会去找那个不存在的畸形夹具，找不到就可能得出「这条规则已经没用了，删掉吧」—— **而它其实仍然承重，只是换了承重方式。**

⇒ **代码/文档里的事实性声明是一个系统性盲区。** 可行的缓解：

1. **写声明时优先描述「为什么」而非「是什么」** —— 机制会变，理由通常不变（`types.go` 那段注释是正例：它讲的是「为什么约束放在这一侧」）
2. **改动时把「我这次让哪些声明失效了」当成 checklist 的一项** —— 与「删除的东西所承载的知识要有去处」是同一动作的两面
3. **承认它是运气** —— 不要因为这次发现了就以为有机制在守它

**一条判据**：读到一条声明时问 —— **它描述的是现在的机制，还是写下时的机制？** 二者不一致时，声明会把人引向一个已经不存在的世界。

#### 「为什么 vs 是什么」是**可机械执行**的判据

原以为这是需要品味的判断。dev-agent-38 拿它扫整个文件后的实测结论：

> 只要问一句 —— **「这句话里有没有一个会变的具体事物？」**
> **有**（某个文件、某个数目、某个范围）⇒ 是「**是什么**」⇒ 会失效
> **没有**（因果、约束、失效模式）⇒ 是「**为什么**」⇒ 稳定
>
> **四处失效的全是前者，六处稳的全是后者，没有一处需要我犹豫。**

⇒ **这不只是写作建议，还是一个可以事后扫的 checklist** —— 正好补上「事实性声明唯一的守护是有人恰好想起来去看」这个空白：**至少现在「去看」的时候有个明确的看法。**

**它扫出的第四处，性质比前三处更微妙**：`TestScanDetectsThrottleState` 的注释用一个**已不存在的夹具**解释「夹具不能共用 root」这条规则。实测发现 —— **规则本身仍然正确，但它在这个测试上已不再承重**（改动后把 root 指向 `testdata` 那条测试照样通过）。

⇒ **「未来承重」的第三种形态：规则曾经承重，改动之后退回待命状态。**（前两种：规则尚未承重、规则承重方式转移。）

**改法**：**保留规则、换掉论据** —— 写「为什么」（一次遍历同时受多个夹具影响时，失败信息会指向错误的那个），并注明该具体场景已随夹具迁移而消失。

**它判定不必改的两处也值得记**（判据的负例）：

- 带「**接任务时实测**」时间戳的历史陈述 —— **它是历史事实，不会变假**
- 跨文件指针「如 `yahoo/gate_test.go` 的节流预热注释」—— **只是举例、不承担论证，坏了不误导**

⇒ 判据不是「凡具体事物皆需删」，而是「**具体事物若承担论证，它失效时论证就塌了**」。

## 教训 17：DoD 守护的失效模式可能被后续设计决策消灭——criteria 还在，它守的东西没了

qa-agent-8 在 TASK-015 进行中观察到：内置表用**通配**登记（`eastmoney.*`）后，
`Lookup` 的 `<域>.*` 回退让任何 `eastmoney.xxx` 都能命中 ⇒ 契约陷阱 15 描述的失效模式
（主题名拼错 ⇒ Lookup 落空 ⇒ Gate 静默直通）**在这三家身上根本不存在了**。

于是 TASK-015/016/017 里那条「主题常量与内置表一致」**测不出任何东西**：
无论主题名写成什么，只要域名对，就一定命中。**criteria 原文一字未改，但它守护的缺陷已被
设计决策消灭。** 针对它写的测试会稳定全绿，并在验证时被当作有效证据。

### 与本 Sprint 已有的「锚点过期」同族，但层级不同

| 层级 | 形态 | 本 Sprint 实例 |
|---|---|---|
| 测试 | 断言还在、守护对象已迁移 | `-run` 目标失效、变异正则文本被上游改掉 |
| 文档 | 行号指针指向别处 | checkpoint 行号、契约里的行号引用 |
| **规格** | **criteria 还在、失效模式已不存在** | **本条** |

规格层最隐蔽：测试层的过期往往以「红/绿反常」暴露，而规格层的过期**表现为一切正常**——
测试写了、跑绿了、criteria 打勾了，只是那个勾不对应任何真实保障。

### 判据（可机械执行）

写下形如「X 与 Y 一致」的 criteria 时，问：**如果 X 与 Y 不一致，会发生什么可观测的坏事？**
答不出具体后果 ⇒ 这条 criteria 已经空了。本例中「主题名拼错」在通配登记下的后果是
**什么也不会发生**，所以它守不住东西。

对偶地，**引入通配/兜底/默认值这类「让错误不再产生后果」的机制时，要反查哪些 criteria
是靠那个后果立起来的**——它们需要同步改写，而不是继续挂在任务上。这与教训 8
（规格歧义的真正修复是改规格）同源：**规格的失效也只能在规格里修**。

### 处置

TASK-015（`verifying` 时）/016/017（`pending` 时）三处均已改写为验
「主题名第一段（域）与登记域一致」——**写错域名才是通配登记下真正会落空的那半**。
派验单里明确告知验证者：不要把针对原条目的测试当作有效证据。

### 溯源：错在拼接处

这条不是评审发现的，是 **QA 在 dev 工作进行中只读观察**时发现的——它同时在看
「内置表怎么改的」和「三个任务的 criteria 写了什么」，交叉之下才看出错位。
Dev 只看自己那一条；Leader 写 criteria 时通配登记还不存在；验证者拿到的是既成事实。
**没有任何单一视角能在自己的信息范围内发现它。**

这是错误分类表第四行（共享的错误模型）的变体，但更难防：不是所有人都错，
而是**每个人各自都对，错在拼接处**。对策不是加评审轮次，而是**保留一个持续在场、
横跨多个任务只读观察的角色**——本 Sprint 恰好由待命中的 QA 承担了。

### 教训 17 的自我修正（qa-agent-8 实证推翻了它自己的观察，也推翻了我照抄的那半）

写完上面那节后，QA 做了实证并**纠正了自己**：

| 变异 | 结果 |
|---|---|
| E4 **接口段**写错（`eastmoney.kline` → `eastmoney.WRONG`，同域） | **全绿** |
| E5 **域段**写错（→ `WRONG.kline`） | **转红**，报「查不到 ⇒ 生产路径退化为无策略直通」 |

**E4 全绿是正确的**：通配登记下 `eastmoney.WRONG` 与 `eastmoney.kline` 命中同一条策略，
接口段写错**根本无害**。陷阱 15 的危害只可能由域段写错造成，而 E5 抓住了它。

所以准确说法不是「该 criteria 测不出东西」，而是——
**通配登记把它的检测面收窄到唯一有害的那一段，测试仍然充分。**

#### 这次修正本身的教训（比原教训更重要）

QA 的原话：「**我上次只推了一半就下了结论**。」它推出了「通配 ⇒ 接口段写错不再落空」，
就停在这里下了「criteria 不成立」的判断，**没有继续问「那域段呢」**。

而我**照抄了这个半成品结论**，改了三处规格、写进契约——**改对了方向（验域段一致正是 E5 那半），
但理由是错的**。如果当时按「criteria 已空」把它整条删掉，就会删掉一条真正有效的守护。

- **判据**：听到「X 不再有效」时，问「**X 的哪一部分**不再有效，剩下的那部分呢？」
  失效很少是整体的，通常是**检测面收窄**。收窄 ≠ 归零，而处置完全不同（改写 vs 删除）。
- **这与教训 9（推理链在相邻但不同的两件事处断裂）同源**，但发生在**评审者**身上：
  最擅长发现别人推理断裂的角色，自己的推理也会在同一个地方断。
- **能救回来的唯一原因是 QA 去跑了变异。** 纯推理的评审（包括我的采纳）无法发现
  「结论对但理由错」——**因为结论对，所有事后检查都会通过**。

#### 「结论对、理由错」是最难发现的错误形态

| 形态 | 事后可否发现 |
|---|---|
| 结论错 | 容易——测试/复核会撞上 |
| 结论对、理由对 | 无需发现 |
| **结论对、理由错** | **几乎不可能**——一切验证都通过，直到理由被复用到下一个场景 |

本例中「理由」是「这条 criteria 空了」。若它被复用（比如下次遇到通配登记就删 criteria），
才会造成损失。**所以理由必须单独校验，不能因为结论对就放过。**

## 教训 18：推翻错误前提是对的，但替代方案可能沿用同一个错误模型

TASK-016 的 `boundary[0]` 原带一条 QA 前瞻：crypto 下 binance/okx/coingecko 是三个独立
服务端，`domainOf("crypto.xxx")` = `"crypto"` ⇒ **三家共享一把限流锁**，须显式指定独立 Domain。

dev-agent-36 读源码后质疑，**质疑完全成立**（Leader 核实）：

1. Gate 包在 **Collector 层**（`CryptoCollector.FetchHistory` 外层，对应被删的 `maybeCache`
   装饰点），**不是 per-provider** ⇒ 三个子源根本不会各自过闸门；
2. `crypto.*` 内置条目**无 MinInterval**，`Gate.throttle` 第一行 `if p.MinInterval <= 0 { return }`
   ⇒ 一把锁都不会拿。**去不去 Domain 行为完全一致 = 等价变异**，那条测试无论如何都绿。

### 但它给的替代建议不成立，且错在同一个地方

它提议改验「三子源共用 topic+key 会**串缓存**——binance 的调用命中 okx 写的条目」。

`crypto.go:128` 的 providers 是 **fallback 语义**（依次尝试、首个成功即返），不是并列。
同 symbol 无论由哪家返回，都是「crypto 的该标的日线」——**共用一条缓存槽是正确行为，不是串味**。

**它正确地推翻了「三家会并发争锁」，却在替代方案里继续假设「三家是并列的」。**
被推翻的是前提的*结论*，沿用下来的是前提的*模型*。这与教训 9 同形，但更隐蔽：
质疑者通常被认为「已经把这块想清楚了」，其替代方案会被降低审查强度。

### 处置：不补新判据

今天不存在可观测的坏后果 ⇒ **硬造一条只会得到另一条空 criteria**（教训 17 判据）。
改为**文档承载**：discovery 记录「将来若给 `crypto.*` 加 MinInterval，须先为三子源指定
独立 Domain，否则 fallback 链上一家慢会拖住整条链」。

**真实的将来风险用文档承载，不用假测试承载。** 一条永远绿的测试比一条注释更糟——
它占着「已守护」的名分。

## 教训 19：单向判据放过反方向的失效——而且这个错误可以递归发生

TASK-016 的缓存键缺陷（crypto 用 `UnixNano()` ⇒ 生产命中率恒为零）根因是 criteria 只写了
**区分度**（「至少两组不同参数不互相命中」），没写**聚合度**（「相近时间落进同一槽」）。
dev 完全满足了写下来的那半。

### dev-agent-36 归纳的判据

> **只约束一个方向的判据，会放过反方向的失效。写「A 必须能区分 B」时要同时问
> 「什么情况下 A 必须*不*区分」。**

两个方向的失效性质完全不同：

| 方向 | 失效 | 性质 |
|---|---|---|
| 区分度不足 | 不同标的/区间串进同一槽 | **吵闹的错**——返回明显错的数据 |
| 聚合度不足 | 每次调用键都不同，缓存永不命中 | **静默的错**——不报错、不出错数据、**返回值完全正确**，只有生产路径才暴露 |

单测用固定时刻（`time.Unix(1600000000,0)`）永远看不见后者：**固定时刻在 `Truncate` 前后相等**。

### 这个错误递归了一层

test-agent-16 判 TASK-017 rejected 时给了一个「验证过的补丁」，做了 2×2 闭环。
**但它的补丁只断言「亚分钟差异 → 同一槽」**——把 `Truncate(time.Minute)` 改成
`Truncate(time.Hour)`，`base` 与 `base+3s` 仍落在同一小时，**它的断言照样通过**。

它自己发现并更正：

> **我的补丁犯的就是同一个错误，只是发生在更细的一层**——聚合度自身也有两个方向。

**刚刚亲手验证过某条道理的人，在下一步应用它时仍然会漏。** 「知道」与「在新场景里认出」
是两件事。对策不是更用力地记住，而是**把它变成一个必答的提问**：写下任何形如
「X 必须满足 P」的断言后，问「**违反 P 的相反方向是什么，它会不会也通过**」。

## 教训 20：覆盖率数字被当成质量论据，而它恰好由缺陷所在的那行贡献

dev-agent-36 在 TASK-016 的报告里写「我的新代码：`FetchHistory` 90% / `historyKey` **100%**」，
用来论证「缺口都在既有代码，不该扩大范围」——**而 `historyKey` 正是缺陷所在的函数**。

它的自评（值得全文保留）：

> 那个 100% 是我自己写在报告里当作「我的新代码覆盖良好」的证据，用来论证缺口都在既有代码。
> **当时我用它证明的恰恰是一个有缺陷的函数没问题。**
>
> `historyKey` 只有一条 return 语句，任何一次调用都让它 100%。**语句覆盖度量的是「这行被
> 执行过」，而缺陷是「这行算出的值在生产入参下没有该有的性质」——两者根本不在一个维度上。**

### 判据

**覆盖率只能回答「哪些代码没被执行到」，不能回答「被执行到的代码行为是否正确」。**
报覆盖率时限定为前者，不要当作后者的论据。一行 `return fmt.Sprintf(...)` 的 100%
不包含任何关于那个格式串是否正确的信息。

qa-agent-8 的对照说法：**「测试覆盖了那行代码，但没有断言它该有的性质。」**

这条与本 Sprint 的覆盖率口径问题（91.4/87.4/94.4）是**不同的两件事**：那个是「数字量的
不是同一个东西」，这个是「数字量的东西与结论无关」。前者靠注明口径解决，后者靠**不用它
下那个结论**解决。

## 教训 21：把多个独立失效合并归因到自己头上，会抹掉其中的教训

我在 TASK-016 的答复里写「原 criteria 只写了区分度，漏了聚合度——**这是我的缺口**」。
dev-agent-36 反驳：

> 但我读 DoD 时也没问「反方向呢」，而我是**唯一读过 `app.go` 传参、知道 end 来自墙钟的人**
> ——那条信息在我手上，我没把它和缓存键联系起来。**criteria 不全和实现者不追问是两个
> 独立的失效，这次是两个同时发生。**

它说得对。**把两个失效合并成一个记在自己头上，看起来像担责，实际抹掉了一条独立的教训：
手上有 criteria 没有的信息时，那条信息本身就是提问的义务。**

同型的还有本轮 qa-agent-8 的自我修正：它说 baostock「两条都做对了」，实际只查了实现
（缓存键写法 + 错误映射），**没查有没有守护**——「实现对」与「有守护」是两条独立结论，
它把前者的证据当成了后者的。

### 判据

担责时也要分清**几个**失效。「都是我的错」在多 agent 协作里是一种信息损失——
下一个人只会看到一条要防的，而实际有两条。

## 教训 22（机制建议）：反复出现同一个操作坑，说明它不该靠人记

## 教训 23：照搬别包的测试形态，要检查它与本包的**精度单位**是否匹配——失效方式是「测试照样绿」

dev-agent-35 给 eastmoney 补聚合度守护时，照搬了 crypto 的 `TestCacheKeyAggregatesNearbyTimes`
形态（`base` / `+50ms` / `+900ms`）。**U1 变异预期红、实际绿。**

归因不是变异无效，是**测试构造与本包 key 的精度单位不匹配**：eastmoney 的 key 用
`.Unix()`（**秒级**），去掉 `Truncate` 后这三个时刻的 `.Unix()` 仍然相同 ⇒ (a) 照样绿、
变异测不出。改成跨秒偏移（`+3s` / `+15s`）才拿到真红。

它自己点出的那句最要紧：

> baostock 那条我当时用的是 `+3s`，本就跨秒，所以没踩到——**是运气不是判断**。

### 判据

**同一个测试形态换个包就失效，而失效方式是「测试照样绿」。** 照搬时要问：
这个形态依赖的**量纲/精度/边界**在目标包里是什么？crypto 的毫秒偏移能工作，说明它的 key
精度比秒更细；换到秒级 key 的包里，那个偏移落在同一个桶内，断言退化成恒真。

这与教训 19（单向判据）、教训 17（criteria 守的东西消失了）同属一族：
**一段代码「还在」不等于它「还在起作用」**，而三者的载体分别是断言方向、规格前提、
和这里的精度量纲。

## 教训 24：把信息写成注释，就当成这件事完成了

同一次返工中 dev-agent-35 的自我剖析（比 dev-agent-36 的「信息在手上没联系起来」更直接）：

> `FetchHistory` 的注释里我本来就写了「让上层以 `time.Now()` 为 end 的抖动仍能命中同一槽」
> ——**我知道这个行为、还写下来了，却没为它写测试。**
>
> 这不是「信息在手上没联系起来」，是**把信息写成注释就当成完成了**。

**契约教训 5 问的正是「注释描述的是当前巧合还是被守护的契约」——而它自己写的注释就是
那个形态，它在写下的那一刻没有对自己问这句话。**

### 判据（写注释时的自查）

写下任何描述**行为保证**的注释时（「使得…」「保证…」「仍能…」），当场问：
**这句话如果不成立，哪个测试会红？** 答不出 ⇒ 这句注释是一个**未兑现的承诺**，
不是被守护的契约。要么补测试，要么把措辞降级为描述现状（「目前的实现是…」）。

注释是**给人读的意图声明**，测试是**给机器执行的约束**。前者不会阻止任何人破坏它，
而写下它的人往往因为「已经说清楚了」而获得一种虚假的完成感——这次是作者本人在几十个
提交之后被自己那句注释指认。

## 教训 25：「跨包变异不可达」对 Dev 成立、对验证者不成立——这是角色差异不是技术限制

dev-agent-35 在 TASK-017 如实记录了一条验证边界：内置表 `baostock.*` 的
「`MinInterval==0` 且 `Quota==nil`」**无法在本任务内用变异验证**，因为要改 policy 包、
不在本任务 `writes` 内。

test-agent-16 推翻了这个声明的适用范围：

> **那个约束对 Dev 成立，对验证者不成立。** 我首轮的 T6 就是在一次性 worktree 里给
> `baostock.*` 加 `MinInterval: 300ms`，结果**红 `:197` + `:228`**（策略表侧断言 +

### 通则

**Dev 受 `writes` 范围约束（那是防并发冲突的机制），验证者在一次性 worktree 里不受此约束**

免得每个 Dev 都重新声明一次边界、每个验证者都重新试探一次。

## 教训 26：一个缺陷模式的排查，要主动扫到范围封闭，而不是等下一个被发现

缓存键时间精度这个缺口，本 Sprint 是**四次分别发现**的：

| 发现时机 | 包 | 发现者 |
|---|---|---|
| dev 还在 `in_progress` | crypto | qa-agent-8（点状检查） |
| 派验时补 criteria | baostock | test-agent-16（照 DoD 判据变异） |
| 收到「criteria 变了」通知后 grep | eastmoney | dev-agent-35 |
| **同一次 grep 顺手扫出** | **yahoo（已 verified）** | **dev-agent-35** |

第四次是关键：**yahoo 已经通过验收**，按原路径它要么在 Sprint 末尾被发现，要么在生产上
表现为「缓存加了但命中率是零」——**最难归因的一类**（不报错、不出错数据、返回值完全正确，
只有观测 HTTP 请求数才看得见），而 yahoo 是主源。

qa-agent-8 随后主动把**剩下两家**扫完，把范围封闭：

```
用 Truncate(time.Minute).Unix() 的四家 → 全部已处理或在处理
twelvedata client.go:122  Format("2006-01-02")  → 按天，天然不受影响
lixinger（payload 入键）    全部 Format("2006-01-02")  → 同上
```

### 判据

**发现一个缺陷模式时，立刻问「这个模式的完整范围是什么，我能不能一次扫完」。**
可 grep 的特征（这里是 `Truncate(time.Minute).Unix()`）几乎总能一次扫完，成本是一条命令。

对比代价：本 Sprint 为这一个模式走了 **三轮 reject + 一次 review_fix**。若在第一次发现时
（crypto，dev 还在 `in_progress`）就扫全仓，四家可以一次性补齐。

**「查一次的成本远低于它的收益」在这里是可量化的**：一次 grep vs 一个主源上的静默缓存失效
加三轮返工。

### 固化动作（有明确触发条件，不是劝告）

**收到「某条 criteria 新增/变更」的通知时，立刻 grep 该 criteria 约束的代码特征，
扫全部包，不限于自己名下的任务。**

配套限定（dev-agent-35 自己加的，正确）：**grep 只能证明「没有这个特征」，不能证明
「没有这个风险」**——`grep "Truncate(time.Minute).Unix()"` 无命中的包，可能用了别的时间来源。
所以扫完之后仍需对每个「无命中」的包确认它的实际形态（qa-agent-8 做了：查到那两家
用 `Format("2006-01-02")`，比分钟更粗，天然安全）。

## 教训 27：同一类缺陷的不同**强度**需要不同判据——少一条就漏一种

dev-agent-38 在 TASK-018 按要求逐包跑「摘掉映射层」对照时，发现
`TestNonPolicyErrorsUnaffected` 在**四个包、23 个变异里一个都没打中**——完全符合
「占着已守护名分」的形态。它造了新变异 **N-A**（统一 catch **且丢掉原始错误**，
把所有错误压成一句通用文案），四包全部转红，证明它有内容。

关键在于它与既有的 `PassesThrough`（断言返回同一个 error 值、指针相等）**互补而非冗余**：

| 缺陷强度 | Y6/L5/T6（包一层但 `%v` **保留**原文） | N-A（包一层且**丢掉**原文） |
|---|---|---|
| `PassesThrough`（**值**断言） | **红 ✓** | 红 |
| `NonPolicyErrorsUnaffected`（**文本**断言） | **绿 ✗** | **红 ✓** |

**温和形态只有值断言抓得到**（文本被 `%v` 原样带过去了，所以文本断言看不出差别）；
**激进形态文本断言才够**（值已经变了，但值断言在温和形态下已经红过，激进形态它只是重复报警）。

### 判据

判断一条测试是否空转，不能只问「有没有变异打中它」——还要问
**「我造的变异是不是都集中在同一个强度上」**。

一个缺陷通常有强弱谱系：
- **弱**：行为改变但可观测特征大部分保留（包一层、加前缀、换措辞）
- **强**：行为改变且特征丢失（吞掉、压平、替换）

**同一条断言在谱系两端的敏感度可能完全相反。** 覆盖了一端的变异集会让另一端的守护
看起来像空转——而它实际上是唯一能抓住另一端的东西。

### 与教训 19 的关系

教训 19 说「单向判据放过反方向的失效」（区分度 vs 聚合度，是**方向**的两端）。
这一条是**强度**的两端。两者合起来：

> 一条断言的充分性，要在**方向**和**强度**两个坐标上各问一次。

### 附带：tushare 的等价形态更直白

同一变异在 tushare 上让 `40203_无权限` 子用例转红——**它把永久性错误也吞成了
`ErrRateLimited`**，正是「统一 catch 把不同来源压成一类」的直接体现。
**有哨兵错误的包在这里有可测性红利**：能写成正反两面的类型断言
（必须 `Is(ErrRateLimited)`、绝不可 `Is(ErrNoPermission)`），比文本判别强一个量级。

### 教训 23 的更正（test-agent-17 实证推翻了 Leader 的归因，Leader 现跑核实属实）

### 这次更正本身的教训

**我把「A 有效、B 无效」解释成了「A、B 的前提不同」，而真相是「A 从来就没有效过，只是没人验」。**

「同一形态在两个包里表现不同」有两种可能：
1. 两包前提不同（我当时的解释）
2. **它在两处都无效，只是其中一处被变异打过、另一处没有**（真相）

**默认假设应该是 2 而不是 1**——因为 1 需要「另一处确实有效」这个证据，而那正是没人验过的东西。
我从「eastmoney 这条被验出无效」直接推出「crypto 那条有效」，**而后者从未被验证过**。

### test-agent-17 给出的判据比原文准确

> 真正该问的是「**这几个时刻经过键函数之后还是不是不同的值**」——这个能当场验算；
> 「偏移量看起来够不够小」只能靠感觉。

**把判据从「感觉量纲」换成「代入键函数算一遍」。** 后者是可执行的，前者不是。

dev-agent-36 那句「baostock 我用的 `+3s`，是运气不是判断」反过来也成立——

## 教训 28：顺序属性只能靠静态断言，执行属性只能靠运行期断言——互为替代会留缺口

dev-agent-36 在 TASK-019 用一组互补变异实证了这个分工：

| 变异 | AST 静态断言 | 运行期断言 |
|---|---|---|
| **W1** 删掉 `ensurePolicyGate()` 调用 | **红** | **红** |
| **W2** 把调用**挪到**三家 collector 构造之后 | **红** | **绿 ✗** |
| defer/`go` 闭包包裹、恒假 `if`、提前 return 后的死代码 | **绿 ✗** | **红** |

**W2 下运行期测试绿的原因**：`policy.Default()` 最终还是被设上了，运行期观测的是
「闸门带没带配置」，**看不出「collector 快照时闸门还没装」**（陷阱 4：构造函数快照全局单例）。

反过来，AST 只看词法位置，装配被包进 `defer`/恒假 `if` 时它照样判「存在且在前」。

⇒ **把任一条当成另一条的替代都会留缺口。**

### 与教训 19、27 的关系：这是第三个坐标

- 教训 19：**方向**（区分度 ↔ 聚合度）
- 教训 27：**强度**（温和形态 ↔ 激进形态）
- 本条：**机制**（静态 ↔ 运行期）

合起来：**一条断言的充分性，要在方向、强度、机制三个坐标上各问一次。**

### 附带：一个双赢解

本任务原有一个机制陷阱——`cmd/atlas` 覆盖率余量只剩 5 条语句（dev 自己算的，比
test-agent-16 精算的 6 条更严：门禁比的是整数部分），而 **AST 守护一条覆盖率都不产生**
（它解析源码文本、不执行被断言的代码）⇒ 只加 AST 守护会让一个完全正确的实现被门禁 DENY。

处置是要求 `error_handling[0]` 必须是**运行期**测试（实际调用两条 crisis 路径）。结果：
**覆盖率不降反升 74.29% → 75.23%**——救回来的不是省下的语句，而是 `runBacktest` 原本
**0.0% 覆盖**，运行期测试驱动它到 92.3%，净增 16 条覆盖语句。

**这条运行期要求同时满足了陷阱 8（直接观测而非推断）与覆盖率两个约束**，是这类任务的
唯一双赢解——**不放宽门禁，而让本来就该有的证据同时承担两件事**。

## 教训 29：范围封闭的筛选判据要对准**机制**，不是对准**类别**

TASK-019 要求「穷举全部 collector 构造点并反向追溯」。Leader 给的清单**确有遗漏**

但它做的更重要的一件事是**换了筛选判据**：

> 实测相关 7 家、无关 5 家（akshare/fred/edgar/qlib/qlibpit）。

**把无关的列进用例表会产生假红**：`crisis.NewIngestor(fred.New(...), yahoo.New(), st)`
同一行两个构造，**只有后者相关**。

⇒ 穷举时的筛选条件应当直接对准**要防的机制**（这里是「快照全局单例」），而不是对准一个

## 教训 30：DoD 给了明文变异判据时，必须按原文注入——「我验过它会红」与「它满足了判据」是两件事

TASK-016 的聚合度断言是空转的（`+50ms/+900ms` 偏移遇上 `.Unix()` 秒级键）。
dev-agent-36 自查出的根因**比「偏移写小了」深一层**：

> **根因不是我粗心写了毫秒，是我用「自己选的变异」验证过，却不是 DoD 指定的那个。**
>
> 首轮我跑的 D1 是「退回 `UnixNano()`」——粒度放到纳秒，毫秒偏移可见，所以转红了，
> 我据此认为守护成立并写进了 discovery。**但 DoD 规定的是「去掉 `Truncate(time.Minute)`」**，
> 粒度停在 `.Unix()` 的秒级，毫秒偏移不可见。

**两个变异改的是同一行代码，方向却不同**：

| 变异 | 键的粒度 | `+50ms` 偏移可见? |
|---|---|---|
| 退回 `UnixNano()`（dev 自选） | 纳秒 | **可见 ⇒ 转红** |
| 去掉 `Truncate(time.Minute)`（**DoD 原文**） | 秒（`.Unix()` 仍在） | **不可见 ⇒ 不红** |

**这解释了它上一轮为什么那么自信——它确实做了完整的 2×2 闭环，只是闭环的是错的那个变异。**

### 判据

**DoD 写明变异判据时，按原文注入，不用自己认为等价的替代品。**

「破坏时间截断」在人的脑子里是一个概念，落到代码上却有多个具体操作，而**它们对同一条
断言的敏感度可以完全相反**。dev 的原话：

> 「退回 UnixNano」在我脑子里就是「破坏时间截断」的代表，而 DoD 写的是另一个具体操作。

⇒ 变异不是「体现某个意图的任意操作」，而是**一个具体的代码改动**。意图相同的两个改动，
对断言的可见性可能相反。

### 这条与「2×2 闭环」的关系

2×2 闭环（变异 × 有无守护）只能证明**这个变异**被**这条测试**抓到。它**不能**证明：
- 别的等价意图的变异也会被抓到
- 这条测试满足了 DoD 的判据

⇒ **闭环是充分性证明的必要条件，不是充分条件。闭环之前先核对「我注入的是不是 DoD 说的那个」。**

### 教训 30 的推论：一份错的证据链，比没有证据更容易扩散

dev-agent-36 对空断言事件的归因补充（**它主动把主要责任归到自己这边，而这个归因是准确的**）：

> 你的错是「从『eastmoney 那条被验出无效』推出『crypto 那条有效』」——**一次没有验证的推断**；
> 我的错是**先写出了它，还配了一份看起来完备的 2×2 证据**（只是闭环的是我自己选的变异，
> 不是 DoD 指定的那个）。
>
> **你转达时把它当正确参照，正是因为它带着证据链。**

### 传播机制

| 形态 | 下游会怎么做 |
|---|---|
| 无证据的断言 | 下游倾向自己验一遍 |
| **带完整证据链的错误断言** | **下游直接引用**——证据链本身就是「不必重验」的信号 |

Leader 转达 crypto 那条测试作为「正确参照」，正是因为它有 2×2 闭环。**证据链的存在
关闭了下游的怀疑**，于是错误以「已验证」的身份扩散到 eastmoney、baostock、yahoo 四个包。

**能挡住它的只有一件事：下游按 DoD 原文重新注入变异，而不是复用上游的结论。**
本 Sprint 挡住它的是 test-agent-17 在 TASK-016 二轮的独立注入。

### 与「结论对、理由错」的关系（教训 17 自修正节）

那条说的是「结论对但理由错的东西，一切事后检查都会通过」。这条更进一步：
**结论错但证据链完备的东西，会主动阻止事后检查发生**——因为证据链是一个「已经检查过了」的社会信号。

⇒ **引用他人结论时，证据链的完备程度不能降低复验的必要性，只能降低设计成本**
（知道该往哪个方向验）。

### 教训 28 的补充：判定「顺序属性」的变异，注入点必须落在被测场景**确实执行到**的位置

test-agent-16 复现教训 28 那张表时**先是对不上**：它的 X2b（同样是「挪到 ctor 之后」）
**运行期也红了**，与「运行期看不出顺序」的主张矛盾。

**它没有直接报矛盾，而是查了红的归因**——结果是：

> **那次运行期的红是偶然的。** crisis 的测试场景在参数校验处提前返回，**根本走不到被挪后的
> 位置** ⇒ `ensurePolicyGate` 一次都没执行 ⇒ 账本没生成。**红的是可达性/存在性，不是顺序。**

换到确实会执行的注入点（`backtest.go` 的 `ensurePolicyGate()` 从 `:73` 挪到两次 `Register`
之后，`TestBacktestWiresGate` 完整驱动该函数）重验后，主张成立：AST 红 `:182`、运行期 **PASS**。

### 表要补第三行，缺了会让后人以为表是错的

| 变异 | AST 静态 | 运行期 |
|---|---|---|
| W1 删掉调用 | 红（存在性）| 红（闸门没装）|
| **W2 挪到 ctor 之后·落在【可达】位置** | **红（顺序）** | **绿** ← 真正的盲区 |
| **W2 挪到 ctor 之后·落在【不可达】处** | 红（顺序）| **红（偶然）** ← 实为可达性，不是顺序检出 |
| defer / 恒假 `if` / 死代码 | 绿 | 红 |

### 「红得像是好事」——本 Sprint 最隐蔽的一类归因错误

第三行的危险在于**它看起来是好消息**：两边都红 ⇒「守护更强」⇒ 记成检出证据、收工。

**没有人会去质疑一个符合期望的红。** 而本 Sprint 已有的同族实例全都发生在「红」上：
编译失败的红（6 次）、一次改两个性质导致多红一条、连带损害的红（`tushare.FIXED` 让配额
策略丢失）、以及这次的可达性红。

⇒ **判据：拿到预期中的红时，问「它红的是不是我以为的那个原因」。**
「变异存活」会引发怀疑，「变异被检出」不会——所以后者更需要主动核对归因。

**具体到顺序属性**：注入点必须选在被测场景**确实执行到**的位置，否则测的是可达性不是顺序。
验证方法：先确认无变异时该位置被执行（打点/覆盖率），再注入。

## 教训 31：`fmt.Sprintf` 类变异删 verb 不删实参 → vet 报错 → 红的是编译不是行为

dev-agent-35 在 TASK-007 F2 做的反面对照 X1：只删 `end` 的 `%d` 但**保留实参**。

预期的失效是 `%!(EXTRA int64=...)` 让键仍然变化 ⇒ 假的「变异无效」。**实际结果不同但同样要命**：
`go test` 默认跑 vet，报 `format %s has arg ... of wrong type int64` ⇒ **build failed**。

⇒ 那一格显示为**红**，但**红的是编译，不是被测行为**。照着「注入 → 变红 → 闭环」的流程走，
**会把它记成「守护有效」**。

### 判据

**`fmt.Sprintf` 类变异必须 verb 与实参一并删；判据必须看报错内容而非颜色。**

dev-agent-35 的归纳：这与教训 30 是同一件事的两半——**教训 30 管「打的是不是那个靶」
（注入的是不是 DoD 指定的那个改动），这条管「红的是不是那个原因」。**

这也是「编译失败的红」在本 Sprint 的**第七次**，但前六次都是删符号/删导入导致的，
**这次的载体是 vet 而非编译器本身**——`go test` 默认跑 vet 这件事让「格式串与实参不匹配」
从运行期问题升级成了构建期失败。

## 教训 32：自我修正不是可依赖的品质——能复用的只有已经机械化的那部分

Leader 表扬本 Sprint 的自我修正「都发生在结果没问题的时候，不是被后果逼出来的」。
test-agent-16 指出这个观察有**不对称的代价**：

> 这类记录之所以能写出来，是因为**当时恰好多想了一步**。而「多想一步」不是稳定行为——
> 我这次收尾违规就是没多想（事后核实主仓库状态时才发现自己站错了目录）。
>
> 真正能复用的是那些已经变成**机械动作**的部分：四道门、注入前写预期、还原后 md5 校验、
> 基线测量前比对 sha。**它们不需要我多想一步就会执行**——上次门③拦下我 7 个假存活、
> 这次门①②各拦一次，靠的都不是我当时清醒。
>
> 反过来说，`git worktree remove` 该在哪执行这件事**至今没有机械化**（没有 hook、
> 没有 runner 封装），所以它就靠「记得」，而我这次没记得。

### 判据

**「这条纪律是靠机制执行还是靠记得执行」比「这个人会不会自我修正」更能预测下次会不会再犯。**

盘点本 Sprint 拦下错误的东西，两类泾渭分明：

| 靠机制 | 靠记得 |
|---|---|
| 四道门（门③拦下 7 个假存活、门①②各拦一次）| `git worktree remove` 的执行目录 |
| 写通道的 epoch 校验、权限矩阵 | 派验时带对 `verifier`（Leader 只能靠 checkpoint 提醒自己）|
| validator 的 scope 互斥、DAG 校验 | 「消息说的事要落盘」（Leader 本 Sprint 违反三次）|
| `dev_done` 门禁的覆盖率/测试 | 变异注入前核对「打的是不是那个靶」|

**右列每一项在本 Sprint 都至少失手一次，左列没有一项失手。**

⇒ 复盘时该问的不是「谁又忘了」，而是**「这条能不能挪到左列」**。挪不动的（如注入前核对靶子，
本质是判断而非动作），至少要给它一个**会被机制触发的检查点**——比如让报告模板强制要求
「本次注入的具体改动 vs DoD 原文判据」并列写出。

## 教训 33：「一个用例同时服务两个方向」与「一条测试凑合覆盖多条 DoD」的分界

本 Sprint 一路在防后者（复合句 DoD 必须分句取证、每个维度各自独立变异）。TASK-007 F2 出现了
一个**正面**例子，test-agent-16 实证并给出了分界。

### 事实

dev-agent-35 在 F2 的 `/start` 用例上写：

> F1 的「粒度不得放粗」**只变动 end**，start 的 `Truncate` 被放粗到小时**原先无人能抓**。
> 故此处取整分钟偏移。

变异 R3 证实：**只把 `start` 的 `Truncate` 放粗到 Hour（end 不动）→ 红 `:555`(/start)、
不红 `:436`(F1 粒度)** ⇒ 该缺陷在 F2 之前确实无守护。

**这不是 F2 要求的**（F2 只要区分度），是 dev 自己看出来的；而且**偏移量的选择是有意的**——
随便取个不同时刻只能验区分度，**取整分钟偏移才能同时压住粒度放粗**。

### 分界

| | 凑合覆盖（要防的）| 一举两得（正当的）|
|---|---|---|
| 做法 | 一条断言同时挂多条 DoD，靠「都能红」交差 | **先各自独立成格**，再让其中一格的**参数选择**顺带压住另一条 |
| 独立性 | 被牺牲——分不清哪条 DoD 在起作用 | **保留**——R3 只红一格就是证明 |
| 变异后 | 多格同红，归因不明 | 各格只红自己那格 |

**判据：加强是不是通过「参数选择」而非「断言合并」实现的。** 前者不改变断言结构，
每格仍只对自己那条负责；后者把两条判据塞进一个断言，红了不知道是谁红。

### 与「M3/M7 双红照实报」的关系

同一份交付里 dev 也报了「去掉 `end` 会同时红 F2 的 end 格与 F1 的粒度格」，并**拒绝把它
包装成单格命中**。那是**两条测试对同一变异都敏感**（客观事实），与本条的「一格参数选择
顺带压住另一条」是不同的事：前者是重叠，后者是加强。**两者都要照实报，但性质不同。**

## 教训 34：证据充分但支撑关系没写明，等于没有

TASK-007 F2 的验证里，dev-agent-35 自曝了一个取证缺口（harness 只抓 `--- FAIL` 行，
拿不到失败原因，所以「那格红了」不等于「因为计数断言而红」）。

**test-agent-16 的证据其实早就完成了归因**——它的 runner 判红条件是「存在
`<file>_test.go:NN:` 断言行」**并记录行号**，而两条失败路径的行号不同：

```
gate_test.go:551  t.Fatal(err)                  ← 请求出错
gate_test.go:555  t.Errorf("缓存键未区分 ...")   ← 计数断言
```

7 格记的全是 `:555`/`:595`，无一落在 `:551`/`:591`。**归因是完备的。**

**但它当时没把这层含义写出来**——报告里只把行号当「红了」用，没写明「红在断言行而非
Fatal 行」。它的自评：

> **证据充分但支撑关系没写明，等于没有。**

后果是 dev 申报缺口时它无法立刻确认，只能重跑一遍。

### 定位：这条正好落在「靠记得」那一列，而且是同一个人的

它自己指出：**「记录行号」已经机械化了（runner 强制），「说明行号意味着什么」没有。**

⇒ 同一份工作里，**产生证据的动作可以机械化，解释证据的动作往往还是靠记得**——
而读者只能看到解释。**没被解释的证据在协作中不产生价值。**

处置（它给的，一行正则）：把 harness 的 grep 从 `--- FAIL` 换成 `_test\.go:[0-9]+:`，
**这类归因就从右列挪到左列**。

## 机制建议：把「说了 vs 落盘了」的校验扩进 validator

test-agent-16 针对「消息说的事要落盘」（Leader 本 Sprint 违反三次）提的可挪左方案：

> 这一类的共同点是**「说了」与「落盘了」之间没有校验**。而 validator 已经在校验
> 「完成必有产物」了，同类可以扩：**凡 inbox 消息里出现「已改 DoD / 已扩范围 / 已设 floor」

比「记得落盘」可机械化。已进末尾清单。

它的纪律里机械化了。**

## 教训 35：「已经机械化了」本身也会是错觉——harness 的三版演进

dev-agent-35 的失败消息 harness 在本 Sprint 迭代了三版，**每一版都以为已经把归因挪进了
「靠机制」那一列，下一版才发现还差一层**：

| 版本 | 做法 | 归因靠什么 | 何时暴露不足 |
|---|---|---|---|
| **v1** | grep `--- FAIL` | 只知道哪一格红 | TASK-007 F2：**两条失败路径共用一个 FAIL 行**，「那格红了」≠「因为断言而红」 |
| **v2** | `go test -json` 抓失败消息内容 | **靠人读消息** | 本条——**它其实还在右列**，只是把「记得跑对命令」换成了「记得读对消息」 |
| **v3** | 抓**断言行号**（两条失败路径行号天然不同） | 靠比对行号 | test-agent-16 已指出隐患：**行号会随代码变动漂移**，需要自校验 |

dev-agent-35 的自评：**「v2 其实还留在『靠记得』那一列，我当时没看出来。」**

### 判据

**判断一条纪律是否真的挪进了左列，问：执行它时还需不需要一个「人做出正确判断」的步骤？**

- v2 需要（读到消息后要判断这条消息意味着什么）⇒ 仍在右列
- v3 不需要（行号比对是机械的）⇒ 进了左列，**但引入了新的右列项**（行号锚点的维护）

⇒ **机械化往往不是消除「靠记得」，而是把它换到另一个位置。** 每次换位后要重新问一遍

## 教训 39：变异脚本必须用「靶不存在即失败」的替换方式，禁止静默替换

qa-agent-8 做跨包变异（一次注入覆盖八家）时自曝：

> 第一次注入我把缩进写成 3 层 tab（实际是 2 层），`assert` 抛错、**替换没发生**，
> 但我那一轮的 `go test` 照跑，**八包全绿**。
>
> 如果我当时没核对靶就读结果，会得出「所有包都没有守护」——**与真相完全相反的结论，
> 而且是个看起来很有价值的「重大发现」。**

### 为什么这一条比同族的其它条更该被机制化

**失败方向指向「重大发现」。** 本 Sprint 的其它假红/假绿多半让人**低估**问题（守护看起来有效），
这一个让人**高估**——而「我发现了一个大问题」这种结论**没有人会立刻怀疑**，
它会被当作重要产出立刻上报、扩大范围、甚至建任务。

### 救它的是机制不是记性

> 我是靠 `assert old in s` 这行才没翻车——**那是个机制（脚本自己抛错），不是我记得去核对**。
> 若我用的是 `sed`/`perl` 的静默替换（**本 Sprint 我前面几十次变异用的都是这个**），
> 它不会报错，我就直接读到那个全绿了。

### 具体建议（成本一行，可直接机械化）

**变异脚本一律用「靶不存在即失败」的替换方式**——Python `assert old in s`，
或 `perl -0pe` 之后校验 md5 已变更。**禁止静默替换。**

这是本 Sprint「靠记得 → 靠机制」系列里**第一条给出了具体一行改法**的：
教训 32 右列的「变异注入前核对『打的是不是那个靶』」本被判为「本质是判断而非动作、挪不动」，
**而这条证明它挪得动**——把「核对靶命中」从事后判断变成替换动作自身的前置条件。

⇒ 已进「待同步 hooks 清单」。

### 附带：这次跨包变异的产出

同一次注入覆盖八家「错误不写缓存」守护：**yahoo/eastmoney/crypto/baostock/twelvedata/lixinger/policy
七家转红（守护有效，不是空断言）；tushare 31 个用例无一转红**。

**这独立印证了 test-agent-17 横表的结论，但路径不同**——它是「现读」（读代码看有没有那个测试），
qa-agent-8 是实测（注入变异看是否转红）。**同一结论、两种独立方法**，比复述有价值。

## 教训 42：保链/断链的真判据是「下游有无 `errors.Is` 分叉」，而这条判据本身无人守护

dev-agent-35 全仓 grep（非推断）确认的事实：

- 对 collector 哨兵的 `errors.Is` 分叉**全仓只有两处**：`internal/prism/refresh.go:450/:453`，**全是 tushare 的**
- 导出哨兵只有两家：tushare（`ErrRateLimited`/`ErrNoPermission`）、**edgar（`ErrNotUSGAAP`）**

⇒ 真正的因果链是：**下游有 `errors.Is` 分叉 → 必须有哨兵可分 → 必须保链。**
「本包有无哨兵」是**中间产物**，不是判据。

### 这条因果链没有任何东西守着

五家断链是**当前正确**的（下游今天不对它们做分支）。但：

> **若将来有人在 `refresh.go`（或别处）加一句 `errors.Is(err, yahoo.ErrXxx)`，
> 五家的断链设计会让它恒为 false，而没有任何测试会红。**

- 五家现有守护断言的是「policy 哨兵**不得**泄漏」（`errors.Is == false` 是**期望**）
- TASK-021 新加的断言锚的是 `*json.SyntaxError`，**不是本包哨兵**
- **没有一条测试说「本包不导出哨兵，因此下游不得对本包做 `errors.Is` 分支」**

新加分支的人拿到一个**永远走不进去的 case**，症状是「降级没生效」而不是「测试红」。

### 登记措辞（写给下次做接入的人）

> **collector 错误链的口径判据是「下游有无 `errors.Is` 分叉」，不是「本包有无哨兵」。**
> 今天：tushare 有分叉（`refresh.go:450/:453`）⇒ 保链 + 哨兵；其余六家无分叉 ⇒ 断链 + 前缀。
> **新增下游分叉时必须同时把对应 collector 改成保链——二者是一对**；
> 只加分支不改 collector 会得到一个恒为 false 的 case，且无任何测试会红。

### edgar：两条口径第一次给出不同答案的地方

edgar **有哨兵 `ErrNotUSGAAP`、消费者只有它自己的测试（生产代码零处 `errors.Is`）、且未接入 policy**。
今天不受影响，但将来接入时：**按 021 的 DoD 口径（有哨兵 ⇒ 保链）得出「保链」，
按真判据（下游有无分叉）得出「随便，因为没人消费」。**

⇒ 这正是「中间产物被当成判据」的代价——两者在所有现存情形下重合，**只在 edgar 这个
边缘情形上分岔**，而分岔时没人知道该信哪个。

## 教训 43：统计脚本要有独立交叉源，而交叉源本身也可能错

qa-agent-8 在同一轮里**第二次工具误用**：数 crypto 的顶层导出方法时得到 **6**（横表记 2），
已准备报「横表少算了 4 个」；改用 `find -maxdepth 1` 精确重数后是 **2——横表是对的**。
错因是 `grep -rhn` 的 `-r` 与显式文件列表混用，`-h` 又隐去文件名。

**两次误用的共同点**（它自己归纳）：

- **临时脚本没有自校验**，错误以「**看起来很有价值的发现**」形态呈现
- **两次都不是靠警觉救回来的**：第一次靠 `assert old in s` 抛错（**机制**），
  第二次靠**与横表数字对不上而去复核**（**交叉源**）

### 它扩充的建议，以及它自己指出的极限

> **变异脚本要「靶不存在即失败」，统计脚本要有独立交叉源。**
>
> 这次是横表当了交叉源；**如果横表那一格恰好也是错的，两个错误会互相印证成「一致」。**

最后半句是本条真正的价值：**交叉校验的强度取决于两个来源是否真的独立**。
横表与 qa 的计数都源自「读同一份源码」，只是工具不同——**工具独立不等于来源独立**。
真正独立的交叉源应当来自不同的证据类型（如：读代码 vs 跑变异，本 Sprint 在 tushare 缺口上
恰好做到了——test-agent-17 现读、qa-agent-8 实测）。

### 教训 40 的订正：判据是纯机械的，不该留在人这一侧

原文写的处置是「声明 `packages` 时**问一句**『这个路径下有没有子包』」。
**dev-agent-35 指出那还在右列**，而判据是纯结构性的（`go list` 一跑就知道），
**没有理由留在人这一侧**。

它顺手机械化跑了全 Sprint，**crypto 不是孤例，有三处，而且最大的那处不是它**：

```
./internal/collector        → ./internal/collector/... 含 17 个包（少覆盖 16 个）
./internal/collector/crypto → 含 4 个包（少覆盖 3 个）
./internal/prism            → 含 2 个包（少覆盖 1 个）
```

**`./internal/collector` 是 TASK-011（删 CachedCollector）、012（路由表重写）、
013（防回潮 AST）三个任务共同声明的** ⇒ 那三个任务的门禁只测了 `internal/collector`
这一个包本身，**akshare / edgar / fred / qlib / qlibpit / policy 以及全部七家 collector
都在门禁视野之外**。

dev-agent-35 的自陈（TASK-011 是它做的）：

> **我删的是被所有 collector 引用的装饰器，而门禁一个 collector 都没测到。**
> 当时是靠我自己跑了全量 `go build ./...` 和相关包测试才没出事，**不是靠门禁**。
> 这比 crypto 那处严重：crypto 少测的是三个 provider 实现，**这里少测的是变更的全部下游**。

结果上没出问题——三个任务都 verified 且后续无回潮，**但那是因为改动被验证者独立复核过，
不是因为门禁挡住了**。

### 可机械化的检查（warn 而非 block）

```bash
n=$(go list "$p/..." | wc -l)
[ "$n" -gt 1 ] && warn "$p 下还有 $((n-1)) 个子包未纳入门禁范围；确认是有意的还是漏了 /..."
```

**做成 warn 的理由**：有时只改父包确实不需要测子包，**关键是让「我选了 `./x` 而不是
`./x/...`」变成一个被显式确认过的决定，而不是一个从未被想起的默认。**

### 与教训 41 的连接

「沉默的排除等于没有排除」在这里有个变体：**裸路径 `./x` 在文本上无法区分
「有意只测父包」与「忘了写 `/...`」**——与 tushare 那次「没提到 vs 考虑过并判定不适用」
是同一个形状。⇒ **warn 的价值不在拦截，在强制产生一条可对照的记录。**

已进「待同步 hooks 清单」。

## 教训 44：纯函数守护与行为守护是两个对象

TASK-020 的缺口，dev-agent-38 定位得比 DoD 更精确：

> 既有 `TestCallKeyDistinguishesParams` 是 **`callKey` 的纯函数断言**，不走 Fetch 路径。
> 所以把**调用点**换成固定串时它当然不红——`callKey` 本身没动。
>
> ⇒ **缺的不是「`callKey` 会区分」，是「缓存槽真的用了 `callKey` 的输出」。**

**一个函数有单测、单测有效、而它的输出有没有被真正使用，是另一个命题。** tushare 这处
三样俱全（纯函数断言 200 次防 map 顺序抖动、聚合度行为断言、覆盖率达标），**唯独没人验
「行为侧真的用了它」**。

这与教训 20（覆盖率数字被当成质量论据）同族但更深一层：那条说「执行过 ≠ 行为正确」，
这条说 **「函数正确 ≠ 它的正确性被用上了」**。

⇒ **判据：为一个纯函数写守护时，问一句「谁在用它的返回值，那条路径上有守护吗」。**

## 教训 45：陷阱 10（判定顺序）不是并发测试专属

dev-agent-38 首版 `TestBusinessErrorIsNotCached` 把「每次调用都应报错」写在 `hits()`
断言**之前**。E1 变异下确实转红，**但消息是「第 1 次调用应返回业务错误——本轮未构成检验」**
——**缺陷伪装成了测试构造失败，方向指反。**

调整顺序后消息变成「HTTP 请求 1 次, want 2——业务错误被写进了缓存槽」+
「静默返回了成功……上层会当作『该标的今天没数据』并可能落库」。

它的推广（本 Sprint 一直误以为陷阱 10 是并发测试专属）：

> **任何「有效性判定 + 行为断言」并存的测试都可能踩。**

⇒ **判据：测试里若同时存在「本轮实验是否有效」与「被测行为是否正确」两类断言，
被测行为那类必须在前。** 否则缺陷会先撞上有效性判定，报出一个指向测试自身的错误消息。

| **E1** 保留错误语义、只改缓存行为 | **红** | 这才是「错误被缓存」 |
| **E2** 停用 `if env.Code == 40203`（验证者首版） | **绿** | 40203 落到 `env.Code != 0` 分支后**仍然产生错误**，**缓存行为一字未变** |

**E2 不该红，而它绿了** ⇒ 证明新测试在区分「错误被缓存」与「错误类型改变」，
**不是对任何改动都红**。

**正反对照比单向证据强**：单看 E1 红只能说明「这条测试对某个改动敏感」，
E2 绿才排除了「它对什么都敏感」。qa-agent-8 当时看到 5 条转红就采信，
**那些红是「错误类型变了」**——它自己也自报了这次归因错误。

## 教训 46：「拿刚写下的规则跑一遍」不是品质，是判据机械性的副产品——错的自我归因也会扩散

Leader 把 dev-agent-35 连续三次「拿刚写下的规则去跑一遍现有的东西」（教训 40 判据跑出三处、
criteria 变更通知 grep 出第四家、021 横向列平抓出 yahoo 三处调用点）记成一种谨慎品质。
**它拒绝了这个归因，理由比归因本身重要**：

> **那三条规则本来就都是机械判据**（`go list` 数子包 / grep 一个字符串 / 逐家过同一组固定问题），
> 跑一遍几乎零成本。所以「跑一遍」不是谨慎，**是不跑才反常**。
>
> **真正该记的是反面**：当一条规则的判据**不是**机械的时候，**我就没有跑过它**。
> 比如「逐包现读判据不要照搬」——我是靠读代码确认的，**那次若读漏了，没有任何东西会提醒我。**

### 它给的判据

> **先问「这条规则能不能被立刻跑一遍」。能 ⇒ 立刻跑，那是默认动作不是加分项；
> 不能 ⇒ 那才是需要额外警觉的地方，而它恰恰长得像「已经确认过了」。**

**三次命中划出的是边界，不是能力。**

### 记错的代价

> 记成品质的代价是：**下次的人会去模仿一个不存在的能力，而真正该警觉的那一侧反而没人看。**
>
> 这和我坚持把「拦住转用建议」记成运气是同一件事——**错的自我归因也会扩散，
> 而且没有任何变异能打中它。**

**最后半句是本 Sprint 关于自我记录的收束**：代码里的错误结论会被测试打中，
契约里的错误结论可以靠「拿一条核另一条」发现（qa-agent-8 做过），
**而「我为什么做对了」这类归因，两种手段都够不着**——它既不产生可执行断言，
也不与其它条目直接矛盾。**唯一的检查是当事人自己拒绝一个过誉的解释。**

本 Sprint 出现三次：test-agent-16 拒绝「自我修正是可依赖的品质」、
dev-agent-35 拒绝「有意的机制运用」、以及本条。

### 附：一条契约归属订正

契约里「照搬形态时要检查精度单位」（教训 23）现在读起来像是 dev-agent-35 的经验，
**实际是 Leader 提前写进 TASK-007 `fix_items` 的 trap**，它照做而已。**它主动指出了这点。**

## 教训 47：「我论证过它正确」不等于「它被验证过」，而两者在报告里长得一模一样

dev-agent-35 留在 wisdom 末尾的一句，也是本 Sprint 多次实例的共同形态：

- TASK-007 F2 的 9 格「太顺了，我就没往下追一层」——**有论证（变异只改 cache key 字符串，
  构造不出 HTTP 错误），但那是论证不是观察**
- 教训 23 的原始版本——Leader 从「eastmoney 那条被验出无效」**推出**「crypto 那条有效」，
  而后者从未被验证
- 横表 §③ 的「结构性接不了」——**观察到了 yahoo 的解法、写下了机制，结论却是推的**

**判据（它自己的做法）**：M8/M9 是它唯一一次**在跑之前就写下推翻条件**。

> 它有价值不是因为结果证明我对了，**而是因为如果我错了，那句话会逼我改口**——
> 没有那句话，我会去找一个解释保住结论。

⇒ **报告里把「我论证过」与「我验证过」分开写**；对前者，**在跑之前先写下「什么结果会推翻它」**。

## 教训 48：按命名/结构模式批量定位的检查，必须核对「命中数 == 预期数」

qa-agent-8 验「链保留」列时用 `grep 'func.*mapPolicyErr'` 定位六家的 default 分支，
**crypto 没被匹配到**——它是**内联**结构（`crypto.go:159-162` 直接写在 `FetchHistory` 里），
没有独立的 `mapPolicyError` 函数。

按纪律它把那格记为「**未测**」而不是顺手推断，读实际结构后单独补做，转红。

### 为什么这条比同批前三次更值得记

它自己的话：

> 这次是 6 家里命中 5 家，**差值可见**；如果是 **20 家里命中 19 家，我大概率不会注意到**。
>
> 这一条比前三次更值得进契约，因为**它的失效不产生任何错误信号——未命中的那一格
> 只是静默不出现在结果里。**

前三次（变异靶缩进不符、计数 grep 误用、靶文本匹配非语法匹配）都有可察觉的异常：
`assert` 抛错、数字与交叉源对不上、命中数与另一次不一致。**这一次什么都没有**——
结果表看起来完整，只是少了一行。

### 与本 Sprint 另一次的同源关系

qa-agent-8 第一轮漏掉 crisis 装配缺口，机制相同：**`resolveFREDKey` 没有遵循
「命令入口调 `loadConfigOrDefaults`」的模式**，而它是按那个模式找的。

⇒ **判据：凡按命名/结构模式批量定位，先写下「我预期命中几个」，再核对实际命中数。**
差值不为零时，缺的那些**恰恰是最可能有问题的**——因为它们偏离了主流模式。

### 附：横表的实测格与推断格可靠性不同（qa-agent-8 归纳，写入 final-report）

> 横表维度四标 ✓ 的格子，我实测过的部分**无一虚标**——这与横表 §③ 推断出错形成对照：

## 教训 49：让缺席可见——变异记录要能反查，而不只是流水

dev-agent-38 在 TASK-018 找出 `TestNonPolicyErrorsUnaffected` **23 个变异一个都没打中**
（后来演化成契约的「方向/强度/机制」三坐标）。**它自己说明了那不是洞察**：

> **不是洞察，是列表格的副产品。** 我给 discovery 写 verification 时把「变异 → 转红的测试」
> 逐条列出来，那条从头到尾没出现过。**空行不是我找出来的，是一旦排成矩阵它就自己显形了。**

### 判据

> **变异记录不要只写成流水（「Y1 → 红了 X」），要能反查（「X 被哪些变异打中」）。**
> 流水形式下「某条测试从没上榜」需要你记得所有条目才能发现，**而缺席恰恰最难被记起。**

### 它给的连接

> 这与「缺席型故障不会举手」是同一件事的两个场合——**没做的事不会提醒你，没红过的测试也不会，
> 对策都是换一种让缺席可见的表示法。**

**本 Sprint 的「缺席」清单**（全部靠改变表示法或机制才可见，无一靠记性）：
教训 48 的「未命中的格子静默不出现」、教训 40 的「裸路径 `./x` 与 `./x/...` 在文本上无差别」、
教训 41 的「沉默的排除等于没有排除」、本条的「从没上榜的测试」。

## 教训 50：E1/E2 正反对照的来源——「对某个改动敏感」≠「只对该改动敏感」

dev-agent-38 给出 E1 红 / E2 绿对照时的实际推理：

> 当时我盯着 E1 的红，冒出来的疑问是——**这条红只说明我的测试「对某个改动敏感」，
> 没说明它「只对该改动敏感」。一条把 `hits()` 写成 `!= 0` 的烂测试在 E1 下同样会红。**

⇒ **判据：拿到一个红之后，问「有没有一个改动是它本该【不】红的」，跑一个，
绿了才排除「对什么都敏感」。**

它自己点出这与契约里「探针 2×2 的右下格」同源：**都是用一个本该是另一种结果的格子，
去证明判据有分辨率。**

### 附：两处它主动标出的「这不是我的经验」

- **E2 那个错误变异形态不是它发现的**——DoD 里已写明（test-agent-17 自报、Leader 落盘）。
  **按字面执行只需避开 E2 就够了，它多做的一步是把那条「不要这么做」的警告当成负对照去跑。**
- **它起疑 `NonPolicyErrorsUnaffected` 的触发时机，一半来自 Leader 的放行条件②**
  （「逐包单独跑摘掉映射层的对照」）——**没有那个条件，它大概率不会回头重读已写完的变异记录。**

### 教训 46 的前提限定（dev-agent-38 补，不标出来这条会变成推责工具）

Leader 曾接受「**兜底失效不能算到本来就可能失效的那一层头上**」而收回自己揽的责任。
**dev-agent-38 指出这条有一个必须写明的前提**：

> 「B 为 A 的失效而设计」这个兜底关系**必须是被显式声明的**。这次成立**仅仅因为协议
> 白纸黑字写了那句话**（「即使通知丢失，各角色通过轮询自己负责的状态也能发现待办」）

推给下游：「你本来就该检查」。**判据：指出兜底关系时，附上它被声明的位置。**
