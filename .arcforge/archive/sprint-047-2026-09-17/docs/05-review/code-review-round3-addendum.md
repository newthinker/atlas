## 一、P3 变异存活仍判 PASS：结果维持，但「验收线只要求一条测试」这个自辩不成立

### 它的自辩与 Leader 的补充

验证者：「我上轮给的验收线只要求了那一条已存在的测试，拿我没提过的要求去否决按我要求做完的交付不公平。」
Leader 补充：那条验收线（路线 A 三步）是验证者写的、Leader 原样转给 dev 的，
「如果验收线本身定得太松，那是我和它共同的责任，不是 dev 的」。

### 我读了验收线原文，发现问题不在「松」，在「实现结构变了而测试数没跟着变」

路线 A 第 ② 步原文（`TASK-006.json:97`）：

> 给跳过加一个可观测出口：在 `Push` 层的 `Result` 加一个字段，
> **由 `Push` 比对「期望格数 `len(rows)×len(cols)`」与实际产出得出**，这样 `Diff` 的签名不用动。

第 ③ 步原文：

> 补一条测试：越界行进入 `Push` ⇒ `Result` 里能看到它被跳过了。

**注意 ② 描述的实现结构是「由 `Push` 比对期望与实际」——那是一个单点比对。**
照字面实现，`Push` 末尾比一次 `len(rows)×len(cols)` 与 `len(res.Changes)`，
**只有一条路径，一条测试就足够覆盖**，也就根本不会出现「第二条路径无守卫」。

而 dev 实际实现的是：`diffTab` 返回 `dropped`，`Push` 在**两处**累加（`push.go:183` 与 `:203`）。
这个实现**偏离了验收线描述的结构**，并因此引入了两条独立路径。

⇒ **「验收线只要求一条测试」这个自辩不成立。** 验收线要求一条测试，是因为它描述的实现只有一条路径。
实现改成两条路径之后，「一条测试」这个数字不再等价于「覆盖验收线要求的性质」。
**测试数应当跟着实现的分支数走，不跟着验收线的字面数走。**

### 但结论仍是 PASS，理由与它给的不同

1. **dev 的实现比验收线描述的更好。** 逐张表累加能保留「哪张表丢了格」的信息，
   单点比对只能给一个总数。因为实现得更细致而被要求更多测试、却没有人在验收时告诉它——
   这不该由 dev 承担。
2. dev 按要求做了越界申报（`push.go` 已在 `writes` 里，我核过）。
3. 生产路径够不到（`periodYearMonth` 的 1–12 校验，我在 round3 正文核过）。

### 这一条真正的可复用产出

不是「验收线定得太松」，而是一条判据：

> **验收时要问的是「这个实现有几条路径」，不是「验收线要求几条测试」。**
> 当交付的实现结构偏离了验收线描述的结构时，验收线里的数字就失效了，
> 而**偏离往往是朝更好的方向**——所以这不是「dev 没照做」，是验收线的数字失去了锚。

这条比「太松」更有用，因为「太松」的处方是「下次写严一点」，而它的处方是
「**看实现，不看验收线的计数**」——后者可执行。

⇒ **责任归属**：不在 dev。验证者与 Leader 共同写下的验收线在实现结构变化后失去了等价性，
而验收时没有人重新数路径。这是流程问题，不是任何一方的判断失误。

## 二、TASK-009 不必重验：结果维持，我把它的依据从「人工补位」换成结构事实

### 它的自述薄弱处

「『逐条』的完整性取决于我读 `done_criteria` 读全了没——这是人工补位，没有机制兜底。」

### 我的核实让这条不再完全依赖人

本轮 006 对 `cmd/atlas/` 的 numstat（`git show --numstat 8f386a4 -- cmd/atlas/`）：

```
9   0   cmd/atlas/hestia_sheets.go
13  0   cmd/atlas/hestia_sheets_test.go
```

**删除列全 0，纯追加。** 而 009 的 `done_criteria` 共 7 条，`verify_by` 分布我逐条查了：

| 类别 | 条数 | verify_by |
|---|---|---|
| functional | 3 | 全 `test` |
| boundary | 1 | `test` |
| error_handling | 2 | 全 `test` |
| non_functional | 1 | `manual` |

⇒ **6 / 7 条由测试守着，而纯追加保证这 6 条的守卫一条没少、都还在跑。**
这部分**不依赖任何人读没读全**，是结构事实。

**第 7 条（`manual`）确实不受纯追加保护**，需要单独看。我看了：它是 gofmt / vet / 覆盖率 / simplifier 这类。
纯追加不会降低覆盖率；新增的 22 行若格式不对，`gofmt -l` 会报——我实测 `cmd/atlas` 的 gofmt 违规
只有两个文件，都不是 006 本轮碰过的（见第三节）。⇒ **第 7 条本次也安全，但这一步确实需要人看。**

⇒ **精确结论**：这次的绿是 **6/7 由结构保证 + 1/7 由人工核**，不是它自评的「全靠人工补位」。
它对自己的判断过于严厉了。而我在 round3 正文里说的「不完全是人工补位」，这里给出了精确的分子分母。

**机制建议不变**（round3 正文第二节③）：越界申报时按 numstat 删除列分流——非 0 才要求逐条复核，
为 0 时只需核 `verify_by != test` 的那几条。这正好对应 6/7 与 1/7 的分界。

## 三、两个 gofmt 违规不计入判定：结果维持，但我找到了比它三条依据都直接的理由

### 它给的三条依据我逐条核过，全部属实

| 依据 | 我的求证 |
|---|---|
| 本轮未改 | `git diff --stat 6297fee..HEAD -- cmd/atlas/backtest_test.go cmd/atlas/crisis_test.go` ⇒ **空输出** |
| 上一基线上已存在 | `git show 6297fee:cmd/atlas/<f>` 取出旧版跑 `gofmt -l` ⇒ **两个文件在 sprint 起点就违规** |
| 不在 006 的 `writes` 内 | `jq .writes` ⇒ 12 项，均不含这两个文件 |

### 但最强的理由它没说：DoD 那句话自己就带了范围限定

006 的 `non_functional` DoD 原文（`jq -r '.done_criteria.non_functional[]'`）：

> `go test ./internal/hestia/... -count=1` 全绿、`gofmt`/`go vet` 零输出

**范围写在句子里：`./internal/hestia/...`。** 而那两个违规文件在 `cmd/atlas`，
**本来就不在这条 DoD 的射程内**——不需要「本轮未改」「不在 writes 里」这些外部理由来豁免它们。

### 「声明了就该管」这个读法没有文本依据

Leader 转述的另一个读法是「它们现在落在 006 的 `packages` 口径里，声明了就该管」。
我查了两处，这个读法不成立：

1. **DoD 写的是一条具体命令的范围**（`./internal/hestia/...`），不是「`packages` 里的所有包」。
2. **门禁根本不跑 gofmt**：`grep -rn "gofmt" .claude/hooks/` ⇒ **0 命中**（全部 hooks）。
   ⇒ 不存在「`packages` 口径的 gofmt 检查」这回事，`packages` 按 CLAUDE.md 的定义是
   **覆盖率口径**，消费点只有 `go test` / `-coverpkg`。

⇒ **判定：不计入，成立。** 但理由应当是「DoD 自带范围限定」，而不是那三条。
这个区别要紧：那三条是**豁免理由**（东西在射程内但可以放过），
而 DoD 的范围限定说明**它压根不在射程内**。前者需要每次重新论证，后者一次读懂即可。

### 附带记一条小漂移（不阻断，无人有责）

006 的 `packages` 后来加了 `./cmd/atlas`（fix 轮改了那里的文件，是对的），
而 DoD 文本写于最初、范围仍是 `./internal/hestia/...`，两者没有同步。
**这是机制约束下的必然**——DoD 文本在任务进 `in_progress` 之后 Leader 就改不了。
记一笔只为说明：**`packages` 扩大时，DoD 里那些自带范围的句子不会跟着扩大**，
下次读它们的人要知道这两个范围可能不一致。

## 五、🔴 我给这 0.2pp 的成因是错的（Leader 更正，我已独立复证）

**我原写的成因是「采样时点早于最后一个 commit」。那是错的。**

Leader 指出真相是**两把尺**，我实测复证（同一棵树、同一次测试运行、同一份 profile）：

| 工具 | 得数 |
|---|---|
| `go test ./cmd/atlas/ -count=1 -cover` | **78.0%** |
| `go tool cover -func=<同一份 profile>` | **78.2%** |

带不带 `-coverpkg` 都一样分岔。**门禁用的是后者**——`task-completed.sh:477` 是
`TOTAL=$(go tool cover -func="$COVERPROFILE" …)`，我读了那一行。

**为什么这个订正比数字本身重要（Leader 的话，我认同）**：
我的理由若成立，处方是「重采一次」；真相成立，处方是「换尺」。
**前者不会让下一轮避免同一个错。** 这与本 sprint 归档里「结论对但理由错」是同族，
但方向相反——那条讲的是结论对而理由错时理由无人复查，这条讲的是**理由错会导出一个无效的处方**。

### 我在复证时多查到的两件事

**① 逐块求和站在 78.0 那边，门禁那把尺是三把里的少数派。**

我从 profile 文件直接逐块加权求和（第三把尺）：

```
总语句数 1551，被覆盖 1210 ⇒ 1210/1551 = 78.0142% ⇒ 78.0%
```

与 `go test -cover` 一致。⇒ **`go tool cover -func` 的 total 与「profile 全部块的语句加权」不等**，
说明它的分母不是全部 profile 块。

⚠️ **这不意味着门禁那把尺「不准」**——门禁是判定者，它用哪把，哪把就是权威值。
但理解上要分清：**78.2% 是「有权的数」，不是「更准的数」。**

**② 0.2pp 的确切算法来源我没查实，此处不编一个。**

我验证过的：`cover -func` 列出 125 个函数（输出 126 行，125 函数 + 1 行 total，我数过），
profile 有 989 个块覆盖 19 个文件；函数百分比的算术平均是 86.4%，**所以 total 不是算术平均**。
一个未经证实的假设是「profile 里不属于任何函数体的块被 `-func` 忽略，而它们覆盖率偏低」，
方向与观察一致（去掉低覆盖块会让 total 升高），**但我没有直接证据，故记为成因未定**。

⇒ **可执行的结论不依赖这个成因**：报覆盖率一律用门禁那把尺
（`go tool cover -func` 读 profile 取 total 行），不要用 `go test -cover` 的行内百分比。

### 为什么这把坏尺能活到收尾

四个包里**只有 `cmd/atlas` 一个分岔**（其余三个两把尺同值，Leader 测过我也测过）。
⇒ **三个包同值让它一路活到了收尾**——这正是本 sprint 归档里记过的那条：
**一个仪器在粗粒度下给出正确答案，恰恰是它能活到关键时刻的原因。**
（同族先例：我在归档 sprint 里用「数斜杠」判层级，在只分两层时完全正确，只在更细的粒度上才坏。）
