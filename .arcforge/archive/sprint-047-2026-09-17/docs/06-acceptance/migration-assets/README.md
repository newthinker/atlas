## 🔴 使用前必读：移植前先验那份夹具本身

test-m2b-b 的原话（008 返工复验，被验方指出它首验夹具有缺陷之后）：

> **移植前先验那份夹具本身。移植是把验证者的判据固化进交付，而那一刻没有任何人站在验证者的位置上。**

**实例就在本清单里。** `TASK-008-fixture.go.txt` 的 N7 夹具给出 `{说明:10, 2024年:777, 2026年:12}`，
于是 `maxID` 与 `tplID` **都是 777**，「由最大 id 推新 id」与「由模板 id 推新 id」两个算法
**构造上不可能分叉**。对照实验（两位验证者独立各做一次，结论一致）：

| 变异 | dev 改写后的夹具（10/777/9000） | 本清单里的旧夹具（10/777/12） |
| --- | --- | --- |
| `newID := tplID + 1` | KILLED | 🔴 **不红** |
| `newID := maxID` | KILLED | KILLED |

test-m2b-b 自己的结论：**「我首验判 N7 KILLED 是运气不是设计」**——它恰好选了那个在自己夹具下
也能分叉的变异。

⇒ **规则：本清单里每条夹具，接收方必须先在原实现 + 对应变异上各跑一次再抄。**

| 1 | `v.count("**已实现**（2026-09-17）")` 得 4 而非 3 —— 第 4 处是**「粘贴后自查」清单里引用这个字符串本身** | **「这个字符串出现了」与「这个字符串被用作标记」取相同值** |

## 🔴 第 14 个：`dev-m2b-c-mutate.sh` —— 三条闸，每条都来自一次实撞

**① 工作树非干净则拒绝执行。** 立项依据是 dev 自曝的一次事故，**而且是同一个坑的第二次**：
变异 helper 里的 `git checkout -q -- .` 做还原，那一轮它还没提交 ⇒ 第一个变异跑完就把自己
未提交的实现连同测试一起冲回了 master 状态。

它第 1 轮就把这条写进了 checkpoint，然后又犯了一次。自评：
**「我知道那条规则，但触发它的时机不在我当时的注意力里。」**

⇒ 它选的改法不是换 `git stash`，而是**加一条会拒绝执行的前置守卫**，理由是
**「把『必须先提交』这条前置条件变成机制而不是记忆」**。
⚠️ leader 补的边界：**守卫防的是「工作树非干净」，不是「我忘了提交」**
——两者这次是同一件事，下次可能不是（比如故意留一处未提交的探针去跑变异），
所以文案必须是**拒绝跑**、不是自动提交。

**它两个方向都自测过**：脏树被拒、干净树放行。它的理由值得抄：
**只测拒绝那一半的话，一个「永远拒绝」的实现同样能通过。**
⇒ 这与它这轮给 `DroppedCells` 配反空洞对照是同一条，也与本 README 开头那条
「移植前先验那份夹具本身」同源。

**②③ 两条打印防止把「变异没生效」误记成 KILLED**：

```
${desc} ⇒ ⚠ 编译闸命中，变异无效（**不是 KILLED**）
${desc} ⇒ （无测试变红 —— SURVIVED，不是 KILLED）
```

对应项目文档里那条「**外溢闸命中即早退，不得继续打印 KILLED**」。
本 sprint 两位 agent 各撞过一次同形事件（dev 的 M-D 第一版补丁触发编译闸；
006 验证者的 MH 锚点命中 0 次被判跳过），**闸的价值正在于被弃的运行不进表**。

⇒ **新写变异 harness 建议从这个文件起步**，而不是从零写——三条闸都是实撞换来的。

### 🔴 该 harness 的两次修订（都由它自己的双向自测逼出来）

**修订一：把「防什么」写死，堵住一个会把它改坏的「优化」。**

> 它防的是「工作树非干净」，**不是「我忘了提交」——这两件事只是在立项那次恰好重合。**
> 下次可能不重合：比如故意留一处未提交的探针去跑变异（dev 在 TASK-010 就那么干过一次，
> 用临时 test 文件探真实配置的装载行为）。那种情况下**「自动提交」会把探针一起提交进去**，
> **比冲掉工作更坏——它是静默地把不该进仓库的东西放进去。**
> ⇒ **任何把它「优化」成自动 commit / 自动 stash 的改动都是错的。**

**修订二：双向自测当场照出一个「看起来像守卫失效」的用法陷阱。**

改完重跑自测，**干净树那一半报「被误拒」**。查下来不是守卫坏了，而是
`FILES=${MUT_FILES:-.}` 在 **source 那一刻**就固化了——`MUT_FILES` 是 source 之后才设的，
于是它拿整棵树判脏。已改成函数内求值（`files() { echo "${MUT_FILES:-.}"; }`）。

🔴 **那一刻它看起来像守卫失效，而下一个人多半会得出同样的错误结论然后删掉它。**

⚠️ **这次反空洞对照抓到的不是「守卫恒真」，而是「守卫可用性」**：
脏树那一半一直是对的，**是干净树那一半把陷阱照出来的**。
⇒ **双向自测的第二个理由**：除了排除「永远拒绝」的实现，它还会暴露「守卫本身不好用」。

### dev 从这件事里取的判别式

> **写完一个防护措施，问一句「它和它要防的东西，谁活得更久」。答「它更短命」就等于没做。**

立项依据是它自己的自评：**写守卫是为了把纪律变成机制，却把机制放进了一个会随 session
蒸发的目录——等于给「提醒」换了个更精致的外壳。**
