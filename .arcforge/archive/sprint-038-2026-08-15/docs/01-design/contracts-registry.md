## C. 实现陷阱（下游照抄会踩）

**C1｜列表项正则不能写 `[^>]*title="`**（实测，dev-agent-55 在 TASK-001 发现）
`[^>]*` 会**贪进 `istitle="true"`**，捕获组拿到字面量 `true`（p146 上 15 条全部如此）。
🔴 **危险在于条数一条不少、日期一天不差 ⇒ 计数守卫接不住它**，表现为整页静默产出 0 篇报告。
正确写法 `[^>]*?\stitle="`（`\s` 让 `title=` 必须以空白开头，而 `istitle=` 里 `title` 前是 `s`，结构上落不进去）。

**C2｜搜索侧筛选判据只能是栏目前缀，不能是 article_id 形态**（实测，dev-agent-57 在 TASK-004 纠正 Leader）
6 条 `/diaochatongjisi/` 里只有 **2 条**是 32 位 hex，另 **4 条是 19 位纯数字、与 goutongjiaoliu 侧完全撞形**。
按 id 形态筛会让交叉校验的差集**凭空多出 4 条假信号**。
⚠️ Leader 原先据**第 1 页前 4 条**概括成「32 位 hex」——「用样本形状当契约」，与 `discover.go` 里那个 `\d{14,}` 同一形状。
**成因是结构性的**：id 形态按站点重建时间分层，而搜索结果按发布时间倒序 ⇒ **第 1 页前几条必然全是新形态**。

**C3｜「穷举证明了不可构造」——穷举的**范围**才是结论的作用域**（实测三轮，TASK-009；⚠️ **缺口已闭合，本条留的是方法学教训**）

**结论先说：`runBackfill` 的 6 条写盘路径现在 6/6 KILLED**（TASK-006 时 1/6）。本条不是「已知缺口」，是记录**它一度被判定为「不可能补」的全过程**。

**第一轮**：dev 跑探针穷举 —— `manifest.json` 预置为只读文件 ⇒ `rename` 覆盖照样成功；预置为目录 ⇒ `loadManifest` 就返回。结论「**没有中间态**」⇒ 要隔离必须改 `backfill_manifest.go` 给生产代码加注入点。**Leader 采信，据此裁决「不扩 scope」两次，并把它写成了本条的原始版本。**

**第二轮**：验证者 **15 行做出来了**，只用 `backfill_fetch_test.go`：
`runBackfill(ctx, f Fetcher, …)` 的 **`Fetcher` 本来就是注入点**，且同一文件每个用例都在用它。让 fake 在**被问到文章 URL 那一刻** `os.Chmod(out, 0o555)` 再返回错误 ⇒ 首次 `store.Save()` 已成功，循环内 `AppendFailed` 那次必然失败。

```
第四格：跑前     os.Chmod(out, 0555)
第五格：跑到一半 os.Chmod(out, 0555)   ← 差别只有这四个字
```

**第三轮（闭合）**：dev 补上第五格，`backfill_fetch.go` **零改动**，A20 **KILLED**、且**只红第五格**。

🔴 **两个被消融推翻的判断，都不是「不够仔细」**：
1. **「没有中间态」** —— dev 只穷举了**静态预置条件**这一类。在那一类里结论成立，**写成一般命题就错了**。
2. **「A19 与 A20 是同一失败模式、第四格已覆盖」** —— dev 提出、**Leader 采信并写进裁决理由**。消融打脸：**A19 只红第四格、A20 只红第五格，各自唯一命中** ⇒ 是**两个可分辨的失效**，不是一个。

**⇒ 可复用的教训**：
- **穷举的范围就是结论的作用域。**「我试遍了 X 类构造都不行」是**观察**；「构造不存在」是**一般命题**。**前者不蕴含后者，而写下来时两句长得很像。**
- **声称「不可能」之前先问：我枚举的是所有构造，还是所有我想到的构造？**（dev 自己给的收窄；这次答案是后者，而两者差的只是「把已有手法挪个时点」。）

- **「同一失败模式」是个待验断言，不是分类判断** —— 验它只要两个消融看红在哪一格。
- ⚠️ **读报告的一侧**：Leader 采信的是一份**方法可靠、结论越界**的报告 —— 它带实测数据、标了残留风险、连「我可能漏了什么」都写了，**唯独没写「我穷举的是哪一类构造」，而 Leader 也没问**。⇒ 判据（验证者给的）：**看它有没有声明作用域；没声明 ⇒ 当作观察，自己动手。**

🔴 **一个仍未闭合的项（2026-08-14 挂账）：第 2 格身上压着两道守卫，而代码里没有任何痕迹说明这件事。**

`TestBackfillFetchAbortsOnEveryDiskFailurePath` 的**第二格**（检索页快照落盘失败）同时是 **A18**（搜索快照写盘）与 **A16**（搜索路径的 `errBackfillDisk` 例外）的唯一杀手 —— 删掉任一个都让该格的 err 变 nil。**但 `grep -c errBackfillDisk backfill_fetch_test.go` = 0**：

## D. 方法学陷阱（验证与测试）

**D1｜「0 SURVIVED」的强度上限，永远是写变异清单那个人的想象力**
dev 报「26 个变异 0 SURVIVED」属实，但那是**它那 26 个**的边界；验证者独立设计的 34 个里有 1 个 SURVIVED、**不在 dev 清单里**。
⚠️ 验证者紧接着补的一句同样重要：**「同理我这 34 个也有自己的边界，别读成已穷尽」**——它没有用自己的发现去主张自己的完备性。
⇒ **报数时连同清单的边界一起报。**

**D2 追加（2026-08-15，test-agent-27 两次受控实验，可复现）｜`scope-writes-outside-packages` 报出的条数恒等于 `writes` 长度，与 `packages` 无关 —— 零信息量**

**实验一（改 `packages` 内容）**：两份任务图只差 `packages` 一个字段、其余逐字相同 ⇒
```
packages=["./cmd/atlas"]                      → 7 条
packages=["./cmd/atlas","./internal/hestia"]  → 7 条    ← 已改对，输出逐字相同
```
**实验二（改 package 个数 + 任务状态）**：把 **TASK-001**（单 package、3 个 writes **全在该目录下**）
在 `/tmp` 副本里置为 `in_progress`，其余一字不动 ⇒
```
TASK-001（单 package，在途）→ 3 条   ← 它全部 3 个 writes，一条不落
TASK-007（双 package，在途）→ 7 条   ← 它全部 7 个 writes
```

⇒ **不是「单 package 正常、双 package 坏」。它对每个在途任务的每一条 `writes` 全报，一条不落。**
⇒ **既不能发现漏填、也不能确认已修正**，
🔴 **且不能用「某任务 0 条」反推该任务没问题** —— **终态任务恒 0，与形态无关**（该规则只对在途任务生效）。

⚠️ **本条最容易被误用的方式，本 sprint 实撞两次**：
  · dev 用「8 个单 package 任务 0 条 vs 双 package 7 条」推出「多包时匹配逻辑坏了」——
    **那 8 个全是 `verified`，0 条只说明规则没生效**；
  · **Leader 复现了同一个对照并当作确认** —— 而「对照组必须与被测对象处在同一适用条件下」
    **正是本项目上一个 sprint 已登记的教训**（见本组同类条目）。
  ⇒ 危险在于：那个假阴性**恰好支持一个合理的机制模型**（「多包匹配坏了」），所以更不容易被怀疑。

🔴 **由此暴露的真空**：「`packages` 是否覆盖 `writes` 里那些 Go 文件所在的包」**没有任何工具在做**。
本规则**看着像在做，实际不做** —— 而现在有了更硬的说法：**它连「做不做得到」都与输入无关。**

⚠️ **推论（Leader 亲身）**：我曾把「补上 packages 后告警应从 7 降到 2」写进 fix_items 当验收判据 ——
**那会让改对了的人以为自己没改对**。**一个错的验收判据比没有判据更糟。**

**D2｜语句覆盖率对「一个 `if` 里的半个条件」毫无信号**（实测两次，同一数字两种现实）
`if a < lo || a > hi` 是**一条语句**，两个半边共用一格。删掉 `|| a > hi` 后**三级测试全绿、覆盖率仍 100%**。
🔴 最硬的证据形式：**`checkBackfillSearchDateRange` 的语句覆盖率，上界守卫缺失时 100%、补上后仍是 100%**
（同一验证者两轮各实测一次）——不是论证，是同一指标在两种现实下读数相同。
⇒ 覆盖率能告诉你「这行跑过」，**不能**告诉你「这行的每个分支都被检验过」。

**D3｜量级锚点会在一小时内过期**（实测）
验证者首验实测 `qAll=金融统计数据报告` 全区间 **692** 条，复验同一条 URL 返回 **693** ——相隔约一小时，语料真的长了 1 条。
⇒ **能判性质就别判数量**：依赖测量值的判据，正确性挂在一个会漂移的数上。

**D4｜「做不出更外科的变异」往往只是没换思路**
dev 诚实标注「这个变异集里做不出更外科的写法（正常样本 delta 有 +42）」。验证者换方向——**加窗口而不是加上界**
（只在 `delta ∈ [4,8]` 报错，盲区用例的 +5 命中、正常的 +42 落窗外）⇒ **仅目标那一条红**。
⇒ 自我限制**诚实但可以更强**；判据是「换一种约束形状再试一次」，不是「这个变异集里做不到」。

**D5 追加（2026-08-15，收尾时三方共同确认）｜同一道闸，执行者是人时失效、是机器时生效 ——所以要换执行者，不是加闸**

本 sprint 同一道「语义闸」（核对变异体是否如预期生成）出现了三次，结果分裂：

⚠️ 与本组 D5 主条同源：**「我会认真读」和「我已经学到这条教训」是同一类承诺 —— 都把保护建立在下一次自己的状态上。** 唯一能延长射程的是**把它挪出人的判断**。

**D5｜「已经学到这条教训」不构成对下一处同形位置的保护** 🔴 *（本 sprint 最值得机械化的一条）*

**当场实例（2026-08-14，间隔十分钟，同一个人）**：dev 把「`grep -c` 回答的是『有几行匹配这个模式』，而我拿它回答『有几个条目存在』」写进 wisdom；**十分钟后**在本文件上核对条目数，连猜三次模式：
`^\| *[A-G][0-9]+` → **0 条**（以为条目是表格行）；`^\*\*[A-G][0-9]+` → **16 条**（以为都是加粗标题）；`[A-G][0-9]+[｜|]` → **15 条**。真值 **20**。
成因是本文件**两种格式并存**：A/B 在表格里（`| **A1** |`），C–G 是加粗标题（`**C1｜…**`）。

⚠️ **第一次得 0 条时它没有停** —— 「0 条本身就是荒谬的，我却只当成『模式要调一下』」。
⇒ **荒谬的输出是最便宜的警报，而它最容易被当成噪声。**

🔴 **第二个当场实例，同日、同一个人、跨七八小时**：dev 在同一天更早时候已经记过「排除法没封闭」
这个形状（「任何移位量都推不出你那个 pair」），**并且向 Leader 复述过两次**；
当天下午它仍然把「我试遍了静态预置构造都不行」写成了「构造不存在」，换来一次返工。

**它自己给出的机制解释，比 D5 原文更有力**：

> **那次结论碰巧对，所以只成了脚注；这次结论错，就换来一次返工——而缺陷本身一模一样。**

⇒ **结论对的时候，缺陷不产生代价，于是也不产生记忆。** 「学到教训」这件事实际上是由**代价**
而不是由**认识**驱动的 —— 这就是为什么「我已经知道这条」对下一次毫无保护力：
知道它的那一次没让你疼。

**可操作的收窄（dev 自己给的）**：**猜格式超过一次，就停止猜、去看原文。**
理由很具体：**「换个模式再试」比「打开文件看一眼」便宜，所以人会一直换模式**，而每次重试都可能产出一个**像样但错误**的数。

实撞：同一个文件、**200 行之内**、同一条原则的三处 —— dedup 的 `||` ✅拆两条子测试各做消融、日期守卫两半 ✅5 格表驱动、
**交集字段偏好（Title/URL/Published）❌ 只钉了 Title**。
⚠️ 第三处的注释里**原则写对了**（「否则『取哪一侧』在测试里根本不可观测」）——**只是没把它扫过所有字段**。
⇒ **知道原则、写下原则、然后只应用了一次。** 唯一出路是把它变成可机械执行的一问：
> **「这条断言里，有几个字段/分支在两侧取值相同？」** 相同的那些，全部不可观测。

**D6｜同一个词在两份文档里可以是两个意思，而滑轴不留痕迹**
验证者在 TASK-004 报告里把「不可达」分得很清（**生产**不可达：CLI 无 `--to`），转头论证 TASK-005 时滑到了**测试**不可达那个轴上，
据此得出「结构不同」——随后**自己用实验证伪了自己**（纯函数的两侧输入完全由测试构造，改一行辅助函数即可分叉）。
⚠️ **Leader 照着那个滑轴写进了 DoD**（「TASK-005 里不可达」），**两人先后滑在同一个词上**。
⇒ 配套的机械检查：**「我这句话里的关键词，在上一份文档里是哪个意思？」**

**D7｜`go tool cover -func` 必须在与 profile *同源* 的树里渲染**（实测，dev-agent-56）
在 post 树（某文件多 17 行）里渲染 **baseline** 的 profile ⇒ 覆盖块按**行号**归错函数，base 侧冒出 `Path 0.0%` / `AppendArticle 50%`。
**成因**：percentage 来自 **profile**，函数归属来自**源码解析** ⇒ 不同源时**只有后者错**，错法是**整片平移**，看起来完全像真实的覆盖率回退。
⚠️ 它是**靠内部矛盾**发现的：`Path` 由 `Save` 调用、`Save` 跑了 ⇒ `Path` 不可能 0%。**没有那个矛盾，这份错数据会原样进交付报告。**
⇒ 背对背比较覆盖率时，**两侧各自在自己的树里渲染**。

**D8｜linked worktree 的目录副本不是独立仓库**（实测，dev-agent-56；与已登记那条**方向相反**）
`cp -R` 复制的是 `gitdir:` **指针文件** ⇒ 副本与原树指向同一个 git 目录 ⇒ **副本里的 `git checkout` 作用在原树上**。

| | 以为在写 | 实际写了 | 后果 |
|---|---|---|---|
| 已登记那条 | 真相源 | **副本** | 真相源没变，`exit 0` 骗人 |
| **D8** | **副本** | **原树** | 原树被改，且并行的测量被污染 |

⇒ 造基线副本：**`rm -f 副本/.git` 切断联系**，再 `git show <sha>:<path> > 副本/<path>`。

## E. 设计方法

**E1｜同一事实出现在「散文」与「结构化样例」两处时，实现方必然跟随后者** 🔴
实撞：ADR-M1c1-02 的**散文**明写「跳过必须写进 manifest（`search_skipped_reason`）」，而 design-spec §6 的 **JSON 样例**里没有这个字段
⇒ TASK-003 按 JSON 样例实现，字段不存在；缺口直到 TASK-005 要落盘时才暴露（**它返回了这个值，而没人能存**）。
⚠️ **实现方按较具体的载体做，这是对的行为**——JSON 样例可执行，散文不可执行。**责任在写设计的人。**
⇒ **散文里新增字段/约束时，必须同步改那份结构化样例，否则该要求在实现层等于不存在。**
⇒ 反向检查：交付前拿**结构化样例**与**散文要求**对一遍差集。

## F. 流程与环境

**F1｜`../` 下的 worktree 目录不能按「不在本仓库 `worktree list` 里」判定为孤儿** 🔴
实撞：验证者报告某目录是「未注册的孤儿、`prune` 收不掉、归 Leader 收」，**三条表面证据全部成立**；
Leader 删除前查归属，发现它是**另一个仓库的活跃 worktree**（`.git` 的 `gitdir:` 指向那个仓库，9.1M，本仓库 `git cat-file` 没有它的 HEAD 对象）。
**触发条件**：Go 的 `src/github.com/<org>/` 天生是**多仓库共用父目录**，而本框架建议 `git worktree add ../wt-<TASK-ID>` ⇒ **不同仓库的 worktree 必然混在同一层**。
⚠️ **名字是最强的误导源**：那个目录叫 `wt-verify-T001-r7`，`T001` 恰好对得上本 sprint 的 TASK-001，因为那个项目**也在跑同一套 Arcforge 流程**
⇒ **命名约定相同的两个项目共用父目录时，名字本身会伪装成归属证据。**
**正确判据一条命令**：读 `<dir>/.git` 的 `gitdir:` 行，或 `git -C <dir> rev-parse --git-common-dir`。
报告者的自我诊断值得逐字登记：**「『不在我的注册表里』只是关于我的注册表边界的信息，不是关于世界的信息。」**
