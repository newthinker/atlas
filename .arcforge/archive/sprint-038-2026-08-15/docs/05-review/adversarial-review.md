### R2-1｜任一行的标签大小写变化 ⇒ 计数守卫**两边同步移动** ⇒ 静默吞条 + 邻条日期被写错

**来源**：攻击者视角 · **我已独立复现**
**位置**：`backfill_scan.go:107`（`<a\s` 字面小写）× `backfill_scan.go:72`（`.*?</a>` 字面小写）

四行列表页，只把**其中一行**的 `<a>`/`</a>` 改成大写（跑出来的）：

```
第 0 行大写 => ⚠ 无错! 基准=3 items=3 [111@2020-03-11  333@2020-04-11  444@2020-05-11]
                                       ↑111 拿到了 222 的日期，222 整条消失
第 1 行大写 => ⚠ 无错! 基准=3 items=3 [111@2020-02-11  222@2020-04-11  444@2020-05-11]
第 3 行大写 => ⚠ 无错! 基准=3 items=3 [111@2020-02-11  222@2020-03-11  333@2020-04-11]  ← 末条消失
```

**机理**：`<A` 让 `backfillIstitleAnchorRE` 不认 ⇒ **基准 −1**；`</A>` 让 `backfillItemRE` 的
`.*?</a>` 跨过该行去吃**下一行**的 `</a></font><span>` ⇒ **items −1，且存活那条拿到错日期**。
**一次改动同时移动等式两边** ⇒ `n != len(page.Items)` 恒不成立。

**为什么这是本 sprint 自己那条纪律的漏网**：`backfill_scan.go:94` 立的规矩是
「守卫的基准必须独立于它要守护的那个属性」，C1 追加在 **href 形态**这一维上把它做对了。
但两条正则**还共享第三个假设：标签名小写**。这一维从没被考虑过，
而它的失效模式恰恰是 C1 最怕的那一种 —— **条数一条不少，只有内容错**。

**下游后果**（推出来的，读 `runBackfill`）：`Published` 同时驱动翻页判停与 manifest 字段
⇒ 错位日期会挪走判停点；被吞掉的那条**在任何差集里都不可见**（两侧都没发现它）。

**建议**：加第三个**独立**锚——与搜索侧 `backfillSearchBlockRE` 同构的块计数
（数 `<span class="hui12">` 或 `<font` 行首）。三个锚共享的假设越少，同步移动越难发生。
**验收判据**：本节那四种输入各自至少红 1 条，且红的是新加的那条。

### R2-2｜`exhausted` 是正常出口，**不检查日期判停到底生效没有** ⇒ 整趟回填静默截断

**来源**：攻击者视角 · **我已独立复现（totalPages=1 那格）**
**位置**：`backfill_scan.go:406-408` vs 紧邻的 `:409-412`

```
站点自称 totalPages=1  => err=<nil> 翻过页数=1 报告数=1   ← From=2020-01-01，实际需 ~150 页
```

站点分页控件改版、`jumpTo(this,'1',…)` 自报 totalPages=1 ⇒ 整趟回填只拿最近 15 条，
**退出码 0**，manifest 看起来完好。

**这条的说服力在于它的孪生分支**：同一个函数 4 行之后，`MaxPages` 那条出口对
**完全相同的性质**（日期判停没生效）硬失败，注释写着
`refusing to return a partial result silently`。
⇒ 两条出口对同一件事一个报错一个放行，而**放行的那条更容易被站点触发**
（改小 totalPages 比让 200 页都不到 From 容易得多）。

**建议**：`exhausted` 分支补同一条判据 —— 翻完全部页而 `oldest >= from` 仍成立 ⇒ 报错。
「站点确实没有更早内容」与「totalPages 报小了」在这一层不可区分，
但这正是设计文档反复声明的「宁可硬失败」的适用场景。

### R2-3｜搜索侧 `total-records` 与 `total-pages` **从不互校** ⇒ pages 少报即静默只翻第 1 页

**来源**：攻击者视角 · **我已独立复现**
**位置**：`backfill_search.go:98-103`（两字段各自解析）+ `backfill_fetch.go:302/320`

```
站点自报 records=137 pages=1  => 取回页数=3  命中=36  err=<nil>
站点自报 records=137 pages=0  => 取回页数=3  命中=36  err=<nil>
```

（3 = 三个关键词各 1 页；每关键词只拿到 137 条里的 12 条。）

**现有守卫为什么全部挡不住**：每页自洽校验 `want = min(records-(page-1)*12, 12)`
在第 1 页恒等于 got；日期区间守卫也不触发（第 1 页最新，必在窗口内 ——
`backfill_search.go:261` 那句「只取第 1 页的调用方挡不住」的已知边界，
在这里从「已知边界」变成了**实际发生**）。

结果：交叉校验静默退化成「搜索只索到 26%」，`only_in_index` 被灌满，无错误无告警。
而代码里已经有做这条校验的**全部材料**。

**建议**：`parseBackfillSearchPage` 加 `ceil(records/backfillSearchPageSize) == totalPages`
一致性检查，不符即报错（走 fail-open，但**有声**）。

### R2-8｜对账结果、`cutover`、`to`、关键词**都不落盘**，而 M1c-2 被要求「只读这份文件」
