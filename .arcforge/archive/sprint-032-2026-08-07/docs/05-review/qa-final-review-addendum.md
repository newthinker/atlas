## 五、教训（建议入 wisdom）

**1. 判断「HEAD 变动是谁做的」需要三样，缺一不可：**

| 证据 | 回答 | 单独用的失效方式 |
|---|---|---|
| `git status` | 工作树现在有什么 | 抹掉/提交之后都变干净，看不出发生过什么 |
| `git log` | HEAD 动了没有、动了什么 | **所有 agent 共用同一个 git 身份（`author=zuowei`），提交作者字段区分不了任何人** |
| **`tasks/*.json` 的 `last_transition` + `transitions.jsonl`** | **动的是谁、在什么授权下** | —— |

我第一遍只看了 `git status`，第二遍补了 `git log`，**第三样才是唯一能回答归属的**。我把前两条写进了教训，漏掉了第三条——**而漏掉的那条恰恰是唯一能防住这次误判的**。

**2. 共享工作区里的 grep 只能证明「此刻不在」，不能证明「不存在过」。**（dev-agent-40 的原话，我完全同意。）判断归属要查 `git log` / `reflog` / transition 记录，**不能查工作区**。

**3. 变异实证一律在 `git worktree add --detach` 的隔离检出里做，无例外。** 共享树上跑变异双向伤害：读者拿到半写状态的假数字（我有一次读到 `go vet` exit 1 / PASS=0），而任何整目录还原（`git checkout --`、`cp $BAK $FILE`）会**静默、不可恢复地**抹掉并发者的在途编辑。

**4. dev-agent-40 那起事故里最险的一点，值得单独记住**（它的原话）：

> **最险的地方是它无声**：`git status` 干净得看不出发生过什么。我是靠 `grep '^func Test'` 发现新加的测试函数不在输出里才察觉的——**如果我当时直接跑测试，会看到「全绿」然后以为改完了**。

**「全绿」在那个状态下是真的**——125 条全部通过，只是**少了本该新增的那些**。这是本 Sprint 反复出现的「在缩小的范围里量出的结论被当成整体属性」的又一个形态，而且是最难察觉的一个：**通过率不下降的丢失**。

**5. 子代理的「只读」目前只是口头约束。** `.arcforge/` 有 write-guard，**产品代码目录没有任何等价保护**。QA 的 lens 子代理应当在隔离 worktree 里跑；派发者接收结论后必须直读核实——按第 1 条的三样一起看。
