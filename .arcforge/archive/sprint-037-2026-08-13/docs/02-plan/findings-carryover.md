### 兜底（verifier 自己做的，不必 Leader 要求）

预读时固化三份 `done_criteria` 指纹：`jq -S -c '.done_criteria' | shasum -a 256`

|---|---|

**verifier 的措辞是这条的要点**：

> 现在这条无害是靠我俩**记得**它该变什么，**指纹让它不依赖记忆**。

⇒ 与 Sprint 036 的判据同源（「错了的话，什么东西会告诉我？」），

## H2 — sha 判据的第三次指错：**`rev-list --count` 也是 sha 判据**

**dev-agent-53 撞第一次，Leader 撞第二、三次。同一陷阱三种载体。**

### 三次

| # | 谁 | 判据 | 给出的答案 | 真相 |
|---|---|---|---|---|
| 1 | dev-53 | `git merge-base --is-ancestor <我的 sha> master` | **NOT-MERGED**（三次） | 内容早已在 master（两文件 sha256 逐字符相同） |
| 2 | Leader | 同上，用于判断「要不要 merge」 | 合了旧 sha 后，新 sha 仍报 NOT-MERGED | 同上 |
| 3 | Leader | `git rev-list --count master..task/TASK-002` | **1 个未并入的提交 ⇒ 不可删** | 那 1 个是 rebase 出的同内容 sha，**删掉完全安全** |

### 成因

Leader 因 master 前移无法 ff-only，用**三方 merge** 合了 dev-53 的原 sha `bcbcdad2`；
**与此同时** dev-53 在 rebase，产出 `f9136e29`。两者内容逐字节相同，但**不在同一条祖先链上**。

> **sha 是载体的名字，不是载体。** 判据锚在 sha 上，内容经由**另一个 sha** 进去时它就瞎了。

### 第 3 次的特别之处：它会让**清理动作**做错

前两次的后果是「等待」（dev 不敢转 `dev_done`，正确但停滞）。第 3 次的后果是**决策**：
`rev-list` 报「有未并入的提交」⇒ 归档时按惯例会保留该分支 ⇒ **同名 `task/TASK-00x` 分支
跨 Sprint 累积、挡住下个 Sprint 的 worktree 开工**（这是已记录的既有坑）。

⇒ **判「某分支能否安全删」同样要用内容判据**：比对该分支与 master 上对应文件的 sha256，
或 `git diff master..branch -- <文件>` 为空。**`rev-list --count` 非零 ≠ 有内容未并入。**

### 可操作（dev-53 补的那条最好）

> **催办两轮无解时要怀疑判据本身，而不只是怀疑对方没动作。**
> 我三次重查的都是「merge 发生了吗」，**一次都没问「我这个判据能不能回答这个问题」**。

⇒ 通用形式：**凡 rebase / cherry-pick / 三方 merge / squash 可能发生的协作里，纯 sha 判据
就有假阴性** —— 多 agent 并行合同一个包时这是**常态，不是边缘情况**。

**本 Sprint 的处置**：归档清分支时对 `task/TASK-002` 用 `git branch -D`（内容判据已确认安全），
不用 `-d`（它按 sha 判，会拒绝）。

### ⚠️ 第 4 次 —— **发生在写完上面这段的三分钟之内，作者是我**

我写完 H2、正要用「内容判据」核实 `task/TASK-002` 能否安全删，跑的是：

```bash
git diff master..task/TASK-002 --stat     # 期望：空
```

**输出不是空的** —— 10 个文件、2732 行删除。我差一点据此判「不可删」。

真相：那些差异是 **TASK-001 的文件**（`discover.go` / `types.go` / 四份 testdata）。
`task/TASK-002` 基于 `2e93115`，**不含 TASK-001 的代码** ⇒ 这个方向的 diff 在说
「该分支缺少 master 上的东西」，而**我要问的是「该分支自己的改动在不在 master 里」**。

正确的问法是**限定到它自己的 `writes`**：

```bash
git show master:internal/hestia/config.go      | shasum -a 256   # 352f16ef…
git show task/TASK-002:internal/hestia/config.go | shasum -a 256 # 352f16ef… ✅ 相同
```

三个分支同法复核，六个文件**全部相同** ⇒ 三个分支都可安全删。

#### 这一次与前三次**不同族**，值得分开记

| | 错法 | 判据本身 |
|---|---|---|
| 前 3 次 | 锚在 **sha** 而非内容 | 判据问对了问题，只是尺子会因换名失效 |
| **第 4 次** | 用了内容判据，但**范围/方向错** | **判据答的是另一个问题**，而输出看起来完全像个答案 |

⇒ **「改用内容判据」不够** —— 内容判据同样可以问错问题。
补一层：**写下判据之后，先问「它的输出为真时，我要的结论成立吗？为假时呢？」**
本例中 `diff` 非空**既可能**是「它的改动没进去」、**也可能**是「它缺别人的改动」，
**两者对我的决策指向完全相反**，而输出本身不区分。

⇒ 与 G31（聚合信号不携带因果）同形：**`diff --stat` 非空是个聚合值**，
它把「谁缺谁」这个方向压掉了。

## H6 — 「绿有很多种原因」：单看一次消融的 PASS 证明不了它承重

test-agent-26 在复现 dev-52 的 M4 时给出的读法，比 Leader 与 dev 原来的说法都准。

M4 声称证明「三条内容锚点是承重的」：改正则 **且** 删三条锚点 ⇒ `assert.Zero` 在空集上
平凡为真 ⇒ **PASS（假绿）**。

> ⚠️ **单看 M4 的 PASS 证明不了它是承重的** —— 我是靠 **M2 与 M4 的差集**才确认的：
> M2（只改正则、**锚点还在**）→ 四个子测试**全红**；M4（改正则**且**删锚点）→ **PASS**。
> **两者并排才是证据。单跑 M4 只能看到「一个绿」，而绿有很多种原因。**

⇒ 通用形式：**一次消融的结果（红或绿）都是单点，承载不了「某物承重」这种因果命题。**
要证明「X 承重」，需要的是**控制变量的一对**：其它条件相同、仅 X 有无不同，两次结果相反。

⚠️ 这是 G31（聚合信号不携带因果）的**下一层**：G31 说「别看测试红不红，要看哪条断言红」；
本条说「**即使看对了那条，单点仍不构成因果，要看差集**」。

## 🔴 H8 — `Discover` 的判停规则：一次重发会让管线**永久静默停摆**

**test-agent-26 发现并实证，Leader 独立复现。这比 Sprint 036 记的 W1「修订版不可达」严重一个量级。**

### 机制

`discover.go:313-315` 是 **`if has { return out, nil }`** —— **不是 `continue`，是命中已入库期次
就立刻停止翻页并返回**。文档注释给的理由：

> 为什么碰到已入库的期次就停：**index 按时间倒序，再往后只会更旧。**

> **这句话把「发布时间倒序」和「期次倒序」当成了同一件事。**（verifier 的诊断）

无修订时两者同构；**央行重发某期时分叉** —— 修订版的**发布时间最新 ⇒ 排在最前**，
而它的**期次是旧的（已入库）**。

### 实证（verifier 构造，Leader 在隔离树 @ `67249ffb` 独立复现，逐字一致）

第 1 页放 p7（`2026-03/q1`，**已入库**），第 2 页放 p2（`2026-06/h1`，**未入库**）：

```
Discover 返回 0 条候选
实际翻了 1 页
是否发现了未入库的 2026-06/h1：false
err == nil                        ← 完全静默
```

### 为什么它比 W1 严重一个量级

| | Sprint 036 记的 W1 | **本条** |
|---|---|---|
| 影响 | 修订版**自己**进不了候选 | **修订版之后的所有未入库期次都发现不了** |
| 自愈 | — | **不会**：每次唤起都停在同一处 |
| 可观测 | — | **返回空 + `nil` error，与「今天没有新报告」在调用方看来完全一样** |

⇒ **低频 × 静默 × 持续 × 检测难度极高。** 与 TASK-001 的 D6 恰好是反面：
那里至少是**响亮失败**（会淹掉退出码但看得见），**这里连报警都没有**。

### 触发条件的证据强度（如实分级）

## H11 — **用例名描述真实场景，断言覆盖的却只是纯函数**（dev-agent-52 抓，Leader 是当事人）

### 事实

Leader 为「站点迁移后自愈链条是否成立」找证据，给 dev-52 引了这条现成用例：

```go
// internal/macro/bitemporal/classify_test.go:31
{"同键同 revision——站点迁移换了 URL", State{Exists: true, LatestRevision: "2026-07-15"}, "2026-07-15", Duplicate}
```

### dev-52 的拆解

> 它**直接构造 `State`**，不经过 `Lookup`。⇒ 它证明的是「**给定**一个 `Exists=true, LatestRevision=X` 的 State，
> `Classify` 会判 `Duplicate`」，而**不是**「站点迁移换了 URL 之后，**系统真的会走到** `Duplicate`」。
>
> 后者需要 `Lookup` 在「同期次 + 新 article_id」时构造出那个 State —— **而用例名却已经把结论说出来了。**

⇒ **这是「守卫在场 ≠ 守卫有效」的近亲**：
**用例名描述的是真实场景，断言覆盖的却只是纯函数。**
光看测试名清单的人会以为迁移场景已被端到端覆盖。

⚠️ **那条用例本身没错** —— `Classify` 是纯函数，直接构造输入是对的测法。
问题只在于**它能支持什么结论**：它是「**如果** Lookup 给出那个 State，后面就对」的证据，
**不是**「那一环成立」的证据。**两者差的正是待证的那一环。**

### Leader 的错法（自陈）

我在同一条消息里写了「我看到的只是 `Classify` 这一层，`Lookup` 那一半留给你」——
**边界我意识到了，但开头那句「⇒ 自愈链条不会断在这一环」已经把结论说满了。**

⇒ **前面说满、后面补限定，读者记住的是前面那句。** 这与 H7 是同一族
（「原 DoD 那句『p1–p14 全 19 位』超出了当时的证据」，也是我）——
**证据刚好够时把边界说出来**，而不是先给结论再补边界。

### 可操作

**引用一条现成测试作为某个结论的证据时，先问：它的断言直接覆盖了我要的那个命题，
还是覆盖了该命题的一个前件？** 用例名不算数 —— **用例名是作者对场景的描述，断言才是它实际验证的东西**，

⇒ 判据：**读断言，不读用例名。** 尤其当用例名里出现真实业务场景（「站点迁移」「央行重发」）时 ——

**来源**：DoD（我写的，照抄自独立 reviewer 报告）要求把 `TestProfileAlternationsHaveNoPrefixPairs`
的判据从 prefix 扩到 **substring**，理由是「substring 覆盖 prefix，所以是收紧」。
dev-agent-53 **拒绝执行**并给出四条实测；test-agent-26 **用自己的探针逐条复现，全部吻合**。

| | 实测（Go regexp，leftmost-first） | 含义 |
|---|---|---|
| A | `人民\|人民币`→`"人民"`；`人民币\|人民`→`"人民币"` | 前缀对**有**顺序语义 |
| B | `外币\|本外币` 与 `本外币\|外币` **都**→`"本外币"` | 子串非前缀**无**顺序语义 |
| C | `全年\|上半年\|三季度` 对「前三季度…」→ `"三季度"` | **真正的陷阱是单个词写错**，不是词对关系 |
| **D** | 「全年 / 上半年 / 三季度」**两两无子串包含** | ⇒ **substring 判据对陷阱 C 全绿放行** |
| **E** | `currencyAlt` 里 `外币` ⊂ `本外币` | ⇒ substring 把一个**安全**词对判成违规 |

⇒ **那条字面要求：抓不到它要防的目标（D），同时误伤既有安全形状（E）。**
**那不是收紧，是制造一条既挡不住真问题、又恒响的假红守卫 —— 而假红会被训练成忽略。**

**真正守住陷阱 C 的是语料锚定的正向断言**（拿真实样本断言捕获组**逐字等于**期望词），
不是词表内部的结构不变量。前者能抓「写错了一个词」，后者只能抓「词之间的关系不对」。
验证者做了消融：把 `periodAlt` 的 `前三季度` 写成 `三季度` ⇒ **4 条转红**（含替代方案本身、
端到端、外币孪生句），`q1` 侧全绿，**外溢 0**。

**「A 覆盖 B」不蕴含「A 能防住 B 防不住的那个具体缺陷」** —— 缺陷可能根本不在 A 和 B 的
形状语言里。**改守卫判据前要问两个问题**：①新判据能抓到那个具体缺陷吗（构造缺陷跑一次）；
②新判据会把现有哪些通过项判红（直接跑一次现状）。**只问①会漏掉误报，只问②会漏掉无效。**

⚠️ **这是本 Sprint 第二次「DoD 字面被实测推翻、dev 用更强方案达成目的」**（另一次是 TASK-010）。
两次的共同形状：**我把一条读起来完全合理的建议照抄进 DoD，而写它的人没跑过对照。**

## H27 — 漏挂 `discovery` 指针的真成因是**窗口长度**，不是疏忽、也不是「读错清单」

**本条连续推翻了三个归因，其中两个是我们自己刚提出的**，全过程记在这里因为
**每一步都读起来完全合理，而只有最后一步有数据。**

| 第几版归因 | 谁提的 | 说法 | 为什么被推翻 |
|---|---|---|---|
| ① 疏忽 | 我（leader） | 「2/3 的 dev 漏了，下 Sprint 把两步并列写清楚」 | 改文案不改窗口 |
| ② 认知 | test-agent-26 | 「不是偶尔忘，**是 3/4 的人稳定读错**」 | 同上：暗示改文案能修 |
| ③ 时序 | dev-agent-52 | 「`dev_done → verifying` 可以插在两步中间，**我是被状态机挡住的**」 | 方向对，但**没说清为什么只有它被挡住** |
| **④ 窗口长度** | **test-agent-26 实测** | 见下表 | **有数据** |

### 数据：`dev_done → verifying` 的间隔 × 指针谁补的

| 任务 | 间隔 | 指针谁补的 |
|---|---|---|
| **TASK-003** | **1500 秒（25 分钟）** | **dev-agent-54 自己挂的** ✅ |
| TASK-005 | 96 s | 验证者 |
| TASK-010 | 110 s | 验证者 |
| TASK-004 | 116 s | 验证者 |
| TASK-011 | 129 s | 验证者 |
| TASK-001 | 157 s | 验证者 |
| TASK-006 | 158 s | 验证者 |
| TASK-002 | 160 s | 验证者 |

⇒ **唯一一个 dev 自己挂上指针的任务，恰好是窗口最长的那个** —— 其余七个的窗口只有它的
**1/15 到 1/9**。**不是「一个人记得、七个人忘了」，是「一个人有 25 分钟、七个人只有一分半到两分半」。**

（**数量订正：7 例，不是我先前说的 5 例。**八个任务里七个由验证者补。）

### 为什么归因错了会导致修错

验证者自己点破：

> 如果按我的归因去改（把清单拆成两步、写得更醒目），**七个任务里仍会有七个漏** ——
> 因为窗口还是 90 秒。……**结论正确让判断不再被复查，而理由才是别人据以设计修复的入口。
> 我给了你一个会导向错误修复的理由，而它听起来完全合理。**

⚠️ 归因 ③（我采纳并据以改了流程的那个）**方向对但不完整**：它解释了「存在一个窗口」，
没解释「窗口长度是变量」。**若停在 ③，我可能会满足于『提醒 dev 动作要快』** ——
那和 ①② 一样是往人身上加要求。

### 两条处置防的是同一缺口的两端

- **「派验前先查指针在不在」**（已生效，写进 leader checkpoint）—— **让「窗口存在」不再有后果**。
  成本为零，且**不管窗口多短都有效** —— 因为它把检查放在了**触发方**手里。
- **「把挂指针并进 `transition dev_done` 做成原子」** —— **让窗口不存在**。根治，
  但属运行时资产 ⇒ 进「待同步 hooks 清单」，由人类会话外执行。

**前者不是后者的临时替代。**

### 通用形式

**当一个动作的失败率高得反常时，先去量「留给它的时间窗口」，再去问「做它的人够不够细心」。**
窗口是可测的、人的细心不是；而针对不可测量的成因设计的修复，**无法证伪也无法验收**。

## H28 — 「模板一致」不蕴含「每条句式一致」

来源：test-agent-26 用 `curl` 核对央行页面模板时发现，某处缺一个「为」字 ——

## H27 补充 — 那 25 分钟不是「我偶尔慢了一次」，是**我被阻塞了 25 分钟**

我写 H27 时对 TASK-003 那个异常窗口给的解释是「**八成**只是因为我当时在忙别的」。
test-agent-26 去查了 `transitions.jsonl`：

```
15:04:40  TASK-003 → dev_done
15:14:07  TASK-002 → blocked_clarification      ← dev-53 提问
15:16:37  TASK-001 → blocked_clarification      ← dev-52 提问
15:29:13  leader 答复 TASK-001 的 questions
15:29:14  leader 答复 TASK-002 的 questions
15:29:40  TASK-003 → verifying                  ← 答复完 26 秒
```

⇒ **Leader 的默认反应是秒级；那 25 分钟是被两个并发澄清请求阻塞出来的，不是选择等待。**

**推论（比 H27 原版更硬）**：**这个窗口不会自然变长。**
指望「Leader 有时会慢一点」不可靠 —— 慢的唯一原因是被别的事占住，
**而那本身正是要被优化掉的东西**。⇒ **「派验前先查指针」不是保险，是唯一的那道网。**

### 方法论：「八成」是一种**读起来诚实、因而没人会查**的表述

我用「八成」给了一个猜测。它**承认了不确定**，所以读起来像负责任的说法 ——
**而恰恰因此没有人会去查它**。若我写的是「因为我当时在忙别的」（断言），
它会被核；写成「八成是」，它就以一个永不被检验的状态留在文档里。

⇒ **可查的东西不该用概率词表述。** 判据很简单：**「这件事有没有一条我能去查的记录？」**
有 —— 就去查，然后给数；没有 —— 才轮到「八成」。
与 [[shell-silent-failure-and-harness-self-proof]] 的「写结论时给可被打脸的具体数，
别给恒真的概括」同源，但这一条针对的是**概率词**这个更隐蔽的载体。

## H31 — 「写权时点陷阱」的三个实例**可补救性不同**，立机制要按这个排序（dev-52 提）

我把三次撞见归纳为同一形状：**某字段必须在某时点前写入，而写权在那时点前后属于不同的人。**
dev-52 指出形状虽同，**后果分两类**：

| 实例 | 错过时点后 | 类别 |
|---|---|---|
| `discovery` 指针 | 转 `verifying` 后**验证者能补** | **补的人换了** |
| `coverage_floor` | 同上（验证者也写得了） | **补的人换了** |
| **越界申报（`writes`）** | 一进 `dev_done`，**leader 写不了、dev 也交棒了** | 🔴 **没有任何角色能补** |

⇒ **按频次立机制会排错序**：前两个频次高但有第二道网，第三个频次低却是**硬死锁**。
**要立机制，第三个才是硬约束；前两个更像「让 dev 顺手做掉最省事」。**

⚠️ 这条修正了我自己的表述 —— 我说「本 Sprint 第三次撞上同一个陷阱」时，
**把三者当成了同等严重**，而那正是会导致**优先修错那个**的读法。

## H32 — 否定式判据在「**保留并驳回**」的文本上必然假阳；两人独立踩中，而我自己是**侥幸**躲过的

**场景**：我订正 TASK-009 的 DoD 时，**没有删掉旧说法，而是保留它并标注「这句现在是假的，不得写进 CONTRACTS」**——
让照抄旧计划的人当场撞上警告。

**于是任何「旧说法还在不在」的检索都会命中。** 一个 Sprint 内**三个人**用了这个判据：

| 谁 | 判据 | 结果 |
|---|---|---|
| test-agent-26 | grep 旧说法 + 我消息里的新措辞 | **假阳**（还叠加了脚本 bug 与「读转述不读原文」，见其自陈） |
| dev-agent-52 | grep 两句旧说法 | **假阳**，「差一点就发消息说订正没落盘」——**读了上下文才发现完全相反** |
| **我（leader）** | grep 旧说法 + grep 新说法 | **侥幸为真**，见下 |

### 我这次是运气，不是设计

我当时的自检是：

```bash
grep -o '结构上不可达；\|`HasPeriod` 会当场返回空'   → 0    # 判「旧说法已清」
grep -c '没测过，所以不承诺'                          → 1    # 判「新说法在场」
```

事后实测：**`grep -c '结构上不可达'`（去掉那个分号）= 1**。
⇒ **我的否定式判据之所以没假阳，只是因为我随手选的模式恰好带了标点、比保留下来的引文更长。**
我并没有意识到「保留并驳回」会让否定式判据失效 —— **换一个更自然的短模式，我会得出「订正没落盘」的结论，然后去改一份已经正确的文件。**

### 结论：判据要用**肯定式**

> **判据应当是「新说法在不在」，不是「旧说法没了没」。** —— dev-agent-52

**子串检索分不出「被主张」与「被引用并驳回」。**
而**写得越好的订正，否定式判据的假阳率越高**——因为好的订正会**故意保留**旧说法。
⇒ 这是一条**惩罚正确做法**的判据，属于最坏的一类。

**与 [[negative-assertions-pass-vacuously-on-empty]] 互为镜像**：
那条是「否定式断言在空集上**假阴**（漏放）」，本条是「否定式判据在**含引文的文本**上**假阳**（误控）」。

### ⚠️ 上面那句处方（「与肯定式成对」）**不够，且我写它时是错的**（test-agent-26 更正，采纳）

**肯定式不是否定式的解药。** 验证者那次 grep **两种判据都用了，两个都失效，而且方向相反**：

| 判据 | 它查的 | 结果 | 真相 |
|---|---|---|---|
| 否定式 | 「结构上不可达」还在吗 | 命中 1 ⇒ 以为**残留** | 刻意保留的对比句 ⇒ **假阳（误控）** |
| 肯定式 | 「机制上可达」在场吗 | 命中 0 ⇒ 以为**缺失** | 文件写的是「不再被判停挡住」⇒ **假阴** |

⇒ 肯定式的失效原因是**措辞自由度**：它 grep 的是**我消息里的措辞**，而落盘时用的是另一套说法
（这同时也是「读转述不读原文」的又一次实例）。

⇒ **真正的结论**：**判断「某个文本改动是否落实」根本不适合模式匹配。**
要判的是**语义**，grep 判的是**字面**，而订正这件事恰恰允许（并鼓励）字面自由。
**唯一可靠的是读原文。**
若一定要机器辅助，判据应当是「**旧说法出现处，其上下文若干字符内有无否定标记**」
（「现在是假的」「已被推翻」「不得」）——方向对，但仍是近似，**不能当判定**。

### 更强的一半：这个判据不只惩罚正确做法，它**奖励错误做法**

| 订正方式 | 否定式 grep 的结果 | 实际质量 |
|---|---|---|
| **保留旧说法 + 标注「现在是假的」** | ❌ **假阳**（看起来没清干净） | **更好**（防后人重新发明它） |
| **直接删掉旧说法** | ✅ **全绿** | **更差**（后人可能重新发明它） |

⇒ **判据与做法质量是反向相关的。** 一个照着这个判据优化的人，**会被推着去做更差的订正**。
这比「惩罚好的」严重一档：前者只是不奖励，后者是**主动把人推向错误方向**。

### 附：dev-52 自陈的元观察

> 我这次差一点就凭一个 grep 去指控你没做事 —— 而**上一次我被指控时，要求的正是「贴原文而不是相信转述」**。
> 我这次先读了原文，没有先发消息。

### 第三次实例（我，`18:00Z`），带一个新的一半：**当时手边就有一个精确判据**

我把验证者的四条预读结果折进 TASK-009 的 DoD 后，做了**两种**核实：

| 判据 | 结果 |
|---|---|
| **sha256 比对**（落盘的 `done_criteria` vs 我构建的 JSON） | `60c764b1f12a236a == 60c764b1f12a236a` ✅ **精确、无歧义** |
| grep 四段新增文字 | 三段命中、**第四段 0** ⚠️ |

第四段「查无此文」的原因：我 grep 的是 **`validate() 的全部条款`**，
而落盘的原文是 **`` `validate()` 的全部条款``**（带反引号）。
⇒ **我又一次 grep 了自己的转述，而不是文件里的字面。**

**新的一半在于**：这次**精确判据就在同一次操作里，而且先跑、先绿**。
一个 sha 相等已经证明「落盘内容 == 我构建的内容」，**grep 提供不了任何额外信息**

> **dev 干活本身就是那半的检测器**，信号很明确：「DoD 说这是第一步，而我不用做」。
> 它之所以通常沉淀，不是**测不到**，是**没有上报义务** —— 一个 no-op 不会让人想去报告，
> **报了还显得像在挑刺**。我这次报了（写进 discovery 的 `open_items`），所以它进了你的视野。

## H38 — 我差点用一个**五小时前的时钟读数**收回一个活着的 agent 的六小时工作

**省掉那一步之后，一切看起来都会很合理**：时限到了、五条消息无回应、mtime 冻结

⇒ 这正是 [[discipline-beats-judgment-when-stakes-invisible]] 的形状：

- **与 H27 同构，但方向相反**：H27 是「我反应太快，压出 90 秒的窗口」；
  本条是「我以为只过了 13 分钟，实际过了 5 小时」。**两者的共同点是

⇒ 已把这条并进 checkpoint 里那段收回改派的操作步骤，**放在命令的前一行**。

我在上面把这次归功于「纪律」，但没说透。它说透了：

## H42 — 「**没测就推**」与「**测了但工具把结果吃掉**」是同一族的两面，而后者更险

dev-agent-52 复核我 H40 那条 `scope-mutex` 时，**自己撞上了第二种**：

```bash
validator-run.sh … | tail -12; echo EXIT=$?     →  EXIT=0    ❌ 假
validator-run.sh … >file 2>&1; echo EXIT=$?     →  EXIT=1    ✅ 真
```

> **`$?` 取的是 `tail` 的退出码。`tail`/`head` 几乎恒 `0`，
> 所以跨管道取退出码不是丢信息，是系统性报成功。**
> 我差一点就回你「validator 是绿的，你记错了」。

它自陈这是**它记过、且记着「已踩中过四次」的同一条**，**这是第五次**。

### 它给的对比比我的原版准

> **你是没测就推，我是测了但测量工具本身把结果吃掉了** —— 而后者更险，
> 因为**我手上有一个看起来像测量结果的数字**。

⇒ **H30/H34/H40 那族（用推演代替测量）的处方「先去量一次」是不完整的**：
量了之后还要问「**我这个量法会不会系统性地只产出一种答案**」。

**判别标志**：一个测量若**只可能报成功**（跨管道取退出码、`grep -c` 计数在总为一行的
JSON 上、否定式 grep 在含引文的文本上），它就不是测量，是**装扮成测量的假设**。

⇒ 与 [[shell-silent-failure-and-harness-self-proof]] 的「『0 红』是唯一一种能被
『测试没跑起来』完美伪造的结论」同源；本条把它推广到**任何取退出码/计数的判据**。

### 一次自查（顺手做的，结论是好的）

我复查了自己今天全部 validator 调用，**都是 `>file 2>&1; echo $?` 形式，没有跨管道** ——
**不是因为我这次特别小心，是因为这条在我的长期记忆里且写着「三个 agent 独立踩中同一处」。**
⇒ 一个佐证：**这类错法一旦被写成「命令形状」而不是「原理」，就真的挡得住。**
（对照 H38 的结论：能传播的只有写进命令序列本身的东西。）

### dev-52 顺带给了 H40 一个更好的落点

> 「**文件腾出来了**」与「**任务不在途了**」是两回事，而前者是更自然的直觉。
> 这个区分值得留在 CONTRACTS 或 validator 的 `--rules` 输出里。

⇒ 采纳：进 final-report 的建议清单（**放在 `--rules` 输出里**，因为那是人在
判断「能不能派」时唯一会去读的地方）。

### 修正版

> **差集标出的是：你的代码对「这两道在回答同一个问题」这个假设，可能为假的地方。**
>
> 拿到差集后先问两件事：**① 它们各自在回答什么问题？② 我的代码依赖的是哪一个？**
>
> 三种落点：① 某一道确实有 bug；**② 两道都对但问的不是一回事（本例）**；③ 输入本身该修。
> ⚠️ **② 最容易被「两道都没错」打发掉。**

**另两处松一格**（dev-52 提）：

- 「差集**就是**攻击样本」→ **「差集是攻击样本的候选集」**。这次差集恰好只有 1 个元素且恰好可用，
  **那是运气**；一般会混着**合法的分歧**（两道守卫本就该在某些输入上答案不同）。
- **前置条件**：要求两道守卫**输入域可重叠、能批量跑**。对文件格式类成立
  （11 份 plist × 2 个解析器 = 20 行）；对输入域不同的守卫
  （如「配置能装载」vs「plist 有排班」）**根本跑不出差集**。

**价值**（dev-52 的表述比原版准）：

⇒ 这也是它比 H49 阶梯第 ① 步更强的地方：**那一步仍要求你先说得出要 grep 什么。**

## 🔴 H51 — **否定式断言让人警觉，肯定式断言让人放松**（test-agent-26，本 Sprint 最后一条，也是最可执行的一条）

**Leader 的版本**：「你和 dev-52 的消融都覆盖了『有没有』，都没覆盖『在哪』。」——**对，但不是成因。**

**它的版本**：

> **消融这个工具的方向是「什么破坏能让它红」** —— 它确认守卫在守什么。
> **而发现假通过需要相反方向：「什么绕过能让它绿」** —— 那才暴露它漏什么。

⚠️ **而它在同一次验证里两个方向都用过，只是用在了不同的断言上**：

| 断言 | 它问了什么 | 结果 |
|---|---|---|
| `TestHestiaPlistSetsNoProxyKeys`（**否定式**） | **「什么能让它假绿」** ⇒ 识别出 `plistEnvKeys` 的 `break` 会静默返回部分键 | ✅ 抓到（记为观察，见 H47） |
| `TestHestiaPlistSchedulesThreeTimes`（**肯定式**） | **只问了「什么破坏能让它红」** | ❌ 漏了 |

⇒ **成因：否定式断言让我警觉，肯定式断言让我放松。**

### 为什么肯定式同样会平凡为真 —— 只是形态不同

它有那条判据（「**有没有一个我想排除的实现，能让这条断言照样绿？**」），
**并且在同一份报告里对否定式用过它**，只是没对肯定式用。

```go
assert.Equal(t, [][2]int{{15, 30}, {17, 30}, {21, 30}}, got, ...)
```

**看起来钉得很死** —— 三个具体数值、精确相等。**而 `got` 是从哪来的没人守。**

⇒ **两种平凡为真的形态**：
- **否定式**：「不存在 X」在**空集**上平凡为真（见 [[negative-assertions-pass-vacuously-on-empty]]）
- **肯定式**：「等于这几个值」在**数据来源不受约束**时平凡为真 —— **值对了，来源可以是任何地方**

⇒ **可执行**：**对每一条断言都问一次「什么能让它绿而约束被违反」，不分肯定式否定式。**
把「平凡为真」这个风险**只挂在否定式上**是一种错误的直觉分工，
而它恰恰会让**看起来最扎实的那类断言**（精确相等）逃过审查。
