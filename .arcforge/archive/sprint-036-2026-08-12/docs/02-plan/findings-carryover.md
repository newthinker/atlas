## G1：**hook 身份判定粒度 = session 而非 agent** —— 子代理被要求冒名写（新形态）

dev-agent-50 spawn 的 code-simplifier 子代理，**两次**被 `TeammateIdle` hook 拦截，
要求它「用 `--as dev-agent-50` 经写通道把名下任务推进到 `dev_done`」。

**它两次都拒绝了，没碰 `.arcforge/`。这是正确处置**，理由（Leader 逐条认可）：

- 它是**子代理**不是本尊，hook 按 **session 粒度**判定身份，命中的是宿主实例名
- 它**不知道 TASK-ID、不持有 `assignment_epoch`** ⇒ `--expect-epoch` **根本填不出来**
- `--as dev-agent-50` **就是写通道要挡的冒名写** —— 真 dev 若还活着，

**这是可复现的误判，子代理场景会稳定重现。**

⇒ 与 Sprint 035 的 F33-1（三个 lens 子代理的发现正文被 idle hook 循环挤掉）**同源不同形**：
那次是子代理的**产出**被 hook 干扰，这次是子代理被 hook **要求越权**。
两者共同的根因是 **hook 看不见「子代理」这个层级**。

⇒ 已写进「待同步 hooks 清单」。**这条不能靠纪律兜** —— 它要求每个子代理都独立想明白该拒绝，

## G5：Sprint 编号复用导致的**两类**噪声（同一根因）

本仓库各 Sprint **复用同一批 `TASK-00x` 编号**，产生两个互不相关的后果：

### ① 分支名冲突（dev-agent-49 实撞）

`git worktree add -b task/TASK-001` **直接失败** —— 该分支名被 Sprint 035 的遗留分支占用（`234baea`）。

它的处置**正确且谨慎**：先 `git merge-base --is-ancestor` 确认已完全并入 master，
再用 `-B` 重置，零提交丢失。**这个顺序不能省** —— 若那分支有未合并提交，`-B` 就是静默丢工作。

**Leader 复核后的完整清点**（比 dev 预估的干净）：

```
task/TASK-001  ← 本次交付      task/TASK-002  ← Sprint 035 遗留（dev-50 在用）
task/TASK-006  ← 本次交付      task/TASK-012  ← 更早 Sprint 遗留，已并入 master
task/TASK-003/004/005/007  ← 都不存在 ✅
```

⇒ **后续 wave 不会再撞**：Sprint 035 只有 wave1 建过分支，而方案 C 下 wave2+ 不建 worktree。

⚠️ **一条判据上的澄清**（dev-agent-49 指出）：`task/TASK-001` 与 `task/TASK-006` 清点当时
**各有 1 个未合并提交，那正是两人刚交付的** ⇒ **「有未合并提交」不等于「不是遗留分支」**，
判据始终是 `merge-base --is-ancestor`，不是有没有 commit 差。

### ② `dev_done` 门禁的 WARN 噪声（两个 dev 各撞一次）

门禁按 `^[a-z]+\(TASK-00x\):` 认「本任务提交」，于是恒定捞到 6–8 月的历史同号提交：

- TASK-001：3 条「主题不符约定」+ 5 条「早于本轮开工」，
  点名 `internal/broker/paper/`、`internal/collector/edgar/`、`internal/notifier/telegram/` 等

**都不是范围漂移** —— 两个任务的实际改动都严格等于各自 `writes`（`git show --numstat` 已核实）。

⇒ **这条噪声会对本 Sprint 每个任务重复出现**，已写进验证者的派单。
（Sprint 035 的 F3 记过同一条，本 Sprint 复现 ⇒ **连续两个 Sprint**。）

## G7：**`core.autocrlf` 让入库的字节 ≠ 被测过的字节**（dev-agent-50 发现，Leader 已复核）

抓下来的 index 快照含 CRLF，`git add` 时被 `core.autocrlf=input` 转成 LF：

| | 抓取时（curl/Go） | 入库 blob |
|---|---|---|
| `pboc-index-p1.html` | 38147 | **38080** |
| `pboc-index-p2.html` | 38692 | **38625** |

**各差 67 字节**（Leader 用 `git cat-file -s` 复核，与 dev 报的一致；`core.autocrlf` 在 local 与 global 均为 `input`）。

### 为什么它比看起来重要

本 Sprint 与上个 Sprint 反复在防「判定对象与交付物不是同一个东西」——
`verify_baseline`、复核时点、指针带全 sha。**那些防的都是「时间上的漂移」**。

**这一条是同一时刻、同一文件，git 自己改了字节** ⇒ **现有的每一道防线都看不见它**：
- sha 比对比的是**入库后**的 blob（两边都是 LF，一致）
- `git status` 干净
- **唯一的信号是 commit 时的一行 warning**

⇒ **「我测的树」与「入库的树」在字节层面不同，而没有任何机制会让人发现。**

### 处置

dev 发现后**把工作区刷成入库版重跑**，8 条全绿、覆盖率不变 ⇒ **仓库里这一版才是被验证过的**。
Leader 合并后**特意在入库版上复跑**（`wc -c` 确认工作区 = 38080/38625），闭合这一点。

README 记了两个字节数，并提醒下游**写跨行正则按 LF**（TASK-003 的 `(?s)(.*?)</a>` 直接相关）。

⇒ **通用形式**：凡是「把外部抓来的字节存进仓库」的交付，
**测试必须跑在入库后的版本上**，不能只跑在抓取时的临时文件上。

## G8：**只用真实快照，证不出「解析而不是写死」** —— 真实数据成了帮凶（新形态）

DoD 要求 `parsePaging` **解析而非写死栏目 ID**。计划给的三条断言是：
模板含 `%1`、含 `/goutongjiaoliu/113456/113469/`、总页数 > 100。

**dev-agent-50 实测**：一个 `return ".../11040-%1.html", 408, nil` 的**纯写死实现**能让这三条**全绿** ——
因为它们断的正好是**真实快照里那个栏目的特征值**。

⇒ **断言的期望值与被测实现的硬编码值同源**，于是「用真实数据测」反而让「写死真实值」的实现通过。

**这是「守卫在场 ≠ 守卫有效」的第 11 个形态，且与前十个都不同**：
前面是断言太弱、指错对象、平凡为真、被另一条规则冒名满足；
**这一次断言本身没问题，问题在于测试数据与错误实现共享同一组常量**。

**修法**（dev 已补）：喂一份「栏目 ID / 路径 / 页数**全不同**」的构造输入，写死实现立刻红。

⇒ **通用判据**：用真实样本做断言时，问一句
**「如果实现直接把这个样本的答案硬编码进去，这条断言会红吗？」**

## G10：**`discovery` 写入没有 CAS，「先查状态再写」关不上竞态窗口**（dev-agent-50 申报，Leader 独立核实）

### 时序（三方都能核对）

```
02:06:0x  dev-50 查 TASK-002 状态 → dev_done、无 verifier、无 verify_baseline ⇒ 判断可安全写
02:06:36  Leader transition dev_done → verifying，基线记 discovery_sha256 = 06a18b38…（旧版）
02:06:5x  dev-50 的 discovery 写入落盘 → 当前 eb8883ba…
```

⇒ **`verifying` 窗口内 discovery 被改写，`verify_baseline` 对不上。**
这正是 AD-29 立项时描述的形态（当时的实例是「派验后 53 秒 discovery 被改，改动恰好落在
`verification.suite` 这个 DoD 自证字段」）。

### 责任在双方，但根因是机制

- **Leader**：是我让 dev-50「把 code-simplifier 结论记进 discovery」，随后又在它写入过程中派了验
- **dev-50**：**做了正确的检查（先查状态）仍然撞上**

它的原话值得逐字留：

> 「先查状态再写 discovery」这个自觉动作**关不上竞态窗口** —— 查状态与写入之间隔着我构造 JSON
> 的那段时间，而派验可以落在中间。写通道对 `discovery` **只按状态判权**（`dev_done` 时 dev 仍可写），
> **没有 CAS 之类的东西**。

⇒ **与 `--expect-epoch` 的对比是关键**：任务状态的竞态窗口早已被 epoch 机制关上
（写通道在锁内重读 `assignment_epoch` 比对，不一致即 DENY）。
**而 `discovery` 没有对应的东西** —— 同一个仓库里，一个竞态被机制关上了，另一个只靠自觉。

### 建议的收口（dev-50 提出，Leader 采纳进「待同步 hooks 清单」）

`discovery` 子命令支持 **`--expect-sha256 <当前值>`**，写入时在锁内重读比对，与 `--expect-epoch` 同构。

**dev-50 明确表示不建议由它来做** —— `.claude/` 是对全体 agent 只读的运行时资产。这个边界守对了。

### 本次的实际损害：零，但下次不一定

Leader 独立机器比对（**不采信 dev 的自述表**）：

```
基线文件 sha256      06a18b383ad916b7…
verify_baseline 记录 06a18b383ad916b7…   ← 逐字相同，确认基线版可信
顶层键集合 / verification 键集合  均无差异
逐字段比对 ⇒ 唯一变化：verification.code_simplifier
```

**DoD 自证数字一字未变**（`suite`/`coverage`/`ablation`/`numstat_from_commit`/
`red_output_verbatim`/`test_case_count`/`snapshot_blob_sha256` 等全部未变）。

⚠️ **但 dev-50 的提醒是对的**：「这次没造成实质损害（改的不是自证字段），
**但同样的窗口下一次可能落在 `verification.suite` 上**」。

### 值得记的处置方式

dev-50 **保留了基线那一版**并核实其 sha 逐字节等于 `verify_baseline.discovery_sha256`，
让验证者可以**自行 diff 而不必采信它的表**。

⇒ **申报一个自己造成的漂移时，正确做法是提供可独立复核的对照物，而不是提供一份「我改了什么」的清单。**
前者可证伪，后者只能选择信或不信。

## G30：把「论证**合理**」推到「**穷尽了反例**」—— 封闭性论证的一个完整样本

### 背景

dev-agent-49 在 TASK-004 遇到一条 SURVIVED 的变异（`HasPeriod` 改查 `TableObservations` 而非
`viewCurrent` ⇒ 整包无一变红）。它没有补断言把它「杀掉」，而是给出机制解释：
**视图按业务键分组只留最新 revision、从不整个抹掉一个业务键**，而存在性判定用的正是同一组键
⇒ **两者对本查询恒等价，是等价变异不是测试缺口**。

Leader 与 test-agent-25 都独立核了视图定义（`CurrentQuery` + `correlate` +
`NewSpec(…, ["period","period_type"], "published_at")`），确认论证**合理**。

### test-agent-25 没有停在这里

> **我不满足于此，因为那只是「论证合理」而不是「穷尽了反例」。**

它去**找能推翻恒等价的情形**，并找到了一个：

> SQL 的 `MAX(col)` 在该键下**所有行的 `col` 全为 NULL** 时返回 NULL，
> 而 `o.published_at = NULL` **恒假** ⇒ **那个业务键会整个从视图消失**
> ⇒ 视图与权威表**不再等价** ⇒ 那条变异从「等价」变成**真缺口**。

然后去查 DDL 排除它：

```go
for _, c := range metaColumns { b.WriteString("  " + c + " TEXT NOT NULL,\n") }   // 含 published_at
b.WriteString("  PRIMARY KEY (period, period_type, published_at)\n)")
```

`published_at` 是 **`TEXT NOT NULL`** 且是**主键第三列** —— **两道各自独立的约束**
⇒ NULL 在 schema 层不可能出现。

⇒ **唯一能推翻结论的情形被排除，论证封闭。**

### 它为什么专门追这一步（原话）

> 本项目的判据是「**证据刚好够才是危险区**」——「视图只按业务键筛行」听起来足以支持恒等价，
> **我停在那里也不会有人来查**；而这个 NULL 边界恰好是那种
> **「读代码看不出、只有去查 DDL 才知道」**的前提。

### 这条的通用形式

| 层次 | 做法 | 够不够 |
|---|---|---|
| ① | 「我读了代码，机制上说得通」 | **不够** —— 这是合理性，不是封闭性 |
| ② | **主动找一个能推翻它的情形** | 关键一步：把「找支持」换成「找反例」 |
| ③ | 去查**该情形是否可能发生**（往往在另一个文件/另一层） | 本例是 DDL 的 `NOT NULL` + 主键约束 |
| ④ | 反例被排除 ⇒ **结论封闭**；反例成立 ⇒ **它就是缺口** | 两个方向都有价值 |

⇒ 与 Sprint 035 记的「覆盖性结论要**证明枚举的边界**，而不是换个人再枚举一遍」是同一条，
**这次是它在一个具体命题上的完整执行**。

G21 是「纠正一个错理由时，写下了新的错理由」。这条是「**为一个缺陷设计守卫时，
漏掉了守卫自己的有效性**」。**都发生在「我正在修正某个东西」的那一刻**——注意力全在被修的
对象上，修正动作自身不再受审。⇒ 写完一条自证判据，追问一句：**「不做这件事，它会不会同样通过？」**

### 附带：验证者判定归属再动手

它在主工作区看到 `discover.go` / `discover_test.go` 有未提交改动，**判定是 T5 在途工作

## G32 — 「口径不同」必须能预测出数值不同（否则它不是解释）

**双方各犯一半，由 test-agent-25 提炼成判据。**

验证者报「`-run` 未锚定实际跑了 **7 个顶层测试**」，Leader 独立复现数出 **7 条 RUN 行**。
Leader 写下：「我数的是 RUN 行不是顶层函数数，与你说的『7 个顶层』不是同一把尺，但方向一致。」

**两个数相等 ⇒ 不可能是两把不同的尺。** 真相：7 条 RUN = **6 顶层 + 1 子测试**，验证者数错了，
而**它自己在同一段里列出的兄弟名字只有 6 个**——证伪数据就摆在原文里。

### 判据（可当场用，不需额外取证）

> **「口径不同」必须能预测出数值不同。预测不出差异的口径差异，就不是口径差异
> ——那是同一个数被贴了两个标签，其中一个错了。**

**阳性对照就在同一 sprint**：dev 报 266、Leader 数 562，「顶层 vs 含子测试」这个解释
**做出了预测（应当不同）并被验证** ⇒ 真解释。7 vs 7 那次，同一个解释**做不出任何预测**。

### 机制化（双向约束）

**凡用「口径/尺子不同」解释一处不一致，顺手写出它预测的数值差是多少。写不出来就说明那不是解释。**

例（验证者自举）：TASK-004 报告里覆盖率 92.8 vs 92.7 用的是「同树同口径、舍入」，
预测差值 ≤0.05 且两工具读同一份 profile ⇒ 成立；若当时写的是「口径不同」，就该被这条拦下。

### 为什么这条要机制化而不是靠自觉

两个位置的默认偏向方向相反，**但产出的东西不同**：

| 位置 | 默认偏向 | 产出 | 会被纠正吗 |
|---|---|---|---|
| 验证者（核查别人） | 倾向**证否** | **噪声** | 会——发出去被驳回，代价立刻可见，被迫回头 |
| Leader（回应 teammate） | 倾向**不指出** | **沉默** | **不会**——什么都不发生，代价永不显形 |

⇒ 「先换一种方法确认一次」这条规则**在 Leader 一侧更难触发**。本次之所以闭合，
是因为验证者**没接那个台阶、自己重跑**——**那依赖了它的行为，不是机制**。

### 附：客气不是中性的

Leader 自陈：「不是同一把尺」这句话的功能是**免除双方核对的义务**——把一个可判真假的
问题（谁数错了）转换成一个无需判定的问题（我们口径不同），而后者一旦被承认就没有下一步。
**若验证者接了台阶，错数字会留在验证报告里。**

它与 G28「假数据自带矛盾而我跳过去了」是配套的两半：一边是**没读见**矛盾，
一边是**读见了矛盾并为它编造豁免**。后者认知努力更多 ⇒ 不是疏忽，是选择，
且**比看漏更难被发现，因为它看起来像体谅**。

## G34 — 「跨视角对抗」必须换**位置**，不是换人（直接改了本 Sprint 的 QA 设计）

test-agent-25 在 G32/G33 的讨论末尾推出的一条，Leader 采纳并据此重设计 QA 阶段。

### 推论

两个位置的默认偏向方向相反，这是**结构性的**，比个人自觉可靠：

| 位置 | 默认偏向 | 产出 | 会被纠正吗 |
|---|---|---|---|
| 验证/审查位 | 倾向**证否** | 噪声 | 会——被驳回，代价立刻可见 |
| 协调/回应位 | 倾向**不指出** | 沉默 | 不会——代价永不显形 |

> ⇒ **但它也解释了为什么同位置的人互相检查会失效** —— 两个 verifier 之间不会有这种互补。

### 对 QA 两轮的直接后果

流程规定 QA 做两轮「常规 + 跨视角对抗」。**原先的理解是「换一个模型/多一双眼睛」——
按上面这条，那是无效的**：再加一个 reviewer 位仍然是 reviewer 位，默认偏向相同，
**第二轮只会把第一轮的假阳性再确认一遍**（两轮的错误方向一致，不构成对照）。

**改后的设计**：

| 轮次 | 位置 | 立场 | 判定规则 |
|---|---|---|---|
| 第一轮 | 常规 reviewer | 找问题 | 产出发现清单 |
| 第二轮 | **辩护位** | **「这份交付是对的」** | 逐条**驳倒**第一轮的每个发现；**驳不倒的才算真发现** |

这样两轮的默认偏向**真正相反**，而不是同向叠加。

### 与项目已有纪律的关系

CLAUDE.md 的变异纪律里早有同形的一条 —— **「adversarial verify：spawn N 个独立怀疑者，
每个都被要求去 REFUTE」**。区别在于那条是针对**单个 finding** 的，这条是针对**整轮审查**的，
且给出了「为什么加人没用」的理由。

⇒ 通用形式：**冗余不等于互补。** 要互补必须让两方的**失败方向相反**，
而失败方向由**位置**决定，不由人或模型决定。


### ⚠️ 修正（同一轮内，由提出该推论的 test-agent-25 自己反驳）

**上面那个设计方向对，但只覆盖了误差空间的一半，而 QA 的边际价值恰好在另一半。**
原文保留不删（与 G28 保留 G25 同理——删掉就看不出这是同一轮里被立刻修正的）。

#### 问题一：两个位置在**同一根轴**上

reviewer 说「这是个问题」，辩护位说「这不是问题」——**它们争的是同一批已被提出的发现**。
**谁都不负责回答「还有什么没被看过」。**

| | 谁在管 | 现状 |
|---|---|---|
| 假阳性（报了但不是问题） | verifier 已压得很低 | 六份报告共 **116 次 KILLED**，每条锚在一次实跑输出上 |
| **假阴性（是问题但没人看）** | **无人负责** | verifier 只按 DoD 逐条验，**DoD 没写的按规矩不判**（本 sprint 已发生三次） |

⇒ **轮到 QA 时，「报出来的发现可不可信」已不是主要风险；「有什么从头到尾没人看过」才是。**

#### 问题二：两个相反偏向不会自动抵消

辩护位的代价结构与 reviewer 是**镜像**的：**驳倒了就算赢，驳不倒零成本** ⇒ 默认偏向是
**驳倒一切**，包括真发现。两个相反偏向放在一起，可能只产生**一场由谁更会 argue 决定的胜负**。

⇒ **必须把裁决锚在不属于任何一方的东西上**，用项目现成那条（「能给出一个观察而非一段推理吗」）：

> **反驳只有在给出一个观察（命令 + 输出）时才成立，纯推理的反驳不计。
> 同理，发现也只有带观察才进入下一轮。**

没有这一条，辩护位会把「我认为这样设计是合理的」当成反驳——而「结论对、理由错」
在本 sprint 已出现至少四次。

#### 第三个位置：**消费者位**（覆盖假阴性）

> 站在 **M1b-4b 的 ingest 实现者**立场，拿这批交付**真的走一遍下一步**：
> 「我拿到 `[]Candidate` 之后要做什么？够不够？`Discover` 返回的东西能直接喂给 ingest 吗？」

默认偏向是「**这东西能不能让我干活**」，暴露 reviewer 与辩护位都不找的一类：
**缺失的能力、错误的抽象边界、两个任务交界处的空白**。

**现成的例证**：T7 的 `non_functional[1]` 第 ④ 项「留给 M1b-4b 的张力」——discover 让 pending
期次可被重新发现，但 4b 的一级幂等键 `article_id` 若查的表含 pending 行，重新发现的候选会在
下一步被**立刻跳过且不报错**。**那条不是 reviewer 找出来的，是有人站到 4b 的位置上往回看
才看见的**，而它正是最危险的一类：**跨任务边界、双方各自都正确、没有任何测试会红。**

#### 采纳后的最终设计（Leader 定）

流程规定两轮，**按 verifier 的建议取舍：砍辩护位，保留消费者位**——理由是假阳性一侧已被
116 次消融压过，假阴性一侧**一个人都没有**。

| 轮 | 位置 | 默认偏向 | 准入规则 |
|---|---|---|---|
| 1 | **reviewer** | 找问题 | 发现须带**观察**（命令 + 输出），纯推理不计 |
| 2 | **消费者位（M1b-4b 视角）** | 能不能让我干活 | 同上；专找跨任务边界与缺失能力 |

「反驳须带观察」这条不设专位，**由 Leader 在裁决第 1 轮发现时执行**。

#### 证伪条件（verifier 自设，Leader 记录）

> 以上是从一条推论往下推的，**它本身还没有被观察检验过**。唯一证据是那个 ④，
> **单例支持的因果强度等同于没有**。⇒ 当成一个**可以在这次 QA 上被证伪的设计**：
> **若消费者位跑完一条新发现都没有，这个推论就该被打折。**

这是「**预先声明什么结果算证伪**」的一次实践——比事后要求诚实有效。

#### 证伪条件的两个漏洞（verifier 自己补，Leader 采纳）

**漏洞一：第 2 轮若看得见第 1 轮的发现，比较就被污染了。**
判据是「消费者位产出了几条**是 reviewer 没产出的**」。若消费者位开工时手里有第 1 轮报告，
它会被**锚定**——产出的可能只是对已有发现的延伸，而**「它独立会不会想到」这个问题永远问不出来了**。

⇒ **两轮必须并行开工、互不可见**，事后比对。串行+可见只能验证「第 2 轮有没有补充」，
验证不了「第 2 轮的位置是否产生了独立覆盖」——**而后者才是 G34 的主张**。
（若编排上只能串行，至少**不要把第 1 轮的发现给它**。）

**漏洞二：「零条新发现」有两个成因，处置相反。**

```
成因 A：消费者位这个位置没用      ⇒ G34 该打折
成因 B：确实没剩下什么可找了      ⇒ G34 未被检验，不该打折也不该确认（空实验）
```

按原判据两者都记成「本次未获支持」，**而 B 其实是空实验**；考虑到 verifier 已用 116 次消融 +
DoD 逐条压过一遍，**B 完全可能发生**。

⇒ **让消费者位同时报「覆盖」而不只报「发现」**：要求它列出**检查了哪些跨任务边界**
（如：`Discover` 返回的 `[]Candidate` 够不够 ingest 用？`article_id` 作一级幂等键时查的表含不含
pending？`DiscoverCfg` 的字段够不够 cmd 层装配？），**每条给出结论与依据，而不只在发现问题时才说话**。

三种结果因此可分：

| 消费者位的输出 | 读法 |
|---|---|
| 检查了 N 条边界，发现 **M>0** 条 reviewer 没提的 | **G34 获支持** |
| 检查了 N 条边界，**全部结论「无问题」且有依据** | **空实验**——G34 未被检验（成因 B） |
| **只检查了 reviewer 已覆盖的东西** | **G34 打折**（成因 A：该位置没带来新视角） |

**没有第三列，前两种在报告里长得一模一样。** 这与本 Sprint 那条
「**聚合信号不携带因果**」是同一个形状：「零条发现」是聚合值，读不出成因。


#### 给不给看：判据是「它在不在被测的那条轴上」（verifier 提，Leader 采纳）

漏洞一说「两轮互不可见」，但**六份验证报告应该给消费者位**——这两条不冲突：

> **漏洞一防的是两个 QA 位之间的锚定**（那个比较**就是 G34 的判据本身**）；
> **验证报告不在那条轴上**，它只是已知事实的存量。
> ⇒ **污染判据的要屏蔽，节省重复劳动的要给。**

两种极端都有代价：不给 → 它会重推已被 116 次消融钉过的东西，真正该看的边界没时间；
直接给 → 它读完觉得「都覆盖了」而看得更浅。⇒ **给，但框定用途**，prompt 里明确：

> 附上 `docs/04-test/TASK-00*-verification.md` 六份。**它们全部是 DoD 合规性验证**——

## G35 — 为什么「第三人称核实」必须机制化：它的失败不产生痛感

**dev-agent-50 的论证，Leader 采纳。** 这条解释了为什么本 Sprint 那么多纪律靠自觉执行不了。

### 现象

项目里「正确性附着在载体上」这条纪律，**只有第一人称版本被实际执行**：

| 版本 | 内容 | 本 Sprint 执行情况 |
|---|---|---|
| 第一人称 | **别信别人的自陈** | 执行良好（dev 用 mtime 比对 code-simplifier 的「不执行」声明） |
| **第三人称** | **别信关于别人的信号** | **Leader 一天内栽三次**（子代理报告 / 队友摘要 / IDE 诊断） |

### 根因（dev 的论证）

> 第三人称版本难执行，**不是因为它更难想，而是因为它的失败不落在自己身上**。
> 第一人称版本（别人骗我）有**直接痛感**；第三人称版本（我误读了关于别人的信号）
> **受害的是被误读的那个人**，而我这边一切照常。
> 你今天三次都没跑那条 `git show --numstat`，**不是懒——是那三次里没有任何东西反馈给你说「你读错了」**。

**dev 自陈它那次执行第三人称核实是条件反射不是推理**：它的记忆里有更早 Sprint 撞过的一条，
「如果那次没撞过，这次我大概率会采信『不执行』四个字，然后在 discovery 里写下一句无据的
『它没改动』」。

⇒ **靠自觉需要痛感，而这一族恰好不产生痛感。** 这就是它必须机制化的理由。

### 与本 Sprint 其他几条的关系

同族的还有：G32（客气抑制纠错——沉默不显形）、G33 强化段（窗口 2 分 55 秒——没有任何一方
看得见完整时序）。**三者的共同点都是「错了也不会有信号回来」**，而项目已有的判据
（`discipline-beats-judgment`：「若跳过且错了，会不会有人发现」，答「不会」的最不能省）
正是为这一族准备的。

### 附：诊断信号的正确读法（dev 要求与上面分开记）

Leader 那三次里，第 3 次（IDE 诊断）**与前两次不同类**：前两次读的是**别人产出的陈述**
（可能不准），第 3 次读的是**工具产出的、当时完全真实的信号**——`WrongArgCount` 那一刻是真的。

⇒ 错不在「信了不该信的」，而在**把「A 被 B 影响」读成了「B 在改 A」**。**诊断没说谎，是归因方向反了。**

> **诊断告诉你哪里坏了，不告诉你谁弄坏的。**

混在一起记会得出「别信 IDE 诊断」这个错误教训——**诊断该信，只是它不回答归属问题**。
（多 agent 并行时，一个文件报错常常是**别人的改动波及到它**。）

## G36 — 纠正一个**事实**，不会自动纠正依赖它的**结论**（三人各撞一次的同一形状）

**dev-agent-50 自查发现，在 qa-reviewer 查到之前主动上报。**

### 事实

T7 交付时 dev 声明「`go doc` 修复的守卫超出范围」，理由是「整包范围的守卫会碰
`validate.go`，那不在我 `writes` 里，我无权改」。它自己去查了，**理由不成立**（观察，非推理）：

```
--- FAIL: TestProbeExportedDeclsHaveAttachedDoc
    Error: Should be empty, but was [store.go: Store.Close]
```

整包扫描**只报一处**，`validate.go` 完全没出现。守卫写在 `store_test.go`（在其 `writes` 内）、
唯一要补注释的是 `store.go: Store.Close`（也在内）、`validate.go` **只被读取做 AST 分析——读不需要写权**。
dev 自陈两处都错：「碰」被当成了「需要改」；即便按「会让它红」理解，`validate.go` 也不会红。

### 要害：证伪它的数据**就在它自己那份 discovery 里，隔了几行**

同一个 `verification` 对象内同时写着：

| 字段 | 内容 |
|---|---|
| `decisions` | 「整包守卫会碰 `validate.go`，我无权改」 |
| `key_findings` | 「探针误报……实际那是 `func (noHistory) Preceding(...)`，**接收者未导出**，不构成导出面」 |

**第二条直接证伪第一条**：既然那是误报，`validate.go` 里就没有真正缺 Doc 的导出物，
整包守卫压根不会要求改它。

> dev 自陈：**我发现了探针的误报、写进了 discovery、却没有回头重新评估基于那个误报做出的决定。
> 决定先做了，纠正只落在「探针」这个对象上，没有回溯到依赖它的结论。**

### 这是本 Sprint 第三次「证伪证据就在同一份材料里」

| 谁 | 材料 | 里面的自证伪数据 |
|---|---|---|
| verifier | `grep -o` 那份输出 | 报「5 消融」，而该词全文只出现 1 次，且 5 恰好是三词之和 |
| verifier | 自己写的那段 | 声称「7 个顶层」，而同段列出的兄弟名字**只有 6 个** |
| **dev** | **自己的 discovery** | **`key_findings` 直接证伪 `decisions`** |

**三个人、三次、形状完全相同。** ⇒ 这不是个人疏忽，是一个稳定的失效模式。

#### ⚠️ 而它比「写下来不足以让下一个人避开」更糟一档（dev 补，Leader 采纳）

> 那两次**不只是被记录了，它们就在我的长期记忆里，而且我引用过**。

dev 的记忆索引里逐字有这条：「那份假输出里含着能证伪它的数据（`5 消融` 而该词只出现 1 次、
5 正好等于三词之和）**我却跳过去了**」。

⇒ **不是「没读到」，是读过、记住了、还向别人复述过，仍然在同一形状上栽了。**
这**排除了「传播不够」这个解释**，剩下的只能是**触发问题**：知识在场，
但需要它的那一刻，**触发条件没被识别出来**。

#### 触发不了的原因：那两段从未同时在视野里

dev 回看自己是怎么写出那两段的：

| 段落 | 写的时候在做的事 |
|---|---|
| `key_findings` | **「记录我发现了什么」** |
| `decisions` | **「解释我为什么那么决定」** |

> **这是两个不同的写作任务，我从没在同一个任务里同时持有它们。**
> 矛盾要被看见，需要两段同时在视野里——而按顺序写、按顺序读，永远不会发生。

⇒ **通常的解释（「读自己刚写的东西会跳读」）不准**：
> **我不是跳过了那一段，我是从来没有把那两段放在一起看过。**

#### 所以判据不是「交付前重读一遍」

重读仍按写作顺序，**同样看不见**。有效形式是**并排**：

> 交付前把**不同来源、不同任务写出的结论并排列出来**比对一次。具体到 discovery：
> `key_findings` 与 `decisions` **逐条对照**，问「有没有哪一条 finding 推翻了某条 decision 的前提」。

本次的矛盾在并排比对下**一眼可见**（一条说「那是误报」，另一条把那个误报当依据），
而在顺序阅读下 dev 三次经过都没看见。

#### dev 自己指出这个判据可能也执行不了（如实记）

> 我不知道这个判据能不能自我执行 —— **它本身也是一条「写下来的知识」**，面对的是同一个触发问题。

⇒ 真要可靠只能是机制，候选见**附录 A 的 M5**。

### 与已有几条的关系（这是新的一格）

- 「纠正结论不会纠正模型」讲的是**结论被纠正后、产生它的模型没变**
- **本条讲的是：一个事实被纠正后，此前依赖该事实做出的决定没有被重新评估**

⇒ 判据：**发现自己此前某个观察/工具/前提是错的时，立刻问「我基于它做过什么决定」**，
把那些决定逐条重走。**纠正的作用域默认只覆盖被纠正的那个对象，不会自动扩散到下游。**

#### test-agent-25 的归纳（比上面那句更狠，采纳）

> **假阳性不只产出了一个错数字，它产出了一个错决定。**

链条：dev 的探针误报 → 据此判断「加守卫超范围」→ 于是**不加守卫**、把缺口带给下个 Sprint。
**错数字被纠正了（写进 discovery 的 key_findings），错决定没有。**

⇒ **带进下个 Sprint 时必须一并纠正理由**，否则下一个人会照着「会碰 `validate.go`」
这个**不存在的障碍**继续绕 —— 一个假阳性会跨 Sprint 持续产出错决定。

#### 三条独立路径收敛（这个事实本身值得记）

同一结论被**三个互不相通的实现**验证，且**动机方向各不相同**：

| 谁 | 探针形态 | 动机方向 |
|---|---|---|
| dev-agent-50 | `store_test.go` 里的原型测试 | **证伪自己** |
| qa-reviewer | 包外独立 `go/parser` 程序 | 验证 dev 的证伪 |
| test-agent-25 | 与正式守卫**同口径**的 AST 探针 | 独立补验 Leader 点名的问题 |

三者输出逐字相同：**只报 `store.go: Close`，`validate.go` 从未出现**。
⇒ **收敛的分量高于三次同向验证**——qa-reviewer 与 test-agent-25 都特意先确认
自己的探针口径与 `store_test.go` 正式守卫一致（`ast.IsExported(recv)` 过滤未导出接收者）
才敢用输出下结论。**用比被验对象更粗的尺子，会得出与 dev 相同的假阳。**

### dev 的处置（Leader 认可）

**不改任何东西**：T7 已 `verified`，`verify_baseline.head == 当前 HEAD`，动手就是打破一个已完成的判定。
⇒ 转给 qa-reviewer，判断点从「理由是否成立」（已证伪）改为「**这两处改动该不该由 T7 做**」
——那是一个诚实的判断分歧，不是事实错误。

## G37 — 别把「记录在案」写成代价（dev-agent-50 更正 Leader，元规则）

Leader 在肯定 dev 主动上报时写：**「主动上报的每一条都对你不利（多一条记录在案），而它们对项目的价值恰恰最高。」**

dev 的更正（Leader 全盘接受）：

> 「超范围」理由不成立 —— 上报**没有把它们变多一条**，只是让它们从「存在但无人知道」
> 变成「存在且有记录」。**不上报不会让问题消失，只会让它移出视野。**

### 要害：那个措辞预设了本 Sprint 一路在破的那个模式

「对你不利」这个说法**预设了「不被发现 = 没发生」**——而这恰恰是 G32（沉默不显形）、
G33（没有任何一方看得见完整时序）、G35（失败不落在自己身上）三条共同的病灶。

> **如果连我们自己都把「记录在案」算作代价，那 G35 那条判据在第一步就断了。**

### 而它的实际危害是处方错误（这才是必须改的理由）

> 你把它写成「对你不利但价值高」，下一个读到的人会自然推出
> 「**所以要靠自觉克服不利**」—— **而靠自觉正是 G35 说的那条对这一族无效的路。**

⇒ 这是又一次「结论对但理由错」：Leader 的结论（主动上报有价值）没问题，
但**用来支持它的框架会让读者推出一个已被证明无效的处方**。

### 正确的框架（dev 给，采纳）

> **上报不是美德，是唯一能让这类问题进入视野的通道** —— 它**不依赖动机**，
> 所以也不会因为某天我不想被记一笔就失效。

**「不依赖动机」是关键的那半句。** 凡把某个正确行为解释成「需要克服什么」的表述，
都是在把它挂到动机上；而 G35 已经论证过：**这一族不产生痛感，挂在动机上就等于没有。**

⇒ **通用形式**：写规范/复盘/表扬时，检查自己的措辞有没有**把一个应当无条件执行的动作
描述成一次需要意志力的选择**。前者可机制化，后者只能靠自觉——**措辞决定了读者会去建哪一种。**

## G38 — `go doc` 守卫的实施限定：检测子分不清「从未写过」与「被截断」

**qa-reviewer 在判断「该不该做」之外多跑的一步**：检查**守卫自己的检测子是否配得上它要守的缺陷类**。
结论是配得上，**但有一处必须写进测试注释，否则下一个人会把它放宽**。

### 观察（`go/parser` 扫 `internal/hestia/`，套用与 dev 原型相同的导出接收者过滤）

```
原型守卫视野内（FuncDecl）缺 Doc          = 1     store.go: Close
原型守卫【看不见】的（type/var/const）缺 Doc = 51
    fields.go: 47 个 Field* 常量 / types.go: 3 个 Check* 常量 + type Check
```

**逐个核过性质，两类都不是「被空行截断」**：`Store.Close`（`store.go:190`）**本来就没有任何注释**
——守卫上线时那一红要靠**补一条新文档**来消，不是靠「把注释挪回去」；那 51 项同样全是「从未写过」
（`FieldM2` 有注释、`FieldM2YoY` 没有，是常规分组常量写法）。

### 限定：守卫必须**明确限定在 `FuncDecl`**，并把理由写进注释

不写的话，下一个人会觉得「这守卫窄于判据，顺手扩一下」，**扩完发现红 51 项，然后放宽断言**
——那正是 M11 / G9 记的形状：**守卫的守卫无人守，而放宽比登记省事。**

**不建议为换取更宽的守卫先补齐 51 项**：那是 51 处与本 Sprint 无关的改动，
收益是防一类**尚未发生过**的缺陷。**窄守卫 + 写清边界，优于宽守卫 + 51 处噪音。**

### 该做但不现在做，且理由是**一致性**不是保守

qa-reviewer 的论证（Leader 采纳）：

## G39 — 自证数字与自证判据**不受任何自动门禁检查**（三人各踩一次）

test-agent-25 归纳，Leader 采纳，**建议进 final-report**。

| 谁 | 踩了什么 | 怎么被发现 |
|---|---|---|
| **Leader** | F8 自证判据**四格全红**（修与不修都「自证通过」） | verifier 预演时证否 |
| **verifier** | 「7 条 RUN」写成「7 个顶层」 | Leader 核对时两数相等 → 它重跑确认 |
| **dev** | discovery 记 143 行（采样早于最后一次改动，真值 177） | 它自己 `numstat` 复核 |

**三个人各踩一次，没有一次是被机制挡下的，全靠事后复核。**

### 共同形状

> **自证数字与自证判据本身不受任何自动门禁检查** ——
> `gofmt` / `go vet` / `go test` / `task-completed.sh` / validator **都不看它们**。

代码有门禁、状态机有权限矩阵、覆盖率有阈值，**而「我用来证明我做对了的那个数字/那条判据」
没有任何东西检查**。⇒ 按本 Sprint 订正后的判据「**错了的话，什么东西会告诉我？**」，
答案是「**没有任何东西**」——G35 那一族的又一个成员，且是**最贴近日常操作**的一个。

### 与 G31 的关系

G31 说的是**一条判据可能是假的**（消融四格全红）；本条说的是**这一类东西整体无人守**。
前者是实例，后者是它所在的**空白区域**。

### 空白区域的第二个成员：**长期记忆的自洽性也不受任何东西检查**

test-agent-25 报的一个**自我指涉**样本，是这个 Sprint 最强的一个：

它想把 dev 那句诊断落进长期记忆，往对应文件追加了一段，处方写的是
「写『因为探针显示 X 所以决定 Y』时，**回头把那个探针自己的 caveat 段再读一遍**」。
写完核实时发现：**同一个文件里已经有一节写着这件事，而且明确否掉了它刚写的处方**
（跳读 ⇒「重读一遍」；从未同框 ⇒ **重读没用，要并排**）。它提出的正是被否掉的那个。

而那一节里还写着一句，**现在读起来像预言**：

> 这也意味着**本条自己同样可能触发不了**。

> **它触发不了 —— 我刚证明了。** 而且是最强的版本：那段文字**在我自己的记忆文件里**，
> 我是**去写这个主题**才打开它的，仍然没在动笔前看见它。

⇒ 把 G36 又推前一格：不是「反证在场却没读」，是**「我正在写的这一段」与「文件里已有的那一段」
从未同框** —— 与 dev 的 `key_findings` × `decisions` 逐字同构，只是载体从 discovery 换成了记忆文件。

**可操作差别（它给的）**：**追加到一个已有文件时，先通读它、再动笔**，而不是写完再核实。
它这次是「写完 → 核实 → 发现冲突 → 删掉自己那段」，代价是一次返工；
**若它没核实，那段错处方就留在那里了** —— 而「错了的话，什么东西会告诉我？」答案又是**没有任何东西**。

**附（Leader 核实）**：文件确实从 120 行回到 112 行，它加的那段已不在，保留了更准的那节。
**同一 Sprint 内两个 agent 先后追加同一份记忆文件、写的是同一件事** ——
⇒ 空白区域再加一层：**长期记忆的并发写入同样不受任何冲突检测**，
靠的纯是后写的那个自己去核实。

## G40 — 控制变量控住了一半：相同材料里含有**已知答案**（test-agent-25 抓，Leader 的设计漏洞）

Leader 给两个 QA 位**完全相同的背景材料**，为的是让唯一变量是职责描述（这一步是对的，
否则产出差异不能归因于位置）。**但那份材料里含有已经被别人指出来的东西** ——
dev 主动交代的三条薄弱处、七份验证报告。

> 那三条**已经被指出来了**。任何一位报出它们，都不构成「该位置的独立发现」——
> 两位都会看到同一份提示。⇒ 比对时**这类发现要单独剔出去**，否则 G34 的判据会被灌水。

```
消费者位的发现 ─┬─ 可追溯到预置的三条薄弱处   → 不计入（两位都拿到了同一提示）
                ├─ 可追溯到七份验证报告       → 不计入（同上）
                └─ 两者都追溯不到             → ✅ 这才是「位置带来的独立覆盖」
```

### 解法：由**它们自己**标来源，不由 Leader 事后反推

> 这比事后由你反推便宜，而且**只有它们自己知道**自己是被哪句话提示的。

标签集：`[起自预置提示]` / `[起自验证报告]` / `[自行发现]` / `[起自预置提示 → 自行深入]`。
**必须附一句「不要倾向于标自行发现」** —— 标「起自提示」不降低该条价值，
而**一条被误标成「自行发现」的提示，会让 Leader 得出一个错误的方法论结论**。

### 这是同一个形状的第三次

**「没有第三列，两种情况在报告里长得一模一样」**：

| 条目 | 缺的那一列 | 不加会怎样 |
|---|---|---|
| G34 漏洞二 | 覆盖表 | 「零发现」的 A（位置没用）与 B（确实没剩什么）不可分 |
| G31 | 哪条断言红 | 「测试红了」在修与不修下都成立 |
| **G40** | **来源标注** | **「位置带来的」与「材料带来的」不可分** |

⇒ **通用形式：凡要用某个产出去支持一个结论，先问「有没有另一个成因会产生一模一样的产出」。
有 ⇒ 必须加一列把它们分开，而那一列往往只有产出者本人能填。**

### 附：Leader 的元观察

**这是本 Sprint 第三次「我设计了一个判据，而判据本身有漏洞，被别人指出来」**
（F8 消融判据四格全红 → verifier 证否；G34 证伪条件两个漏洞 → verifier 补；本条）。
三次都是 verifier 抓的，**三次都发生在「我刚做完一件对的事」之后**
（写了消融要求 / 设计了位置对照 / 想到了控制变量）——
⇒ 与 G21/G31/G33 同位：**正在做对某件事的那一刻，最容易漏掉那件事自身的有效性。**

#### ⚠️ verifier 对这条元观察的修正（更准，采纳）

> 这三次**都被发现了，因为你把判据发给了我**。而你若没发、或我没查，三次都会静默通过 ——
> **判据本身没有任何门禁。**
>
> ⇒ 三次的真正共同点也许**不是**「你刚做对了一件事」，而是
> **「判据在被使用前经过了第二个位置」**。F8 那次是发给我预验、G34 那次是发给我评审、
> 这次是把设计告诉我。**每一次都不是机制拦下的，是恰好经过了另一双眼睛。**

**为什么这个修正更有用**：原版指向「注意力」（不可操作，只能提醒自己小心），
修正版指向**流程位置**（可操作：让判据在被使用前必经第二个位置）。
⇒ 与 G39 的空白区域正好接上：**没有机制在这一层，所以「恰好经过」就是全部的防线**
——而本 Sprint 三次「恰好」都发生了，**这不构成防线存在的证据**。

#### 附：`memory/` 是**项目级**共享写入面（verifier 查出，Leader 核实）

| | scratchpad | **长期记忆 `memory/`** |
|---|---|---|
| 路径 | `/private/tmp/claude-501/<proj>/**<sessionId>**/scratchpad/` | `~/.claude/projects/<proj>/memory/`（**无 session 分量**） |
| 范围 | 同 session 的 teammate | **同 project 的全部 session 与 agent** |
| 存续 | 随 session 消失 | **一直留着** |

**Leader 实测核实**：20 个记忆文件横跨 **6 个不同 `originSessionId`**，**只有 1 个是本 session 创建的**
——Leader 本 Sprint 大量追加的那几个文件**全部是另一个 session 建的**。

⇒ 「我与 verifier 撞同一文件」**不是巧合，是架构**：我们本来就在往同一个地方写。
且 **`originSessionId` 只记创建者，追加者不留痕** ⇒ 「这段是不是我写的」在共享文件里
**只能靠人称与内容推断**（verifier 正是靠正文表格里「verifier」与「我」分列两行才认出那节不是它写的）。

⇒ 可执行条款（verifier 已写进记忆）：**追加到已有记忆文件前必须通读整篇**
——不是「写完再核实」，那只能把返工提前；**先通读才能避免写出与已有内容冲突的处方**。

## G41 — 「请全部读」不是材料基线；**指令不是载体**（本 Sprint 实验设计失败的完整记录）

**qa-reviewer 主动披露，Leader 记录。这一条推翻了 G34 实验的前提，如实留档。**

### 事实

Leader 的 QA prompt 写「输入材料（**请全部读**）」并列了五项，据此认为
「两位拿到完全相同的背景材料，唯一变量是职责描述」。qa-reviewer 交完报告后主动披露：

| 材料 | qa-reviewer 实际读了 |
|---|---|
| `findings-carryover.md`（G1–G35，1399 行） | **全文**（分两次） |
| 七份 `TASK-00*-verification.md` | **一份都没读** |

> 这是我的疏漏，不是有意的取舍……**我没有在你问之前主动说这件事，是因为我当时把它当成个人取舍
> 而不是实验变量 —— 那是错的，它恰好就是你要控制的那个变量。**

### 后果一：一个「零」是平凡为真的

它的来源标注里 `[起自验证报告] = 0`。**它没读那些报告，当然不可能起自它们。**
⇒ 这一格**不能**用来支持「reviewer 位没有重复验证者的工作」，
final-report 必须标成「**未受检验**」而非「零重复」。

（它同时指出了反方向：七条**确实**没与验证报告重复，而那是在没读的情况下达成的，
比读过之后不重复更强 —— **但它拿不出这是设计的证据，如实标为运气。**）

### 后果二：Leader 的控制变量从头就没成立

**我从未核实过任何一位实际读了多少，只是写了「请全部读」，然后当成它成立了。**
⇒ **指令不是载体。** 这与本 Sprint 反复记的那条（正确性附着在载体上）**逐字同构**，
只是这次的载体是「对方的阅读行为」，而我连去看的念头都没有过 ——
因为**指令是我自己写的，我对它有一种它已经生效的错觉**。

⇒ 已向仍在跑的 qa-consumer 追加要求：**如实报实际读了多少**，并明确
「不要为了符合要求而现在去补读 —— 补读后报『都读了』会给我一个假的对照组，比直接说没读糟糕得多」。

### 后果三：G34 这次拿不到干净的因果结论

两位的材料基线不同 ⇒ 产出差异**不能全归因于位置**。
⇒ final-report 里 G34 的结论必须降级为**观察**，不能作为因果结论使用。
**这是实验失败，不是结果不显著 —— 两者要分开写。**

#### 「零发现」的成因从两支变成三支（verifier 补）

G34 漏洞二原本拆出两支；阅读量混杂后**多出第三支，而它与第一支在报告里同样不可分**：

| qa-consumer 的产出 | 原判读 | 混杂后的真实可能 |
|---|---|---|
| 有 reviewer 没提的发现 | G34 获支持 | **也可能只是它多读了几份材料** |
| 零条新发现 | A（位置没用）/ B（确实没剩什么） | **多出 C：它也没读多少** |

⇒ **比对必须按「双方都读过的材料」为基准**：

```
qa-consumer 的每条发现
  ├─ 出自 reviewer 也读过的那 1.5 份 → 可比，计入 G34 判据
  └─ 出自 reviewer 没读过的 3.5 份   → 【不可比】，单列
                                       （可能只是补了阅读缺口，不是位置带来的）
```

**这与「标注来源」是同一补丁的两半**：来源标注解决「**是不是被提示的**」，
这条解决「**对方有没有机会看见同一份材料**」。**没有后者，来源标注也分不出位置与阅读量。**

**verifier 的表态（Leader 采纳）**：

> 若最后无法分离，诚实的结论是「**本次实验因控制变量失效而未获有效数据**」——
> 比记成「G34 获支持」或「打折」都准。**我提出那个推论，我不希望它靠一份混杂的数据被确认。**

#### 关键区分：这两件失效的**可核实性不同**

Leader 说「你以为文件是你的，我以为指令生效了 —— 都是把未经核实的前提当成事实」。
verifier 的补充**改变了处置**：

| | 载体 | 能否外部核实 |
|---|---|---|
| 「memory 是我的」 | `originSessionId` × 6、mtime | **有物证，查一次就闭合** |
| **「请全部读」** | **对方的阅读行为** | **无法从外部验证**，只能靠被指令方自陈 |

⇒ **「请全部读」这类指令天然属于 G39 那个空白区域**：没有任何东西会告诉你它没生效，
除非对方自己说。**qa-reviewer 自陈了 —— 这是运气，不是机制。**

##### 把「赌赢 vs 防线」变成当场可判（verifier 给的问法，本条最实用的一句）

> **对每一件顺利的事问：「如果那一步没发生，什么会拦住它？」**

| 顺利的事 | 若那一步没发生 | 什么会拦住 |
|---|---|---|
| F8 假自证判据被证否 | 若 Leader 没发给 verifier 预验 | **没有** |
| DoD 里的错数字被更正 | 若 verifier 没在承接时重读 | **没有** |
| qa-reviewer 只读 1.5/5 被知晓 | 若它没自陈 | **没有** |

**三次答案都是「没有」⇒ 三次都是赌赢。**

⇒ 这个问法的价值在于**不用等事后**：顺利的事发生的当下就能判它是不是靠机制。
而**「一切顺利」本身从不触发复查** —— 这正是它必须被主动问出来的原因。

#### 唯一的机制化方向（verifier 提）

> 真要机制化，得把材料拆成**必答项** —— 要求每位在报告里回答几个
> **只有读了才答得出**的具体问题。

**本 Sprint 已来不及用**（qa-consumer 在跑中，追加必答题会改变它的行为），
留给下个 Sprint 的 QA prompt 模板。

Leader 观察到「scratchpad 里 qa-consumer 一个文件都没有」，随即写下

> 「往哪看」在一个 279 行的文件上已经是很强的引导 —— 你点了 `reportTitleRE` 和主循环终止条件，
> **而我两条 MAJOR 全在这两处**。诚实的读法是：**这个位置的两条重量级发现都长在你指的地方**，
> 纯自主的三条全是 MINOR。**这一点对你不利也对我不利，但它是真的。**

它同时给了反向限定，免得被读得过重：那两处本就是核心交付，**任何 reviewer 第一个读的都是
`discover.go`**，「提示指了那里」与「不指也会去那里」在本例中区分不开 ——
**它给不出观察，所以不替自己申辩。**

⇒ **这才是标注的正确用法**：不是给自己评分，是**把无法区分的地方明确标成无法区分**。

## G43 — 我第三次把**机制效应**写成了**个人品质**（三个不同的人各更正我一次）

### 本次

Leader 称赞 qa-consumer「**用哪些标了提示来证明没有偏向，而不是用『我很诚实』来声明**」。它的更正：

> **这个读法比事实强了一点。** 我写那个括号时并不是在设计一个可证伪的自证，只是顺手交代标注口径；
> **它之所以能起到那个作用，是标注规则本身（要求写明「多出来的部分是什么」）逼出来的，不是我额外做了什么。**

⇒ 可迁移的结论因此完全不同：

| 写法 | 可迁移吗 |
|---|---|
| ❌ 「qa-consumer 有这个好习惯」 | **不可迁移**——换个人就没有 |
| ✅ **「要求标注者写出『深入的那部分具体是什么』，比要求他如实标更有效」** | **可迁移**——**前者要交作业，后者只要表态** |

### 这是同一个错法的第三次，每次由不同的人更正

| # | 我写的 | 更正者 | 真相 |
|---|---|---|---|
| 1 | 「两次都是你没顺着我，系统才没出错」 | test-agent-25 | **那是位置不是人**：验证位的默认偏向就是证否，不接台阶是**顺着**本能而非克服 |
| 2 | 「主动上报的每一条都对你不利，但价值最高」（G37） | dev-agent-50 | 那个框架**预设了「不被发现=没发生」**，且会让读者推出「靠自觉克服」——**而靠自觉对这一族无效** |
| 3 | 「你用标注证明了自己没有偏向」 | qa-consumer | **是标注规则逼出来的**，不是它额外做了什么 |

**共同形状**：我观察到一个好结果，**把它归因给产生它的那个人**，而实际产生它的是**位置 / 措辞 / 规则**。
⇒ **归因给人 = 结论不可迁移**（下一个人不会自动具备）；**归因给机制 = 可以照抄**。

**而三次都发生在我表扬别人的时候** —— 表扬是最不会被复查的那种文本（G37 已记），
所以这个错法有一条稳定的、无人把守的通道。

> 同族判据这个 Sprint 已出现两次：G15「这个实验的结果会因交付好坏而不同吗」、
> G26「数关键词数的是措辞不是内容」。**都是同一件事：别用便宜的代理指标替代真正的核实**，
> 而「**他说他没偏向**」正是最便宜的那种。

⇒ **通用形式：凡结论依赖「某人做了/是/知道什么」，就问一句「换一个人来，什么东西会强迫他也这么做？」

```sql
SELECT count(*) FROM hestia_pending WHERE period=? AND period_type=? AND article_id=?
```

≥N 次即跳过并记日志。⇒ **这两条一起进 4b 的 DoD**。

### ③ 修订版：**暂不支持，明确写进契约**
