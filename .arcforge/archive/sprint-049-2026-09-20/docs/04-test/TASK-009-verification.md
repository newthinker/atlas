## §7 🔴 我查到的一处缺陷：V-6「正对照不可省」结论对而理由不完备

**不构成 REJECT，但建议订正。** 这是本任务 `error_handling` 那条 DoD 立意（「结论对但理由错」）的一个现成实例。

文档写：

> 只看守卫符号命中 0，无法区分「二进制是旧的」与「`strings`/`grep` 根本没在工作」（路径写错、文件不可读、`grep` 模式打错都会给 0）。`crisis` 那个数非 0，才说明工具链在工作、**那个 0 是真的 0**。

我把三种成因逐个实测：

| 成因 | 守卫列 | 正对照列 | 正对照挡得住吗 |
| --- | --- | --- | --- |
| 二进制是旧的 | 0 | 318 | —（这正是要检出的） |
| 路径写错 | 0 | **0** | ✅ 挡得住 |
| 🔴 **`grep` 模式打错**（`verifyBitemporalShap0`） | 0 | **355** | ❌ **挡不住** |

**推理链第二步断了**：正对照非 0 ⇒ 工具链在工作（**对**）⇒ 那个 0 是真的 0（**不成立**）。
「工具链在工作」不蕴含「我要查的那个模式打对了」——两个模式是独立的，打错其中一个不影响另一个。

文档的二分法（「二进制旧」vs「工具链没在工作」）**漏了第三种：工具链在工作，但问的问题不对**。

⚠️ **这个洞正好落在该段自己的主题上**（它的全部意义就是防「假 0」），而且它给出的保证**强于它实际能提供的**——读者会以为查了正对照就安全。

**建议订正**（一句话即可）：正对照能排除「文件读不到」，**不能**排除「模式打错」；后者要靠**把守卫符号从源码里复制出来**，而不是手敲。

### 为什么这不构成 REJECT

1. **六条 DoD 的字面判据全部满足**，这条缺陷不在任何一条 DoD 的覆盖范围内（DoD 没有要求「防假 0 的推理必须完备」）；
2. **结论方向正确**——「正对照那一行不可省」这个结论是对的，错的只是它声称的覆盖范围；
3. 修复成本一句话，且属于增强而非返工。

⇒ 交由 Leader 决定是否要 dev 补一句。**我把它写在这里，是因为若不写，下一个照做的人会以为正对照是完备的。**
