## 机制发现（本 sprint，交 final-report 与 PENDING-MECHANISMS）

**M-1 问答窗口不对称，且代价是「裁决没有载体」。** 提问方 dev 在 `in_progress` 就能写 `questions`；
答复方 leader 要落盘 answer，必须任务落在它持有的格子里。本次实际：dev 23:19:18 转 `dev_done`、23:20:52 派验，
窗口 94 秒 ⇒ 即使一条消息都没丢，晚于该窗口的答复同样写不进去。**代价不是「dev 空等」，是裁决没有载体**
——TASK-002 的 D1/D2 三次没到 dev 手上，`questions[0].answer` 至今 null，验证者只能靠 plan.md 的散文还原裁决。

**M-2 `blocked_clarification` 是全表唯一的双写者格子**（`owner_table` 实读：leader 可写的格子共 7 个——
pending/assigned/review_fix/accepted/skipped/blocked_clarification/blocked_human；而 `length>1` 的只有
`blocked_clarification: ["leader","dev-*"]`）。其余 6 个都要 leader **先把任务收回自己手上**才写得动，
只有这一个能在**任务仍在 dev 手上**时写——这正是「用它换答复可落盘」这条纪律成立的性质。
⚠️ 框架整篇建立在「同一 task 任意时刻只有一个 owner」上，**而这张表恰好有一个格子是例外，用这条纪律的人正好踩在例外上**。

**M-3 同一性质带来静默互吃，审计看不见**（test-m4c-a 实撞过一次，覆盖了 leader 写的 answer）：
`arcforge-write.sh:276` 的 `def strarr: type=="array" and all(.[]; type=="string")` 决定 `added`/`removed`
只对**字符串数组**（packages/writes）生效；`questions` 是**对象数组** ⇒ 落 `else` 分支只记 `{type:"array",len:N}`。
而 `--json-field` 对数组是**整数组替换、无 merge**。⇒ 「leader 写 answer → dev 用转状态前读到的那份整体替换」
这条路径上 answer 消失，审计行只显示长度变化，**谁都看不出少了一个 answer**。

**M-4 因此纪律取「单写者约定」而非「写前重读」**：`blocked_clarification` 期间 dev 转进来后不再碰 `questions`，
等 leader 写完 answer、由 dev 自己转回 `in_progress`。理由：重读依赖人在正确时刻想起来，而这是全表唯一的
双写者格子、最不该依赖自觉的地方。

**M-5 但单写者去掉了竞态、去不掉沉默——纪律还需两个终止条件**（test-m4c-a 补，出边实读确认）：
`blocked_clarification` 的出边只有 `→ in_progress`（dev-*）与 `→ blocked_human`（leader）⇒ **dev 没有任何自救出边**。
若 leader 的答复消息丢失而 dev 遵守单写者约定，它会一直等下去，且该状态在 leader 的周期扫描里与「dev 正在合法等你」完全同形。
故补两条：
1. **dev 侧推进条件写成可观测的**：轮询自己那份任务文件的 `questions[-1].answer != null`，非空即转回 `in_progress`
   （这条边本就是它的）。**不靠收到通知**——通知正是会丢的那一环。
2. **leader 侧把这个格子纳入 `stale-dispatch`**：CLAUDE.md 现文是「`blocked_clarification` 只在 questions 全部已答复时才可能命中」

   ——前者不该告警、后者该。判据：`answer != null` 且仍停在 `blocked_clarification` 超阈值 ⇒ dev 没接住，该重发。

**M-6 变异有效性闸的补充判别式**（test-m4c-a 实撞两次）：编译失败会让套件全面变红而 `--- FAIL:` 一条都没有

**或「rc≠0 且 FAIL 列表为空」**（后半条必要：vet 未必拦得住只在测试文件里的编译错）。

## M-16 生产迁移查出的三个机制事实（都与迁移本身无关）

### M-16a 🔴 `cp` 原地覆盖二进制 ⇒ SIGKILL，而三项静态核实全过

症状：`bin/atlas` 的**任何**子命令 `rc=137`（128+9）、**stdout 与 stderr 全空、无日志**。
当时 `sha256` 一致、`codesign -dv` 逐字段相同、可执行位正确——**三项全过**。
成因：`cp` 原地覆盖保持 inode，macOS 内核对该 inode 缓存了**旧二进制的代码签名**。
修法：`rm` 释放 inode 再 `cp`（实测 `216433589` → `220870847`）。

⇒ **`sha256` + 签名 + 可执行位全对，不足以证明二进制能运行。** 若只核这三项就宣布部署完成，
第一个撞上的是**无人值守的定时任务**（本次是 `crisis-daily` 22:45），排查者看到的是
「二进制一切正确、一跑就死、没有任何日志」——**本次整个迁移里最难归因的失效形态，
而它不由迁移引入、纯粹由部署手法引入**。

**这一跑是 Leader 要求的「部署后必须实际调一次 crisis 命令」**，本意是验守卫，结果验出了一个与守卫无关的问题。
已按人类直接指示持久化到 `docs/deployment.md`（三个新小节）与 **`scripts/ops/deploy.sh` 头注释**
（后者因为**执行部署的人一定会打开脚本，而手册要主动去翻**）。

### M-16b 🔴 AD-11 的前提为假：反序不是「响亮失败」，是「静默污染」

我们原以为「先部署后迁移会让三个 crisis launchd 任务**失败**」。dev 实测：**不失败**。
成因：老二进制的 `INSERT OR REPLACE` **本来就带 `fetched_at`** ⇒ 三段主键下从「替换」变成「**追加**」；

状态判定错 → 落进 `crisis_evaluations`、可能发 Telegram，**且全程不报错**。

⇒ **结论不变（先迁移后部署），理由反转。** dev 的措辞：**「不是怕它崩，是怕它不崩。」**
⚠️ 而「任务会失败」其实是**好事**（会被发现）；「任务会成功但算错」才是要防的。

### M-26a 由此得出的一般形式，以及它推翻的那条旧教训

> **回放类产物（导出 / 备份 / 回滚脚本 / 迁移脚本）的测试环境，必须是「使用它的那一刻的环境」，不是干净环境。**
> 干净环境测的是产物的**合法性**，只有受损环境测得了产物的**可用性**。
> 判别式：问「**这个产物会在什么状态下被使用？**」然后把测试环境布置成那个状态，**而不是布置成最容易复现的状态**。

⚠️ **它修正了本 sprint 已有的一条记录**（来自 dev-agent-55 的自查）：「交付物的可用性要在一个干净环境里照着自己写的说明再跑一遍」。

**两条都对，各有适用类 —— 这是本 sprint 第一次出现「新教训推翻旧教训」**：

| 对象类 | 正确的测试环境 |
| --- | --- |
| 留给别人跑的脚本 / 复现说明 | **干净环境**（验「说明能不能跑通」；正是为了暴露「你的路径锚指向了只有你有的目录」） |
| 回放类产物（导出 / 备份 / 回滚 / 迁移） | **使用它的那一刻的环境**（验「产物能不能用」） |

⚠️ **两者用同一句「验可用性」来描述 —— 这正是它们会被混用的原因。** final-report 请原样放这张表，**不要压缩成一条通则**。

🔴 **这一类（旧结论在一类对象上对、在另一类上正好相反）比「旧结论错了」更危险**，机制是：

> **人对它的信心，来自它成立的那一类；而它被误用，正是在推翻它的那一类上。**

（同形：「坏仪器在粗粒度下给出正确答案 ⇒『我以前用它没出过错』不构成它可用的证据」。）

## M-39 🔴 方法的采用是被事故驱动的，不是被判据驱动的

**这是本 sprint 唯一一条能预测「下次会在哪里复发」的观察**，出自验证者对自己两次错误的归因。

它自己的归因：

> 差别不在我懂不懂这个方法，在于 **TASK-008 那里我被打过脸（第 2 轮判错），TASK-007 这里没有。**
> ⇒ **方法的采用是被事故驱动的，不是被判据驱动的** —— 这比「这次我疏忽了」更值得记，因为它预测了下一次会在哪里复发：**在我还没被打过脸的地方。**

⚠️ 这条解释了本 sprint 反复出现的「写下纪律 ≠ 用上纪律」为什么不是意志问题：**纪律被写下时附着在它诞生的那个场景上**，迁移到一个还没出过事的场景需要一次额外的动作，而那个动作没有任何东西会触发。

⇒ **可操作的推论**：审查一份交付时，不要只问「它违反了哪条纪律」，要问「**这条纪律是在哪个场景下立的？当前场景与它有多远？**」。距离越远，越需要主动检查，而不是指望它自动适用。

### M-39a 两个错误的具体失效机制（都比「粗心」更具体）

**错误 ①：没做控制变量。** 它测的那个输入**同时有两个属性**（带偏移 ∧ 小数位不足），失败了，它把失败归因给了当时正在想的那个属性。穷尽 5×6 矩阵后成因直接显示出来：

```
小数位\时区    Z      +08:00  -05:00  +00:00  z小写   无时区
9位           ✅收    ✅收     ✅收     ✅收     ❌拒    ❌拒
9位非零        ✅收    ✅收     ✅收     ✅收     ❌拒    ❌拒
6位/3位/整秒    全部 ❌拒
⇒ 失败是按行成立的（小数位不足），不是按列（带偏移）
```

⇒ **单变量结论必须在其他变量固定时求值**；拿一个混杂两变量的输入去判定单变量的作用，得到的归因是任选的。

**错误 ②：把「被验对象给的那一格」当成上界。** 穷尽尾随零 0..9：9 格削 0~8 位（≤1µs），**只有尾随零=9 那一格**削满 10 位变整秒（过包含 999.999999ms）。注释挑的 `.150777000Z`（3 个尾随零）恰好落在那 9 格里。

> 我实测了它，而且测对了 —— 这正是最麻烦的地方：我做对了每一步（自己写程序、不采信注释里的数、逐条实测），**唯独没问「这一格是不是上界」**。

⇒ **判别式**：被验对象给出一个**量**（≤X／最多／上界／至少／全部／唯一）时，实测它给的那个例子只能证明「该例子下成立」。**上界断言的验证集不是它给的例子，而是自己构造的极值。** 要证伪一个上界只需一个反例，而**反例一定不在它自己挑的例子里 —— 否则它不会那样写。**

⇒ 验证者已把它固化成承接动作（不靠记）：**凡 `fix_items` 里出现「≤X」「最多」「上界」「全部」「唯一」这类量词，一律先构造极值/穷尽小矩阵再判，且报告里写明穷尽的维度和格数。**

### M-39b 顺带查出的第三件：C 接受 `±00:00`，与第一轮缺陷同形

穷尽矩阵的右起第三列显示 **9位 × `+00:00` ⇒ ✅收**。⇒ 若采用 C 方案，**零偏移文本形态会原样透传进 SQL** —— 正是 TASK-007 **第一轮**查出的那个 `±00:00` 缺陷的同一形态。

⚠️ 验证者给 dev 的建议里那句括注最要紧：

> 否则读者会以为「偏移」只指非零偏移，**而那正是第一轮漏掉它的原因。**

## M-40 🔴 「位置不同」而非「谁更强」——返工轮的默认动作顺序要反过来

## M-41 同一列数字里，口径可以在最后一格悄悄跳变

## M-48 Leader 把处方机械化时引入了一个静默错误，而正例掩盖了它

### M-53a 根因不是「加段长闸」，是「markdown 里空行不是段落终止符」

**错 2 —— 模拟本身无效**：`git log --all -S'串' <ref>` 里 **`--all` 让那个 ref 形同虚设**：

```
git log --all -S'columnsNotMigrated' b43832e~1   ⇒ 命中 1   ← 整个仓库都算进去了
git log       b43832e~1 -S'columnsNotMigrated'   ⇒ 命中 0   ← 正确
```

🔴 **两个错互相暴露了对方**：若不是硬编码结论与数据打架逼人去看，「模拟成立」这个假前提不会被发现。**这次是运气，不是设计。**

### M-54c 「我的模式漏了 X 形态」是关于世界的知识，不是关于他的轶事

验证者替 Leader 验 `plan.md` 引用完整性时，**第一版报「8 个悬空引用」—— 假的**，成因是它只认标题式定义，而 `M-1`~`M-8` 定义在**粗体行**。

> **Leader 在同一条消息里刚告诉过我这件事**（他自己踩过同一格）。**我读到了，然后在下一条命令里原样踩了一遍。**
> 成因不是没看见：我构造模式时想的是「标题 vs 引用」这个二分，而他说的是「**定义点还有另一种形态**」—— **我把它读成了一条关于他的事实，没读成一条关于「定义点有几种形态」的知识。**

⇒ **固定动作**：

> 别人告诉我「我的模式漏了 X 形态」时，那是一条关于「**X 形态存在**」的知识。收到后要问的是「**我手上哪些检查也用了同一个模式？**」，而不是「知道了」。

**Leader 照此自查的结果**：第④项假绿防护用的是 `-S '<串>' | wc -l ≥ 1`，**同样是数量判据**（与 ops 那道段长闸同构）⇒ 它的性质保证来自**串的选择**（必须是本轮新增独有），**不来自那个计数**；若串选了跨版本都存在的字串，命中 ≥1 但什么也不证明。该局限先前未写出，已补。

⚠️ 最终结果：`plan.md` **零悬空引用**（标题式 78 ∪ 粗体式 8 = 86 = 文件内 M-编号总数 86）。**改描述性标题、保留编号的做法没有打断任何引用。**

## M-55 🔴 「特征串的区分力」必须自验 —— 选错是默认结果，不是偶发

### M-55a 🔴 ①「从 diff 挑」单独不够 —— Leader 实测补的一格

`git diff` 的 `+` 行里**会出现已存在的标识符**（新增代码当然要引用旧符号）⇒ **「它出现在新增行里」≠「它是本轮新增的」**。

⇒ **①只把候选集缩小到合理范围，②自验才是判据。** 若有人只做①会以为已经安全。

**两步的可照抄形式**：

```bash
# ① 候选从 diff 抽，不从记忆抽
CAND=$(git diff "${BASE}~1..${BASE}" -- "$FILE" | grep '^+' | grep -v '^+++' \
       | grep -oE '[a-zA-Z_][a-zA-Z0-9_]{12,}' | sort -u)
# ② 区分力自验，进条件不进旁白
N=$(git log --oneline -S"$STR" "${BASE}~1" -- "$FILE" | wc -l | tr -d ' ')
[ "$N" = 0 ] || { echo "🔴 '$STR' 在基线前已存在($N) ⇒ 区分力 0，判定不成立"; exit 2; }
```

⚠️ **`-S` 不要带 `--all`** —— `--all` 让那个 ref 形同虚设（M-54b），自验会恒过。

⚠️ 验证者的提醒：**Leader 早就有这个工具了** —— 他跑的那张验收表（「基线前 0 / 现在 1」）正是它，只是**用在了「检查的验收」上，没用在「串的选择」上**。⇒ 这是 M-54c 的又一实例：**同一个工具，只用在了自己想到的那个位置上。**

## M-56 🔴 两人同一小时、在演示同一条处方的命令里，各自犯了它一次

## M-59 🔴 那个「废品率」不可比 —— 三个数都对，分母由抽取器定义

## M-60 🔴 收口：①该留的理由不是废品率 —— 那个指标从设计上不可测

**验证者的收口结论，它推翻了自己先前「样本量不够」的说法**：

## M-61 🔴 假诊断的代价不在它本身，在它指向的下一步动作

dev 上一轮报「交棒脚本退出码假绿，已改用临时文件传递失败标记」。这一轮直接跑才发现：

```
bash predone-check.sh … | sed 's/^/  /'   ⇒ $? = 0     ← 它上次就是这么测的
bash predone-check.sh … > /dev/null       ⇒ $? = 1     ← 真实退出码，一直是对的
```

**脚本没坏，坏的是测法** —— 跨管道取到了 `sed` 的退出码。本轮第二次踩它，**而这条就写在它自己的 checkpoint 里**。

🔴 **它对后果方向的分析是新的**：

> 我因此**多改了一遍已经正确的代码**。那次改动本身无害，但**它建立在一个假诊断上** —— **若那个「修复」引入了新问题，我会同时拥有一个假诊断和一个真缺陷。**

⇒ **假诊断的危害不在「没修真问题」，在于它触发了一次不必要的修改，而那次修改本身成了新的风险面。**

⚠️ 与 M-60e（验证者的「错的射程声明」）**同族**：那条说「把『实验设计不成立』伪装成『还需要更多数据』⇒ **下一个人去补数据而不是换判据**」。两条合起来：**假诊断的代价都在下一步动作上，而不在诊断这句话上。**

## M-71 🔴 当证据是「某个东西的缺席」时，它对「别处新增了一条不需要它的路径」完全不敏感

那条跨 sprint 存活的假知识（「门禁的 `git log --grep` 不带 `--all` ⇒ 未合并分支的 commit 对门禁**结构性不可见**」）被 dev 与 code-simplifier 先后撤回。**code-simplifier 给出了它为何能抗住复查的解释**，这比撤回本身重要：

> ⇒ **当证据是某个东西的缺席时，它对「别处新增了一条不需要它的路径」完全不敏感；缺席只能证明这条路没走，不能证明没有别的路。**

| | 复查时会发生什么 |
| --- | --- |
| 结论错、理由错 | 复查结论就能发现 |
| **结论对、理由错** | 结论正确让理由永不被复查 |
| **观察为真、推论为假**（本条） | **复查观察会确认它仍为真** ⇒ **复查动作本身产生「已核实」的错觉** |

⇒ **可操作**：记录一条「因为没有 X，所以不能 Y」的知识时，**把推论与观察分开记**，并在复查时**验推论而不是验观察** —— 验观察只能确认「这条路仍然没走」。

## M-83 dev 给出的自检改法：先完备、后定点

> **先用一条完备命令问「它做了什么」，再用 `grep` 定点检查「是否违反约束」——
> 我当时把顺序做反了，而且省掉了第一步。**

**为什么六条 grep 必然不够**：它们的并集**在构造上**等于「我预先想到要禁止的东西」，
**加到六十条也不多覆盖一寸**。而 `git diff` 一条就够，因为 **diff 的定义不依赖我想到什么**。

```bash
git diff > /tmp/before-$$.patch     # 调用子代理之前
# ……子代理运行……
git diff > /tmp/after-$$.patch      # 之后
diff /tmp/before-$$.patch /tmp/after-$$.patch   # 空 = 真没动；非空 = 逐行就是它改的
```

🔴 **关键在于它同时解决两个问题**：**完备性**（不依赖我想到什么）与**归属**
（两次快照的差**就是**它的改动，不需要推断）—— 而 dev 正是栽在推断上
（拿 `74/17 → 81/22` 的总量去归因，两人改动落在同一文件同一区域时**总量守恒，倒推必然出错**）。

### M-83a 它的更深一层，以及为什么"绿"看不出问题

> 我把「**验证对方遵守了我的约束**」当成了「**了解对方做了什么**」。
> 前者 ⊂ 后者，而且前者的覆盖面等于我的想象力。

dev 补的推论（接 M-73a + M-81a 那条「任何由我生成的检查集都与我的盲区同构」）：

> **同构意味着「检查通过」和「没有问题」在我的视角里不可区分** ——
> 我的检查集绿了，我不可能从绿本身看出它没覆盖到什么。
> **要打破同构，检查的输入必须是实际状态（diff、快照），不能是我的预设。**

⇒ 验证者补跑全集 diff 那个动作是正确示范：**它不是"更仔细地"跑了一遍禁令清单，而是换了输入。**
