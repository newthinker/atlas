### 5. 「它已经过了门禁」是待验假设，不是前提——门禁挂在**边**上，代码却能不走边而改变

TASK-001 的 dev 在转 `dev_done` **之后**又追加了 `+36/-13`（第二轮 code-simplifier 采纳），

Leader 复盘时说得比我准：「这三条排除里**有两条是你补上的，不是机制保证的**——换一个不做
独立门禁跑的验证者，那 `+36/-13` 就真的没有任何东西量过。」

⇒ **推论**：验证者跑 `go test`/`vet`/覆盖率**不是**「重复 dev 已经做过的事」。分工去重的前提是
「那件事确实发生过」，而**状态字段只证明它当时发生过，不证明它对当前交付物发生过**。
⇒ **固定动作**：核对「最后一次过门禁的时点」与「交付物最后一次改动的时点」，前者早于后者就
自己补跑一遍。这两个时点都在 `transitions.jsonl` 与 `git log` 里，一条命令能对。

### 6. 声称也有采样时点，而过期的声称读起来和新鲜的一模一样

dev 在测试注释里写「措辞是变异实测定下来的」。这不是描述，是**断言**，且它的证据必须来自
**它所描述的那一版代码**。dev 改完注释后用新代码重跑了 M1/M2，我在最终态又独立重跑一遍，
两次都与注释逐字相符。

⇒ 这是「自证数字必须采于最后一次改动之后」的**一般形式**：不只数字，**声称本身也有采样时点**。
而拿旧版实测去背书新注释时，**那份注释读起来一模一样**——这正是这类错误无法被阅读发现的原因，
只能靠重跑。凡看到「经实测/经验证/已确认」这类措辞，问的不是「真的吗」，而是**「测的是哪一版」**。

### 7. 口径差异 ≠ 事实差异，混起来会制造一个不存在的缺陷

搬迁保真度核实中，dev 报「只剩 6 行差异」，我数到「5 行旧独有 + 2 行新独有」。差的那一行是
`return shaUnverified`——函数结构必需的返回语句，不属于搬迁差异。

我的处理是**写明两种口径、结论相同**，而不是写成「dev 报错了」。

⇒ 数字对不上时，先问「我们在数同一个东西吗」，再问「谁数错了」。**顺序反了就会产出一个不存在
的缺陷**，而且它看起来证据确凿（两个具体数字不相等）。报告里把两种口径都写出来，成本是一句话，
省掉的是后人重新查一遍。

### 8. 变异要一次坐实多件事时，选能让预期数**精确命中**的那种

DoD 只点了 `res.Periods++`，漏了 `--`（Leader 认领为疏漏）。我没有停在「dev 说它也搬了」，

### 9. 一个模式，两个实例：**校验挂在某个时点或某条边上，而被校验的东西可以在那之后改变**

本 sprint 我独立撞到两次，形状完全相同，当时没认出是同一个：

| 实例 | 校验挂在哪 | 被校验的东西怎么绕过去 | 后果 |
|---|---|---|---|
| TASK-001（本文件第 5 条） | `task-completed.sh` 挂在 `in_progress → dev_done` 这条**边**上 | dev 在 `dev_done` 之后又追加 `+36/-13`，不走那条边 | 那批改动没有任何东西量过 |
| TASK-005 / TASK-011 | scope 互斥校验挂在 **派发那一刻** | dev 中途经 `update writes` 合法补进一个文件，与另一在途任务重叠 | 「派发时无冲突」与「运行中产生冲突」之间没有检查点 |

⇒ **通用形式**：任何「在 T 时刻校验、而对象在 T 之后仍可变」的机制，都有这个缺口。
⇒ **找它的判据**：拿到一条「X 已经校验过了」，问两件事 ——
   ① **校验发生在哪个时点/哪条边上？** ② **从那一刻到现在，X 能不能合法地变？**
   两问都答得出来，缺口就浮出来了；只问第一个会得到「校验过了」这个真话。

⚠️ 我第一次（TASK-001）是被 Leader 复盘时点破的，第二次（scope-mutex）是自己撞的 —— **中间隔了两个任务，
我没有主动去找第二个实例**。模式认出来之后，它是**可以主动去找的**：列出所有「一次性校验」的点，
逐个问第二问。

## test-m1c3b-b / TASK-012 验证（2026-09-01）

### 12. 「删整块」式变异在有 import 依赖时会静默变成**崩溃型变异**

我的第一版 NaN 变异是**删掉整个守卫块** ⇒ **编译失败**：`math` 包变成未使用的 import。
若不检查编译结果就记 KILLED，得到的是**假 KILLED** —— 崩溃型变异让全套变红，与「守卫真的生效」
在输出上完全不可分。

正确手法是**把条件整条置 false**（`if false && (原条件) {`），保留对 import 的引用：

```go
-  if math.IsNaN(r.Min) || math.IsNaN(r.Max) ||
-      math.IsInf(r.Min, 0) || math.IsInf(r.Max, 0) {
+  if false && (math.IsNaN(r.Min) || math.IsNaN(r.Max) ||
+      math.IsInf(r.Min, 0) || math.IsInf(r.Max, 0)) {
```

⇒ **推论**：变异 harness 的有效性闸必须**区分「编译失败」与「测试转红」**。`go test` 对两者都返回非零，
只看退出码会把前者记成 KILLED。判据是输出里有没有 `[build failed]`。
⇒ 被删的代码是块中最后一处引用某 import 时，删除法必然触发这个陷阱 —— **优先用「条件置 false」而非删除**。

### 13. 变异定位必须是函数级：同一行文本在一个文件里可能出现多次

`for _, f := range fieldOrder {` 在 `validate.go` 出现 **2 次**：

```
行 442 → func yoyFields() []string          ← 全文件替换会先命中这里
行 512 → func gateMagnitudeSanity(...)      ← 目标
```

⇒ 全文件 `replace(old, new)` 会把变异打在 `yoyFields` 上，**得到的 KILLED 是假的**（红的是别的性质，
而报告上写的是目标性质）。这类假 KILLED 特别难发现，因为**它确实红了**。

⇒ **固定动作**：变异前先 `grep -c` 数锚点出现次数；不唯一就按**行号或函数体**定位，并在 harness 里
打印 diff 逐字核对。我用行号、dev 用函数体，两种都行 —— **不行的是直接全文件替换而不数一遍**。

### 14. 报「N 格全 PASS」不等于「N 格各自守着目标性质」——要解析到子测试级做假绿检测

dev 自己抓到过一个假绿：YAML 用例第一版 `min: .inf, max: 1000`，`+Inf >= 1000` 为真 ⇒ 被**既有的
倒置区间校验**拦下，与它要测的 NaN 守卫毫无关系，而 RED 阶段显示 PASS。它重构成六格、每格刻意避开
`Min >= Max`。

**但它的变异结果只报到顶层测试**（「M6 ⇒ RejectNaNOrInf」），没有逐格确认。我把同一个变异的输出
解析到子测试级（`--- FAIL: X/Y`），两组各 **6/6 格转红** ⇒ 每一格都只能因目标性质而红。

⇒ **判据**：表驱动测试报 KILLED 时，问「**是所有格都红了，还是只有一格红、其余格根本没在守这个性质？**」
顶层 FAIL 只需要一格红就会出现。**格数越多，这个盲区越大。**
⇒ 这与「一个为错误理由变绿的测试，从外面看和真正守住了完全一样」是同一件事的两个方向 ——
前者查绿的，后者查红的，都只有解析到格才分得开。

## test-m1c3b-b / TASK-012 收尾追记（2026-09-01，Leader 复盘后）

### 15. 「聚合信号不携带因果」有**层级**，每层都要单独破一次

Leader 把我这次的发现接到了一条已有的线上，三层递进（前两层不是我发现的，记在这里是为了看清结构）：

| 层 | 聚合信号 | 它推不出什么 | 谁抓的 |
|---|---|---|---|
| ① | `KILLED` / `SURVIVED` | 推不出「杀死它的是目标断言」 | 归档已有 |
| ② | RED 阶段「整体红了」 | 推不出「红的是目标性质」（可能因别的校验而红 = 假绿的镜像） | dev-m1c3b-c 上一轮 |
| ③ | **顶层测试的 PASS/FAIL** | **推不出「它的每一格都在守目标性质」** | 我这次（TASK-012） |

第 ③ 层的机制：`--- FAIL: X` 出现在顶层只需要 **任意一格** 红。所以「六格顶层 PASS + 变异下顶层
KILLED」与「六格里五格是摆设、只有一格在守」**在输出上完全相同**。⇒ **格数越多，盲区越大。**

⇒ **可执行判据**：凡分了子格的测试，变异结论必须解析到 `--- FAIL: X/Y` 这一级，报「N/N 格转红」。
⇒ **找第 ④ 层的方法**：问「我现在依据的这个信号，是由多少个更细的东西聚合而成的？聚合时丢了什么？」
   —— 每一层都是同一个问题在更细粒度上重问一遍。

### 16. **修过一次不等于修干净了** —— 修复动作本身会产生「已处理过」的完成感

这次最隐蔽的地方不是 dev 没检查，而是**它检查过**：它自己抓到了假绿（`.inf` 被既有倒置校验拦下）、
为此把用例重构成六格、每格刻意避开 `Min >= Max`、然后验证通过。**而它的验证停在顶层。**

⇒ 一个 bug 被修过之后，它所在的位置会获得一种「这里已经看过了」的豁免，而**修复的彻底程度取决于
当时用的那把尺，不取决于修复这个动作**。dev 当时的尺是顶层 PASS/FAIL，那把尺看不见格。

⇒ **触发条件**：看到「这里出过问题，已修」时，问的不是「修了吗」，而是**「当时用什么尺验的？那把尺
能看见我现在担心的这一层吗？」**
⇒ 这与「『我照做了』这个自我认定会直接关掉复查」同族，但更难防 —— 因为那里确实做了实事，
不是措辞层的自欺。

### 17. 断言射程要从**两个方向**验，只验一个方向都不够

核 `min(100)` 这条断言时我做了两件事，Leader 点出它们缺一不可：

| 方向 | 做法 | 单独做它时，答不出什么 |
|---|---|---|
| **横向** | 打印五个分支的**实际**错误串，看哪些含 `min(100)` | 答不出「它守的是哪个比较符」——`>=` 改成 `>` 它可能照样绿 |
| **纵向** | 变异 `>=`→`>`，看它是否独家转红 | 答不出「会不会被别的分支冒名满足」——另一条错误串里也含这个串就白搭 |

⇒ 横向查「**谁能满足这个断言**」（射程有没有溢出），纵向查「**它到底在守什么**」（射程指向哪里）。
两条都验，射程才算钉死。

### 18. 🔴 验证者验的是「**现存**测试是否通过」，不是「**该有的**测试是否还在」

TASK-006 的 dev 用 `cat >` 覆盖了一个它以为不存在的文件，**删掉了上游 TASK-003 的 7 个测试**（−121 行）。

它抓到这件事靠的是顺手跑 `git diff --numstat` 看改动量 —— **起因不是怀疑**。若那次没跑，7 条测试会随
交付合进 master，而**所有门禁、所有验证者的「全绿」都会照常报绿**，没有任何东西会响。

⇒ **这是验证者的结构性盲区**：我的全部判据（测试 PASS、覆盖率、vet、变异 KILLED）都建立在「测试集合
是完整的」这个前提上，而**这个前提本身从不被检查**。删测试与测试通过，在输出上完全同形。

⇒ **固定动作（两层，`writes` 与上游任务重叠时必做）**：
   1. 读上游 discovery 列出的测试函数名，逐个 `grep` —— 快，但**只能证明名字在**
   2. 提取这些函数的**函数体**，与上游原树逐个算 sha256 —— **名字在不等于内容对**，
