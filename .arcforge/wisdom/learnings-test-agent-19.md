
## 核验脚本的作用域错误会伪装成「重大发现」（TASK-002，2026-08-07）

**实撞**：核验 dev「只改组织方式」声明时，我写脚本比对需求文档与实现的测试函数名，
首轮报出 **19 个「文档有、实现无」的测试**——看着像一次大规模删除，是那种会让人立刻
上报的结论。逐个回查其所属 `### Task` 段后确认：**全部属于 Task 1/3/4/5**（Spec /
fixture / Query / Lookup），根因是**我的脚本扫了整份需求文档，而不是本任务的 Task 2 段落**。

**为什么危险**：这类失败的**方向指向重大发现**，而不是指向「工具坏了」。没有人会
立刻怀疑一个「发现了严重问题」的结论——包括写出它的人。上个 Sprint 有 QA 两次栽在
同一形状（工具作用域错 → 看起来很有价值的发现）。

**规则**：核验脚本报出**超出被验任务 scope 的异常**时，先怀疑脚本的作用域，
后怀疑被验对象。具体做法——**把每一条异常回查到它的归属**（属于哪个任务/哪个文件/
哪个段落），归属对不上本任务 scope 的一律先排除，再看剩下的。这与「拿到预期中的红时，
问它红的是不是我以为的那个原因」是同一条纪律的另一半：**红要问原因，异常要问归属**。

**副产物**：肉眼比对不可复现，机械比对可复现。核验「只改组织方式 / 只是重构 / 语义不变」
这类**易说难验**的声明时，抽结构化元组（如 `(state, incoming, want)`）做集合比对，
比通读两遍强——但前提是**元组的抽取范围必须钉在被验 scope 内**，否则就退化成本条教训。

## 「红了」不等于「红对了条数」——当条数本身就是判据时（TASK-006，2026-08-07）

**实撞**：验 F1（修复 hestia 空断言）时，判据是「修复前只有 crisis/single-key 红，修复后三套**全红**」。
我跑修复前与修复后，harness 两侧读到的都是 **`FAIL=1`**——**看起来这个修复什么也没改变**。

根因：`TestFailureMessagesNameTheShape` **没有用 `t.Run`**，三套形状共用一个测试函数。
testify 的 `assert`（非 `require`）失败后继续执行，所以差异只体现在**函数内断言失败的次数**上：

```
修复前: 2 次 Error Trace（crisis / single-key，hestia 缺席）
修复后: 3 次 Error Trace（形状 hestia / 形状 crisis / 形状 single-key）
```

必须 `grep -c 'Error Trace'` 下沉到**断言粒度**才能看见。

**规则**：**判据说「几条红」时，先确认自己的计数粒度与判据的粒度一致。**
`--- FAIL` 计数的粒度是「测试函数 / 子测试」，**不是断言**。当被验对象在一个函数体内循环多个用例
且**不用 `t.Run`** 时，这两个粒度会分离——**判据落在断言粒度，而 harness 只有测试粒度**。

**与已知失效模式的关系**：本 Sprint 已有「0 红可被编译失败伪造」（靠 PASS 计数 + vet 自证三条堵住）。
这一条是它的**邻居而非同一条**——那条是「红的条数为 0 且不可信」，这条是「**红了、条数也非零，但条数不是判据要的那个数**」。
自证三条**拦不住它**（diff 非空、vet 绿、PASS 计数正常，全部通过）。
⇒ **一句话**：`0 红`要问「是不是真跑了」，`n 红`要问「**这个 n 和判据的 n 是同一个单位吗**」。

**顺带**：这也是判断「该不该用 `t.Run`」的一个具体理由——不是为了输出好看，
而是**让失败的粒度与判据的粒度对齐**，否则守护的强弱在 harness 层面不可观测。
