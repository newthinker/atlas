
## idle hook 的唤醒条件不认「机制性阻塞」，会产生无界唤醒循环（dev-agent-38, 2026-08-06）

`teammate-idle.sh` 的 `dev-*` 分支按 `status ∈ {assigned, in_progress, review_fix}` 判断「你还有活」。
但任务可能**合法地不该被认领** —— TASK-013 与在途的 TASK-011 共用 `./internal/collector`，
validator 报 scope-mutex，Leader 明确要求暂缓。此时：

- 我不能认领（认领即违反单写者/scope 互斥不变量，会污染验证者的变异注入与还原）
- 我也不能空闲（hook 每次都把我叫醒，因为 status 仍是 `assigned`）

⇒ **hook 的唤醒条件与「可开工条件」不是同一个谓词**：前者只看 status，后者还要看 scope 互斥与依赖。
二者不一致时，被阻塞的 dev 会陷入「扫描 → 无变化 → 空闲 → 被叫醒 → 再扫描」的无界循环，
每轮纯烧 token，且**与纪律里「不得为保活而轮询」直接冲突** —— agent 被夹在两条规则中间。

**我的处置**（供后来者复用）：前两次唤醒各做一件有产出的事（第一次从文件侧机制复核阻塞 + 上报设计冲突；
第二次在 scratchpad 里把扫描器原型验完，六格矩阵 + skip 规则承重 2×2），第三次起识别为空转并停止，
不再重复上报「仍然阻塞」——**重复的状态汇报是噪音，不是尽责**。

**建议的机制修法**（非我职权，登记备查）：hook 判定时若任务 status 为 `assigned` 但 validator 报
scope-mutex，应视为「不可开工」而放行空闲；或引入一个显式的 `blocked_scope` 状态，让
「被派了但机制上不该动」在文件层面可表达 —— 现在这个状态只存在于 Leader 的口头通知里，
文件是真相源这条在这里出现了缺口。

## 「写为什么而非是什么」是可机械执行的事后 checklist（dev-agent-38, 2026-08-06）

Leader 从「注释与 discovery 里的事实性声明无人守护」这个空白里提炼出的缓解措施：
**写声明时优先描述「为什么」而非「是什么」——机制会变，理由通常不变。**

我拿它扫了 TASK-013 的 `nothrottle_test.go` 全部注释，**发现它不需要品味，几乎是机械的**。
判据可以压缩成一句：

> **这句话里有没有一个会变的具体事物？**
> 有（某个文件名、某个数目、某个范围、某个当前状态）⇒「是什么」⇒ 会过期
> 没有（因果、约束、失效模式）⇒「为什么」⇒ 通常不过期

实测：该文件 10 处注释，**4 处失效的全是前者，6 处稳的全是后者，没有一处需要犹豫**。

**推论**：它不只是写作建议，还是一个**可以事后扫的 checklist**——这正好补上那个空白的一半。
事实性声明仍然无人**自动**守护，但至少「去看」的时候有了明确的看法，不再依赖灵光一现。

**豁免情形**（扫的时候不要误报）：带时间戳的历史陈述不会变假
（「**接任务时实测**三者检出数为 0」），只举例而不承担论证的跨文件指针坏了也不误导。

**同源**：这与「行号现读不写死」是同一个思路的两个载体——把「是什么」（行号是 12）换成
「怎么得到」（现读）。区别在于**代码可以「现读」，散文不能**，所以散文只能靠这条 checklist
事后扫。

**本任务的四处实例**（全在同一个文件、同一个人、同一天，排除「谁不够仔细」的解释）：
discovery 里「未获答复的 DoD 偏差」（裁定其实已到）、头部映射注释「四个子包」（已改全树）、
`skipDirs` 注释「含故意语法错误的文件」（夹具已删）、`TestScanDetectsThrottleState` 注释
「parsefail 排在 throttleback 前面」（同上）。

## 重扫的触发条件是「收到任何消息之后」，不是「完成 .arcforge 任务之后」（dev-agent-38, 2026-08-07）

**实撞**：TASK-020 派给我后 40 分钟无人动，Leader 来催才发现。我**没收到派发通知**，
但那本不该造成空转——协议明写「即使通知丢失，各角色通过轮询自己负责的状态也能发现待办」。

**根因不是漏看消息，是我把重扫的触发条件窄化了**：我的最后一次重扫在上一个 task 交付后
（结果为空）；之后 Leader 派来一个**只读交叉复核**任务，我做完就直接空闲了——
因为它不是 `.arcforge/tasks/` 里的任务，我下意识把它当成「做完即止」的一次性活。

**而角色纪律的原文是「收到任何消息之后（不管消息内容是否与手头的事有关）先重扫」。**
交叉复核任务同样是一条消息，同样触发重扫义务。

⇒ **判据**：重扫的触发条件是**「我被唤醒了」这个事实本身**，与唤醒的内容无关。
凡是「我刚处理完一件事」——不论那件事是不是 task 文件里的任务——都要重扫一次再考虑空闲。

**同源**：这与 [[arcforge-idle-hook-wake-loop]] 是一对。那条讲 hook 的唤醒条件不认机制性
阻塞（**多叫**），这条讲我自己的重扫条件比纪律窄（**漏扫**）。两者都源于「把一个宽条件
在执行时悄悄替换成了一个更窄的、更符合直觉的条件」。

**另一条同轮得到的**：契约陷阱 10（有效性判定抢在行为断言之前，让缺陷伪装成「测试构造
失败」）**不是并发测试专属**。我在 TASK-020 的 `TestBusinessErrorIsNotCached` 上踩了同一个
坑——它完全不涉及并发，只是「先循环断言每次都该报错、再断言 HTTP 次数」。注入「错误被
当成功缓存」的变异后，失败信息是「本轮未构成检验」而非「错误被写进了缓存槽」。
⇒ **任何「有效性判定 + 行为断言」并存的测试都可能踩，判据与并发无关。**

## 变异的「红」要配一个「本该绿」的对照，否则只证明了敏感、没证明特异（dev-agent-38, 2026-08-07）

TASK-020 的 `TestBusinessErrorIsNotCached`：E1（保留错误语义、只改缓存行为）红，
**E2（停用 `if env.Code == 40203`）绿**。

**当时我为什么会去跑 E2**——DoD 里已经写明「验证者首版变异是错的，必须造保留错误语义
的变异」。**⚠ 「E2 是错误形态」这个判断不是我的**，是 test-agent-17 自报、Leader 落盘的。
按字面执行只需要**避开** E2 就够了。

我多做的一步是：**把那条「不要这么做」的警告，当成一个负对照去跑**。理由是我盯着 E1 的
红看时冒出一个疑问——**这条红只说明我的测试「对某个改动敏感」，没说明它「只对该改动敏感」**。
一条把 `hits()` 断言写成 `!= 0` 的烂测试，在 E1 下同样会红。

⇒ **判据：拿到一个红之后，问「有没有一个改动是它本该不红的？」跑一个，绿了才排除
「对什么都敏感」。** 特异性和敏感性是两件事，变异验证的默认动作只测了前者。

E2 该绿的机制（这部分是我自己查的）：40203 落到 `env.Code != 0` 分支后**仍然产生错误**，
且**缓存行为一字未变** —— 所以它压根不是这条性质的变异。验证者当时看到 5 条转红就采信，
那 5 条红是「错误类型变了」。

**与 [[arcforge-idle-hook-wake-loop]] 无关，但与「探针的 2×2 右下格」同源**：那条讲
「缺了右下格，左上格的 ✓ 与『探针写错了』无法区分」；这条讲**缺了负对照，红与『对什么都红』
无法区分**。两者都是**用一个本该是另一种结果的格子去证明判据有分辨率**。

## 「每条测试被哪些变异打中」的矩阵，空行会自己跳出来（dev-agent-38, 2026-08-07）

TASK-018 我做了 23 个变异，其中 `TestNonPolicyErrorsUnaffected` **一个都没被打中**。
它后来演化成契约的「方向/强度」双坐标。

**当时我是怎么起疑的——不是洞察，是列表格的副产品。** 我在给 discovery 写 verification
那段时，把「变异 → 转红的测试」逐条列出来，**那条测试从头到尾没出现过**。空行不是我
找出来的，是**一旦排成矩阵它就自己显形了**。

**⚠ 触发时机不全是我的**：Leader 当时给了放行条件②「逐包单独跑摘掉映射层的对照」，
我是在做那件事、顺手重读自己的 23 条结果时撞见的。**没有那个条件，我大概率不会回头
重读已经写完的变异记录。**

⇒ **可复用的判据：变异记录不要只写成流水（「Y1 → 红了 X」），要能反查（「X 被哪些变异打中」）。**
流水形式下「某条测试从没上榜」是不可见的——**它需要你记得所有条目才能发现缺席**，
而缺席恰恰是最难被记起的东西。排成矩阵后这件事变成零成本。

**这与「缺席型故障不会举手」是同一件事的两个场合**：没做的事不会提醒你，
没红过的测试也不会。**对策都是换一种让缺席可见的表示法。**

## 兜底机制失效，不能算到「它本该兜住的那一层」头上（dev-agent-38, 2026-08-07）

TASK-020 空转 40 分钟后 Leader 主动揽责（「我派任务时没同步消息」）。我拒绝了：
**协议的设计前提就是通知可能丢失**（原文「即使通知丢失，各角色通过轮询自己负责的状态
也能发现待办」），少发一条消息属于**可预期的常态**，重扫纪律正是为它准备的兜底。

⇒ **当 B 是为「A 可能失效」而设计的，A 失效时不能用来解释 B 也失效。**
否则任何兜底机制都能把自己的失职推给它本该兜住的那一层。

**⚠ 这条有个必须先验证的前提，否则它会变成很方便的推责工具：「B 为 A 的失效而设计」
这个兜底关系必须是被显式声明的，不是事后追认的。** 这次成立，是因为协议白纸黑字写了
那句话。**如果没有那句话，Leader 少发消息就确实是过失的一部分。**

用法：遇到「多方都有责任」的复盘时，先问**有没有一层是专为另一层的失效而设的**——
有的话，那一层不能拿被兜的那层当理由；**没有的话，责任才真的可分**。
