
## test-agent-18 · Sprint 032（M1a bitemporal）验证方法沉淀

验了 TASK-001 / 003 / 005（+005 交付报告复核）。以下五条是本轮实撞出来、可复用的。

### 1. 「逐载荷形态问」而非「逐断言问」
判据「若被测代码完全不做 X，这条断言还会通过吗」——**同一条断言、同一个问题，不同输入形态可以给出相反答案**。
实撞：TASK-005 的注入测试，对单引号载荷答案是「不会」（守住了），对**双引号**载荷是「会」（没守住）。
按「每条断言问一次」执行会得出「守住了」并漏掉整个双引号系。⇒ 对每一类**输入形态**各问一次。
同族：driver 消息形态、边界值符号方向、编码/转义方言。

### 2. 「存活」不等于「等价变异」——必须实证区分
变异存活有两种含义：等价变异（无害）或缺口（有害但没人看见）。**三条自证只证明「存活是真的」，不证明「存活是无害的」。**
实撞：MI-2（取值用 `fmt.Sprintf("%s = %q", ...)` 拼进 SQL）存活且三条自证齐备，
我写探针直接观察 → 载荷 `x" OR 1=1 --` **实际命中**（返回全表 MAX）。机理：Go 的 `%q` 用反斜杠转义 `"`，SQLite 不认反斜杠转义。
⇒ 拿到「存活」时，追问「这个变异下，被守护的性质真的还成立吗」，并造一个能直接观测该性质的探针。

### 3. 「加强/冗余覆盖」的正当性证据 = 造一个只有它抓得住的变异
「跑三套形状而不是两套」这类加强，光说理由不够。**正当性只能由「存在一个只有该加强才抓得住的变异」构成。**
实撞：TASK-005 跑 allShapes。我造「只把**最后一列**取值拼进 SQL、载荷放首列」→ 两列形状打不中、单列打中，红 4 条全在 single-key。
⇒ 加强是独立覆盖而非保险起见。（我的机理与 dev 陈述的不同，结论一致、证据独立——这比复述有力。）

### 4. 两种「断言被环境满足」的机理，修法不同
- **命名巧合**：TASK-003 的 `assert.Contains(failureContext, f.name)`，`"hestia"` 恰是表名 `"hestia_observations"` 的子串 ⇒ 去掉形状名后该迭代照样绿。**修法：改断言**（断言含 `"形状 "+f.name`）。
- **测试数据的过度差异**：TASK-005 样例的对照键两列都与库中数据不同 ⇒ WHERE 只用首列也查不到。**修法：改数据**（构造首列相同、次列不同的键对）。
同一个判据能问出这两者，但改错地方就白改。

### 5. 归因污染：红对了，但归给了错的测试
实撞（TASK-003 核 M14）：用整包 `go test -v` 输出做分桶，**其它测试的 `=== RUN` 行被交错进来**，归到了错误的测试名下。
改用 `-run '^测试名$'` 逐个隔离重跑才得到干净数据。
⇒ 「拿到红时问它红的是不是我以为的那个原因」还有一层：**红本身可能没问题，问题在我把它归给了谁。**

### 6. 完整性核验优先用 git blob hash，不用 md5 快照
核「spec.go 未被改动」时，`git rev-parse <commit>:<path>` 逐 commit 比对 blob hash，比对单点 md5 强：
它同时证明「从未被改过」而不只是「现在和某次一样」（中途改了又改回来，md5 看不出）。
配合 `git log <base>..<head> -- <path>` 空输出作交叉验证。
