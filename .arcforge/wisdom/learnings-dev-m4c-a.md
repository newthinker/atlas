### 1. 🔴「merge 必须在 dev_done 之前」——结论仍成立，但流传的理由已经过期

**流传的理由（错，请停止引用）**：「`task-completed.sh` 的 `git log --grep` 不带 `--all`，
未合并分支上的 commit 对门禁**结构性不可见**」。

⇒ 那是 M1c-3a 的结论。**sprint-011 P2 已经修了**，现读代码即可见：

```bash
task_branch_ref() { git rev-parse --verify -q "refs/heads/task/$TASK_ID" ...; }
task_branch_log() { git log -E --grep="^[a-z]+\(${TASK_ID}\):" --name-only \
                        --pretty=format: "HEAD..$ref"; }
BRANCH_MINE=$(task_branch_log)
[ -n "$BRANCH_MINE" ] && COMMITTED_MINE="$COMMITTED_MINE\n$BRANCH_MINE"
```

实证（原样跑，非推理）：该命令在未 merge 状态下**命中了我提交的 2 个文件**。

**真理由**：门禁**识别范围用 git（看得见分支），执行测试用工作树（看不见分支）**：

```bash
TEST_OUTPUT=$(go test $PKGS ...)   # 跑在 $(pwd) = 主仓库工作树 = master
```

master 上没有我的改动 ⇒ 它跑原有测试、全绿、**门禁 PASS**。

⇒ **区别很重要**：不是「我做不了」（门禁会 BLOCKED），而是「**我做得了但那个 PASS 是空的**」。
前者靠退出码就会拦住你，后者不会 —— 照做没有任何报错。

⚠️ **推论：idle hook 催的「推进到 dev_done」在此状态下机制上可行。** 它指向的不是一个会失败的
动作，而是一个**会成功但无意义**的动作。我被催了 7 次，每次都得重新想一遍为什么不照做。

### 4. 小教训：负数是反证，别让它溜过去

算「提交至今多少分钟」时得到 **-455 分钟**。成因：`git log --format=%cI` 给的是
`2026-09-19T21:03:35+08:00`，我 `cut -c1-19` 砍掉时区后当 UTC 解析，差了整 8 小时（480 分钟），
而 `25 - 480 = -455` 正好吻合。

⇒ 用 **`--format=%ct`（unix 时间戳，无时区歧义）**，不要手工砍时区。
⚠️ 真正的运气在于**结果是负数**——如果提交时刻恰好落在 UTC 上午，差值会是个正的、看起来
合理的分钟数，**不会有任何东西提醒我**。这与第 3 条是同一个形状。

### 6. 🔴 归因不能用「总量守恒的量」——我据此写下了一句假声明

用的是 `git diff --numstat`：调用前 `74/17`，调用后 `81/22`，而我**自己**在这中间做过一次
注释订正（4 行换 9 行）。我算了一下，觉得 `+7/+5` 的增量「可由我的注释订正完全解释」，
于是写进 discovery：**「它未改动任何文件」**。

**假的。** 它把 `columnsNotMigrated` 里的 map 成员判定改成了 `slices.Contains`，还加了一个
import。我提交时把它的改动一起提交了，而 leader 把那份含假声明的 discovery 提交入库。

它自己回来更正我，并一针见血：

> 用 numstat 的**总量**去归因，而两个人的改动恰好都落在同一个文件同一个区域时，
> **总量守恒，倒推必然出错**。判归属要去看**具体符号在不在**，不是看行数差。

⚠️ **最难堪的是：我在同一个任务里刚做对过这件事的反面。** `functional[2]` 验「无回归」时我
明确拒绝了 `142+3=145` 的减法、改按测试名逐条取差集，理由白纸黑字写着「算式成立不排除
**少 1 条多 4 条**」。**然后我在归因上用了减法。** 同一形状、同一小时、同一个我。

⇒ **通用判据**：要回答「**谁改的 / 改了什么**」，只能用**列举式**证据（`git diff` 全文、
符号在不在、sha256），**不能用任何会守恒的聚合量**（行数、文件数、计数差）。
聚合量在多来源叠加时**必然**给出自洽但错误的解。

### 7. 🔴 只验禁令，没验全集

同一件事的第二个错误，**比第一个更严重，而且没人指出，是我自己找的**。

我"核实"时跑了 6 个 grep：`沉默的两个来源` / `_v1 已被清理` / `strings.Join(lost, ", ")` /
`copying rows 那一步` / 撤回留痕 / `:125`。事后实测：**没有一个能发现那个改动**。

成因：它们全在问「**我禁止它动的东西还在不在**」，**没有一个问「它有没有动别的**」。
而那份禁令清单**是我自己列的** ⇒ 它天然覆盖不到我没想到的改动。

⇒ **验「对方遵守了我的约束」≠ 验「对方做了什么」。** 前者的覆盖面等于我的想象力。
⇒ **正确做法是一条 `git diff`，不是 N 条 grep**：diff 的定义就是「列出所有差异」，
**它的完备性不依赖我预先想到什么**。grep 只适合在 diff 之后做定点确认。

### 9. 🔴 缺席证据的盲区：真观察 + 假推论（来源：code-simplifier `a9075e5d`，我独立复核过）

第 1 条那个过期结论，**为什么能活下来**：它是**两句**，只有第二句假。

| | 内容 | 今天求值 |
| --- | --- | --- |
| **观察** | `task-completed.sh` 里 `--all` 出现 **0** 次 | ✅ **仍然为真** |
| **推论** | ⇒ 未合并分支的 commit 对门禁**结构性不可见** | 🔴 **假** |

🔴 **危险就在这里：任何人想复查这条知识，最自然的动作是去数一遍 `--all`，而那一数会"确认"它。**

成因：sprint-011 P2 修它的方式是**新增一条路径**（`task_branch_ref` / `task_branch_log` 走
`HEAD..refs/heads/task/<ID>`），**不是**给旧的 `git log` 补 `--all`。⇒ **修复没有触碰我记下的
那个可观测量**，于是我的证据完好无损地指向一个已经不成立的结论。

⇒ **判别式**：当「证据」是**某个东西的缺席**（`--all` 出现 0 次 / 没有 X / 找不到 Y）时，
它对「**别处新增了一条不需要 X 的路径**」完全不敏感。
**缺席只能证明「这条路没走」，永远不能证明「没有别的路」。**
⇒ 要判「机制在不在」，去找**它在的证据**（具名函数、具名字段），**不是数它不在的次数**。

⚠️ 这与第 7 条（只验禁令没验全集）**是同一个形状**：**缺席证据与禁令清单都只覆盖「我想到的那些」**，
而 `git diff` / 正向查找覆盖全集。

我那 6 条 grep 全绿时，拿到的是**一份看起来很勤勉的证据**。但它们的并集**在构造上**就等于
「我预先想到的东西」，**加到六十条也不会多覆盖一寸**。而 `git diff` 一条就够——diff 的定义
不依赖我想到什么。

⇒ 与本仓库既有那条「**3 个同代样本的确认力等于 1 个**」是同一件事的两个面：
**条数是勤勉的证据，不是覆盖的证据。**

### 13. 🔴「工具在手边但被问错了问题」的三种形态（来源：leader 归纳，三例均实撞）

同一个 sprint 的同一段时间里出现了三次，**形态不同、难度递增**：

| 谁 | 手边的工具 | 问错在哪 | 留下什么 |
| --- | --- | --- | --- |
| leader（30 分钟没 merge） | `git branch --list 'task/TASK-*'` 判据 | **根本没问**（想不起来） | 无记录 |
| 我（6 条 grep 核子代理） | `git diff` | 问了「**禁令还在吗**」，没问「**有没有动别的**」 | ✅「我核实过」 |
| 我（`predone-check` 判据②） | `git log -S` | 问了「**提交了吗**」，没问「**门禁那棵树上有吗**」 | ✅「我核实过」 |

🔴 **后两种比第一种难防得多：它们都跑了、都绿了、都留下了「我核实过」的记录。**
「想不起来跑」和「跑了但问错」在结果上不可区分——**都是零告警**，但后者还附赠一份伪证。

⚠️ **同一个 flag 可以回答两个不同的问题**，这是 `predone-check` 那次的直接成因：

| `git log -S` | 回答的问题 |
| --- | --- |
| **带** `--all` | 「这些改动**存在于某个提交里**吗」 |
| **不带**（指定 ref） | 「这些改动**在这棵树的祖先链上**吗」 |

我要问的是前者（代码提交了没），门禁问的是后者（它将要跑的那棵树上有没有）。
**我和 leader 各自都对了一半，而两个半对合起来正好漏掉「门禁跑的是哪棵树」。**

⇒ **判据**：写核实命令前先把问题写成一句话，再问「**这条命令回答的是这句话，还是一句相似的话？**」

### 14. 🔴 时序错位的第三种形态：把两个时点的事实并成一句话（leader 自曝，我受益）

leader 对我说过：「这次门禁会在 master 工作树上跑，而 **master 现在有你的代码了**，所以那个
PASS 不再是空的。」**假的** —— 门禁跑在 `13:38:06Z`，它 `13:40:58Z` 才 merge，**差 2 分 52 秒**。

⚠️ **这句话的每一半单独看都对**：门禁确实跑在 master 工作树上；master 现在确实有我的代码。
**错的是把它们接在一起时隐含的「同时」。**

同族的三个实例，**难防程度递增**：

1. **快照过期**（leader 用已作废的「九个全 verified」去转 `accepted`）——可用现读破
2. **拿现值判过去的陈述**（我差点判 leader「同一封消息里又犯一次」，实为它写时确实还在 `verifying`）——可用审计行破
3. **把两个时点的事实并成一句**——🔴 **现读和审计行都破不了**，因为两个事实都是真的

⇒ **判据**：一句话里同时出现「**当前状态**」与「**过去发生的动作**」时，
显式写出两者的时点并比较。**不要让「现在…所以那时…」这种句式溜过去。**

### 15. 🔴 自检子代理改了什么：先完备、后定点（第 7 条的处方，可照抄）

第 7 条只说了「6 条 grep 不够，该用 `git diff`」。**具体怎么做**：

```bash
git diff > /tmp/before-$$.patch      # 调用子代理之前，对工作树取快照
# ……子代理运行……
git diff > /tmp/after-$$.patch       # 之后再取
diff /tmp/before-$$.patch /tmp/after-$$.patch   # 空 = 真没动；非空 = 逐行就是它改的
```

**它同时解决两个问题**：
- **完备性**——不依赖我想到什么（diff 的定义就是列出所有差异）
- **归属**——两次快照的差**就是**它的改动，**不需要推断**。而我当时正栽在推断上
  （拿 `74/17 → 81/22` 的总量去归因；两人改动落在同一文件同一区域时总量守恒，倒推必然出错）

⚠️ **grep 仍有用，但位置要挪到后面**：拿到完备 diff 之后再定点确认「我禁止动的那几样没在 diff 里」。
**先完备、后定点**——我当时只做了后者，还以为做完了。

🔴 **更深一层（真正要改的）**：我把「**验证对方遵守了我的约束**」当成了「**了解对方做了什么**」。
前者 ⊂ 后者，且前者的覆盖面**等于我的想象力**。
⇒ **判据：当我需要知道「发生了什么」时，任何以我的预设为输入的检查都不合格，只有以实际状态
为输入的才行。**

### 16. 守卫只做了一个方向，而另外两道防线漏的是同一个方向（TASK-010 复审，我实测）

场景：库已是三段主键，但新表**缺 `source`**（`source` 在 `migratedColumns` 里），`_v1` 有且有数据。

```
MigrateBitemporal        err=<nil>  AlreadyMigrated:true      ← 静默放行
verifyBitemporalShape    err=<nil>                            ← 也放行（只验主键形状，不验列齐全）
跑完 schemaDDL() 后新表列 = [ts indicator value fetched_at]    ← 🔴 补不回来
```

**三重放行，而且状态自我维持**：`tablesDDL` 用 `CREATE TABLE IF NOT EXISTS`，对已存在的表是
no-op ⇒ **跑多少次 `schemaDDL()` 都补不上那一列**，没有任何「重新初始化」能修复。

🔴 **最值得记的不是缺陷本身，是它的成因形状**：
`verifyBitemporalShape` **自己的错误文案里就写着** `CREATE TABLE IF NOT EXISTS does not change it`
——**作者知道这个事实，但只把它用在「主键」维度，没用在「列」维度。**
⇒ **同一个事实，一个维度想到了，另一个维度没有。** 与「守卫两个方向只做了一个」同形，
且出现在同一个文件里。
⇒ **判据**：写守卫时把「它比的是 A 对 B」显式写成两句话——「A 有而 B 没有」与「B 有而 A 没有」
——然后逐句问「这句要不要管」。**默认只会写出其中一句。**

⚠️ 可达性别用「得手搓 SQL 才行」估低：一条 `ALTER TABLE … DROP COLUMN`（sqlite 3.35+）就够，
而**运维手工清理一个不再需要的列是完全正常的动作**。

### 17. 报错的文案没人验（与 QA-F7 同形，第二次）

②场景：`_v1` 与新表**都有** `note` 且都填好了，但 `note` 不在 `migratedColumns`
⇒ 报「有 1 列**从未被搬过来**: note」——**假的**。

**方向安全（报错而非放行），但值得修，理由不是「文案不准」而是它会指挥运维做错事**：
文案紧接着说「请先把这些列的数据从 `_v1` 补回」，而数据**已经在新表里**。
而该场景**真正的问题**文案完全没说：**`note` 不在清单里 ⇒ 下一次迁移会丢掉它**（前瞻性警告，
不是「过去丢了数据」）。

⇒ **红色输出天然带着「这是坏消息」的可信度，而它说的是什么很少被核。**
⇒ 修法不是「改一行文案」，是**该分支本来就该分成两种情况**（新表有没有这一列），
与第 16 条的双向比对是同一次改动，**别拆成两个任务**。

### 18. 🔴 有些事实没有载体——git 问不出来，不是命令不对

TASK-010 那句假声明（「code-simplifier 未改动任何文件」）之后，leader 跑
`grep -c 'slices'` 想独立确认「那 2 行是谁写的」，写下「核实成立，不采信 dev 自曝」。
**验证者指出那句站不住，它对：**

> 那证明的是「**最终状态用了 slices**」，不是「**这 2 行是谁写的**」。`have` map 出现在**删除行**里，
> 而它是旧实现的写法 ⇒ diff 区分不了「dev 先改成 map 版、simplifier 再简化」与
> 「dev 没动、simplifier 直接替换」——**两种历史最终态逐字节相同，中间态无 commit ⇒ git 无法作证。**

我逐处核过，**字面成立**：

```
checkpoint / wisdom / discovery 中 'have := make' 或 'have['  → 0 处
分支 reflog                                                   → 2 条（创建 + 提交）
```

我自审时**确实看到过** map 版本，但那份 diff 只存在于当时的上下文里，**一个字都没落盘**。

⇒ **判据**：想核实一个事实前先问「**这个事实有载体吗？**」没有载体时，换什么命令都问不出来，
而每条命令都会给你一个**看起来是答案的输出**（这里是「2」，在两种对立假设下都是 2，零区分力）。
⇒ **零区分力的检查比没做更糟**：它把「1 个来源」记成「2 个独立来源」，
**还降低了那唯一来源的权重**——而那个来源是**对自己不利的自陈**，本该可信度最高。

⚠️ **推论（写给未来的我）**：做 TDD 时若中间态有诊断价值，**就给它一个 commit**。
「反正最后要 squash」不是理由——中间态一旦没有 commit，它就永久不可证。
