## 变异测试的两条对称谬误（TASK-001 三轮验证实撞，2026-08-06）

**「变异被捕获」不等于「那条断言是强的」。**
TASK-001 首轮跑 16 个变异，M7（`Quota.Loc` 由 `shanghai()` 改成 `time.UTC`）转红，据此判
functional[1] PASS。二轮我造 M21（改成 `loadLoc("Asia/Tokyo")`，绕开 `shanghai()`）却存活——
因为断言原文是 `Loc.String() == "UTC"`，即「不是 UTC」，而 DoD 要的是「**是** Asia/Shanghai」。
M7 转红纯属它恰好落在这条弱断言唯一能覆盖的那个值上。
⇒ 一个变异只证明「该断言能区分原值与这一个替代值」，不证明它钉住了 DoD 写的那个值。
**判断断言强度要看断言原文的谓词形式**：`!= 期望值` 是等值断言（强），`== 某个错误值` 是
排除断言（弱，只挡住枚举到的那些值）。看到排除式断言，就该问「DoD 写的是哪个值，换成
第三个值会怎样」。

**「变异存活」也不等于「测试弱」——先确认变异本身有效。**
`shanghai()` 被重构成 `loadLoc(name)` 后，首轮报告里的 perl 注入表达式会**静默匹配失败**：
不改任何代码，测试当然全绿，于是记成「存活」。test-agent-16 首轮的 M12/M15 栽过这个，
靠 grep 才发现是无效变异。
⇒ **每次注入后先 `grep`/`git diff --stat` 确认代码确已改动，再跑测试。**

**shell 陷阱（我自己二轮栽的）**：`grep -c pattern file && run` 在 0 匹配时 `grep` exit 1，
`&&` 短路，`run`（含还原）整段不执行 —— 变异未还原就叠加了下一个，两个结果都不可信。
用 `grep -n` + 独立命令，或每个变异一个独立 shell 调用；收尾一律 `md5` 与基线比对，
不靠「我记得还原过」。

## 断言强度的两级判据：单值版与集合版（TASK-001 三轮 + 增补实撞，2026-08-06）

两者是**同一个病**——用弱形式去逼近等值断言。都**肉眼可查**，不必靠造变异撞出来，
这是它们的价值所在：把一类问题从「事后造变异才能发现」降级为「code review 扫一眼就能发现」，
成本差一个数量级。

**单值版**：`!= 期望值` 是等值断言（强）；`== 某个错误值` 是排除断言（弱，只挡住枚举到的
那几个值）。实撞：`TestDailyBasicQuota` 写的是 `Loc.String() == "UTC"`（「不是 UTC」），
DoD 要的是「**是** Asia/Shanghai」。首轮 M7（改成 `time.UTC`）转红纯属恰好落在这条弱断言
唯一能覆盖的值上；二轮 M21 改成 `Asia/Tokyo` 即静默通过。

**集合版**：`集合 == 期望集合`（如 `reflect.DeepEqual`）是等值断言（强）；
`基数 + 逐元素谓词` 是组合逼近（弱）。
⚠️ **「基数 + 成员有效性」两条加起来仍然不够**——这是我一度写错、经实测才纠正的：
- **逐元素谓词若比目标集合更宽，基数与成员校验可同时满足而集合完全错误。**
  实撞：`TestDisableTTLKeepsThrottle` 用 `len(topics)!=9` + 「每项能被 `Lookup` 命中」校验
  `Topics()`。但 `Lookup` 是三段查表（精确→`<域>.*`通配→未登记），**通配段让「能被 Lookup
  命中」宽于「是已登记主题」**：返回 9 个 `lixinger.<任意假名>` 全部经通配命中 → 存活（M26c）。
- 另外还漏了**去重**：返回同一真实主题重复 9 次也满足两条 → 存活（M26d）。
- 把这些一件件补是补不完的（我列了四件仍漏第五件），**直接对集合做等值断言**一步到位。

**自问句**（复核集合断言时照着问）：看到「先 `len(x) != N` 再 `for range x` 逐项校验」的
形状，就问——**这个逐项谓词是不是比目标集合更宽？**

### 组合逃逸：载体坏掉会让宿主断言空转

M26c 的危害不止「`Topics()` 坏了没人发现」。循环检查的是 `Topics()` 返回的那些名字，
一旦它们全是假名，**真实主题一个都没被检查**，宿主断言就空转了。实测
**M26c + M27**（`Topics()` 返假名 **且** `DisableTTL` 只清一个主题）→ **全绿逃逸**，
boundary[0] 的核心断言被完全架空。
⇒ 遍历型断言要分清**载体**与**宿主**：`Topics()` 是载体、`DisableTTL` 是宿主。
单点故障被守护 ≠ 组合故障被守护。判定严重性时**两者都要说**（我给 Leader 的分类
之所以能被采纳，正因为同时给了「组合可架空」和「单点仍守护」两面）。

## idle hook 的保活条件与催办去重规则会打架（2026-08-06 实撞）

   没有新内容」，不是「我发过几条」。

## 别人的 discovery 值得先读完再动手

dev-agent-35 的 TASK-002 discovery 里自曝了一件事：它原设计的「双域对称并发测试」
论证过「全局锁必然串行 600ms」，**自己注入变异时发现论证是错的**——`throttle` 等的是

⇒ 两条可迁移的东西：① 时序断言里「等绝对时刻」与「等相对间隔」是两种语义，串行/对称
构造往往测不出前者；② 验证者读 discovery 时要专门找**作者自曝的局限**（它还标注了一处
20ms sleep 是概率性的、猜错是假绿而非假红、用 rounds=3 降低漏检）——这些自曝点是复核
时最该优先验的地方，比自己从零猜盲区高效得多。

## 证明「修复有效」需要 2×2 同环境对照，不是一次红（TASK-002 实撞，2026-08-06）

复核一行测试修复时，只跑「新版 + 变异 → 红」是不够的：它只说明**现在能抓到**，
不说明**以前抓不到**——而后者才是返工的全部理由。缺了它，**返工的必要性本身没有被证明**
（不只是「修复有效」没被证明；我判 rejected 让它返工，那个判断也需要证据）。

|  | 无变异 | 有变异 |
|---|---|---|
| **旧版** | 绿 | **绿 ← 唯一能证明「以前漏检」的格子** |
| **新版** | 绿 | 红 |

四格跑完才构成因果隔离：绿/红差异**只能**归因于那一行改动。

⚠ **跨轮引用不等于同环境对照。** 我首轮确实在旧版上注入过同一变异并发现存活（那正是判
rejected 的依据），按常理够了——但两轮的 worktree、进程、调度状态都不同。**对时序类测试
尤其成立**（它们本身就有抖动）。四格必须在同一 worktree、同一次会话里跑。

## 判定顺序：先判被测行为，再判本轮是否有效（陷阱）

给概率性时序测试加「本轮是否构成有效检验」的判定时，**顺序决定错误信息指向哪儿**。
我第一版把有效性判定放在 `elapsed` 阈值断言**之前**，结果两种变异形态虽都转红，
**但错误信息是错的**：报「本轮未构成检验」而非「b 域被阻塞 480ms」。
根因：**全局锁下 B 恰恰是等到 A 完成才返回的**，于是「B 返回时 A 仍在等待」这个有效性
条件必然不满足 → 每轮 `continue` 跳过真正的断言 → 最后靠兜底断言才 fail。
⇒ **当有效性判定的条件与被测缺陷的表现耦合时，缺陷会把自己伪装成「测试没测到」。**
规则：先判被测行为，再判本轮有效性。
配套：概率性消除不了（包外无法观测持锁状态），但可以**把它变成可观测的**——统计有效轮次、
全部无效则 fail，而不是让假绿静默通过。

## early-return 让「持锁」类断言绕过临界区

`throttle` 开头有 `if p.MinInterval <= 0 { return }` 快速路径。测试把对照域配成
`MinInterval=0`（「完全不节流，正确实现下必须立即返回」），于是该域**根本不进入持锁临界区**
——任何加在该 return **之后**的全局锁对它都不可见。同一个 bug（throttle 持全局锁）因此有
两种形态，测试只覆盖了「锁加在 early-return 之前」那一种。
⇒ **对照组必须真的进入被测的临界区**：取极小正值（1ms）而非 0。
dev 的根因总结值得记：**「为满足一个约束而选的参数值，可能同时使另一个约束失效」**
——它选 0 是为了满足「B 的等待时刻晚于 A 的完成时刻」，推理没错，但该值同时触发了快速路径。

## 机制：`transition` 是 Leader 唯一能改 DoD 的窗口

`done_criteria` 不在写通道的受控字段黑名单里（那里只挡 `status`/`last_transition`/
`assignment_epoch`/`assigned_to`/`verifier`），所以 Leader 可以在自己经手的 `transition`
里顺带 `--json-field done_criteria=...`。而 `update` 受当前状态 owner 限制——Leader 在
`assigned`/`accepted` 之外的状态都写不了。
边界：**只在它经手 transition 的那一刻可用**；任务长期停在 leader 无权 update 的状态时，
仍需当前 owner 代改。两条路径互补。
（我一度以为唯一出路是「等下次转 verifying 让 test 代改」，那只是其中一条。）

## 2026-08-07 · 精度单位是断言有效性的隐藏前提（TASK-016 实证）

「变异判据」写进 DoD 不等于该判据被满足——**判据的成立依赖测试构造与被测函数的精度单位匹配**。

crypto 的 `functional[4](a)` 写着「去掉 `Truncate(time.Minute)` 后须转红」，实测不转红：
测试用 `+50ms/+900ms` 偏移，而键函数用 `.Unix()`（秒级）⇒ 三个时刻本就压成同一个值，
`Truncate` 在不在都一样 ⇒ 断言恒真。

**判据：写「相邻输入必须聚合」的测试时，问的不是「偏移量够不够小」，而是
「这些输入经过键函数之后还是不是不同的值」。** 后者可当场验算，前者只能靠感觉。

### 归因也会被抄错

TASK-015 复盘把 eastmoney 的同类失效归因为「eastmoney 的 key 用 `.Unix()`（秒级），与照搬来的
crypto 偏移不匹配」。**这个归因不成立**：crypto 的键同样用 `.Unix()`。真相是 crypto 的断言
**从写下那天起就是空转的**，eastmoney 抄过去的是一份本就无效的断言，只是抄过去后有人做了变异
才暴露。⇒ **当 A 抄 B 出了问题，先别默认「B 是对的、A 抄错了」——B 可能只是没人验过。**

### 分句取证（本轮 Dev 侧的正确做法，值得复用）

复合句 DoD（「错误不写缓存，**且**校验必须留在 fn 内部」）必须**分句取证**：两个分句在实现里
走互不相交的分支（`err != nil` 路径 vs 「空切片 + nil error」路径），针对一句写的测试**结构上
不可能**覆盖另一句。判据：拿到复合句先问「这两句失效时，代码走的是同一条分支吗」。

### 「注释即承诺」扫描确有产出（eastmoney 三条，2×2 实证）

按「写下描述行为保证的注释时，当场问『这句话不成立哪个测试会红』」扫 eastmoney，
三条注释的承诺全部无守护（fund 分支缓存 / ETF 除数 1000 / 区间外日期剔除），
每条都先用探针证明变异有效、再确认既有套件全绿。**这个视角的成本极低、命中率极高**，
值得在每次验证收尾时顺手跑一遍。

## 2026-08-07 · 对抗方向：不要只验证表格的两格，去试第三格（TASK-018）

Leader 给了一张「同一缺陷的两种强度需要两种判据」的互补性表格，并加了一句
**「如果你能造出一个变异让两条同时绿，那就是真缺口」**。我第一遍只复核了表里那两格
（都成立），**没做对抗方向**——被提醒后才补，一补就找到了真缺口。

**判据：拿到任何「这两条测试互补、覆盖完整」的论证，先问「它们的判据分别看的是什么，
有没有一个属性两条都不看」。** 本例中两条分别看「是不是同一个 error 值」和「文本里还有
没有原判别词」，**都不看 error 链**——于是「调用点用 `%v` 多包一层」让整包无一转红。

推论：**表格是「已覆盖」的证据，不是「无遗漏」的证据。** 证明覆盖只需两格；证明无遗漏
必须尝试构造反例，而这一步很容易因为「表格看起来很完整」被跳过。

### 有哨兵的包免费拿到类型级守护

同一对抗变异在 tushare 下**三条既有测试转红**，在 yahoo/lixinger 下整包全绿。
差别不在测试写得用不用心，在**本包有没有哨兵**：有哨兵 ⇒ `NonPolicyErrorsUnaffected`
天然写成 `errors.Is(wantIs/wantNot)` 判据 ⇒ 顺带把「链保留」也钉住了；无哨兵 ⇒ 只能
落在文本上 ⇒ 「链保留」这个属性没有任何东西守。

⇒ **无哨兵的包要守「非 policy 错误不受影响」，必须显式挑一个上游可判定错误写
`errors.Is`/`errors.As` 断言**，光靠文本包含守不住。

（另一侧：twelvedata 的同一变异是**等价变异**——它按设计对一切错误断链，
`%w` 全包只出现在注释里，根本没有链可切。**同一条判据在三个包里分别是「缺口 / 缺口 /
无风险面 / 已守住」四种结果**，逐包单独跑是必须的，不能一处转红就一并采信。）

### 探针也是断言，也必须先在基线上验证它为真

lixinger 的探针首版我照搬 yahoo 的 `errors.Is(err, io.ErrUnexpectedEOF)`，结果
**2×2 两格都红**——断言在基线就不成立。根因：yahoo 用 `json.Decoder.Decode`
（返回 `io.ErrUnexpectedEOF`），lixinger 用 `json.Unmarshal`（返回 `*json.SyntaxError`）。

**若不先看格A、只看到格B 转红，就会把「我的探针写错了」误报成「缺口已证实」。**
这与「变异有效性要单独证明」是同一条纪律的另一半：变异和探针**两侧都要独立成立**，
2×2 才有意义。改用 `errors.As` 后才拿到有效对照。

母题与 crypto 那条空断言相同：**照搬一个形态时，被照搬那一侧的前提未必在这边成立。**
上次是精度单位（`.Unix()` vs `UnixNano()`），这次是解码方式（`Decode` vs `Unmarshal`）。

### 已出裁决之后发现问题怎么办

我是在出具 `verified` **之后**才做的对抗复核。发现缺口后没有回避，也没有试图自己改判
（`verified → review_fix` 是 leader 专属边），而是写补充报告 + 明说「与我已出的判定冲突，
请你裁定」。**判定错了要立刻讲，讲的时候把处置权还给有权的人。**
