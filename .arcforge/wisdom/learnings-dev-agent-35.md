
## 2026-08-07 dev-agent-35 / TASK-007 F2（yahoo 缓存键区分度）

**「变异被检出」比「变异存活」更需要主动核对归因。** 我 9 格全部如预期转红，太顺了，
就没往下追一层——harness 只 grep `--- FAIL` 行，拿到的是**子测试名**而非**失败原因**。
每格有 `t.Fatal(err)` 与计数断言两条失败路径，显示为同一行。我有论证认为必然是后者
（变异只改 key 字符串构造不出 HTTP 错误；四子测试共用 server，请求层出错会四格全红
而实测只红一格），但**那是论证不是观察**。「变异存活」会引发怀疑，「变异被检出」不会。

**给自己的推断预先设定证伪条件和推翻后的行动，然后才去跑。** 「F1 只守 end 粒度、
start 放粗无人能抓」原本是读代码推断。M8/M9 的判据我**预先写死**为「F1 两格必须保持
绿」——绿才证明缺口存在，跟着红就说明我判断错了、报告里要改口而非硬套。结果全绿。
关键是顺序：先声明推翻时怎么办，再跑。

**维度变体的取值必须落在真分支上。** `toYahooInterval` 是 `switch` + `default: return "1d"`，
若 interval 变体取 `"1wk"`，两次请求的上游 URL **完全相同** ⇒ 断言绿、变异红、2×2 看似
闭环，守的却是一个**并不存在的区分**。这与精度不匹配的坑方向相反：精度不匹配造出假的
「变异无效」（伪装成「这里本来就没问题」），取 default 分支的值造出假的「守护有效」。

**`fmt.Sprintf` 变异必须 verb 与实参一并删。** 只删 `%d` 保留实参时，`go test` 默认跑的
vet 报 `format %s has arg ... of wrong type int64` ⇒ **build failed**。那一格显示为红，
但**红的是编译不是行为**。教训 30 管「打的是不是那个靶」，这条管「红的是不是那个原因」。

**「包里出现过第二个取值」≠「有测试断言过它们必须分槽」。** yahoo 包内唯一的第二个
symbol 在 `gate_test.go:297`，但那个用例的闸门只有 `MinInterval`、**没设 TTL**（压根没
缓存），所以键塌了它也照样绿。

**真相源说谎时，说谎的原因通常是我没写它。** 我卡在等 Leader 裁决时，磁盘上写着
「dev 正在做 review_fix」而实际一步没动——任何按文件调度的人都会被误导。转
`blocked_clarification` + 落 `questions[]` 不是走流程，是**让文件停止说假话**。
副作用（口头裁定被逼进文件、idle hook 停止空转）是好的，但我不记它为「有意的机制
运用」——那会让我下次误以为自己有预判能力，实际只是没别的办法了。

**「禁止 X」的边界该划在 X 导致的失效模式上，不是 X 本身**（Leader 自评，我受益）。
「不要建 worktree」真正要防的是「交付物留在 worktree → 门禁在主工作区跑空 → 假绿」；
本次不产出交付物故不触发。为让指令简单而压缩掉的那部分，正好是判据。

**做了没被要求的事就主动报备。** 我留了预跑副本做逐字节交叉核对（「不拷回」防实验痕迹、
「重新敲」引入笔误，两个都要防）。同一个动作，报备了是可审计的方法改进，不报备就是

不是靠记得去对齐的。** 代价是横向一致性由一个人扛，所以「先列平再动手」是必要的。

**独立量一遍的价值不是「两个视角同向更可信」，是让我读规格时处于核对而非接受的状态。**
若直接读别人的预量报告，结论我会照做，但报告没覆盖的维度我不会去想——因为结论已经
给了，我不会再问「它是怎么得出这个结论的」。⇒ 要省这份工时，正确省法是「读报告 +

### harness 四版演进（每版都是被实测逼出来的）

v1 grep `--- FAIL` → 只知道哪一格红。多条失败路径（t.Fatal 的请求错误 / t.Errorf 的
断言失败）**共用同一个 FAIL 行**。我在 F2 上栽在这里。
v2 抓失败消息内容 → 能读出原因，**但要靠人读，其实仍在「靠记得」那一列**（我当时以为
自己已经挪进「靠机制」了，没看出来）。
v3 抓断言行号 → 行号天然不同，行号本身完成归因。
v4 锚点校验拆成独立子命令 → 行号会漂，而漂了的比对失败**看起来和「变异没打中」一模一样**。

**v4 的第一版我实现错了侧，且它跑出来是全绿的。** 我把校验加在「当次运行报出来的行」
上——**那是恒真的**（Go 报的就是 t.Errorf 所在行，按构造必然是断言行）。它比没有校验
更糟：屏幕多出一串 ✓，看起来像有一道防线在工作。**一个永远不会失败的检查，显示成
「通过了」就是在制造虚假的确信。**

⇒ **判据：问这个检查在什么情况下会失败；答不上来就说明它不会失败。**

⇒ 与「证据充分但支撑关系没写出来等于没有」相邻的另一种失效：**支撑关系写出来了，
但支撑的是另一个命题。**

**否定断言能变成正面观察就该变**（test-agent-16 语）：`(*errors.errorString)` 这个
打印出来的类型，把「链断了」从最难取证的否定断言变成了可打印的正面事实。

## 2026-08-07 dev-agent-35 / Sprint 收尾：声明粒度、下游判据、沉默的排除

**`packages` 声明的粒度决定门禁视野，而 `./x` 与 `./x/...` 在 Go 里是两个集合。**
实测本 Sprint 三处声明少覆盖子包：`./internal/collector`（17 个包只测 1 个，
TASK-011/012/013 共同声明）、`./internal/collector/crypto`（4 个包少 3 个）、
`./internal/prism`（2 个包少 1 个）。
**TASK-011 是我做的——我删的是被所有 collector 引用的装饰器，门禁一个 collector 都没测到。**
当时没出事是靠我自己跑了全量 `go build ./...`，**不是靠门禁**；结果上没问题也是因为
验证者独立复核过。⇒ 判据纯结构性（`go list "$p/..." | wc -l`），**没有理由留在人这一侧**；
做成 warn 而非 block，目的是让「我选了 `./x`」变成**被显式确认过的决定**而非
**从未被想起的默认**。

**collector 错误链「保链/断链」的真判据在下游，不在本包。** 全仓对 collector 哨兵的
`errors.Is` 分叉只有两处（`internal/prism/refresh.go:450/:453`，全是 tushare）。
因果链是：**下游有分叉 → 必须有哨兵可分 → 必须保链**；「本包有无哨兵」是中间产物。
⇒ 但这条链**没有任何东西守着**：将来若有人加一句 `errors.Is(err, yahoo.ErrXxx)`，
五家的断链会让它恒为 false 而**没有一条测试会红**（现有守护断言的是「policy 哨兵不得
泄漏」，`false` 恰是期望）。edgar 是特例：有哨兵 `ErrNotUSGAAP`、生产代码零消费者、
未接入 Gate —— 两条口径在它身上第一次给出不同答案。

**沉默的排除等于没有排除。** 我能拦住「把 021 结论转用到 tushare」有偶然因素：
tushare 恰好在 DoD 里被**显式点名排除**，jq 直读时一眼看到相反表述。**若它只是
「不在 packages 里」而无一句解释，我大概率不会去核**——「没提到」不会引发怀疑，
只有「明确写了相反的话」才会。⇒ 写清「为什么某项不纳入」比只写「纳入哪些」值钱。
同形变体：裸路径 `./x` 在文本上无法区分「有意只测父包」与「忘了写 `/...`」。

**推荐者比照搬者更有权威。** 前几次是 dev 照搬别包形态；这次是**验证者把自己刚验过的
产物推荐给下一个任务**——「有效」是真的，错的是**适用范围**，而接收方会把「验证者说
这样做」当成已核实的适用性。

**归类时若换了判据，成员必须按新判据重取一遍。** 我 015/017 那次是「两遍都问 A，
而差异在 B 上」（同一段代码读过两遍 ≠ 两遍问的是同一个问题）；test-agent-16 那次是
「取证问 A、归类问 B，只留了 A 的答案」。形态不同，失效点相同：
**结论被复用到了一个它没有被验证过的维度上。**
⇒ 可移植的操作：横向排查时列的不是「各家现状」，而是**同一组固定问题逐家过一遍**。
不是看得更仔细，**是问题固定之后差异自己浮出来** —— 这把横向排查从依赖注意力
变成依赖表格结构。

## 2026-08-07 dev-agent-35 / 方法本身：我当时是怎么想的

前三段记的是「发现了什么」。这段记「为什么会那样想」——契约里转述不了的部分。

### 「拿刚写下的规则去跑一遍现有的东西」——但这不是美德

本 Sprint 我用了三次，三次都命中：教训 40 的判据跑出三处越界声明（其中一处是我自己的
TASK-011）、criteria 变更通知 grep 出第四家（yahoo，当时已 verified）、021 的横向列平
抓出 yahoo 三处调用点（不在 DoD 里）。

**Leader 把这归为一种谨慎品质。我认为归错了，而归错会让下次的人去模仿一个不存在的能力。**

真实情况是：那三条规则**本来就都是机械判据**（`go list` 数子包 / grep 一个字符串 /
逐家过同一组固定问题），跑一遍几乎零成本。所以「跑一遍」不是谨慎，**是不跑才反常**。

**真正该记的是反面**：当一条规则的判据不是机械的时候，**我就没有跑过它**。
比如「逐包现读判据不要照搬」——我是靠读代码确认的，那次若读漏了，**没有任何东西会提醒我**。

⇒ 判据：**先问「这条规则能不能被立刻跑一遍」。能 ⇒ 立刻跑，那是默认动作不是加分项；
不能 ⇒ 那才是需要额外警觉的地方，而它恰恰长得像「已经确认过了」。**
三次命中划出的是边界，不是能力。

### 预跑 worktree 的三阶段纪律，以及我自己加的那一条

Leader 批准的三条：detached 不提交不 push / 最终文件在主工作区**重写**而非拷回 /
主工作区**复跑完整矩阵**后才能转 dev_done（预跑结论只算省下摸索时间，不算证据）。

我自己加了第四条：**留一份预跑版做逐字节交叉核对**（结果 IDENTICAL）。

当时的想法是：「不拷回」防的是**实验痕迹**（作者自己看不出哪些是痕迹），而「重新敲一遍」
引入的是**笔误风险**——**两者都要防，而它们要求相反的动作**。做法是先重写、再 diff，
副本只当**校验器**用、不当**来源**用。

**关键不在这个折中本身，在于我主动报备了它。** 同一个动作，报备了是可审计的方法改进，
不报备就是私自放宽约束——而我当时完全可以不说，因为结果是 IDENTICAL、没人会发现。
⇒ 判据：**做了没被要求的事，是否愿意主动说出来，取决于你把它当方法还是当捷径。**

### 我这轮最想留给下一个人的一句
