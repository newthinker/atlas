## 2026-09-02 · 「已交付等 merge」是流水线上唯一无活性保障的状态——提案素材（M1c-4 实撞）

### 缺口的确切形状（两个 dev 独立读源码 + Leader 核实，非推测）

**① `teammate-idle.sh:96-98` 的 `dev-*` 分支只有一条 jq**：

```
select(.assigned_to == $me and (.status | IN("assigned","in_progress","review_fix"))) | .id
```

只读 `.arcforge/tasks/*.json` 的三个字段：`assigned_to` / `status` / `id`。**不看 git、不看 mtime、不看产物。**
文件开头注释（第 8–9 行）写明：`exit 0` 是**不可逆停机点**，不是周期心跳 ⇒ 它只有两种输出：放行（此后不再调用），或用**同一句写死的文案**再催一次「把名下任务推进到 dev_done」。**它没有「已经催过 N 次」的状态。**

**② validator 的 `stale-dispatch` 阈值表**（`--rules` 直读）：`assigned=15m` / `blocked_clarification=30m` / `verifying=30m`。
**`in_progress` 不在其中**——这不是疏漏，CLAUDE.md 记了理由：dev 正常干活实测 p90 就有 65 分钟，任何可用阈值都会淹掉正常长任务。

**③ 两个状态在任务文件层逐字段相同**：

| | 还在写代码 | 已提交等 merge |
|---|---|---|
| `status` | `in_progress` | `in_progress` |
| `assigned_to` | 该 dev | 该 dev |
| `last_transition` | 进 `in_progress` 那次 | **同上，不变** |
| git | 分支无 commit | **分支有 commit 且非 master 祖先** |

⇒ **这不是「规则漏了一个状态」，是判据所需的信息不在被检查的介质里。** 给 `stale-dispatch` 加 `in_progress` 阈值不解决问题——它只会开始告警全部正在正常写代码的 dev。

### 🔴 前人已经想到了，但写在了无效的载体上

`merged_into_master` 在归档里命中 **7 个文件，6 个在 `discoveries/`**（sprint-038 两份、sprint-039 四份，形态是全 sha），**`tasks/` 里 0 个**。

⇒ **前人想到了要记 merge sha，但写进了一个没有任何调度机制会读的载体** —— 想法留下了，活性保障没留下。这与「载体强度排序」是同一族：`done_criteria` > `questions[].answer` > `discovery` > inbox，而 **`discovery` 对机制而言等同于零**。

⚠️ **提给人类时按「task 文件顶层字段 + validator 规则」提，不要按「已有先例」提**——先例只到 discovery 这一层，而那一层恰恰是无效的那层。

### 三条出路（dev-m1c4-c 整理，代价递增）

1. **写进任务文件**（如 `merged_into_master`）：零机制改动，但靠 dev 自觉写，而「忘了写」与「还在写代码」**又同形**，把问题推后一层。
2. 🔴 **给 `stale-dispatch` 加一个新的探针维度**（不是新阈值）：判据是「分支有 commit ∧ 不是 master 祖先」。它是**产物探针**，与既有的 `LivenessProbe` 同类 —— **推荐这条**。
3. 新增状态 `awaiting_merge`：最干净也最贵，要动状态机、write-matrix、全部角色文档。

## 2026-09-02 · 「等 merge」缺口的**量化证据**（M1c-4 全程实测，供人类裁决用）

前一条记了缺口的形状。本条补**成本数字**——它们都是本 sprint 实测的，不是估计。

### 空转成本

| 实例 | idle hook 催「推进 dev_done」次数 | 处置 |
|---|---|---|
| dev-m1c4-c（TASK-001） | 33 次（3 分钟内 18 次） | 全部拒绝，每次复查 merge 状态 |

🔴 **每一次唤醒都要求实例重新加载上下文、复查状态、写一条拒绝理由。** 而 hook 的解锁文案**恒为**「把名下任务推进到 dev_done」——它没有「已经催过 N 次」的状态（`exit 0` 是不可逆停机点，不是心跳）。

### 停滞时长

| 事件 | 状态 | 有无阈值 | 实际停滞 | 谁发现的 |
|---|---|---|---|---|
| TASK-004 / TASK-001 等 merge | `in_progress` | **无** | **280 / 286 分钟** | dev 反复催办 |

⇒ **差别不在于谁更负责，而在于那个状态有没有可用的阈值。**

### 🔴 dev 侧连「让阻塞可见」的手段都没有

TASK-008 的 dev 在三条催办无回应后，**借用 `blocked_clarification`** 把阻塞写进文件系统，并在 `questions[0]` 第一句自己声明「这不是 DoD 疑问，是流程阻塞，借用本状态是因为它是我唯一能让阻塞在文件里可见的合法迁移」。

⇒ 这比「leader 可能漏扫」更深一层：**问题不是没人看，是没地方看**。dev 只能借用一个语义不符的状态。

### 更精确的判据（test-m1c4-b 在 TASK-007 停滞后提出）

时长阈值只能猜「慢 vs 死」。更精确的是**产物探针**：

> **`verifying` 状态下 `verifier` 已指定、却没有任何 `by=<该 verifier>` 的审计行** ⇒ 它一次都没动过手，而不是「动过手但慢」。

同理可推 `in_progress`：**`assigned_to` 已写、分支已有 commit、但该 commit 不是 master 祖先** ⇒ 「已交付等 merge」，与「还在写代码」（分支无 commit）**在文件层可区分**。

⇒ **这就是给 `stale-dispatch` 加「产物探针维度」而非「新阈值」的具体形态。** 加阈值会淹没正常长任务（dev 干活 p90 就 65 分钟）；加探针不会，因为它判的是**性质**不是**时长**。

### 机制核实（三方独立同结论）

`task-completed.sh` 的 `git log` 调用**全文件带 `--all` 的 0 处** ⇒ 未合并分支的 commit 对门禁**结构性不可见**，此时转 `dev_done` 会在一棵没有该 dev 代码的树上报绿。

⚠️ 三个 dev 各自独立核实过这一条并据此拒绝 idle hook —— **纪律被执行不是因为写在文档里，是因为每个 dev 自己去读了那个 shell 脚本**。

## 2026-09-02 · 🔴 `update` 缺 `--expect-status` ⇒ 状态切换会切在 dev 的「读」与「写」之间

### 实撞（TASK-014）

```
15:54:17Z  dev_done   by dev-m1c4-b
15:58:20Z  verifying  by leader        ← 我派验
```

dev 的自述（我核过审计行，属实）：

> 我**读到 `dev_done`**、开始拼装那份 `done_criteria`、**写入时已是 `verifying`** —— 派验恰好落在「读」与「写」之间。

`owner_table`：`dev_done → ["dev-*"]`，`verifying → ["test-*"]` ⇒ **DENY**。

### 为什么 dev 侧闭合不了

| 命令 | 有没有乐观锁 |
|---|---|
| `transition` | ✅ `--expect-epoch <N>`（锁内重读 `assignment_epoch`，不符即 DENY） |
| **`update`** | 🔴 **没有 `--expect-status`** |

⇒ **epoch 挡的是「你还是不是 owner」，挡不住「状态在你手上变了」。** 这两件事正交，而只有前者有锁。

⚠️ **与本 sprint 记过的「`dev_done` 之后改 discovery 必漂」同族** —— 那条的结论是「真结论是**时机**不是纪律：`dev_done` 前安全 / 之后窗口可以是 0 / 派验后必漂」。**这次证明窗口真的可以是 0**：dev 在 `dev_done` 后 4 分钟内动手，仍被切走。

### 建议

给 `update` 加一个 `--expect-status <S>`，语义与 `--expect-epoch` 同构（锁内重读 `status`，不符即 DENY 并提示「状态已变，回到扫描循环」）。

⚠️ **不改也可以，但那样「dev 在交棒后还能补字段」就是一个**只在运气好时成立**的能力** —— 而本 sprint 已经连续五次「`dev_done` 之后的补充请求落空」（TASK-005 的 87 秒、TASK-006、TASK-007、TASK-011 的 46 秒、TASK-014 的 4 分钟）。

🔴 **五次的共同点：Leader 的消息都发在 dev 交棒之前，到达都在之后。** ⇒ 这不是「提早发」能解决的，**发出时刻不由到达时刻决定**。

### dev 的处置值得记

它**没有硬闯、没自作主张换方案**，而是把机制事实（审计行 + owner_table + DENY 原文）和三个可选方案摆出来让 Leader 定，并指出方案 C（让验证者代写它要对照的验收条款）不妥。

⇒ **被机制挡住时，正确动作是把机制事实摆出来，而不是找一条绕过去的路。** 与 QA 那次「知道未登记名字免验 token 但不走」同一形状，本 sprint 第二例。
