### 缺口的确切形状（两个 dev 独立读源码 + Leader 核实，非推测）

**① `teammate-idle.sh:96-98` 的 `dev-*` 分支只有一条 jq**：

只读 `.arcforge/tasks/*.json` 的三个字段：`assigned_to` / `status` / `id`。**不看 git、不看 mtime、不看产物。**
文件开头注释（第 8–9 行）写明：`exit 0` 是**不可逆停机点**，不是周期心跳 ⇒ 它只有两种输出：放行（此后不再调用），或用**同一句写死的文案**再催一次「把名下任务推进到 dev_done」。**它没有「已经催过 N 次」的状态。**

**② validator 的 `stale-dispatch` 阈值表**（`--rules` 直读）：`assigned=15m` / `blocked_clarification=30m` / `verifying=30m`。

| | 还在写代码 | 已提交等 merge |
|---|---|---|
| `status` | `in_progress` | `in_progress` |
| `assigned_to` | 该 dev | 该 dev |
| `last_transition` | 进 `in_progress` 那次 | **同上，不变** |

⇒ **这不是「规则漏了一个状态」，是判据所需的信息不在被检查的介质里。** 给 `stale-dispatch` 加 `in_progress` 阈值不解决问题——它只会开始告警全部正在正常写代码的 dev。

⚠️ **提给人类时按「task 文件顶层字段 + validator 规则」提，不要按「已有先例」提**——先例只到 discovery 这一层，而那一层恰恰是无效的那层。

### 三条出路（dev-m1c4-c 整理，代价递增）

1. **写进任务文件**（如 `merged_into_master`）：零机制改动，但靠 dev 自觉写，而「忘了写」与「还在写代码」**又同形**，把问题推后一层。
2. 🔴 **给 `stale-dispatch` 加一个新的探针维度**（不是新阈值）：判据是「分支有 commit ∧ 不是 master 祖先」。它是**产物探针**，与既有的 `LivenessProbe` 同类 —— **推荐这条**。
3. 新增状态 `awaiting_merge`：最干净也最贵，要动状态机、write-matrix、全部角色文档。

### 空转成本

| 实例 | idle hook 催「推进 dev_done」次数 | 处置 |
|---|---|---|

### 停滞时长

| 事件 | 状态 | 有无阈值 | 实际停滞 | 谁发现的 |
|---|---|---|---|---|
| TASK-004 / TASK-001 等 merge | `in_progress` | **无** | **280 / 286 分钟** | dev 反复催办 |

⇒ **差别不在于谁更负责，而在于那个状态有没有可用的阈值。**

### 🔴 dev 侧连「让阻塞可见」的手段都没有

TASK-008 的 dev 在三条催办无回应后，**借用 `blocked_clarification`** 把阻塞写进文件系统，并在 `questions[0]` 第一句自己声明「这不是 DoD 疑问，是流程阻塞，借用本状态是因为它是我唯一能让阻塞在文件里可见的合法迁移」。

⇒ 这比「leader 可能漏扫」更深一层：**问题不是没人看，是没地方看**。dev 只能借用一个语义不符的状态。

### 更精确的判据（test-m1c4-b 在 TASK-007 停滞后提出）

时长阈值只能猜「慢 vs 死」。更精确的是**产物探针**：

> **`verifying` 状态下 `verifier` 已指定、却没有任何 `by=<该 verifier>` 的审计行** ⇒ 它一次都没动过手，而不是「动过手但慢」。

同理可推 `in_progress`：**`assigned_to` 已写、分支已有 commit、但该 commit 不是 master 祖先** ⇒ 「已交付等 merge」，与「还在写代码」（分支无 commit）**在文件层可区分**。

⇒ **这就是给 `stale-dispatch` 加「产物探针维度」而非「新阈值」的具体形态。** 加阈值会淹没正常长任务（dev 干活 p90 就 65 分钟）；加探针不会，因为它判的是**性质**不是**时长**。

### 机制核实（三方独立同结论）

`task-completed.sh` 的 `git log` 调用**全文件带 `--all` 的 0 处** ⇒ 未合并分支的 commit 对门禁**结构性不可见**，此时转 `dev_done` 会在一棵没有该 dev 代码的树上报绿。

⚠️ 三个 dev 各自独立核实过这一条并据此拒绝 idle hook —— **纪律被执行不是因为写在文档里，是因为每个 dev 自己去读了那个 shell 脚本**。

## M3｜Leader merge 时「核实的对象」与「merge 的对象」不是同一个（2026-09-08 实撞）

**经过**：dev 报 `task/TASK-003-m3 @ 537b0ef1`（394 行）。我 `git rev-parse task/TASK-003-m3` 核实 = `537b0ef1` ✓，

**处方（立刻可用，本 sprint 还有 5 个任务要 merge）**：
`git merge --no-ff <核实过的全 sha>`，**不用分支名**。核实与操作锚定同一对象；分支若已前进，
新 commit 需要再核实一次再 merge —— 这正是我们想要的。

以及 `git diff --numstat <merge-base> <sha>` 看**累计**变更（`git show --numstat <branch>` 只看最后一个 commit，

## M3｜`comm` 在 CJK 上不报错地给垃圾，而我把它写进了 DoD 判据（2026-09-08）

**事实**（子代理发现，我复算证实且更严重）：判据「`methodology.md` 的 `## ` 标题集合与源文件 `## ` 集合交集 ≤ 1」，
用 `comm -12` 实现时：

```
源 ## 标题 12 个，methodology.md ## 标题 5 个
comm -12  → 5   （子代理另一次跑得 3）
grep -Fxf → 0   （真值，两边原样清单肉眼核对过）
```

`comm` 要求两侧按**同一 collation** 排序，CJK 不满足该假设 ⇒ **不报错，只给貌似合理的数**。
⚠️ **同一个坏仪器给出两个不同的假值（5 和 3）**——比稳定的错更难发现，因为「重跑一次数变了」
会被读成「有别的东西在变」而不是「仪器坏了」。

**我错在哪**：这条判据我这轮**刚改过**（reviewer 指出原判据会误伤合格文档，我把比较对象从
`##`/`###` 改成只比 `##`）。**我只改了比较对象，没考虑实现工具。**
⇒ 判据 = 比较对象 × 求值方式，**两者都要钉死**。只钉前者，后者会由执行者按直觉选，
而直觉在 CJK 上恰好选中一个会静默失效的工具。

**处方**：涉及**非 ASCII 文本集合**的判据，一律钉死 `grep -Fxf`（整行定长匹配、与顺序无关），
**禁用 `comm`**（也慎用 `sort -u | uniq -d`、`join`——同一族 collation 假设）。
DoD 里写集合判据时把求值命令原样写进去，不要只写「交集 ≤ N」。

**与本 sprint 其他仪器错的关系**：前三例（我 ×2、dev ×1）是**用错了尺**（拿相关量代替性质本身）；
这一例是**尺本身在特定输入上坏掉**。前者靠「换一把独立的尺复算」能发现，
后者也一样——子代理正是用 `grep -Fxf` 复算才发现的。**两把独立的尺，对两类错都有效。**

**判别式（它给的，我采纳）**：**改任何 sha / 版本号 / 路径时，先 `grep -c <旧值> <整个文件>`，

## M3｜追加而不废止 = 两个互相矛盾的断言并存；全称词是分界（同一事件）

dev-m3-c 自评 `verification` 那处「更糟」：它加了兄弟键 `resampled_after_fix`，

**但同一轮里 dev-m3-a 做了看似相同的事却没问题**，差别值得记清楚：

| | 旧断言 | 追加后 |
|---|---|---|
| dev-m3-a（TASK-001） | `verification.anchor = 7e24b11`，**明确限定这批采自哪棵树** | 新增 `rework_round_1`（锚 `1c7af81`）+ `anchor_note` 说明分工 ⇒ **不矛盾** |

## M3｜🔴 订正上面那条「判据若必须偏，宁可偏宽」——它是个过宽的全称断言（dev-m3-a 补，2026-09-08）

**上面那条我写成了全称句，现予收窄。** 它只在**一类用途**上成立：

| 判据的用途 | 偏宽的后果 | 该怎么偏 |
|---|---|---|
| **扫描 / 搜索**（「有没有漏掉的东西」） | 多报，人一眼筛掉 | ✅ 宁可偏宽 |
| **判定真假**（「这个合入了吗」「这条断言在守吗」） | **假阳 ⇒ 停止追查并推进流程** | 🔴 **偏宽危险** |

没有任何东西会再来纠正**。所以它这轮每次判 merge 都用拓扑 + 内容双判据，
且**只在拓扑报 0 时才信它单独的结论**。

⇒ 正确的记法：**「宁可偏宽」只适用于「找东西」；「判真假」时假阳比假阴更贵。**
两类用途必须分开说，否则这条会被搬到判定场景上。
（dev 的三次失误都属第一类，所以我对那三次的观察成立——错在我把它写成了无限定的全称句。）

## M3｜变异有两种失效，我只记过一种（test-m3-a 补，2026-09-08）

我先前记的是：**「一个变异要能证明 A 比 B 强，必须是 A 抓得住而 B 抓不住的那个」**
（防「变异区分不出优劣」）。test-m3-a 补了第二种，而且它自己先撞了：

它把 `WHERE period_type = 'monthly'` 改成 `'annual'` 想造污染，**结果那一刻库里根本没有 annual 行**
（annual 观测是 `Ingest` 期间才存的）⇒ UPDATE 命中 **0 行** ⇒ **零污染** ⇒ 测试红在
`require.Error` 而不是被核的那条断言。

⇒ **设计变异要问两个问题，不是一个**：
1. 这个变异下，**我想淘汰的那一版会不会也恰好红**？（防区分不出优劣）
2. **我的变异真的造成了我以为的那个状态吗**？（防变异根本没生效）

**第二个更隐蔽**：它给出的是「红」——**一个符合预期的结果**，看上去像变异成功杀死了断言。
若不去看**红在哪一行**，就会得出「那条断言有效」这个**正确的结论、错误的理由**，
而下次有人依赖那个理由时会踩空。

⇒ 机械做法：**变异后先确认变异体本身达到了预期状态**（UPDATE 影响行数、文件 diff、
`bash -n` / `jq -e .` 语法闸），**再看测试红在哪一行**——不能只看「红了没」。
（CLAUDE.md 的变异纪律里本有「有效性闸」与「语义闸」，这一例是它们在**数据层**的翻版：
语法没问题、脚本跑通了，但**被变异的那个状态压根不存在**。）

## M3｜只产假阳、且假阳指向对方的仪器（test-m3-a 自报）

它一度报「discovery 里没有 `rework_round_1` / `anchor_note`」——**错在查了顶层**，

**方法论上值得记的三点**：
1. **「两个数不一致」是线索不是结论。** 我停在「有两把尺，都过门槛」；它去问**为什么差**，

2. **它用的是「穷举 + 找孤儿」**：把 926 个块逐个归属到 483 个函数，**剩下几个就是差异的全部来源**。

3. **验证方式是「剔除后复算与另一把尺精确吻合」**——不是「大概解释得通」，

   不是从名字出现次数推出来的；再加上与磁盘现行文件逐字节一致，出处链闭合。

**一句话**：**「谁写的字」和「谁做的这次写入」是两个问题，共享目录里它们会分开。**

## 「我认定它是误报」不构成绕过它的授权（M3，verifier 报告 + Leader 当场复犯）

> **一个我认定是误报的拦截，和一次真实拦截，在 hook 那里长得完全一样**——我判断它是
> 误报这件事本身，不构成绕过它的授权。

**这不是洁癖，是那道闸的强度所在**：一道对全体生效、不认身份的闸，全部强度来自它

处置：不改写命令，读正则把边界钉死 + 用那次真实的 DENY 当观察。**读代码得到的边界，

**配对的第二条：误报的正确处置是让它可发现，不是让它消失。** 它做了两个动作——改措辞

同构，只是被掩盖的从缺陷换成了摩擦。

文案说的是「运行时资产只读」，而当事人在写 checkpoint，两者对不上，它花了一步才反应
过来是正文内容触发的。**规则名回答「你违反了什么」，人需要的是「我这条命令的哪一部分
命中了」**——后者才让人一眼看出这是不是误报。这也是我把 PENDING 第 11 条的处方定成

## 循环里数据变、目的地靠表达式算 ⇒ 全写进同一处，且每次 rc=0（M3，我覆盖了自己的 checkpoint）

**事件**：我要把同一处订正打进 plan.md 与 leader-checkpoint.md，写成
`for T in plan checkpoint; do python3 - "$T" … | arcforge-write.sh … $( [ "$1" = plan ] && echo plan || echo checkpoint ); done`。
**`$1` 在 Bash 工具的命令里不是循环变量**——它是未设的位置参数，`[ "$1" = plan ]` **恒假** ⇒ 两次都走
`checkpoint` 子命令。第一轮把**改过的 plan.md 内容写进了 checkpoint**，第二轮读到的已是被覆盖的
checkpoint（内容是 plan），0 命中、原样写回。净结果：**checkpoint 全文被 plan.md 顶掉，而 plan.md 的
订正一个字都没落盘**。写通道两次都 `rc=0`——它无从知道我想写哪个。

**结构性形态（比 `$1` 本身通用得多）**：**循环让数据变，目的地却由一个脆弱表达式算出来**。
数据错了会长得不一样、会被发现；**目的地错了每一次都长得完全正常**，只是全落在同一个坑里。
⇒ **目的地是身份，不是参数**：要写 N 个不同目的地就写 N 条命令，或让目的地**本身**是循环变量
（`for T in plan checkpoint; do … --as leader "$T"; done`），绝不从循环变量再算一次。

**救我的不是纪律，是一个偶然的 0。** 我按落盘核实纪律打印了「命中几处」，第二轮的 **命中 0** 让我起疑。
**如果那处订正在两个文件里都存在**，我会看到两次「命中 1」+ 两次 `rc=0`，**全部符合预期**，而 checkpoint
已经没了——而 checkpoint 恰恰是没人会去读、直到需要它恢复的那一刻才发现是空的东西。
⇒ 与我记过的判据一致：**「这一行输出错了的话，什么东西会告诉我？」**——这里的正确答案是「没有」。
真正管用的核实不是「写成功了吗」（rc 恒 0），而是**写完后读回目的地、确认它的首行/标题是它自己**。
本轮补的固定动作：**多目的地写入后，逐个 `head -1` + `wc -l` 核对身份**，不是只看 rc。

**为什么这次能全额恢复**：checkpoint 正文是我几条消息前亲手拼的，完整在上下文里，原样重打即可。
⚠️ **这是运气，不是设计**——被覆盖的若是别人写的、或是压缩前写的，就没了。写通道只做原子覆盖，**没有备份、没有删除**。

## 「没找到那个字段」同时兼容三种情形，而它们的处置完全不同（M3，子代理报 TASK-005 漂移）

**事件**：dev-m3-c 的 code-simplifier 子代理报 TASK-005 的 VERIFIED 可能判了旧字节，依据是
「审计行里没有 `ack_drift` 字段」。**它的结论不成立，但它的发现成立**——两者必须分开评估。

**它自己写的限制声明是整份报告最值钱的一句**：
> 我只探了 `ack_drift` 这一个字段名，换个字段名或根本没记录，在我这里长得一模一样
> ⇒「没看到 ack」≠「没给过 ack」。

**而真相是它列的可能性之外的第三种，也是更彻底的一种：那个字段对谁都不存在。**
写通道的 ack 只往 stderr 打一行 INFO，审计行**从不记录**它。⇒ 通则：
**「探测某字段不存在」之前，先 grep 写入侧确认那个字段名真的会被写。**
否则「没找到」同时兼容三种情形，而处置完全不同：
① 没发生（该追查）② 记在别处（该换地方找）③ **根本不记**（该改机制，且**所有历史记录都同样查不出**）。
③ 最危险，因为它让「查过了、没有」变成一句在任何情况下都为真的话。

**定性用的手法值得单记：审计缺失时，用「它没被拒」当证据。**
我没有去找 ack 的痕迹（找不到），而是重建守卫的前置条件：
merge 落 master `04:33:34Z`（commit 时间带 `+08:00`，须换算 UTC）**早于** verified `04:43:48Z` 十分钟
⇒ 判定那一刻 `NOW_HEAD ≠ B_HEAD` 且声明范围内确有 148/16 变更 ⇒ 守卫必然 DENY，除非传了 `--ack-drift`；
**而那次迁移成功了** ⇒ ack 给过。**「那条边跑通了」本身就是「守卫的前置条件被满足」的证据**——
这在审计轨沉默时是唯一还说话的东西。与我记过的「从机制推导比重跑更强」同族，新场景是**证据缺失**。

**两条确认必须先问是否同源**（我记过这条，这次真去问了）：验证报告 §4 自述「带显式漂移确认」是
**自述**；我的时间戳推导**不依赖报告任何一句话**。⇒ 独立，可以叠加。若我只有报告那一条，
它和被质疑的那次判定出自同一个 agent，强度等同于一条。

**对子代理报告的正确读法**：它的结论错、观察对。**如果我只评估结论，这个真缺口会跟着结论一起被驳回。**

## 订正一个**论断**与订正一个**字串**，清查方法不同（M3 TASK-006，dev-m3-c 自查出来的）

**事件**：dev-m3-c 订正 discovery 里对 code-simplifier 的错误定性，做了全文件 grep，报「已清干净」。
**但它只搜了自己用过的那个措辞**（`子代理的报告与事实相反`），得 0 就收工；而 `decisions[6].rationale`
里用的是**另一种说法**（`报告是假的`）——**同一个断言、不同措辞，搜一个查不出其余的**。是我逐字段
遍历 JSON 才捞出来的。

**它自己给出的成因分析比缺陷本身值钱**：
> 「改 sha 时 `grep -c <旧值>` 全文件数一遍」那条处方的前提是**旧值是一个固定字串**。这次旧值是
> **一个论断**，它在文中有多种表达 ⇒ 那条处方直接套用会给出「已清干净」的**假绿**。

⇒ **订正论断时，清查对象是「语义的一组表达」而不是一个字串**：先列出该论断的若干种写法逐个扫，
再**逐处取上下文判性质**（是仍在生效的断言，还是被否定的引用 / 订正历史）。它复扫后的分布：
`报告是假的 0` / `谎报 3`（全是被否定的引用）/ `报告与事实相反 2`（订正历史）/ `未送达我的线程 3`（新说法）
——**5 处引用无一是仍在生效的断言**，这个结论只有逐处看上下文才得得出，计数本身给不了。

**第二条，位置上的盲区**：那个假断言藏在 `decisions[6].rationale` 的**第一个从句**里，而该字段表面上
讲的是「我为什么接受它的改动并重跑变异」。dev 订正时盯的是「哪里在讲那个子代理」，于是**按主题搜就漏掉了
按理由用的地方**。⇒ 判据加一条（它的原话）：
> **订正一个论断时，不只搜它出现在哪，还要搜它被拿来当理由用在哪。**

这与我记过的「结论对但理由错」严丝合缝：`decisions[].rationale` 里那个决定**是对的**（以 diff 为准、
重跑变异），所以不会有人回头查它的理由 ⇒ 藏在理由里的假断言**寿命最长**。

**它做对而值得抄的一件事**：它没有声称「我只改了那一处」，而是**在写入脚本里加了机器断言**——
顶层变更字段集恰为 `['decisions']`、变更下标恰为 `[6]`、`decisions[6]` 键集不变、`decisions[6].decision`
文本一字不变，三条全过才落盘。⇒ **「只动了一处」这种自证，人说不算，让写入路径自己验。**
（与我记过的「同一道闸，执行者是人时失效、是机器时生效 ⇒ 要换执行者不是加闸」同构。）

**时序结果**：它第四处订正落盘 `09:02:33Z`，我派验写基线 `09:03:00Z`，**相差 27 秒**；事后核对
`verify_baseline.discovery_sha256` 与文件现值逐字节相同 ⇒ **订正进了判定对象**。若我按上一轮那条
「刻意压着」的止损线（`09:15Z`）之前任何时刻抢跑派验，这处订正就会变成判定对象漂移。
⇒ 记一笔：**压住派验的那 10 分钟不是空等，它换来的正是这 27 秒。**

## 好结果不告诉你它是怎么来的（M3 TASK-006 收尾，dev-m3-c 两次纠正我的表述）

**① 止损线的价值恰恰在它没被用上的时候。** 我说「压住派验那 10 分钟不是空等，换来的正是这 27 秒」，

> 能验，只是判的对象里躺着一句假断言）。这类「因为等了所以没出事」**在事后是不留痕迹的，它和
> 「本来就不会出事」外观完全一样**。

⇒ 这是我记过的「省掉纪律后一切仍会显得合理，损失不留痕迹」的**反方向**，而且更难察觉：
**遵守纪律后一切也显得合理，收益同样不留痕迹。** 两个方向合起来 ⇒ **从结果看不出纪律有没有起作用**，
所以「这次没出事」既不能用来证明纪律有用，也不能用来证明它是多余的。
⚠️ 这直接反驳「上次等了也没出什么事，这次快点吧」——那句话的证据基础是空的。

**② 下游的谨慎抵消上游的错误，这件事不该被记成机制。**
我写过「下游的谨慎抵消了我的错误，但不能指望每次都这样」。它把这句收得更紧：
> 这轮之所以没出事，是因为我每次都先读审计行——**而那是纪律，不是保障**。真正的机制是你后来做的
> 那件事：把两条 DoD 从消息搬进 TASK-007 的 `done_criteria`。

⇒ **它指出了我复盘里的归因错误**：我把「没出事」记在了「下游谨慎」头上，而那是一个**每次都要重新
付出、随时可能不付**的东西；这轮唯一新增的**持久**保障是载体升级（inbox → `done_criteria`）。
判别式：**复盘一个好结果时问「下次换个人/换个我，这个保障还在吗？」**——答案是「要看那个人记不记得」
的，都是纪律；答案是「在文件里/在写入路径里」的，才是机制。
（同族：它自己那次「只改了一处」不靠声称、而是在写入脚本里加机器断言——**换执行者，不是加闸**。）

## 假 Z：我在格式串里写死的时区标记，第二次骗到我，这次还传给了下游（M3 TASK-007 改派期间）

**我记过这条**，原话：「`find -newermt` / `stat %Sm` **按本地时间**，我贴 `Z` 读成 UTC，差点把早于本轮的
coverprofile 当成『verifier 在工作的证据』——**假绿方向，比假红危险**。改用 epoch 秒比较。」
**然后我在整个 TASK-007 监视期间一直用着 `stat -f '%Sm' -t '%H:%M:%SZ'`**——那个 `Z` 是格式串里的
**字面量**，`%Sm` 给的是本地时间（+0800），于是本地 18:49 被打印成 `18:49:31Z`。

**这次的新伤害是它传了出去。** test-m3-a 据我这类输出读到 worktree 的 `18:49`，判断「很新，可能它醒了」
并报给我核。真值是 **`10:49:31Z`，117 分钟前**——旧痕迹，那个实例根本没醒。
⇒ **仪器错误会顺着报告链传播，而下游没有办法从数值本身看出它被标错了时区。**

**为什么记过还犯**：我**决策用的仪器是对的**——`find -newermt '-5 minutes'` 用相对窗口，与时区无关；
判「本轮产物」时我特意换了 epoch 秒比较。**错的只是「显示」那一路**。⇒ 触发条件是
**「这个值只是打出来给人看的，不参与判断」这个自我分类**——它一出现，我就不再检查那个值的正确性。
与我记过的「快速看一眼这个自我分类会让纪律不适用」是同一族，只是载体从「要不要跑」换成了「要不要校」。
🔴 **但「只是给人看」是假的**：给人看的值会被人（和下游 agent）拿去做判断，test-m3-a 就是这么用的。
**凡会出现在消息或报告里的数值，都是参与判断的数值。**

**处方（换结构不换意志）**：**格式串里永远不写时区字面量**。要 UTC 就显式换算：
`python3 -c "...datetime.fromtimestamp(m, timezone.utc)..."`，或干脆只打 epoch 秒与「距今 N 分钟」
——**相对量不需要时区，也就无从标错**。

**顺带一个反向的好例子**：test-m3-a 把那个 mtime 标成「**观察，不下结论**」交给我核，理由是
「mtime 不回答『谁改的』」。**这个习惯这次救了它**——那个值本身就是错的；若它据此推断「test-m3-b 醒了」，
下一步很可能是去等或改计划。⇒ **把可疑观测交给能核实的人，比自己就地推断更省**。

## 我批评一个机制「没做它本来就没打算做的事」，还差点把这个错判写成永久记录（M3 TASK-007）

**事件**：三任验证者卡死期间，`stale-dispatch` 对前两任报警、对第三任不报。我据此断言
「本轮产物判据看不见工作痕迹，**已经第二次让告警指错人**」，并准备写进 PENDING。
**写之前去对了一次数，当场证伪**：

| 实例 | checkpoint mtime | 本轮起点 | 属本轮 | 告警 |
|---|---|---|---|---|
| test-m3-b | `08:23:11Z` | `10:45:27Z` | ✗ | 报了 ✓对 |
| test-m3-a | `09:11:45Z` | `12:44:01Z` | ✗ | 报了 ✓对 |
| test-m3-c | `15:17:44Z` | `15:14Z` | ✓ | 没报 ✓对 |

**三次全对，规则按设计工作。**「内容命中而时间不命中就不算数」正是它刻意的设计（防上一轮旧产物消音），
而我把这条设计读成了缺陷。

**错因（这才是要记的）**：我拿「**我知道它们在建 worktree、所以它们在动**」去反推「告警不该响」。
但**告警问的不是「它有没有在动」，是「owner 有没有留下可核查的产物」——那是两个问题**，
而 worktree 恰恰不是产物（它是我从 `git worktree list` 里侧面看到的，不在任何声明的产物路径里）。
⇒ 判别式：**指责一个判据「漏报/误报」之前，先把它的判定问题原样写出来，再问我的反例是不是在答同一个问题。**

**真正的结论方向相反**：规则是对的，缺的是**下游纪律**——前两任中途不落盘，规则就只能报警；
我给第四任加了「每完成一步落一行 checkpoint」之后，规则立刻恢复静默。
**这是机制正常工作的证据，不是它的缺口。**

⚠️ **最该记的是「差点写进哪里」**：PENDING 是给下一个 leader 读的、寿命跨 sprint 的载体。
一条**错的机制批评**写进去，后果不是「多一条噪声」，而是**有人照它去改一个本来正确的判据**。
⇒ 与我记过的「结论对但理由错」同族，但更险：这次**结论也错**，只是错得像个有据可查的观察。
**触发条件：我准备把一条批评写进跨 sprint 载体时，先去取一次原始数据对照**——成本是一条命令。

## 证伪自己的假设比证实它便宜得多（同一任务，同日）

三任卡死后我写给人类：「最可疑的一环是**独立复算三个存活变异**，那是我在每份交底里都强调的重活」。
然后我**自己跑了一遍它们要跑的命令**：`python3 -m unittest -v` → **84 tests / 2.313s / rc=0**。
⇒ **工作是秒级的，「太重」当场不成立。** 一条命令、几秒钟，推翻了我准备写进交底和 PENDING 的因果。

**为什么这个证伪重要**：人类已据我那个假设做了决定（「换人 + 砍掉变异复算」）。动作**仍然可取**
（减少工具调用次数 = 减少暴露在挂起窗口里的机会），但**理由必须换**——
若照原理由记档，下次有人会以为「验证太重」而去砍别的重活，**方向就错了**。
⇒ **动作对而理由错时，要单独更正理由**，不能因为「反正做法没变」就让错理由跟着正确动作一起留下来。

## 计数判据的四种坏法，一个 dev 在一个任务里全撞齐了（M3 TASK-008，dev-m3-a 自己归纳）

| # | 坏法 | 本轮实例 | 报出的数 | 真值 |
|---|---|---|---|---|
| ① | **硬编码结论**（`echo` 一句写死的话盖住数据） | 此前两次 | — | — |
| ② | **数错对象**（`grep -c` 数的是**行数**不是**项数**） | 此前 | — | — |
| ③ | **模式过宽** | `grep -cE '^### [A-D]\.'` 数到了**全文所有 sprint** 的小节 | 34 | 4（限定 M3 节内） |
| ④ | **模式过窄** | `test_prepare.py\*\* \*\*55\*\*`，而原文用的是**反引号** `` `test_prepare.py` **55** `` | 0 | 1 |

**它自己总结的共同点，比分类本身值钱**：
> **输出一个形状合理的数，没有任何东西会因为它错了而变红。**

⇒ 这四种都不报错、都给出「看起来对」的数字，而**验证者与 Leader 都是拿这个数去下判断的**。
与我记过的「自证数字与自证判据本身不受任何自动门禁检查」是同一件事的四个具体形态。

**③④ 是同一维度的两个方向，值得配对记**：过宽=模式匹配到了我不想数的东西；过窄=模式匹配不到我要数的东西。
**我此前给的处方只防了过宽**（「先问这个模式会不会匹配到我不想数的东西」）。dev-m3-a 把它扩成：
> **再问一遍：原文到底是怎么写的。**

**这个扩法同时防住两个方向**，而且它还防住另一个我单独记过的坑——**搜索空间不含对象**（它同一天先撞过：换对了工具 ugrep→python，却只搜七份 discovery，而数在**验证报告**里）。
⇒ 合起来是一条判据、三种失效：**「找不到 / 数不对」= 匹配式过宽 ∨ 匹配式过窄 ∨ 搜索空间不含它。去看一眼原文，同时排除三者。**

**它做对而值得抄的一件事**：两次判据错误**都写进了 discovery 的 `verification` 与 `key_findings`，不是私下改掉**。
⇒ 与我记过的「静默修复会掩盖系统性缺陷」互补：**把自己的仪器故障留痕，才拿得到「同族四种坏法」这个频次结论**——
私下改掉的话，每一次都只是「偶发手滑」，永远凑不出这张表。

## 数字的锚必须是它实际来源的那棵树，不是事后好看的那棵（同任务）

TASK-008 的 §B 表头锚写 `fd933f49…` 而非交付时的 `41a19d87…`，dev 的理由：
> §B 六行数字**实际采自那棵树**。两锚之间只有本任务自己的 `.md` 追加、`.go` 变动 0 文件，已重跑复现。
> **数字的锚必须是它们实际来源，不是事后好看的那个。**

**我认可并在派验消息里替它挡了一道误判**（要求验证者核「两锚间 `.go` 确实 0 变动」，而不是质疑「锚为什么不等于 HEAD」）。
⇒ 这与我记过的「自证数字必须在最后一次改动之后统一重采」**不矛盾，是它的正确边界**：
**重采是为了让数字与产物同源；而当重采区间内被测对象根本没变时，保留原锚 + 证明区间无关变更，比换个新锚更诚实**——
换新锚会让读者以为这些数字是在新树上测的。**「锚要准」压过「锚要新」。**

## 「他能自查出来」是**能力**判断还是**学习**判断——搞混会得出相反的用人结论（M3 收尾，dev-m3-a 纠正我）

我对 dev-m3-a 说：「两次零命中，一次你自己追出来的、一次我指出的——**能自查出来的错，和要别人指出来的错，是两个量级**。」
它接受这个区分，但纠正了因果：
> **模式过窄那次我能自查出来，恰恰是因为前一次（搜索空间）你先指出过。反射不是我自带的，是那次之后建立的。**
> 准确的说法是「一次被指出、一次内化后自查到」，不是「我本来就会」。

**这个纠正改变结论，不只是措辞**：
- 我的说法读起来像**能力属性**（有的 agent 会自查、有的不会）⇒ 推论是「挑会自查的人」。
- 它的说法是**学习事件**（自查反射由某一次具体纠正装上）⇒ 推论是「**纠正一次就能装上，值得花那一次**」，而且**可以数装了几次**。

⇒ 判别式：看到「他这次自己发现了」，先问**「上一次同族的错是谁发现的、隔多久」**。
两次都自查 = 能力；先被指出再自查 = 学习**且已生效**；反复被指出仍不自查 = 处方没落到能触发的位置。
**三者的下一步动作完全不同**，而它们在「这次他自查到了」这个观察上**完全同形**。

⚠️ 与我记过的「归到人身上下一步是『下次仔细点』，归到空缺角色上下一步才是『谁来补这个位置』」同族：
**归到能力上，下一步是换人；归到学习上，下一步是给出那一次纠正。**

**顺带**：它还把我那条修正（「约束不在我什么时候发，而在它什么时候能被执行」）接到了我自己的旧记忆上——
「**文字里声明作废不构成机制**」（我曾白纸黑字写「前两个 sha 已作废」，对方仍取到旧的）。
**发送时刻 ≠ 到达时刻 ≠ 可执行时刻**，三者都不同，而消息文本对此一无所知。
它对我处方的评价也准：要求里附一句「若你已转 `dev_done`，不要执行，回我改落点」，好在**把判断交给唯一知道当前状态的人**
——**这是「改结构优于加意志」的实例：不依赖任何一方记得算时序，只依赖接收方读一眼自己的 status。**

## 17 处 DoD 缺陷全部由下游发现——不是「我不仔细」，是**没有角色以 DoD 为审查对象**（M3 Step 6，qa-m3 诊断）

我整个 sprint 把这件事记成「我的 DoD 缺陷累计 17 处，全部由 dev/verifier 发现、**无一由我自查出**」，
并把它当作一条关于**我**的观察。qa-m3 接到交底后当场换了归因：
> 17 处、全部由下游发现，说明缺的是「**有人专门以 DoD 为审查对象**」这个角色，**附带审会再次漏掉**。

⇒ 它据此把「DoD 质量」从我建议的「第一轮的一个方面」提到**与代码同级的独立维度**，逐条做
「可测试性 / 计数与位置锚是否自洽 / 闸是否装反」的机器可核查复核。

**这个归因改变下一步动作**（与我记过的分配纪律同构）：
- 归到人：下一步是「下次仔细点」——**而这条处方在本 sprint 已被证伪 17 次**。
- 归到空缺角色：下一步是「**谁来补这个位置**」——本 sprint 其实有过一次半吊子实现（Step 3 的独立 reviewer
  只读需求反审，找出 17 项、其中 5 项实质义务），**但它只在 DoD 定稿那一刻跑了一次**，
  而我此后因裁决、改名、拆任务又反复改写 DoD，**改写之后再无任何人以它为审查对象**。

⇒ **真正的缺口是「DoD 变更后没有复审触发点」**，不是「初版 DoD 没人审」。
判别式：**一份会被反复修改的判定依据，它的审查者必须绑在「每次修改」上，而不是「首次定稿」上。**
（同族：我记过「产物写采样锚，验证者对每个锚跑 diff」——那也是把审查绑在变更上而非绑在时刻上。）

**为什么 dev/verifier 发现它们不算「有人在审」**：他们是在**用** DoD 的过程中撞到的——
撞到的必然只有「挡了我路的那些」，而**不挡路的缺陷（如装反的闸、恒真的判据）会一路通过**。
本 sprint 恰好有实例：`##` 计数装反、构建树 grep 恒真，**都不是被 DoD 的使用者撞出来的，
是被专门去求值的人算出来的**。⇒ **使用与审查是两种关系，前者的覆盖面由「碰巧走到哪」决定。**
