## dev-agent-42 / TASK-002（hestia types.go）2026-08-08

### L1. 「正确的结论 + 错误的理由」是最难被发现的一类缺陷
派单让我别照抄需求文档的 `assert.Contains(err.Error(), field)` 弱断言，理由是「实现把
`period` 与 `period_type` 搞混时该用例照样通过」。**结论对，理由不对**：我用变异对照实测——
- **完整互换**两个标签：`Contains` 半数拦得住（`period` 子测误判 PASS，`period_type` 子测 FAIL）
- **单侧误写**（只把 `period` 的标签写成 `period_type`）：`Contains` 下 6/6 子测试全 PASS，完全存活

结论正确会让这条判断一直不被复查，而**理由是别人复现时唯一的入口**——理由错了，等于给后来人
埋一个「结论看起来被证伪」的陷阱。验证者按错理由复现会得到部分 FAIL，只能二选一地误判：
要么「Leader 结论错了」（放过弱断言），要么「实现有问题」（冤枉开发者）。本次这条更正在
test-agent-21 正按错理由做变异时被 Leader 转发拦下。

**做法**：拿到「因为 X 所以要 Y」的指令，若 Y 成本低就照做，但**X 值得花一次变异去实测**。
证伪 X 不等于推翻 Y。报告里要把「结论仍成立」和「理由已更正」分开写。

### L2. 交付后不要碰已被钉住基线的文件——哪怕改动本身是对的
`dev_done → verifying` 时写通道会钉 `verify_baseline = {head, discovery_sha256}`。此后

**做法**：交付后发现的小改进，走 reject/返工环去补（那时才名正言顺重新持有 owner），

复合字面量在**编译期**就强制了字段名与类型，运行时断言只是锦上添花——否则容易被当成真缺口返工。

### L4. 形态校验与值域校验的失效机制不同，别混为一谈
G1 要求 `period` 匹配 `YYYY-MM`、`published_at` 匹配 `YYYY-MM-DD`。我刻意**只校形态、不校
日历有效性**（`2026-13`、`2026-02-31` 放行），并把缺口显式登记进注释与 discovery，请 Leader
裁定归属（已确认归 M1b-3 闸门层）。依据：G1 三条静默后果的共同机制是「长度不定 ⇒ 字典序失效」，
定长补零是该机制的**充分**修复；而 `2026-13` 是定长的，不破坏字典序，只是语义无效。

**做法**：一个被隐式假定已覆盖的缺口，比一个公开登记的缺口危险得多。范围外的东西要

收益为零，是记录在案的排除而非遗漏」——沉默的跳过和显式的排除在输出上都是「没跑」，
但只有后者可被复核。

### L6. 写给未来自己的禁令必须带**可机器验证的失效条件**
L2 让我在 checkpoint 里写了「不要再动 types*.go / 不要覆盖 discoveries/TASK-002.json」。
这句在 `verifying` 期间成立，但**一旦 TASK-002 被 reject 进返工环、我重新持有 owner，
改这两个文件恰恰是我的本职工作**——压缩后重启的我会拿这条禁令拒绝该做的事，
理由还看起来很充分（「checkpoint 里白纸黑字写了」）。自查发现，已先修再报。

**两种过期的危害不是一个量级**：过期的**指针**只是失效，去用它会立刻撞墙（比对 HEAD 即可发现）；
过期的**禁令**让你什么都不做，而「什么都没发生」在任何输出里都不可见。

**只补「为什么」不够——「为什么」本身也会过期。** 真正让禁令安全的是失效判据，
因为它把「这条还算不算数」从记忆问题变成一次 jq 查询。

**禁令三件套（缺一不可）**：
1. 禁令内容
2. 为什么（如：`verify_baseline` 已钉在某 sha，改动会逼验证者 `--ack-drift`）
3. **失效条件，必须可机器验证**（如：`jq -r .status TASK-002.json` 不再是 `verifying`；
   变成 `rejected`/`review_fix` 且 `assigned_to` 是我 ⇒ 禁令作废，继续守等于拒绝返工）

外加元指令：**先验条件，再决定守不守，不要无条件照做。**

警惕「**过期得更有解释力**」——一个带充分理由的错误决定，比一个没理由的错误决定更难被推翻。
更一般的形状：**把一个需要人记得的判断，换成一次可执行的查询**（同 [[L2]] 与写通道的
epoch 断言：机制化断言优于口头自觉）。

### L7. KILLED 只说明「有东西抓住了它」，消融实验才说明「是这条抓住的」
TASK-006 闭合 T5 交接的存活变异 M7' 时，光有「M7' → KILLED」并不能说明我新写的那条测试起了作用
——也可能是别处顺带覆盖的。做法是**消融**：同一变异 + 把那条新测试改名停用（Go 里改成
非 `Test` 前缀即可，未使用的包级函数合法，不影响编译），再跑一遍。结果是**完全存活 72/72**
（停用一条含 2 子测的测试后基线正是 75-3=72），于是因果唯一性成立。

**做法**：凡是「我写了 X 来闭合 Y」的交付，除了 `Y → KILLED`，再补一次 `Y × 停用 X`。
两次都要带完整自证。停用比删除好：改名保留了代码，复原只需一次 `git checkout`。
注意基线要**跟着调整**（停用了几条就减几条），否则「PASS 数变了」会被误读成有测试变红。

同一形状也适用于覆盖率：`覆盖率上升`说明有代码被执行，不说明有断言在看它。

### L8. 自己上游任务里的论证，会被下游原样引用——复核它是义务，不是可选项
我在 T4 为「pending 表不做漂移检查」给的论证是「两表由同一 NewStore 建出，观测表通过则
DDL 整体执行成功」。Leader 在 T6 的 DoD 里**原样引用了它**。到 T6 复核时我发现它**不够强**：
挡不住「某个版本只改 pendingDDL 而不动 fieldOrder」。

真正成立的论证是**危害结构性不同**，而不是「风险较低」：观测表的 INSERT 列由 Values 里实际
存在的字段决定 ⇒ 缺列只在恰好含该字段的那一期才炸；pending 的 INSERT 八列固定不变 ⇒
任何不符在**第一次**写 pending 时就确定性失败。⇒ G7 的「静默到某一期才炸」在 pending 上
**结构性不成立**。

**Why**：我若照着自己原来的论证写，没有人会发现问题——它已经披上了 DoD 的外衣，看起来是
被 Leader 审过的判断。**一个论证被引用的次数越多，越难被重新检查。**

**做法**：接到引用了自己旧结论的任务时，把那条结论当成**别人写的**重新验一遍；
「风险较低」型论证要升级成「危害机制不同」型才算数——前者是估计，后者可证伪。
且**论证不能停在声明**：把它的关键一环做成可执行证据（本例是
TestSavePendingFailsLoudlyOnDriftedPendingTable，M5 变异被它杀死）。

### L9. 「当前无害」的正确处置是钉成契约，不是不管
改用 RFC3339Nano 后发现它去掉小数尾零 ⇒ `"…:00Z"` 与 `"…:00.5Z"` 的字典序与时间序相反。
当前确实无害（ingested_at 不是 revision 列，bitemporal 不碰它，pending 主键只要求唯一）。
但「当前无害」与「不用管」是两回事：无害是**当前用法**的性质，不是**这个值**的性质。
按仓库既有做法（bitemporal 的 TestLookupRevisionFormIsCallerGuaranteed）钉成可执行契约，
谁将来对它做 ORDER BY/MAX() 会被那条测试拦住，并被提示改动需要迁移既有数据。

### L10. 删掉别人的钉子测试，要区分「目标行为」与「当时状态的副产品」
T5 的 TestSaveDuplicateIsLoudNotSilent 断言「Duplicate 必须报错」，与 T6 的 DoD
「Duplicate 只刷 article_id 不新增行」**不可能同时成立**。判断依据是它自己的注释：
「此刻**没有专门处置**，会撞主键约束而响亮失败」——可见「响亮失败」是**尚无处置的副产品**，
不是有人想要的目标行为；而它真正要防的是「顺手加个 INSERT OR IGNORE 变成静默丢弃」。

**做法**（四步，缺一步就是无声删除）：①在注释里说明为何原前提被推翻；②给出**等价强度**的
新防线（这里：行数不变 **且** article_id 已刷新——INSERT OR IGNORE 会让后半条失败）；
③原位置留一段注释指向取代它的测试，别让人 git log 考古；④**用变异证明新防线真的挡住了
老防线要挡的东西**（M2「静默丢弃」被杀死）。第④步是关键：前三步都只是说法。

### L11. 「显式 pathspec」只限制文件、不限制 hunk —— 提交后必须核实产物归属
2026-08-09 实撞：dev-agent-41 用了 `git add internal/hestia/store.go internal/hestia/store_test.go`
（**遵守了**「只 add 自己的文件」这条纪律），却把我在同一文件里的未提交改动一起提交了，
commit message 只描述它自己的修复。**纪律的措辞有盲区**：它防的是误提交别的文件，
防不住同一文件里别人的在途改动。

**做法**（便宜且不依赖调度正确）：提交后立刻
`git show --stat HEAD` 确认文件数与行数符合预期，再按**他人产物的符号名** grep 一遍
（`git show HEAD | grep -c '<别人的函数/测试名>'` 应为 0）。我提交 C3/C4 时做了这步，
所以那条是干净的——但我做它只是因为刚被咬过。

**发现污染的探针是测试计数差额**：我只加了 1 条测试，重测却从基线 61 顶层/75 含子测试
变成 64/84。**差额对不上就停下来查，不要上报**——不查的话我会带着虚高的 84 提交并上报。
覆盖率同样会被污染，且比计数隐蔽得多（89.3% 里含了别人的代码与测试）。

**并行同文件时，判定数字一律取自隔离检出**：`git worktree add --detach <tmp> <干净 ref>`，
在干净基线上**只重放自己的改动**（用唯一边界从共享树抽取），再测。共享树的数字不可用。

**不要反向剔除别人的改动**——那是对别人正在写的文件做读-改-写，是同一个竞态的另一面。
正确动作是：不提交、通知对方、自己在隔离检出里继续。

### L12. 队友（含 Leader）的消息可能基于你上一轮之前的状态——先直读再回答

### L14. 「我在核实」和「我核的是那个东西」是两回事
同一天两个人踩同一类坑：
- 我：`validator-run.sh ... | tail -20; echo "EXIT=${PIPESTATUS[0]}"` 打印出**空的** `EXIT=`，
  我没注意到，转而用输出里的「✗ 发现 4 个问题」当判据——而被测脚本的注释恰好写着
  「**判别只看退出码，不解析 stderr 文案**；按文案判会在改一句提示时静默失效」。我干的正是它禁止的事。
- dev-41：`... | head` 之后取 `$?`，拿到的是 `head` 的 0，差点得出「validator 不拦」的反向结论。

两例都是**结论正确、取证方式无效**——最难自查，因为没有任何东西变红。

**做法**：取退出码不要跨管道（要么 `cmd >/dev/null 2>&1; echo $?`，要么确认 `PIPESTATUS`
真的取到了值）；**打印出来的自证字段是空的，等同于自证没做**——空值要当失败处理，不要略过。
凡「判据是退出码」的地方，不要退回去解析文案，哪怕文案看起来正好印证你的结论。
与 [[shell-silent-failure-and-harness-self-proof]] 同源。

### L15. 机制越显眼，越容易让人以为它管的范围更大
本 Sprint 的注脚，来自刹车代码自己的注释：

> 刹车拦的是**任务图问题**，不是代码缺陷……它查的是 DAG 成环 / wave 序 / scope 互斥 /
> epoch 不变量这类**声明层**的错，对 C2、C3 那类实现层漏洞一无所知。
> **装了刹车不等于不会再出那种洞——别让下一个读者据此放松代码审查。**

对照本 Sprint：Leader 在这道刹车上撞了半小时死锁（它很显眼、很响、很难绕过），
而 QA 抓到的 C1/C3/C4 **全是实现层的**，刹车对它们一无所知。**注意力被响的那个吸走了。**

**做法**：给机制写注释时，把「它**不**管什么」写得和「它管什么」一样显眼——那段注释之所以
有用，正因为作者预判了「下一个读者会高估我」。反过来读别人的机制时，先问一句
「它的判据是什么层的」：声明层的闸挡不住实现层的洞，覆盖率门禁挡不住断言缺失，
类型签名挡不住语义自相矛盾（G10 就是这么来的）。

**同一形状还有一例**（L14）：`validator-run.sh` 的退出码是契约、stderr 文案不是，
而三个人都去解析了文案——因为文案显眼、退出码不显眼。**显眼 ≠ 权威。**

discovery 路径相对任务目录解析，副本换了目录，`../discoveries/` 自然不存在。
**exit 仍是 1，只看退出码会得出「即使两个 verified 也解不开」的反向结论**；它是去看了具体条目
才认出那是自己制造的伪影。

本次 mutex 结论不受影响（该规则不读 discovery 路径），但**方法对任何路径敏感的规则都会给错答案**。

**做法**：沙箱副本必须先跑一次**未改动的 t0**，与真实环境的输出逐条比对；
**差异即你的伪影地板**，后续所有读数都要减掉它。这与变异实验里「基线要跟着调整」
是同一条纪律，只是这次被污染的不是基线，而是**测量装置本身**。

推论：**聚合信号（exit code / 计数）必须能落到具体条目，落不到就不算核实过**（dev-41 的总结）。
这与 L14 的「空值要当失败处理」互补：一个防「读数缺失」，一个防「读数里混了别的东西」。

### ⚠ 撤回：上面「L14 补充：先跑未改动对照量伪影地板」那条**是错的，不要照做**
（本文件只能追加，所以原文留在上面。**读到那条请以本条为准。**）

dev-agent-41 实测推翻了它：副本里 `missing-discovery` 的条数是 t0=4 / tA=5 / tB=6，
**不是常数**。成因是该规则只对 **verified/accepted** 的任务生效（CLAUDE.md 第 425 行
「完成必有产物」），而它的**被测变量恰恰就是 status**——每把一个任务改成 verified，
就多触发一条。

⇒ **地板 = f(被测变量)。** 照我说的「t0 量地板、后续减掉」会算出 tB 有 `6-4=2` 条真实新问题，
**而实际是 0 条**——我的补法会**制造**一个不存在的问题，方向和它想防的正好相反。

**正确做法（dev-41 给的，我核过机制）：按规则名切片，只读被测规则的计数，不读总数、不读 exit code。**
不同规则受不同变量影响，加总本身就是在制造耦合；**混合信号没有稳定的地板可减。**
它当时只报 `scope-mutex 4→2→0` 而不报总数是凭直觉，现在有依据了。

**副本法的第二个弱点（dev-41 发现）**：快照会过期。它的 t0 复制于三个任务都 verifying 时，
做对照时真实已推进到两个 verified，于是「t0 vs 真实」的差异里**既有伪影也有漂移**。
⇒ 用副本法要记下**快照时刻的真实状态**，解读前确认真实状态没变，变了就重新复制。
与 checkpoint「产物指针要带 sha、恢复时先比对」同一条纪律。

**我从这次学到的（比上面的技术细节更该记）**：我提出了一个**验证技术**却没有验证这个技术本身，
还把它写进了共享 wisdom。这与本 Sprint 反复出现的那条同源——
[[L8]] 说「自己被引用的旧论证要当别人写的重验」，而这次我连一轮都没验就交付了方法论。
**给别人的方法，比给别人的结论更需要先自证**：结论错了只影响一处，方法错了会被反复套用。

### L16. 造实验装置之前，先翻现有数据里有没有**已知答案的样本**
dev-agent-41 提出、我在真实环境核实：要验「`verified` 是否移出 scope-mutex 的在途口径」，
当前任务图里就现成躺着一个阳性对照——

```
TASK-001 verified  writes 含 ./internal/hestia/fields.go
TASK-007 verified  writes 含 ./internal/hestia/fields.go   ← comm -12 确认确实相交
真实 validator: scope-mutex 0 条, exit 0
```

两个任务的 writes 真的相交、都已 verified、validator 不报。**零成本、零装置、就在真实环境里。**

它当时注意到过这个对照，第一版脚本里写了「场景 C：现成的反证」，那条命令被 write-guard 拦掉，
重写时只保留了副本部分——**把免费的对照组扔了，然后花力气造了三个副本**，而副本恰恰引入了
伪影（见上面那条撤回）。

**做法**：现有数据里的已知答案样本有两重价值，且第二重更重要：
①**校验装置**（装置在它上面给错答案 ⇒ 装置有问题，不必等到解读阶段）；
②**可能直接替代装置**——本例中 T1/T7 让整个副本实验变得不必要。
所以顺序是「先找样本，找不到再造装置」，不是「造完装置再找对照」。
真实环境的观测天然没有伪影，证据等级高于任何自造副本。

### L17. 审视姿态是**不对称**的：推翻别人时天然在，提出自己时不在
dev-41 的自省，我认为是本 Sprint 最该记的一条：

> 我推翻你的补法时去量了，但我提出自己的方法时没量。**两件事之间隔了不到一小时，同一个人，
> 一个做了一个没做。** 差别在于推翻别人的东西时我天然处在审视姿态，提出自己的东西时不在。

对称地，我也一样：我给它的方法挑出了弱点（副本会引入伪影），却把自己的补法（减去常数地板）
直接写进共享 wisdom，**一轮都没验**——而那条补法是错的，会凭空制造一个不存在的问题。

**两条不对称叠在一起就是这次的形状**：
- 提方法时不验（两人都犯）
- 而**方法比结论更需要先验**：结论错了只影响一处，方法错了会被反复套用

**做法**：把「这是我自己提出的」当成**提高**而非降低举证门槛的信号。具体到可执行：
凡要写进共享 wisdom / 交给别人复用的**方法**，先在一个已知答案的样本上跑一遍（见 L16），
跑不通就别写。这条比 [[L8]]（自己的旧论证要当别人写的重验）更靠前——L8 管的是被引用之后，
这条管的是**交付之前**。

### L17 改写（采纳 dev-41 的更好表述）：举证门槛由「**会被多少人用**」决定，不由「谁产的」决定
我原来的 L17 写成「把『这是我自己提出的』当成提高举证门槛的信号」——**那还是以「谁产的」为轴**，
只是把方向反了过来。dev-41 换了轴：

> 审视姿态默认由「谁产的」触发，而不是由「**会被多少人用**」触发。后者才是该触发它的变量。

这个版本解释力更强：它**顺带解释了为什么方法比结论更需要先验**（方法的使用人次天然更多），
不必再单立一条。也解释了为什么「推翻别人 vs 提出自己」的不对称是个 bug——
使用人次与作者是谁无关。

**可执行判据**：交付前问「这东西会被套用几次」。一次性结论 → 常规自证即可；
要写进共享 wisdom / digest、要被别人复用的方法 → 先在一个已知答案的样本上跑通再写（L16）。

### L18. 现成样本与自造装置是**分工**，不是替代——但顺序仍是先翻样本
L16 我写成「现成样本可能直接替代装置」，dev-41 修正得对：**现成样本的覆盖面受限于
「恰好存在的状态组合」，装置能构造任意组合。** 这次是 verified×verified（T1/T7）与
verified×verifying（当前 T4 verified / T5 verifying / T6 verified，mutex 0 条，我核实过）
两个组合真实环境**恰好都有**，所以副本不必要——**但这是事后才知道的**。

**收敛后的动作顺序**：先翻现成样本 → 看还缺哪些组合 → **只为缺的那些造装置**。
缺口可能是零，也可能不是；不翻就永远不知道。装置那一侧仍受「伪影可能是被测变量的函数」
约束（见上面的撤回条），所以能用真实观测的地方不要用副本。

### L19. 这轮四次纠正，全部靠「去量」而不是靠「同意」
本 Sprint 末尾我与 dev-41 互相纠正各两次：我错在 test 边归属、错在减常数地板；
它错在 test 边的推断来源、错在覆盖面判断。**四次没有一次是靠谁让步达成的，全部是一方
实际去跑了一遍数据。** 其中三次纠正的是**对方刚刚才认可过的东西**。

⇒ 协作里「对方同意了」不构成证据。**收到认可与收到反驳都应触发同一个动作：去量。**
这条与 [[L5]]（子代理回复不可采信）、[[L12]]（队友消息可能基于过期状态）同族——
只是那两条防的是「别人给的信息不可靠」，这条防的是「别人的**赞同**不可靠」，后者更难警觉。

### L20. 观察性证据 ≠ 受控实验——覆盖面相同也不等价（dev-41 指出，我完全没想到）
我在 L18 里说「两个组合真实环境恰好都有，所以副本不必要」，**隐含把两类证据当成了同一种，
只比较覆盖面**。dev-41 指出的区别是根本性的：

- **真实环境的前后两个时点**是观察性证据：中间除被测变量（status）外还变了 discovery 落盘、
  commit 推进、任务数 ⇒ **排除不了「其他因素同时变化」**。
- **副本**是受控实验：只改 status 一个变量，其余逐字相同。

这次两者结论一致纯属两者都对，不是「副本冗余」的证明。

**收敛后的完整顺序**：先翻现成样本 → 看缺哪些组合 → 为缺口造装置 →
**真实环境事后走到同一组合时，用它反过来校验装置**。最后这半句这次成立了
（真实 0 条 = tB 副本 0 条），额外好处是**装置的可信度会随时间自然增长**，不必一次性证明。

（顺带记一个本次的强观察：当 T5 成为**唯一在途**任务、其 writes 与两个 verified 完全相交而
mutex 仍为 0 条时，它排除了「规则 = 在途 × 所有任务」这个竞争解释——**排除竞争解释的观察，
比单纯的一致性观察值钱得多**。）

### L21. 「靠量不靠同意」的前提是**把量的入口留出来**（dev-41 的收口，整轮的地基）
> 四次被纠正的点，都是被纠正者自己留下了可查的把手 —— 你标了「这是推断不是实测」，
> 我报了具体的副本读数和场景构造，双方才有得量。

只给结论不给过程时，对方只能**选择相信或不相信**——而那正是 [[L19]] 要防的「靠同意」。

⇒ **「留把手」不是透明度姿态，是让纠错在技术上可能的前提条件。** 具体到可执行：
交付里要带上**别人能独立重跑的那一项**——命令原文、读数、样本构造、以及哪一步是推断。
这也解释了为什么 [[L13]]「标注不确定性」有用：它是把手中最便宜的一种，直接告诉对方该验哪一段。

**本轮总账**：我与 dev-41 互相纠正五次（我 3、它 2），**全部靠一方实际去跑数据达成，
没有一次靠让步**；其中三次纠正的是对方刚刚才认可过的东西。
