### A. 自证机制本身会骗人——四种形态，我撞了三种

判据的可信度不取决于我跑了多少条命令，取决于**我读的那个数是否真的在度量我以为的东西**。

1. **「0 红」被编译失败伪造。** 变异后测试无 FAIL，看着像存活，实为编译失败（顶层 PASS=0、`go vet` exit≠0）。
   ⇒ **Go 的「声明未使用」让「关掉一个分支」类变异格外容易编译失败**——关掉收集逻辑，收集变量就没人用了，而那恰是最自然的变异写法。可编译的等效写法：保留收集、改为不据此报错（`if false && len(x) > 0`），或整体替换成另一份完整实现。
2. **「全红」被语法错伪造。** 删掉 `PRIMARY KEY` 整行 ⇒ 前一列残留尾逗号 ⇒ SQL 语法错 ⇒ 6 个测试一起红。那证明的是「语法错会被抓」，不是「无 PK 会被抓」。
   ⇒ **一个变异杀死多个测试时，先怀疑它顺带破坏了别的东西**，而不是当成「测试很强」。用 `CHECK (1)` 占位替换才隔离出单点红。
3. **变异工具自己静默改坏文件。** `perl -0pi -e 's|…\|\|…|…|'` 模式里的 `\|\|` 与 `|` 分隔符冲突，把整个文件替换掉，首行变成 `if`。
   ⇒ 每个变异加**文件完整性自证**（首行必须是 `package X`）；替换改用 `python3` + 对锚点 `assert`。
4. **取错了那个数。** `cmd | head -20` 之后 `echo $?` 取到的是 `head` 的 0，而输出里明明写着「✗ 发现 4 个问题」——差点据此得出「validator 不拦」的**反向结论**。
   ⇒ **取退出码不要跨管道**；`PIPESTATUS` 或去掉管道。（dev-42 同期撞到 `PIPESTATUS[0]` 打印为空而未察觉，同族。）

**四条自证里真正救场的是 `vet exit` 与「PASS 计数低于基线」——不是「等于 0」。** 后者更严格：整包编译失败会塌成 0，部分文件失败只塌一部分。只看「有没有 FAIL 行」，形态 1 与 3 都会误报存活。

### B. 聚合信号会被环境伪影污染，且伪影可能是被测变量的函数

用 `tasks/*.json` 的副本做受控实验（改 status 后跑 validator）时，副本换了目录 ⇒ 相对路径解析跟着变 ⇒ 冒出 6 条 `[missing-discovery]`。**tB 的 scope-mutex 是 0 而 exit 仍是 1**；只看退出码会得出「即使两个 verified 也解不开」的反向结论。

dev-42 提议「先跑未改动副本量出伪影地板，后续读数减掉它」。我实测后**证伪**：地板是 4→5→6，因为 `missing-discovery` 只对 verified/accepted 生效，而被测变量恰恰就是 status。

⇒ **地板 = f(被测变量)，混合信号没有稳定基线可减。** 按它的补法 tB 会被读成「2 条真实新问题」，实际是 0——补丁会**制造**一个不存在的问题。
⇒ **可用的替代：按规则名切片，只读被测规则的计数，不读总数、不读 exit code。**

副本法的另外两个弱点（我自己撞的）：**快照会漂移**（我的 t0 复制于三个 `verifying` 时，做对照时真实已推进到两个 `verified`，于是差异里既有伪影也有过期）；以及它是**受控实验**而真实环境读数是**观察性证据**，两类不等价——前者只改一个变量，后者的两个时点之间还变了别的。

### C. 证据来源的分工：现成样本 vs 自造装置

- **现成样本**：免费、无装置伪影、证据等级高；但覆盖面受限于「恰好存在的状态组合」。
- **自造装置**：能构造任意组合；但引入伪影，且伪影可能与被测变量耦合（见 B）。

⇒ 顺序：**先翻现有数据里有没有已知答案的样本 → 看还缺哪些组合 → 只为缺口造装置 → 若真实环境事后走到同一组合，用它反过来校验装置。**

本次的具体教训：现成对照（TASK-001 与 TASK-007 都 verified、writes 都含 `fields.go`、validator 不报）**我注意到了、写进了第一版脚本、被 write-guard 拦掉、重写时没捡回来**。⇒ **免费的对照组是被流程摩擦挤掉的，不是没想到。**

### D. 举证门槛该由「会被多少人用」触发，不是由「谁产的」

我推翻 dev-42 的地板补法时去**量**了；我提出副本探测法时**没量**。两件事隔不到一小时、同一个人。差别在于：审视姿态面对他人产出是默认开启的，面对自己产出不是。

我的原方法碰巧结论正确，**只是真实环境事后替我验了——那是运气不是纪律**。若 test 侧没在那几十分钟里验完 T4/T6，我的结论到那时仍只有一条自产证据链，与被证伪的补法处境相同。

⇒ **过程上两人都犯了「提方法不自证」，结果上一个被证实一个被证伪——两件都要说，只说一件都失真。**
⇒ 方法比结论更需要先验：**结论错只影响一处，方法错会被反复套用。** 而这正是「使用人次」而非「作者是谁」决定的。

配套：**「靠量而不是靠同意」的前提是把量的入口留出来。** 四次互相纠正之所以可能，是因为双方都留了可查的把手（对方标注「这是推断不是实测」，我报了具体读数与场景构造）。只给结论不给过程，对方只能选择相信或不相信。

### E. 共享工作区：显式 pathspec 有盲区

`git add <file>` **只限制文件、不限制 hunk**。TASK-004/005/006 声明了完全相同的 `writes`，我提交返工时把 dev-42 的在途 C1 一并提交了。「只提交你的文件」这条纪律防的是误提交别的文件，**防不住同一文件里别人的在途改动**；scope 互斥也挡不住，因为三者的 writes 本来就是合法地完全相同。

⇒ 补法（dev-42 提，我采纳）：**提交后 `git show --stat` 再按符号名 grep 一遍**，确认没有他人产物。它是**事后可执行**的，不像「小心别 add 到别人的改动」那样只能靠注意力。
⇒ 发现方式值得记：dev-42 是靠**测试计数差额**发现的（只加 1 条测试，计数却涨了 3）。数字对不上时去查，比事后审计有效得多。

### F. 「宣称但不成立」是一类反复出现的缺陷形状

同一 Sprint 撞到三次：
- **G9 并发契约**：DoD 说「确认包注释里已有」，grep 全部非测试 `.go` 输出为空——契约根本不存在。
- **`Skipped` 必填 Reason**：`types.go` 注释这么写，但无任何机制强制。
- **G10 的守护**：`CheckStatus` 是 string 具名类型，`c.Status == CheckFailed` 单值黑名单等于默认「不等于 failed 就是好的」，错拼即穿透。**而白名单（`checkValues` 对 Values 的键）是我在同一次提交里写的**——同一个包、同一条路径、同一类外部输入，我用了两种把关强度，没回头看隔壁十行的标准。

⇒ 注释若声称一个约束，要么让机制强制它，要么改注释。**「宣称、机制不支持、判据测不到」三者并存时，最先该动的是判据。**
