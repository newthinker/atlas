## AD-28：变异测试报「KILLED」时必须同时报**作用域**

**问题**：同一个变异在不同作用域下给出相反读数，而两个读数都不假。

**实测**（test-agent-12，同一变异 `maxClassEPSFilings` 28→12，同一棵树 `a73110e`）：

| 作用域 | 选中测试数 | 结果 |
|---|---|---|
| `-run '^TestFetchClassEPSRespectsLookbackCap$'` | 1 | **0/5 红（存活）** |
| package `.` | 113 | **5/5 红（杀死）** |

整包跑时唯一的 `--- FAIL` 是 **`TestClassEPSAndSegmentCapsAreIndependent`**
（`classeps_test.go:578` 的 `assert.Equal(t, 28, maxClassEPSFilings, ...)`）——
**被审查的那个测试根本不在失败列表里**。

**⇒ TASK-002 报的「M12 KILLED 10/10」字面属实，但它证明的是「包里有人杀得掉」，
不是「被审查的用例有判别力」。**

**决定**：

1. 变异记录必须写成 **「N 次中红了几次 @ 作用域」**，作用域是记录的必需字段而非可选说明。
2. **审查某个用例的判别力时，必须用 `-run` 收窄到该用例**。整包读数不能用于这个目的。
3. 报告里出现「变异 X 被 KILLED」而未注明作用域的，视为**未验证**。
4. **作用域必须记录 `-run` 正则的原文，不能只写描述**（test-agent-13 在 TASK-004 实撞）：
   dev 报的作用域计数 `1/14/12/1/1/1/1/11` **无法被复现**，因为旧作用域的正则从未被逐字写下——
   「限定到该用例」「旧作用域」这类描述在复核时无法还原成同一条命令。
   **记录格式**：`MUT-x: N/M @ -run '^TestFoo$'`，正则照抄，不转述。

   > 这与本条正文是同一个道理的两层：正文说「读数必须带作用域」，本项说
   > **「作用域必须可复现」**。一个不能被重新执行的作用域标注，与没有标注的差别只是看起来更可信。

**与 AD-27 的关系**：AD-27 记过「**满分的 N/M 要问它是在哪个档位测出来的**」（p 是 fixture
的属性）。本条是同一问题的另一个维度——**档位是采样维度，作用域是范围维度**。
两者都会让一个真实的读数支撑一个错误的结论。

**典型症状**：一个用例长期绿、变异也报 KILLED，而它对被测取值零判别力——
真正在守护的是别处一句字面量断言。**删掉那句断言，两个测试同时失去意义，而没有人会发现。**

## AD-29：变异坑第七类——`-run` 正则选中零个测试时冒充「存活」

**AD-27 已记六类**（还原失败致累积 / 编译失败 / `sed` 未命中 / 语义等价 / 执行环境错误 /
fixture 与生产不同）。**第七类**由 test-agent-12 在 TASK-003 实撞：

**`go test -run <regex>` 在正则选中零个测试时正常退出 0**，输出里没有任何 `--- FAIL:` 行——
**与「变异存活」的输出形态完全相同**。

**它与前六类同族**：变异测试的输出信号只有红/绿两位，任何环节出错都伪装成合法结果。
本类的特殊之处在于**错的是选择器而非被测代码或环境**——前六类的守卫（编译检查、
还原校验、命中数检查、对照组）**没有一个会触发**。

**触发条件**（实测）：把变异限定到一个**尚不存在**的测试名（例如在补测试之前的树上，
用补测试之后才有的用例名做 `-run`）。这在「先验证缺陷存在、再补测试」的正常 TDD 流程里
**极易发生**——两棵树的用例集合本来就不同。

**决定**：harness 必须加 **`-run` 作用域自检**——执行前确认该正则**至少选中 1 个测试**，
为零则以专用退出码中止，**不得计入 SURVIVED**。test-agent-12 的实现用 exit 6。

> ### ⚠ 自检本身可以是坏的（test-agent-13 在 TASK-004 实撞，本条初稿即为错例）
>
> 本条初稿写的自检命令是 `go test -run <regex> -list '.*'` —— **这是错的**。
> `-list` 接受自己的正则参数，**完全无视 `-run`**。Leader 实测（`internal/collector/edgar`）：
>
> ```
> go test -run 'TestFiscalYearEndMonthPicksMode' -list '.*'   → 列出全包所有测试
> go test -list 'TestFiscalYearEndMonthPicksMode'             → 只列出该测试
> ```
>
> 于是那个自检对**任何**作用域都报「选中 40 个」，**永远为真、永远不会触发** ——
> 一个恒真的守卫，与没有守卫的差别只是让人以为有。
>
> **正确形式**：`go test -list '<同一条 regex>'`，数输出行数（末行 `ok ...` 不计）。
>
> **这件事本身是本类坑的自我复现**：第七类讲的是「选择器错了而输出形态正常」，
> 而写来防它的自检**犯了同一个错**——用了一个看起来在筛选、实际不筛选的命令。
> **凡是「检查某某为零/非零」的守卫，都要先构造一个应当触发的输入验证它真的会触发**
> （test-agent-12 当初就是这么发现自检有效的：把变异限定到尚不存在的测试名，exit 6 正确触发）。

## AD-30：SEC inline XBRL 是**分层**推行的，404 边界因申报人规模而异

**背景**：`maxClassEPSFilings = 28` 的注释称「`reportDate ≤ 2019-03-31` ⇒ 老式非 inline XBRL
⇒ 实例文档必 404」。该结论对 **V(CIK 1403161)** 经逐份 curl 实测成立（序号 0–27 全 200、
28 起连续 404）。

**但 SEC 的 inline XBRL 是按申报人层级分批强制的**（test-agent-12 指出）：

| 申报人类别 | 强制起始（财report期结束日） |
|---|---|
| 大型加速申报人（large accelerated） | 2019-06-15 |
| 加速申报人（accelerated） | 2020-06-15 |
| 小型申报公司（smaller reporting） | 2021-06-15 |

而 `maxClassEPSFilings` 是**通用常量**，任何走类别维度 EPS 回退路径的公司都用它。
**对小型申报人，真实的 404 边界会晚得多**，28 份里可用的会少于 28。

**决定**：**暂不改**，理由三条（均由 test-agent-12 给出且我认同）：

1. **后果良性且已被守护**：多余的 404 由 `TestFetchClassEPSSkipsPre2019NotFoundTail`
   覆盖的逐份跳过逻辑处理，**只浪费请求、不丢数据**。
2. 注释**明确点名 V 为测量对象**，对该标的边界精确。
3. 偏差在**跨公司轴**而非**时间轴**——不属于 TASK-003 `functional[0]` 要求的
   「数据增长后仍正确」。

**触发重估的条件**：当第二家公司需要走类别维度 EPS 路径时，必须重新测定它自己的 404 边界，
**不得沿用 28**。届时应考虑把常量改为「按申报人层级查表」或「探测到连续 N 个 404 即停」。

> **这条记录的意义不在于当下要做什么，而在于把一个「对 V 精确、对他人未必」的常量
> 标记为有条件成立。** 没有这条记录，第二家公司出问题时会从数据源查起——
> 而 TASK-002 的整个调查过程正是这么开始的。

## AD-31：变异坑第八类——**崩溃型变异冒充「KILLED」**，且既有守卫只防住对偶方向的一半

**由 test-agent-49 在 ArcForge/TASK-002 实撞**（跨仓库，但属 AD-27 主干的直接延伸）。

**AD-27 记六类、AD-29 加第七类，本条是第八类。**

### 现象

变异算子把函数头改成 `guard_field_name() { return 0; } _unused() { #`：

```
$ bash -n <变异体>
line 94: syntax error near unexpected token '_unused'
```

**产生的不是「守卫退化成放行一切」，而是一个不可运行的脚本。**
139 条红里 **109 条落在目标作用域之外**（`leader 写 plan 放行`、`checkpoint 放行` 之类，
清一色 `expected 0, got 2`）。目标作用域内变红只是「脚本坏了」的副产物，
**对它声称验证的那条 DoD 零证据力**。

### 为什么既有守卫全部失效

该 harness 已有一条纪律：**断言变异前后 sha256 不同**，用于排除「空变异伪装成 SURVIVED」。

**它只防住了对偶方向的一半。**

| 方向 | 现象 | sha256 守卫 |
|---|---|---|
| 空变异 | 文件没变 → 报 SURVIVED | ✅ 挡住 |
| **崩溃型变异** | 文件变了但语法非法 → 报 **KILLED** | ❌ **完全无防护** |

sha256 确实变了，于是一路绿灯报 `MUTATION OK`。

**危害是永久性假信心**：今后谁把该守卫的判定逻辑改坏，这条变异**照样报 KILLED**——
它测的是「脚本还能不能跑」，不是「守卫还在不在」。

### 与 AD-27 主干的关系

**同族**：变异测试的输出信号只有红/绿两位，任何环节出错都伪装成合法结果。
**本类的特殊之处**：错的是**变异算子的语法**，而前七类的守卫
（编译检查、还原校验、命中数检查、对照组、`-list` 自检）**没有一个会触发**——
崩溃型变异让被测物**全面**变红，命中数检查看到的是「红得很充分」。

### 处置（可机械化，成本极低）

**在 `mutate()` 内加一条 mutant 有效性闸**：施加变异后先 `bash -n "$TARGET"`
（Go harness 则先编译），不过即 FAIL 并终止，**不得计为 KILLED**。约 2 行，
一次性覆盖该 harness 的全部变异及今后新增的。

### 判别方法（本次实际用的）

**对照实验分离「坏算子」与「坏断言」**：把算子换成语法合法的形式
（函数体首行插 `return 0`），重跑得 **总红 12 / 目标作用域内 8 红 / 作用域外 0 红**
——证明断言本身是合格的窄命中，坏的只是算子。

**没有这一步就无法判断该返工什么**：是重写断言，还是只换算子。

### 元教训

该任务要防的缺陷是「**一个从未生效的东西，因为恰好符合预期而被当成有效**」
（写通道 `--append` 参数不存在却被静默忽略，在 `wisdom` 上「成功」过一次，
于是被当成通用语法，最终覆盖了整份 580 行 ADR）。

**同一个形态在它自己的变异 harness 上原样复现了一次。**

## AD-32：对「输出即产品」的检查类脚本，**文案断言是唯一能分辨「正确地红」与「坏掉地红」的手段**

**由 dev-agent-50 在 ArcForge/TASK-016 撞到，test-agent-51 独立复现确认。**

### 触发的缺陷

```bash
"顶层字段「$F」非空"
```

紧跟变量的 `」` 是**多字节字符**，bash 把它并进变量名 ⇒ `set -u` 下运行期报
`F」: unbound variable`。**`bash -n` 完全通过。**

### 为什么它比普通 bug 危险

被测物是一个**漂移检查脚本**，它的产品就是它打印的 DRIFT 文案。该缺陷的表现是：

> **脚本 exit 1，但一条 DRIFT 都不打印。**

也就是**一个更严格的恒红**——而该脚本**修复前的病症正是恒红**。
两者症状几乎无法区分：都是「跑了、红了、该修」。

⇒ **只断言退出码的套件会让它带着全绿上线**，而且上线后人看到的是「检查还在红」，
与修复前的观感一致，不会有人怀疑修复没生效。

### 判别方法（test-agent-51 实测）

手工把 `${K}`/`${F}` 改回 `$K`/`$F` 重现该缺陷，跑 44 条断言：

| 断言类别 | 结果 |
|---|---|
| **文案断言**（D1-D4 / B6 / B7） | **6 条全红** |
| 退出码断言（M1-M9 / B1-B5 / B8 / H* / E*） | **全绿** |

### 附带发现：反向断言（`ngrep`）在这类缺陷下无效

D5 是 `assert_no_grep`，该缺陷下**照样绿**——**什么都没打印，当然「没出现不该出现的」**。

⇒ **真正的守卫是正向 grep**。反向断言在「产物为空」这个方向上恒真，
与 AD-27 的「通过的断言 ≠ 有判别力的断言」同族。

### 与 AD-31 的关系：三道闸各挡一层

| 闸 | 挡的是 | 挡不住的 |
|---|---|---|
| `bash -n` / 编译 | 变异体**跑不起来** | 跑得起来但改错了地方 |
| **diff 逐字审计** | 改的**不是注释声称的那处** | 改对了地方但产物坏了 |
| **文案断言** | 产物**内容**坏了，即使退出码「正确」 | — |

**AD-31 是「假 KILLED」，本条是「假红」**——两者都让红/绿这两位信号失去信息量。

### 适用判据

**凡脚本的输出本身就是它的交付物**（检查器、校验器、报告生成器、门禁），
**凡改动触及输出文案处，必须有文案断言**。退出码只能证明「它认为自己失败了」，
不能证明「它失败的理由是对的」。

### 补充（当日实测，test-agent-52 验证 ArcForge/TASK-016 时发现）

#### 一、判据必须写到「变量插值点」，否则会被**形式满足**

AD-32 原文「凡触及输出文案处必须有文案断言」**门槛过粗**。实测反例：

TASK-016 的新增文案是 `顶层字段「X」与模板不一致(实为 <类型>)`，
断言 E7b/E8b/E9b 正向 grep 了「顶层不是 JSON 对象」，E2b/E4b 是负向 `ngrep`。
**把 `(实为 <类型>)` 这个子句整个抹掉 —— 57 条断言全绿，一条不红。**

> 「处」这一级满足了，「**子句**」这一级是空的。

⇒ **收紧判据：文案里每个变量插值点都要有正向断言**
（`实为 null` / `实为 number` / `实为 array` 各一条），
否则「有文案断言」会退化成一个可以形式满足的门槛。

这与 AD-27 的贯穿判据同源：**通过的断言 ≠ 有判别力的断言**，
而本条说的是**存在的断言 ≠ 覆盖到位的断言**。

#### 二、推论：**「后一道防线接管」应当是可观测事件，而不是静悄悄兜住**

同一轮里出现了一个初看像「等价变异」的形态：TASK-016 加了顶层类型断言后，
**变异 N5（删掉非法 JSON 分支的 exit 1）一度变成 SURVIVED** —— 因为新防线把它接住了。

**这是宣称「等价变异」的最佳借口**（AD-27 变异坑第四类：语义等价，无机械堵法）。
dev 没有走这条路，而是补了一条断言：**非法 JSON 的诊断不得级联出「实为 未知」**。

理由是诊断质量：`{ broken` 的正确诊断是「非法 JSON」，
再跟一句「顶层不是对象（实为 未知）」**就是误导——文件根本没解析成功，谈不上类型**。

验证者用反向注入确认这条断言独力承载 N5 的 KILLED（把它的模式换成永不匹配，N5 重新 SURVIVED），
并给出了它的一般形式：

> **多重防线的项目里，「后一道防线接管」应当是可观测事件。**

否则前一道防线失效时，系统整体行为不变、变异全部 SURVIVED，
**看起来像「这段代码不重要」，实际是「另一段代码在替它挡着」** —— 两者的运维含义完全相反。

#### 三、附带形态：**「一条恒真的绿」与「一条守住它的红」并排**

同一套件里 `PASS: 修前基线套件对未变异副本 0 红` 在基线退化（空跑 `exit 0`）时**仍恒真地绿**；
新增的 `btot > 0` 自检排在它上面把整体打红，处置正确。

**但两条并排放着**：将来有人删掉上面那条守卫，下面这条会继续绿着骗人。
⇒ 恒真断言即使当前被上游守卫覆盖，也应改成有判别力的形态，或**显式断言它对上游的依赖**。

#### 四、**数值插值点必须断言精确值**——正则区间会把「零」放进去

补充二把判据收到「每个变量插值点」，仍**不够**。实测（dev-agent-52 撞到、test-agent-52 独立复现）：

文案是 `已比对 N 个文件`，断言写成 `已比对 [0-9]+ 个文件`。
变异「计数恒不递增」（N 永远是 0）——**`0` 也匹配 `[0-9]+`，变异 SURVIVED**。
改成精确值（夹具下应为 `2` / `6`）才 KILLED。

复现实验：把断言改回 `[0-9]+`，其余一字不动 → 控制组仍全绿，该变异下**总红 0/90，重新 SURVIVED**。

> **「有断言」不等于「断言了什么」。** 区间型断言在「退化到区间端点」这个方向上恒真，
> 与 `assert_no_grep` 在「什么都没打印」时恒真是同一形态。

**⚠ 这条规则的代价必须一并写明，否则它会被下一个人改回去：**
精确值把断言**锚定到夹具**（写死 `2` 和 `6`），**往夹具里加一个 hook 就会红**。
**这条红是设计意图，不是维护负担**——夹具变了，「比对了几项」这个事实也变了，
它本来就该被重新确认。**看到它红时正确的动作是更新期望值，不是把它放宽回区间。**

## AD-33：有意作废一条既有断言时，必须给出**一对**自检——「作废恰好 N 条」与「非作废的红为 0」

**由 dev-agent-52 在 ArcForge/TASK-017 提出，test-agent-52 构造两种破坏独立验证，并指出单条不够。**

### 场景

改动 A 会**必然**打断既有断言 B（本例：`check-runtime-sync.sh` 的退出码从二态扩为四态，
上一轮 `mutation-016` 的基线断言「无布局 ⇒ exit 0」必然失效，实测 `1 MUTATION FAILURE(S)`）。

**错误处置**：放宽或删掉 B、或把排除口子开大。
**正确处置**：**窄排除 + 自检**。

### 为什么必须是一对

| 自检 | 挡住的 |
|---|---|
| (i) **作废项恰好 N 条** | 排除规则**变宽**（吞掉了别的红）；`0` 条则说明规则已失效 |
| (ii) **非作废的红为 0** | 排除规则**漏掉真红**（新出现一条它不匹配的红） |

test-agent-52 的两种破坏实测：

- 让排除正则真命中 2 条 → `FAIL: 基线里匹配作废规则的红有 2 条(期望恰好 1)` ⇒ **(i) 抓住**
- 制造一条排除正则**不**匹配的新红 → **「恰好 1 条」照绿**，是 **(ii)** 把它抓住的

> **只写 (i)，一个精心构造的窄正则仍可能放过它本该覆盖的红。**

### 与 AD-32 的关系

AD-32 治「断言存在但没覆盖到」，本条治「断言被有意移除时留下的口子」。
两者共同的形态是：**排除/放宽这类动作没有自己的守卫**，
而它们恰好是唯一一类「让红变绿」的合法操作——**合法性必须被量化，不能只靠意图声明**。

## AD-35：验证报告是下游 DoD 的**原料**——「A 或 B」的谓语必须对每一支单独成立才能合写

**由 test-agent-51 在 ArcForge/TASK-012 回查自己 TASK-010 报告时发现并主动归因到自己。**

### 事故链

TASK-010 的验证报告原文（`TASK-010-verification.md:393-395`）：

```
393  真正的守卫是 ...HitsArchivedTASK016Verifying（阈值 33 时它会红），
394  所以没有功能缺陷；但若日后有人删掉 fixture 用例、只留这条辅助断言，
395  或照着注释把阈值「优化」到 33，规则会静默地不再检出...
```

394–395 是「**A 或 B**」共用一个谓语「会静默」：

| 支 | 是否成立 |
|---|---|
| **A**（删掉 fixture 用例、只留辅助断言） | ✅ 成立 |
| **B**（只把阈值改到 33） | ❌ **不成立**——**而且同一段 393 行刚写过「阈值 33 时它会红」** |

Leader 提炼进 TASK-012 的 DoD 时取的是 **B 支**，于是 DoD 里出现了一条**前提被自己上一行否定**的要求。
TASK-012 的 dev 在 HEAD 快照上实测：改阈值到 33 → `go test .` **exit 1、红 4 条**，**从来不静默**。

### 为什么这不是「读者理解错」

**验证报告在本工作流里不是终点，是下游任务 DoD 的原料。** Leader 拆任务时逐条读报告的
「非阻断问题 / 建议」段并把它们变成 done_criteria——**报告里一句宽松的合写，会以硬要求的形式
出现在别人的验收标准里**，而写报告的人此时已不在场。

⇒ **纪律：「A 或 B ⇒ P」只有在 P 对 A 单独成立、且对 B 单独成立时才能合写。**
否则必须拆开写，或明确标注哪一支成立。

### 同族形态

这与 AD-34 附带的那条同源：**抽样结论的适用边界必须与抽样范围一起写下来**。
两者都是「**产出被下游当作全称命题引用**」——
一个是把抽样当全量，一个是把「或」的一支当全体。

**共同判据：写下一句会被别人当依据的话之前，先问它在哪些支/哪些范围上成立。**

### 附带：口径不敏感性是一条有用的旁证

同一次复算中，test-agent-51 先用了与被验对象不同的口径（cwd 与语料两个轴都不同），
得 17/206（差 **189**），与 dev 的 144/261（差 **117**）对不上。它**没有据此判 dev 错**，
而是先读方法学原文、按其口径重跑，完全吻合。

**附带收获**：即便在那个「错」口径下也有 189 条翻转 ⇒
**「cwd 依赖」这个结论的严重性对口径不敏感，只有精确量级依赖口径。**
⇒ 当两个口径给出**同向但不同量级**的结论时，**方向本身往往已经可信**，
争议只在量级——这能省掉一轮「谁的数对」的拉锯。

### 补充：抽样可能得出**相反**结论，不只是「不完整」（test-agent-51 实测）

AD-34 原文说「抽样结论的适用边界必须与抽样范围一起写下来」。复验 TASK-012 时拿到了更强的形态。

改动前二进制逐 sprint 复跑 ArcForge 全部归档（格式 = `仓库根命中 / 空目录命中`）：

```
sprint-001  0/11      sprint-005  0/6
sprint-002  6/6       sprint-006  1/13
sprint-003  8/8       sprint-007  0/5   ← Leader 那次抽样的出处
sprint-004  6/6
```

**002 / 003 / 004 三个 sprint 根本不翻转**（6/6、8/8、6/6）。

⇒ 若当初抽的是这三个中的任何一个，得出的不是「样本偏小」，而是
**「这个问题不存在」——一个与事实相反的结论**。

**判据升级**：抽样不仅可能低估量级，**还可能给出反向结论**。
因此「我抽查过、没问题」这句话，**在没有说明抽了哪几个、以及不同样本是否同向之前，不构成证据**。

## AD-36：「静默假绿」的第三种形态——**检查存在但不可达**，变异测试对它无效

**由 dev-agent-61 在 ArcForge/TASK-015 交付后查出，Leader 读码定性。**

### 前两种在断言方，第三种在被测方

| 形态 | 在哪一侧 | 变异 harness 能否抓到 |
|---|---|---|
| 断言恒真（作用域全选、区间型判据、`assert_no_grep` 无输出） | 断言方 | ✅ 作用域自检 |
| 断言恒红但理由无关（`grep -qF "$2"` 缺 `--`，`-` 开头的 needle 被当选项吞掉） | 断言方 | ✅ 外溢闸 / 文案断言 |
| **检查存在但不可达** | **被测方** | ❌ **不能** |

**第三种抓不到的理由**：harness 证明的是「**断言在守卫被测代码**」，
而这里是**被测代码那一整段根本没跑**——变异它、不变异它，输出都一样。

### 实例（ArcForge/TASK-018 暴露）

```
af038eb :20  echo "No go.mod found; skipping Go coverage gate."
        :22  exit 0                                    ← 早退
        :98  BLOCKED: 声明范围为空或声明路径全部不存在      ← 永远走不到

修复后  :142 BLOCKED: 声明范围为空或声明路径全部不存在
        :192 echo "No go.mod found…"; exit 0            ← 早退挪到其后
```

框架仓库根**没有 `go.mod`**（`go.work` 在根、`validator` 在子目录），
所以 `:22` 的 `exit 0` 让 `:98` **一次都没执行过**。

⇒ 测试套件里 6 个 fixture 声明 `packages:["./x"]` 而沙箱里没有 `./x`，
**一直是错的，靠不可达维持绿**。修复让检查可达的那一刻，6 条同时变红。

### 判据

**「这段代码在本仓库/本环境下真的会被执行吗」是一个独立于测试覆盖率的问题。**
覆盖率工具会说这几行没覆盖，但在 bash 脚本、条件早退、环境依赖分支上通常没有覆盖率数据；
而变异测试**默认前提就是被测代码会跑**——前提不成立时，它给出的全是空信息。

⇒ 引入或修改**早退 / 短路 / 环境判定**时，必须显式回答：
**它之后的哪些检查因此变得不可达？那些检查此刻有没有测试在依赖它们「不会触发」？**

同一件事上，dev-61 先做了行为层 A/B（只换 `task-completed.sh`，看红绿）：

「让既有检查可达」引向「那 6 个 fixture 一直是错的」，**两条路的返工范围完全不同**。

## AD-37：A/B 的第二种失效形态——自变量不覆盖成因时，差值是噪声甚至反号

**背景**：AD-36 记录了 A/B 的第一种失效（能定因果，不能定机制）。sprint-004 TASK-018
的复验暴露了第二种，**更危险，因为它产出的是看起来像证据的数字**。

test-agent-48 把「只换 `task-completed.sh` 一个变量」的 A/B 施加到四个红了的套件：

| 套件 | B（新树） | A（仅换回旧 hook） | 判读 |
|---|---|---|---|
| `test-write-pipeline.sh` | 4 FAIL | ALL PASS | **A/B 有效** |
| `test-readme-inventory.sh` | 2 FAILURES | 2 FAILURES | **无区分力** |
| `test-mutation-audit.sh` | 1 FAILURES | **3 FAILURES** | **反向，是假象** |

后两个套件的红来自**新增的文件**和**测试文件自身的行数变化**，不来自 hook。
自变量（hook 版本）根本不在成因链上，于是：

- 最好的情况是**无区分力**（差值 0），还容易识别；
- 最坏的情况是 `mutation-audit` 这种——**A 臂比 B 臂更红**。若照字面读，会得出
  「TASK-018 **改善**了 mutation-audit」这个与事实相反的结论。实际上 3 红是
  **「旧 hook + 新 harness」这棵两版混合树**的产物，**两臂都不对应任何真实存在过的状态**。

**规则**：

1. **A/B 施加前先确认自变量在候选成因链上**。红若来自「新增文件」「测试文件自身变化」
   这类不随自变量变化的东西，A/B 从一开始就不适用。
2. **换臂产生的差值，只有在自变量确实覆盖成因时才是证据**；否则它是噪声，**且可以反号**。
3. **反号是信号不是结果**：A 臂比 B 臂更红时，第一反应应是「我造了一棵混合树」，
   而不是「改动带来了改善」。
4. 这类套件的**唯一有效判据是整树背对背**（此例：`e413971` ALL PASS →
   `2209065` 1 FAILURE / 2 FAILURES）。

与 AD-36 并列看：AD-36 是**结论层级用错**（因果 vs 机制），AD-37 是**实验设计不成立**
（自变量与成因无关）。前者结论对了一半，后者可以整个反过来。

## AD-38：反事实/变异施加后必须验证落点——换工具只是换一种翻车方式

**背景**：我（leader）在一次取证失误后立下规则「反事实别用 `sed`，用 `awk`」。
test-agent-48 反驳：它这次用的就是 `sed`，没翻车，**因为它 diff 了替换后的那一行确认落点**
（`grep -vE '^$|^\.arcforge/'` → `grep -vE '^$'`）。

> durable 的规则不该是「用 awk 别用 sed」，而是「**任何变异/反事实施加后必须验证落点，
> 别信它默默成功了**」——这跟变异 harness 的空变异闸是同一条道理，**换工具只是换一种
> 翻车方式**。

**接受，原规则作废。** 我原先的错误类型是：**把某次翻车的工具当成根因，记住了现象的
表面特征而非判据**——与 dev-agent-60 那句「别把条数当判据」同族。

**规则**：任何施加于源文件的反事实、变异、mutation，施加后必须**独立确认落点**
（diff 该行 / sha256 前后比对 / grep 目标模式已消失）。**工具无关。**
这与变异 harness 的**空变异闸**（sha256 前后相同 ⇒ 变异未生效 ⇒ FAIL）是同一条规则的
两个实例：**不能把「命令返回 0」当作「它改到了我以为的地方」**。

**补记（leader 自撞，同日）**：我在把本条写入 ADR 的**同一个脚本里**违反了它。
落点校验写成 `diff <(head -"$N" file) src`，而 `N=$(wc -l < file)` 在 macOS 上带前导空格，
`head -" 614"` 直接报 `invalid option` ——**校验步骤自己没跑起来**；又因为写入命令在
下一行、没有用 `&&` 串联，**校验失败了写入照样执行**。事后 `git diff --numstat` 显示
`70 0`、前缀逐字相同，结果是对的，**但那是运气不是流程**。

⇒ **本条追加一款**：**落点校验步骤本身必须 fail-closed** —— 校验与其后的动作用 `&&`
串联（或 `set -e`），使「校验没能执行」与「校验不通过」产生**相同的后果**。
否则守卫退化成 AD-36 那一族：**检查存在、但它不阻止任何事**。

## AD-39：「跳过一条本任务不测的检查」≠「绕过一条本该拦住它的检查」

**背景**：TASK-018 的 fixture `mk_task` 声明 `packages:["./x"]` 但从不创建 `./x`。
我（leader）读码后判定「让 `./x` 真实存在 = 用 fixture 把新的空 scope 拒绝档绕过去」，
据此支持 dev-agent-61 拒改。**理由是错的。**

test-agent-48 实测：`./x` 存在时同一沙箱走到 `No go.mod found; skipping Go coverage gate.`
`exit 0`，**恢复的正是该 fixture 原本的测试意图**；空 scope 拒绝是一条**该 fixture 从来
没打算测**的检查，且沙箱非 git 仓库，`CHANGED_FILES` 本就为空，漂移检查不受影响。

**这条错理由的后果比它本身严重**：按它的逻辑，**dev-agent-60 修 fixture 也会被判成作弊，
而那恰恰是唯一正确的修法**——一条错理由会把正确路径整个堵死。

**规则**：判断「fixture 修改是否属于作弊」，判据是**该检查是否在本 fixture 的测试意图内**，
不是「修改后是否少走了一条分支」。

- 少走的是**本 fixture 不测**的检查 ⇒ 恢复意图，**正当修法**；
- 少走的是**本 fixture 正要验证**的检查 ⇒ 绕过，**作弊**。

**附带的方法论**：我是读码推断，test-agent-48 是实测。**读码能确定控制流，不能确定
「这条路径对本用例意味着什么」**——后者要看 fixture 的意图，而意图只在跑起来时才暴露。
（正确的拒改理由是**所有权/scope 不在 dev-61 手里**，与门禁语义无关。）

## AD-40：变异外溢的归因判据是「红的是哪几条」，不是「红了几条」

**背景**：dev-agent-61 报 TASK-015 的变异外溢为 `5/66/3/29/0`，与 dev-58/验证者的
`0/65/3/29/0` 差 M1(+5)、M2(+1)。它第一轮的解释是「新增的 WT4 组 11 条被连带打红，
属预期内」——**这是一个差值解释，而差值解释无法与「树不一致」区分**：两者在数字上
长得完全一样，而该任务此前正因树不一致被退过一次。

第二轮它改用**枚举**复核，列出作用域外的**每一条**红：

- **M1（关闭整条 worktree 防线）** ⇒ 作用域外 5 条，**全部是 WT4 的四条「反例」断言
  + 「副本未被写」**；而 WT4 的三条**对照**（fixture 完整性、基线一致、子模块放行）**保持绿**。
- **M2（打坏主判别式）** ⇒ 作用域外**恰好 1 条**，正是**子模块对照**那条
  （主判别式失灵 ⇒ 子模块不再被正确放行）。

> **每一条红都落在它逻辑上该红的位置**——这不是「树不一致」能产生的形状。

**规则**：

1. **变异外溢的归因，证据是红的分布，不是红的计数。** 计数（含差值）在
   「预期内外溢」与「树不一致 / 环境污染」之间**没有区分力**。
2. **合格的归因必须能回答「为什么红的是这几条、而不是那几条」**：
   变异关闭了哪条逻辑 ⇒ 依赖该逻辑的断言必红、不依赖的必绿。
   **绿的那部分和红的那部分同样是证据**（此例 WT4 三条对照保持绿，
   排除了「整组被环境打红」这个竞争解释）。
3. 树不一致产生的红**没有逻辑形状**——它按文件/时序聚集，不按被变异的逻辑聚集。
   **形状是这两者唯一稳定的判别特征。**

**副产物**：这次枚举顺带证明了子模块那条断言**有判别力**——主判别式一坏它就红，
它不是摆设。**枚举法能同时完成归因与判别力核验，计数法两者都做不到。**

## AD-41：纪律会按产物类别断裂——同一轮里，测试断言验 RED，文档断言一次都不验

**背景**：dev-agent-61 在 TASK-015 的同一次交付里：

- **测试断言**：WT4 新增的 11 条，它特意拿旧版实现跑 RED，还因为「红的理由不对」
  （fixture 缺 `seq`、缺 `cp`）返工两次才确认判别力——**「新增断言必须先证明它会红」执行得很严**。
- **文档断言**：新造的 `assert_doc_lacks '一整个 commit'`，**一次都没验**——
  而该 needle 在四份目标文档中的一份上因跨行断开而计数为 0，**这条断言从出生就是空的**。

它自己的总结：

> **同一轮里，测试断言我坚持了「先证明会红」，文档断言我一次都没验。**

**这比任何一条单独的漏检都值得记**：纪律不是「有没有」的问题，而是**它的适用面在
产物类别边界上断裂**。文档断言在形态上像散文而不像代码，于是绕过了那套已经内化的检查。

**同一轮里还有第二个同形状的断裂**（工具层）：`assert_doc_lacks` 是它**这一轮现造的**，
造它的动机（「只断言新值存在，挡不住旧错值留在别处」）被它**写进了函数注释**，
然后**只接到 fix_item ⑥ 的说法上，没接到同一 commit 里同类目标的 ⑤ 上**。

> 不是「工具存在但我没想到用」，是**「我写下了它的用途，然后没按自己写的用途去用」**。

**规则**：

1. **凡「新增断言先证明它在旧状态下会红」，对文档/配置/清单断言同等适用**，无例外。
   needle 必须选**不跨行、不随措辞变化**的最短判别片段，并**先验证它在修改前的每一份
   目标上计数 > 0**。
2. **消灭一个错误说法，验收判据是「全仓库剩余计数 = 0」**，不是「我改的那几份彼此一致」——
   一致性检查对「还有第 5 份我不知道」**结构上无能为力**。
3. **自造的机制必须接到它注释里声明的全部目标上**；只接一处的，等于把该机制的
   适用面缩成了一个特例，而**下一个人会照着注释以为它全覆盖**。

与 AD-35 呼应：写下纪律与用得上纪律是两件事——**同一个提交里，一边把「不能用会漂的
引用」写进两份角色定义，一边把 harness 锚点钉成 `HEAD`**。规则和违反规则的行为出自
同一次交付，**说明写下纪律不产生遵守纪律的能力，需要机制**。
