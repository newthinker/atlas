## AD-28：变异测试报「KILLED」时必须同时报**作用域**

**问题**：同一个变异在不同作用域下给出相反读数，而两个读数都不假。

**实测**（test-agent-12，同一变异 `maxClassEPSFilings` 28→12，同一棵树 `a73110e`）：

| 作用域 | 选中测试数 | 结果 |
|---|---|---|
| `-run '^TestFetchClassEPSRespectsLookbackCap$'` | 1 | **0/5 红（存活）** |
| package `.` | 113 | **5/5 红（杀死）** |

整包跑时唯一的 `--- FAIL` 是 **`TestClassEPSAndSegmentCapsAreIndependent`**
（`classeps_test.go:578` 的 `assert.Equal(t, 28, maxClassEPSFilings, ...)`）——
**被审查的那个测试根本不在失败列表里**。

**⇒ TASK-002 报的「M12 KILLED 10/10」字面属实，但它证明的是「包里有人杀得掉」，
不是「被审查的用例有判别力」。**

**决定**：

1. 变异记录必须写成 **「N 次中红了几次 @ 作用域」**，作用域是记录的必需字段而非可选说明。
2. **审查某个用例的判别力时，必须用 `-run` 收窄到该用例**。整包读数不能用于这个目的。
3. 报告里出现「变异 X 被 KILLED」而未注明作用域的，视为**未验证**。

**与 AD-27 的关系**：AD-27 记过「**满分的 N/M 要问它是在哪个档位测出来的**」（p 是 fixture
的属性）。本条是同一问题的另一个维度——**档位是采样维度，作用域是范围维度**。
两者都会让一个真实的读数支撑一个错误的结论。

**典型症状**：一个用例长期绿、变异也报 KILLED，而它对被测取值零判别力——
真正在守护的是别处一句字面量断言。**删掉那句断言，两个测试同时失去意义，而没有人会发现。**

## AD-29：变异坑第七类——`-run` 正则选中零个测试时冒充「存活」

**AD-27 已记六类**（还原失败致累积 / 编译失败 / `sed` 未命中 / 语义等价 / 执行环境错误 /
fixture 与生产不同）。**第七类**由 test-agent-12 在 TASK-003 实撞：

**`go test -run <regex>` 在正则选中零个测试时正常退出 0**，输出里没有任何 `--- FAIL:` 行——
**与「变异存活」的输出形态完全相同**。

**它与前六类同族**：变异测试的输出信号只有红/绿两位，任何环节出错都伪装成合法结果。
本类的特殊之处在于**错的是选择器而非被测代码或环境**——前六类的守卫（编译检查、
还原校验、命中数检查、对照组）**没有一个会触发**。

**触发条件**（实测）：把变异限定到一个**尚不存在**的测试名（例如在补测试之前的树上，
用补测试之后才有的用例名做 `-run`）。这在「先验证缺陷存在、再补测试」的正常 TDD 流程里
**极易发生**——两棵树的用例集合本来就不同。

**决定**：harness 必须加 **`-run` 作用域自检**——执行前确认该正则**至少选中 1 个测试**
（`go test -run <regex> -list '.*'` 的输出行数），为零则以专用退出码中止，
**不得计入 SURVIVED**。test-agent-12 的实现用 exit 6。

## AD-30：SEC inline XBRL 是**分层**推行的，404 边界因申报人规模而异

**背景**：`maxClassEPSFilings = 28` 的注释称「`reportDate ≤ 2019-03-31` ⇒ 老式非 inline XBRL
⇒ 实例文档必 404」。该结论对 **V(CIK 1403161)** 经逐份 curl 实测成立（序号 0–27 全 200、
28 起连续 404）。

**但 SEC 的 inline XBRL 是按申报人层级分批强制的**（test-agent-12 指出）：

| 申报人类别 | 强制起始（财report期结束日） |
|---|---|
| 大型加速申报人（large accelerated） | 2019-06-15 |
| 加速申报人（accelerated） | 2020-06-15 |
| 小型申报公司（smaller reporting） | 2021-06-15 |

而 `maxClassEPSFilings` 是**通用常量**，任何走类别维度 EPS 回退路径的公司都用它。
**对小型申报人，真实的 404 边界会晚得多**，28 份里可用的会少于 28。

**决定**：**暂不改**，理由三条（均由 test-agent-12 给出且我认同）：

1. **后果良性且已被守护**：多余的 404 由 `TestFetchClassEPSSkipsPre2019NotFoundTail`
   覆盖的逐份跳过逻辑处理，**只浪费请求、不丢数据**。
2. 注释**明确点名 V 为测量对象**，对该标的边界精确。
3. 偏差在**跨公司轴**而非**时间轴**——不属于 TASK-003 `functional[0]` 要求的
   「数据增长后仍正确」。

**触发重估的条件**：当第二家公司需要走类别维度 EPS 路径时，必须重新测定它自己的 404 边界，
**不得沿用 28**。届时应考虑把常量改为「按申报人层级查表」或「探测到连续 N 个 404 即停」。

> **这条记录的意义不在于当下要做什么，而在于把一个「对 V 精确、对他人未必」的常量
> 标记为有条件成立。** 没有这条记录，第二家公司出问题时会从数据源查起——
> 而 TASK-002 的整个调查过程正是这么开始的。
