## 1. 需求目标（转述，非重新设计）

补上「当月口径」这个缺失的**建模维度**：

- 语料 218 篇里 **57 篇处理不了**（实测：本迭代不解析 19 + 解析失败 38）
- 逐篇回原文核对后：**54 篇缺的是「当月口径」这一族列**，2 篇是解析器缺口，1 篇是词表缺项，**需要 LLM 语义判断的 0 篇**
- 央行在 2020–2023 相当多期次里**合计给累计、分部门给当月**，而 schema 只有 `*_ytd`
- 解析器为此**拒绝整篇**——而拒绝是对的：把当月值装进 `_ytd` 会得到**量级完全合理的错值**，下游没有任何闸门拦得住

核心手法：新增 22 个 `_mom` 字段，模板表**每项同时携带 ytd 与 mom 两个字段名**，抽取侧按识别出的口径**选列**。于是「拒绝整篇」变成「路由到正确的列」。

🔴 **本迭代唯一的新风险**：把「拒绝」改成「路由」时，如果拆掉了拒绝而没落实选列逻辑，就是**亲手做了这道守卫最想防的那件事**。可执行的防线是 TASK-011 的断言 `|ytd| ≥ |mom|`（累计值不可能小于它自己的某一个月）。

## 3. 🔴 文档未覆盖的缺口（本次分析的主要产出）

`fieldOrder` 被**三条全覆盖断言**绑住。任何加字段的动作必须**一次性**满足全部三条，否则 `go test ./internal/hestia/...` 转红——而每个任务的 `dev_done` 门禁都要跑它。

| # | 位置 | 断言 | 加 22 字段后的后果 |
|---|---|---|---|
| 1 | `config_test.go:377` `TestShippedConfigLoadsAndIsCalibrated` | 读**仓库真配置** `configs/hestia.yaml`，`len(MagnitudeRanges) == len(fieldOrder)` 且**键集合逐项相等**；另断言 `config_version == "2026-08-31"` | 立即红，且**保持红直到 yaml 填完 22 项**——文档里那是 Task 10，隔了 6 个 wave |
| 2 | `fields_test.go:151` | `require.Len(t, fieldOrder, 27+6+7+10+4)` + 四条**分族前缀计数**（社融 27 / `deposit_` 7 / `loan_` 10 / 利率外汇 4） | 五条同时红。文档只提 `golden_test.go`，**漏了这一条** |
| 3 | `profiles_test.go:73` `TestTemplateTablesCoverAllFields` | `fieldOrder` 每一项都必须被模板表覆盖，且**数量相等** | 🔴 **使文档「Task 4 只加字段、不接抽取」在机制上不成立**——字段一进 `fieldOrder` 就必须有模板负责 |

### 3.1 缺口的形状：一个循环依赖

朴素的修法会撞上死锁：

```
yaml 要填 22 项区间  →  需要 _mom 字段的实测分布
                     →  需要 TASK-005 的抽取路由先跑通
                     →  需要 go test 全绿才能 dev_done
                     →  需要 yaml 已填好          ← 回到起点
```

### 3.2 处置：占位值 + 显式「未标定」标记

TASK-004 做成**原子扩容步**，一次满足三条断言，其中 yaml 的 22 项填**占位区间**并在注释里写明它**不是标定过的**；TASK-010 再用 TASK-009 产出的实测分布重标。

**这不是新发明的做法**：`thresholds.go` 的 `stock_continuity_max` 三档 n=0 就是这个形状（值写下来，注释写明它不是标定过的），需求文档 Task 7 自己引用了这个先例来处理 `DepositSumToleranceMoM`。

**代价**：TASK-004 触及 8 个文件，**超 Realistic Scope 的 ≤5 文件**。
**为什么不拆**：拆开必然留下红测试跨越多个 wave，而 `dev_done` 门禁会逐个 DENY。红测试跨 wave 比单个任务超范围危险得多——**它会被下一个人当成噪声**（这正是需求文档 Task 4 自己对 `magnitude_ranges` 断言说过的话）。

⇒ 此项作为**例外申请**提交 dod-gate 人类确认。

## 4. 人工动作任务（TASK-010 / TASK-013）

需求文档明确：**「工具只产出依据，不做人的判断」**。

- **TASK-010**（标定 yaml）：agent 采依据（TASK-009 的残差分布 + 字段值分布）并整理成表，**填值是人的判断**

## 5. 规模与并行度

13 个任务全部落在 **同一个 package** `internal/hestia`（TASK-010 另含 `configs/`，TASK-012 另含 `CONTRACTS.md` 与 ClawdVault 的 ADR）。

⇒ **`packages` 与 `writes` 必须分开声明**：`packages` 用包路径（覆盖率口径），`writes` 用**文件级路径**（互斥口径）。否则 13 个任务两两 scope 冲突，全部串行。

真实的串行约束来自**同文件写入**，不是同包：

- `profiles.go`：TASK-002 → TASK-003 → TASK-004 → TASK-005（四个任务串行）
- `validate.go`：TASK-006 → TASK-007 → TASK-008（三个任务串行）
- `calibrate.go`：TASK-009 → TASK-012

可并行的窗口很窄。最大并行度出现在 wave 7（TASK-008 / TASK-009 / TASK-011 三者文件互斥）。⇒ 建议 **3 个 dev**，不是 4。
