```go
// migrate adds columns introduced after M2 to pre-existing databases.
func migrate(db *sql.DB) error {
	for _, col := range []string{"gross_profit", "rnd", "sgna", "operating_income", "income_tax"} {
		var n int
		if err := db.QueryRow(`SELECT COUNT(*) FROM pragma_table_info('fundamental_q') WHERE name=?`,
			col).Scan(&n); err != nil {
			return err
		}
		if n == 0 {
			if _, err := db.Exec(`ALTER TABLE fundamental_q ADD COLUMN ` + col + ` REAL`); err != nil {
				return err
			}
		}
	}
	return nil
}
```

## 5. 运维事实

### 5.1 agent 中途失联 8 次,7 次损失为零、1 次需接手收尾

**损失差异不取决于失联时机,而取决于产出是否已落盘。**

有逐次记录的四例(其余四次未单独立档;错误形态均为 `API Error: Connection closed mid-response` 或 stall):

| 谁 | 失联时的状态 | 损失 |
|---|---|---|
| test-agent-7 | TASK-002 **验证途中**,无 checkpoint、无报告 | **产出全丢,需新 verifier 从头重验**;且 `verifying` 无人可接 → 催生 AD-21,并在 TASK-011 上演变为真实死锁(§4 第 11 项) |
| test-agent-7 | TASK-011 **预案已写进 checkpoint**,但任务还没派到它名下 | **零**——预案含两条判据原文,可直接交接 |
| dev-agent-15 | TASK-020 **`dev_done` + discovery + commit 全链完成后** | **零**——它挂在了**所有产出都已脱离自身**的时刻 |
| dev-agent-22 / 23 | TASK-013 **实现途中**(两任先后中断) | **零**——由 dev-agent-24 接力完成;代价是**没有任何单一 agent 完整经历过 RED→GREEN**,verifier 因此对该任务改用从严口径(每条 `verify_by: test` 的 DoD 都要求有变异从绿翻 KILLED) |

第二例最值得记:那份预案当时**还没到交付阶段**,是开工前的勘察产物——**最容易被当成草稿留在脑子里的那类东西**,
它却写进了 checkpoint。

**零损失有个前提**:若任务被 REJECTED、返工需要原 agent 本人(状态机 owner 恒钉在它身上),失联才会真正咬人。
所以「零损失」准确说是**「在当前分支上零损失」**——落盘保住的是**已完成的工作**,保不住**未来需要这个 agent 做的工作**。
对应处置不是让 agent 不挂(做不到),而是**返工路径要能换人**;而换人的前提**也是**落盘
(新 owner 拿不到原 owner context 里的任何东西)。

调度经验(API 大面积不稳定期):每次恢复都有单调进展就继续小步推;**实例连续 3~4 次中断即收回换 fresh 实例**;
收尾指令精简(免重跑慢测、预授权降级)显著提高落盘成功率。

> **口径说明**:本节采用 sprint 结束时的 Leader 汇总口径 **8 次(7 零损 / 1 需接手收尾)**。
> TASK-015 的 DoD 文本写的是「6 次(5 零损 / 1)」——那是任务定义时的读数,**次数随 sprint 推进而增长**。
> 另注:上表第一例在 wisdom 原始记录中标为「全丢」,与「7 次零损失」的分类边界取决于
> 「重验成本」是否计为损失;此处照录原始记录,不做平滑。

### 5.2 code-simplifier 三次自述与事实不符,处置一律「不采信自述,直接 diff 核对」

| # | 任务 | 自述 | 事实 |
|---|---|---|---|
| 1 | TASK-016 首轮 | **自报「Unchanged」** | 实际引入 `segmentBuckets` 命名类型、把复合键去重换成按标签的集合、抽出 `sortConflicts`。改动本身是等价重构且更清晰故保留,但 dev **在其之后重跑全部 3 个变异体**确认断言强度未变 |
| 2 | TASK-016 返工轮 | (被用户中断,父 agent **以为它完成了**) | 中断时它**已半途改了 `periods_test.go`**:把两处重复的日期闭包提取为 `daysBefore` 却**还没定义这个函数** → 工作树处于 `undefined: daysBefore` 的**不可编译状态**。dev 在提交前 `go vet` 才发现;**若直接 commit,交上去的是一个连编译都过不了的分支**。处置:**补齐未完成的提取**(而非回退——两处调用点已改成新写法),重跑全部 11 个变异体 |
| 3 | TASK-011 | 最终回复**语无伦次**(自称「ninth firing… pending your A/B/C」) | dev 未采信自述,**直接 diff 核对**:实际改动仅一处(把 `jfSlice` 从 `sankey.go` 移到 `prism.go` 并让既有 `Series` 复用)。改动合理故保留,其后重跑全部 8 个变异体 |

**共同处置与通则**:
1. **子代理的自述不构成验收依据**,一律以 `git diff` 与工作树实况为准。
2. **子代理被中断后其产出处于任意中间状态**——不是「没做」也不是「做完了」,而是**做了一半**。
   恢复前必须:① 验证工作树可编译/测试可跑;② 判断补齐还是回退更干净;
   ③ 若涉及测试文件,**重跑变异确认断言强度未被削弱**。
3. 第 3 条最容易被跳过:**简化若削弱了断言,`build` 和 `test` 都不会告诉你**。
   本 sprint 每次调用简化器后都重跑了变异体,这是唯一能发现该类问题的手段。

> 第 2 例是一种**新的失败模式**:前几次中断是 agent **自己**停了(产出要么已落盘要么没开始);
> 这次是 agent **调用的工具**被停,而**父 agent 不知道它做到哪一步**。
> 「我调用的工具替我改了文件,但它没跑完」——这类中断不会产生任何失败信号。
