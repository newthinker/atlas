## 交给 M1b-2 的两条复核结论（M1b-1.5 期间产生）

### H8 的严重性需下修 —— 「每期都发生」不成立

H8 称「54 个字段横跨至少两篇央行报告……**同期、通常同日发布、URL 不同**……频率：不是一次性迁移，而是**每期都发生**」。

**核对 `testdata/` 里的真实样本后，这个前提对近期报告不成立：**

| 样本 | 板块数 | 社融 |
|---|---|---|
| `pboc-2020-06-h1.html` | **6** | **不在本篇**（当时单独发布） |
| `pboc-2025-12-annual.html` | **8** | **一、二节就是社融存量与增量** |

2025 年报告的一、二节标题即「社会融资规模存量同比增长8.3%」「全年社会融资规模增量累计为35.6万亿元」，**27 个社融字段全在同一篇里**——M0 的解读文档正是从这一篇做出完整社融存量结构表的。

因此：

- **不阻塞 M1b-2 的 `rule@v2` 解析**——一篇报告就是全的
- **阻塞 M1c 回填**（处理 2020 至社融并入前的期次时才遇到）
- 「与 H6-3 构成永不收敛的循环」只在真的去抓第二篇时出现；**是否抓第二篇是 M1b-2/M1c 的范围决策，不是既成事实**

原判断来自设计文档的字段清单推断，未回头核对 testdata。H8 仍是真问题，只是时机与频率被高估了。

### H10 的 `2026-12/monthly` 用例复核为合法

H10 的实测把 `2026-12/monthly` 与 `2026-06/annual`、`2026-03/h1` 并列为「组合非法」。**M1b-1.5 只落实了后两类**：

已实施的规则是 `h1`→期末月必须 `06`、`annual`→必须 `12`，`monthly` 任意月份放行。

理由：央行每年 1 月的年报同时含全年与 12 月单月数据，解析器若把两者都抽出来，`YYYY-12/monthly` 就是真实期次；且它与 `YYYY-12/annual` 的业务键本就不同（`period_type` 是主键的一部分），不会混淆。禁止它会拦掉合法数据。

### 浮点契约

增量类字段由 万亿×10000 得出，个别值带 ≤1 ULP 表示误差（实测
`4.81×10000 = 48099.99999999999`）。**闸门一律不得对它们做精确相等比较。**
现有七道全是不等式或容差比较，误差被完全盖住（`corp_loan_reconcile` 的残差是
−1.16% 对 ±5% 容差，ULP 的相对占比约 5e-17）。见 `TestTrillionConversionCarriesULPError`。

⚠️ 验证这件事时**不能在源码里手算**：Go 的**无类型常量**算术是精确的，写 `4.81*10000`
得到精确的 48100，会得出「没有误差」的相反结论。必须用运行时变量。

#### ⚠️ ULP 守卫的现状：它**不观察它声称守卫的对象**（QA round2 R2-5）

`TestTrillionConversionCarriesULPError` 的失败文案写着「若这个等式成立说明**换算方式变了**」，
但它测的是自己现写的 `trillion := 4.81; got := trillion * 10000`，
**不经过 `amount.toYi()` / `scaleOf()` 任何一行** —— 它是对生产算术的**再实现**，不是对它的观察。
（本任务作者直读确认：该测试体内对 `toYi`/`scaleOf`/`amount`/`Parse` 的引用数为 **0**。）

QA 实测把 `amount.go:121` 的 `toYi` 改成整数化（**这正是「换算方式变了」**）后：
生产算路 `toYi(4.81 万亿元) = 48100`（ULP 误差已被消除），而该测试**仍全绿**
（PASS=475 等于基线）。⇒ **生产管线的误差被完全消掉，声称钉住它的测试一动不动。**

⚠️ **归因要写对：这不是 dev 的偏离。** TASK-007 的 DoD `non_functional[1]` 白纸黑字要求
「`trillion := 4.81` 用**变量**，`assert.NotEqual(48100.0, got)` + `assert.InDelta`」——
**是 DoD 本身指定了一条不观察生产的测试**，实现逐字照做了。

**修法（QA 给的，约 2 行，本任务未实施——`validate_test.go` 不在本任务 `writes` 内）**：
改从 `golden2025[FieldLoanCorpShortYTD]` 或 `Parse` 的输出取值再断言，
让断言的输入来自生产算路而不是测试自写的表达式。

**一条容易写错的相关措辞**：阈值边界用例成立的条件是**两边舍入到同一个 double**，
不是「比例精确可表示」——`0.02` 本身就不精确（位模式 `0x3f947ae147ae147b`，实为
`0.020000000000000000416`）。而它取决于**参与运算的量是否精确**，不取决于算路长短：
实测 `400→408` 成立、`123→125.46` 低 15 ULP 即失效。改边界用例的常量时，
必须保持参与运算的量为精确整数，否则测试会**静默失效**。

### 口径豁免

命中豁免记 `skipped{caliber_exemption:<version>}` 而**非 passed**，并**保留 Value**。

### 一级幂等键：三种情形（spec 第 2 节定案）

`article_id` 是一级幂等键。三种情形的**期望行为不同**，且在「下一轮会不会重抓」上必须能分开：

| | 情形 | 行为 | 守卫 ✅亲验 |
|---|---|---|---|
| **A** | 抓取 / 解析失败 | 两张表都**不写** ⇒ 下一轮**自然重试**（不需要 `--force`） | `TestIngestLeavesNoRowOnFetchOrParseFailure` |
| **B** | 新 `article_id` | 一级键不命中 ⇒ **抓** | `TestIngestFetchesUnseenArticleEvenWhenStoreIsNotEmpty` |
| **C** | 同一篇没过闸（落了 pending） | 一级键**命中被挡** | `TestIngestSkipsSeenArticleUnlessForce/默认跳过已处理过的文章` |

⚠️ **A 那条曾经只有一个空洞的守卫**：原先用 `HasPeriod` 断言「失败的那期不留下任何行」，
而 **`HasPeriod` 查 `v_hestia_current`，本来就看不见 pending** ⇒ 即使真落了一行 pending，
那句断言照样绿。它证明的是「没进权威表」，不是「没留下行」。现在直接数 `pending` 表行数
**并再跑一轮**证明重试真的发生（只数行数不能证明会重试，只跑第二轮不能证明第一轮没留行）。

**`--force` 是情形 C 的直接推论**：C 说「见过就挡」，那么「我知道见过、但就是要重来」
必须有一个显式出口，否则调了阈值之后没有任何办法重跑。

### 判停规则：`article_id`，且**只查权威表**（推翻 Sprint 036 的「判停用期次」）

`Discover` 的判停键自本 Sprint 起是 **`Store.HasArticleInObservations`**（只查 `hestia_observations`）。

**为什么推翻期次判停** ✅亲验：期次判停的理由是「index 按时间倒序 ⇒ 再往后只会更旧」，
而那句话把**发布时间倒序**与**期次倒序**当成了同一件事。央行重发某期时两者分叉：修订版
发布时间最新 ⇒ 排最前，期次却是旧的、已入库 ⇒ **第一条就命中、当场停**，其后所有未入库
期次一个都发现不了，返回空 + `nil` error，与「今天没有新报告」在调用方看来完全一样。

**为什么是「只查权威表」而不是 `HasArticle`（查两表）** —— 人类 2026-08-13 裁决：
查两表会让**落进 pending 的期次再也不会被自动重试**（Discover 见到它的 id 就停），而本文件
上面「落 pending 的期次对依赖历史的闸门永久不可见」已登记为结构性缺陷 ⇒ 那等于把
「更难自愈」变成「不可能自愈」。只查权威表则三种情形都对：

| 场景 | 判停 | 结果 |
|---|---|---|
| 修订版（同期次、新 id、不在权威表） | 不命中 | **不停、继续翻** ✅ 修复静默停摆 |
| 正常已处理（id 在权威表） | 命中 | 停 ✅ |
| pending 期次（id 只在 pending） | 不命中 | **仍交出候选** ⇒ 由 `ingestOne` 的 `HasArticle` 挡住 ✅ 两层分工保住 |

⇒ **`HasArticle`（查两表）与 `HasArticleInObservations`（只查权威表）分工不同，都对**：
前者是 **ingest 层**的一级幂等键（挡「同一篇重抓」），后者是 **Discover 层**的判停键
（让 pending 期次仍能被交出来重试）。这与本文件上面「同一张表的两面」是同一条道理。

**站点迁移的自愈** ✅亲验：`article_id` **不在业务键里**（`NewSpec` 用的是
`{period, period_type}`，`Lookup` 的 SQL 就是 `WHERE period=? AND period_type=?`）
⇒ 迁移后新 id 不会变成另一个业务键，`published_at` 不变 ⇒ `Classify` 判 `Duplicate`
⇒ `refreshArticleID` 刷新 id ⇒ **下一轮命中、恢复正常**。代价从「每次唤起都翻满」
降级为「迁移后一轮全量重抓，之后自愈」，`MaxPages` 把那一轮限制在有限范围内。

**停止原因可区分**：`Discover` 返回 `StopReason`（`seen_article` / `max_pages` / `exhausted`），
`ingest` 空候选时打印 `no new reports (stopped: <reason>)`。⚠️ **当前最危险的属性是「静默」**：
返回空 + `nil` error 时「正常停」与「翻满上限、窗口外可能还有」完全同形。

### D. 方法学陷阱 —— 验证与测试

**D1｜「0 SURVIVED」的强度上限，是写变异清单那个人的想象力**
一份「26 个变异 0 SURVIVED」属实，但那是**那 26 个**的边界；独立设计的 34 个里有 1 个 SURVIVED
且不在原清单内。⇒ **报数时连同清单的边界一起报。**

**D2｜语句覆盖率对「一个 `if` 里的半个条件」毫无信号**（实测两次）
`if a < lo || a > hi` 是**一条语句**，两个半边共用一格。删掉 `|| a > hi` 后测试全绿、覆盖率仍 100%。
最硬的证据形式：**同一函数的语句覆盖率，上界守卫缺失时 100%、补上后仍是 100%**。
⇒ 覆盖率能告诉你「这行跑过」，**不能**告诉你「这行的每个分支都被检验过」。

**D3｜量级锚点会在一小时内过期**（实测）
同一条搜索 URL 相隔约一小时返回 **692 → 693** 条，语料真的长了。
⇒ **能判性质就别判数量**：依赖测量值的判据，正确性挂在一个会漂移的数上。

**D4｜「做不出更外科的变异」往往只是没换思路**
「这个变异集里做不出更外科的写法」是诚实的自我限制，但换一种**约束形状**（加窗口而非加上界）
即可做到只让目标那一条红。⇒ 判据是「换一种约束形状再试一次」。

**D5｜「已经学到这条教训」不构成对下一处同形位置的保护** 🔴
两个当场实例（同一天、同一个人）：把「`grep -c` 回答的是『有几行匹配这个模式』」写进笔记后**十分钟**，
在同一份文件上连猜三次模式得 0 / 16 / 15（真值 20，成因是该文件两种格式并存）；
以及跨七八小时后仍把「我试遍了静态预置构造都不行」写成「构造不存在」。

**机制**：**结论对的时候，缺陷不产生代价，于是也不产生记忆。**
「学到教训」由**代价**驱动而非由**认识**驱动 —— 这就是为什么「我已经知道这条」毫无保护力。

**可操作**：**猜格式超过一次，就停止猜、去看原文**（「换个模式再试」比「打开文件看一眼」便宜，
所以人会一直换模式，而每次重试都可能产出一个**像样但错误**的数）。
⚠️ **第一次得出荒谬结果时就该停** —— **荒谬的输出是最便宜的警报，也最容易被当成噪声。**

**D6｜同一个词在两份文档里可以是两个意思，而滑轴不留痕迹**
「不可达」在一处指**生产**不可达、在另一处滑成**测试**不可达，据此得出的「结构不同」随后被实验证伪；
而下游照着那个滑轴写进了 DoD ⇒ **两人先后滑在同一个词上**。
⇒ 机械检查：**「我这句话里的关键词，在上一份文档里是哪个意思？」**

**D7｜`go tool cover -func` 必须在与 profile 同源的树里渲染**（实测）
在 post 树里渲染 baseline 的 profile ⇒ 覆盖块按**行号**归错函数，凭空冒出「覆盖率回退」。
**成因**：percentage 来自 **profile**，函数归属来自**源码解析** ⇒ 不同源时**只有后者错**，
错法是**整片平移**，看起来完全像真实回退。
⇒ 背对背比较覆盖率时，**两侧各自在自己的树里渲染**。

**D8｜linked worktree 的目录副本不是独立仓库**（实测）
`cp -R` 复制的是 `gitdir:` **指针文件** ⇒ 副本与原树指向同一个 git 目录
⇒ **副本里的 `git checkout` 作用在原树上**，原树被改且并行的测量被污染。
⇒ 造基线副本：**`rm -f 副本/.git` 切断联系**，再 `git show <sha>:<path> > 副本/<path>`。

### C. 实现陷阱 —— 下游照抄会踩

**C1｜建议区间用**加性**余量 `[min-span, max+span]`，不是乘性**（实测）
乘性规则在**可为负**的字段上会把已观测到的真实值排除在外：`deposit_household_ytd` 的
`min=-8200` 时 `min*0.5 = -4100 > -8200` ⇒ **建议区间把实测最小值挡在外面，而它看起来完全像个正常区间**。
加性余量与符号无关。⚠️ 另必须有**上界**断言（`SuggestMax-SuggestMin <= 3*(Max-Min)`，3 是加性规则的精确值）：
只断 `SuggestMin < Min && SuggestMax > Max` 时，`±MaxFloat64` **两条全绿** —— 那是「建议任何值都合法」。

**C2｜`n < 3` 不给建议，判据是 `n` 不是 `span > 0`**（实测）
过窄的建议比没有建议更危险：**它看起来是个结论**。
⚠️ 判据写成 `if span > 0` 的实现在「n=2 且两值不同」时照样给建议 ⇒ 用例的 n=2 那格
**两个值必须不同**（用 `[100,100]` 则 `span=0`，错误实现照样绿）。

**C3｜分位数用 nearest-rank 的**整数**上取整，脆弱性在 `pct` 不在 `n`**（实测，`n ∈ [1,200000]` 全扫）
`rank = (pct*n + 99) / 100`，**不写** `math.Ceil(float64(pct)/100*float64(n))`。
两种实现逐点比对：`pct = 5/50/95`（本报告实际用的三个）**差异 0 处**；
`pct=7` 有 **1612** 处、首个恰在 **n=100**；`pct=14` 有 3222 处（首个 n=50）；`pct=28` 有 6442 处（首个 n=25）。
⚠️ 早先的注释写成「n=100 时碰巧对、**换个 n** 就差一名」——**方向反了**，照它「换个 n 去验」的人
**一无所获**，可能因此判定这道防御多余而改掉它。**要复现差异得换 `pct`**（加一档 p7/p25 就会撞上）。

### E. 实现陷阱 —— 下游照抄会踩

1. **正向属性是必要不充分的**：判「这篇报告只有当月数」用「正文无累计合计句」是不够的——
   一个 index 页（连合计句都没有）会被判成「该期报告只有当月数」，**一句关于它的假话**，
   还会把一条真失败从 M1c-4 的清单上抹掉。判据必须是「**有**合计句 **且**无一条是累计口径」。
2. **分类理由必须保留原始解析错误**：`2023年5月` 判为「只有当月数」而它的**直接**错误是
   「板块序号不连续」——不带上原错误，那个结构问题会被分类标签盖掉。
3. **Go 的 `\s` 不含 U+00A0**：语料里「余额为」后的空格有两种（`0x20` 与 `0xa0` NBSP），
   写 `\s*` 会修好一部分、**静默漏掉 NBSP 那篇**。`strip.go` 的 `spaceRE = [ \t\x{00a0}]+`
   已把两者折叠成单个普通空格 ⇒ 模板侧用 ` ?` 即可，**且不能用 `\s*` 去「保险」**。
4. **`stripHTML` 的 `punctNormalizer` 只归一逗号/分号/全角空格，不碰括号** ⇒ 全角「（M2）」
   会原样到达模板层，必须由模板自己认。
5. **`sort.SliceStable` 排的是调用那一刻的内容**：`classifyArticles` 末尾对 `Unsupported` 的排序
   跑在解析循环**之前**，循环里追加的条目不经它——顺序正确是因为 `items` 本身已按期次排好。
   ⇒ 那个比较器目前**没有生产者**，看到它未覆盖**不要去删排序**。
6. **放宽期次前缀必须同时改两处**：`periodAlt`（`profiles.go:138`，决定正则认不认得）与
   `cumulativePeriods`（`profiles.go:152`，决定认出来算不算累计口径）是**两个独立的硬卡点**。
   只改前者 ⇒ 候选句变多但口径判定全筛掉，命中 0；只改后者 ⇒ 正则根本不命中，
   **与现状逐字相同**（reviewer B5 四格实测）。⚠️ 「与现状逐字相同」意味着**改错了也全绿**。

### F. 框架层机制发现（带出处，因为流程状态目录会被归档而 CONTRACTS 不会）

1. **`task-completed.sh` 的 `git log --grep` 全文件零次 `--all`** ⇒ 只走 HEAD 祖先链 ⇒
   **未合并分支上的 commit 对 dev_done 门禁结构性不可见**，两个集合双双为空所以「报绿」。
   ⇒ **「merge 必须在 dev_done 之前」是机制决定的，不是流程偏好。**（dev-m1c3a-a 读码查实）

   会被扫进来（实测一次扫出跨 4 个包、回溯到两个月前的 27 文件并集）。加 `--since`，
   或改用逐 commit 的 `--numstat` 并集。（门禁自己也踩到了）
3. **拓扑判据只在报 0 时可信**：`merge-base --is-ancestor` 既假阴（rebase/amend 换了 sha）

   `git diff <旧> <新>` 里挑（挑「主功能符号」会假阳：新旧两版都有它）。

    🔴 **换对了判据的种类还不够，判据的对象也要对**：内容判据**必须打在目标树上**
    ——审计某次验证有无盲区，要判的是「那份内容当时在不在**那次验证的 `verify_baseline.head`**」，
    **不是「在不在今天的 master」**。实撞：判据形式完全正确、跑在 master 上，
    于是「拓扑命中 1 例盲区」被误坐实；在正确的树上重取证后**实际盲区 0 例**。
    ⚠️ 它躲过自查的原因值得单记：**修好了判据的种类，没修判据的对象。**（test-m1c3a-v1 自陈）
4. **`git log <range> -- <path>` 默认有 history simplification**：同区间同路径默认报 0、

7. **中文 harness 里 `$var` 一律写 `${var}`**：macOS 自带 bash 3.2 会把紧跟 `$var` 的
   多字节字符的字节并进标识符。**我们的 harness 输出全是中文，`$var` 后面十有八九就是
   一个中文字符** ⇒ 这不是边缘情况。（dev-m1c3a-a 最小复现，Leader 复跑确认）
   ⚠️ **本条同时更正一条曾写下的错误归因**：最初把这次失败记成「混进了非 ASCII 字符」，
   **按那个说法去做防不住任何一次复发**（听起来像手滑，而真实机制是标识符解析）。
   ⇒ **归因写错比没写更糟：它会让后来的人以为已经有对策了。**
8. 🔴 **BSD awk 的正则对多字节不可靠，而它不报错、只给一个像样的数**：同一份 TSV、同一段
   `awk -F'\t' '$4 ~ /[0-9]月金融统计数据报告$/'`，两次调用分别给出 `80` 与 `218`
   （真值 `55`，python3 复算 + 求和自洽）。⇒ **凡按中文模式分类计数，一律换 python3，
   并要求分层数与总数求和自洽 + 第二把独立的尺。**（dev-m1c3a-a，M1c-3a 的 TASK-008 当场撞上）
9. **报 RUN 层级分解按祖先存在性，不要数名字里的 `/`**：名字自带斜杠的测试会被误记，
   而**求和自洽校验挡不住它**（两种分解总数相同，错的是**再分配**）。
   ✅ **可操作判据**：问「**我这个仪器出错时，总数会跟着变吗？**」——答「不会」⇒
   **求和自洽校验对它零信息量**，而且**恒过，反而给作者以信心**。⇒ 此时必须换一把独立的尺复算。
   ⚠️ 且**「换了方法的名字」不等于「换了方法的机制」**——只剥最后一个斜杠的实现会在
   病态输入上退化回原方法。
   ✅ **机械自查**：换方法后，**拿那个方法本该解决的病态样本单独跑一次**
   ——否则「我换了方法」只是换了个名字。（dev-m1c3a-a 犯并自查；判据由 test-m1c3a-v1 补）
10. 🔴 **取值不携带它测自哪棵树的信息** ⇒ CONTRACTS 里这一类**只写判据
    （「绝对值不低于 95.5%」）不写取值**；跨锚点的同名数字**不可相减**。
    ⚠️ **不要用「十个取值全不相同，因为它们测自十棵不同的树」这个说法** —— 它**有反例**：
    本 sprint 里 `TASK-008 post = 95.6570 @ e086c481` 与 `TASK-010 post = 95.6570 @ fc41da2`
    是**两棵不同的树给出同一个值**（前者只加测试与文档，分子分母都不动）。
    ⇒ **「全不相同」是一个偶然为真的观察，「不携带信息」是一个性质**；
    前者会在下一个只加测试的任务出现时失效，后者不会。

11. 🔴 **`cd` 失败之后，后续命令会静默在主工作区执行**：把 `cd` 与后续命令分行写
    （而不是 `cd X && cmd`）会让隔离**悄悄消失**而退出码正常。
    ⇒ 隔离脚本一律 `cd X || exit 1`，并在关键步骤前打印 `pwd` 与 `git rev-parse HEAD`。
    🔴 **最该记的不是失败本身，是它产出的那两行输出**：一次 merge 预演打出
    「✅ 分支 A 无冲突」与「🔴 分支 B 有冲突」，**前者结论碰巧对（但产生它的地方是错的）、
    后者是假的**（真实原因是上一个 `--no-commit` merge 没提交）。
    ⚠️ **一真一假，而它们在输出里看起来一样可信** —— 差一点据「有冲突」去让 dev 改分支。
    ⇒ 与 F-8 同族：**仪器坏掉时不报错，只是把真假混在同一份格式整齐的输出里。**
12. **`git worktree add <path> <分支名>` 会因该分支已被别处检出而失败** ⇒ 一律用**全 sha** 建。
13. **`find -newermt` 在 BSD find 上不报错、只是什么都不匹配** ⇒ 用它做「本轮有无产物」

14. **`shasum` 会把路径串打进输出** ⇒ 完整性指纹必须固定 cwd 与路径形式，否则同一份内容

15. 🔴 **`in_progress` 无阈值 × 停机后无唤醒 = validator 结构性看不见的停摆**：

### F. schema 迁移 —— `observationsDDL` **只在建表时生效**

`schema.go:46` 的 `observationsDDL()` 逐列从 `fieldOrder` 派生（`CREATE TABLE IF NOT EXISTS`）。

🔴 **`IF NOT EXISTS` 意味着：对一个已存在的非空库，它一个字节都不会改。**
本迭代 `fieldOrder` 由 54 个字段扩到 **76 个字段**（新增 22 个 `_mom` 列）—— 这个扩张**只对新建的库生效**。

**后果与要求**：

- `backfill load` 要求 `--db` **不得已存在**，所以回填路径上不会撞到这条。
- 🔴 **但把本迭代的代码指向一个 M1c-3b 之前建的生产库，那 22 列不会自动出现** —— `CREATE TABLE IF NOT EXISTS` 对已存在的表静默无操作。
- ⇒ **将来对非空库跑本版本，必须显式迁移**（`ALTER TABLE ... ADD COLUMN`，22 列）。这是 M1c-4 的 TASK-013 生产库切换的前置条件。

✅ **它在开库那一刻就响亮失败，不是「无守卫的开口」**（M1c-4 的 TASK-014 订正）：`NewStore` 调 `verifyObservationsSchema`（`store.go:152`，由 `store.go:78` 在开库路径上无条件调用），把库里实际的列与 `fieldOrder` 比对，缺列即返回 error：

hestia: hestia_observations is missing N column(s) (e.g. tsf_flow_mom, ...): this database
was created by an older schema and CREATE TABLE IF NOT EXISTS does not add columns.
Automatic migration is an explicit non-goal; migrate manually with ALTER TABLE ...
```

守着它的是 `TestNewStoreRejectsSchemaDriftOnLegacyDB`（`store_test.go:195`，本任务复跑 PASS）。该测试刻意用「七个元数据列齐全 + 只有前三个业务列」的老库构造，而不是「只有主键列」——后者会让一个只检查 `metaColumns`、根本不看 `fieldOrder` 的实现照样通过。

##### 🔴 第三种姊妹形状：**同名不同义**（M1c-4 的 TASK-014 登记）

包里有**两个都叫 median 的统计量，取值规则不同**：

| 符号 | 位置 | 偶数样本时 |
|---|---|---|
| `medianOf` | `backfill_load_report.go:617` | 取两个中值的**平均** |
| `nearestRank(sorted, 50)` | `calibrate_report.go:108` | **nearest-rank 不插值**，取 `ceil(50n/100)` 位，即两个中值里**靠下**那个 |

奇数样本两者相同；**偶数样本必然不同**，差额是两个中值间距的一半。最小复现：样本 `[1,2,3,4]` ⇒ `medianOf`=**2.5**，`nearestRank(·,50)`=**2**。

⇒ **谁拿这两个数互相印证，会得到一个无法解释的小差异** —— 而它既不是精度问题也不是 bug，是两个不同的定义。

⚠️ **`nearestRank` 不插值是有明确设计理由的**（`calibrate_report.go:49-56`：报告是给人看分布定区间的，插值那点精度对该决定没有影响，却多一处能算错而不会报错的地方）。**两边都不要改**：`medianOf` 喂的是 `checkCaliberFamilyMedians` 的判据，为消一个 9 行函数去动一道刚验收的闸，收益不抵风险。**只登记，不动代码。**

⚠️ **它与上面两种共享同一个致命性质：不会让任何算式不平。** 「同值不同量」「同量不同口径」「同名不同义」——三者都表现为「有个数字看着不对但说不出哪里错」，且**没有任何自动检查会因它们变红**。这正是三者难被发现的共同原因。
